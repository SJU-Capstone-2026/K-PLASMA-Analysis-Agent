# V3 판단 기록 엔진 비교 실험 기록 (2026-11-15)

V3 판단 기록 도구(비용 규칙과 검색 RAG)의 대안을 만들고 PR #36 엔진(`rag4`)과 비교한 기록이다. 각 결정은 다음 순서로 내렸다.

1. 후보와 장단점을 정리한다.
2. 같은 조건에서 비교 실험을 한다.
3. 사용자가 최종 선택한다.

모든 실험은 로컬 CPU에서 실행했고 외부 모델 API는 호출하지 않았다. 따라서 이 결과는 실제 Agent 평가가 아니다. 계획·답변 모델을 포함한 실제 평가는 이후 별도로 승인받아 진행한다.

## 실험 3: 명시 근거 거름망 방식

스크립트: `agent/python/evals/v3_decision_engines/support_modes.py`

PR #36의 `RagService`는 임베딩 검색 전에 `assess_requested_evidence`로 메모를 거른다. 질문이 요구한 내용(예: 비용 + 반려)이 글자로 적힌 메모만 남기는 방식이다. 이는 화면의 "규칙" 스위치(`cost_exclusion`)와 다른 장치다. 조합별 결과(교차 평가, 질문 40개):

| 조합 | 종합 | 정답 포함률 | 정밀도 | 정답 없음에 빈 결과 |
| --- | --- | --- | --- | --- |
| e5-small / a (현재 PR #36) | 0.718 | 0.800 | 0.726 | 2/5 |
| e5-small / b | 0.578 | 0.657 | 0.549 | 2/5 |
| e5-small / c | 0.693 | 0.800 | 0.726 | 1/5 |
| e5-base / a | 0.720 | 0.771 | 0.703 | 3/5 |
| e5-base / b | 0.735 | 0.800 | 0.709 | 3/5 |
| e5-base / c | 0.740 | 0.829 | 0.749 | 2/5 |
| **ko-sroberta / a** | **0.782** | 0.800 | 0.760 | **4/5** |
| ko-sroberta / b | 0.753 | 0.829 | 0.777 | 2/5 |
| ko-sroberta / c | 0.728 | 0.800 | 0.749 | 2/5 |

- **c의 구현:** 실험 코드에서만 구현했다. 거름망이 근거 아님으로 본 메모를 남기되 dense 점수를 깎는다. 감점은 0.02~0.30 중 dev로 골랐는데, 대부분 0.02~0.05로 선택되어 b와 비슷하게 동작했다.
- **현재 모델과 거름망:** 현재 모델(e5-small)은 거름망 없이는 크게 나빠진다. PR #36이 거름망을 넣은 이유가 확인됐다.
- **ko-sroberta에서 거름망을 끄면:** 정답을 더 찾지만, "없음"을 판정하는 능력(4/5 → 2/5)을 잃는다.
- **Q13 "막 두께가 고르지 않아":** 모든 모델에서 b(끔)일 때만 성공했다. 거름망이 표현 차이로 정답을 지우는 문제는 거름망을 끄기보다 거름망이 인식하는 표현을 보강하는 방향으로 다룬다(후속 후보).

## 실험 4: 메모 벡터 저장 방식

스크립트: `agent/python/evals/v3_decision_engines/vector_store.py`
구현: `agent/python/src/kplasma_agent/v3/decision_rag/vector_store.py` ([설정 문서](../development/agent-v3-decision-rag.md#판단-기록-엔진-선택))

**후보**

| 방식 | 저장 위치 | 다시 임베딩하는 때 | 장점 | 단점 |
| --- | --- | --- | --- | --- |
| 묶음 캐시 (PR #36 `LocalIndex`) | worker 로컬 파일 (묶음마다 행렬 1개) | 판단 기록이나 Run 범위가 바뀔 때마다 전체 | 구현이 단순하다 | 메모 수에 비례해 매번 느려지고, 기존 메모 벡터가 배치에 따라 흔들린다 |
| 메모별 로컬 저장 (중간 방식, `IncrementalIndex`) | worker 로컬 SQLite (메모 문장마다 벡터 1개) | 아직 없는 메모만, 검색 요청 때 | 공용 서버·DB를 바꾸지 않는다. 모델별 벡터를 함께 보관할 수 있다 | 첫 검색 요청에서 임베딩한다. worker가 여럿이면 각자 저장한다 |
| 서버 DB pgvector (정석) | 공용 PostgreSQL 벡터 테이블 | 메모 저장 시점 | 저장 직후 검색할 수 있고 여러 worker가 공유한다 | 마이그레이션, pgvector 이미지 변경(현재 `postgres:18.6-alpine`), Java 서버와 Python 임베딩 간 연결 설계가 필요하다. 팀 합의 필요 |

- 이번 실험은 공용 서버·DB를 바꾸지 않는 앞의 두 방식만 비교했다.
- 메모별 저장의 표 구조(모델 키, 문장 해시, 벡터)는 나중에 서버 DB 테이블로 옮길 수 있다.

**공정성 설계**
- 주 지표(임베딩한 메모 수, 걸린 시간, 기존 벡터 변화)는 정답지에 의존하지 않는다.
- 규모를 키운 데이터(3000, 10000건)는 모든 메모에 고유 문구를 붙였다. 같은 문장이 반복되어 중복 제거가 메모별 방식에 유리해지지 않게 하기 위해서다.
- 요청 순서에는 두 방식이 같아야 하는 단계("같은 요청 반복")도 넣었다.
- 품질 확인은 두 질문 묶음을 따로 보고했다. 하나는 실험 2의 질문 40개, 다른 하나는 PR #36 평가의 RAG 질문 6개(07~12)다. PR #36 질문에는 정답지가 없어 두 방식의 결과 일치 여부만 본다.
- 두 방식 모두 ko-sroberta, 기준값 0.47/0.02, 엄격 거름망을 쓴다. 요청마다 encoder의 메모리 캐시를 비웠다.
