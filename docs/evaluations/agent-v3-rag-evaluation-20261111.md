# V3 판단 기록 RAG 평가와 개선 분석

작성 기준: 2026-11-12

## 1. 이 문서가 설명하는 결과

V3에 연결한 판단 기록 RAG를 대상으로 기능 연결 검사, 실제 모델 A/B 평가,
실패 원인 분석과 구성요소 개발 재검사, 같은 12문항의 실제 모델 회귀 평가,
웹 사용 중 발견한 이름 입력 오류의 수정·연결 검증을 구분해 기록한다.

확인된 실제 모델 성적은 다음과 같다.

- 최초 동일 12문항 A/B: 규칙 ON·RAG OFF 3/12(25.0%), 규칙 ON·RAG ON 8/12(66.7%).
- 정밀도 수정 후 같은 기존 12문항의 RAG ON 회귀: 11/12(91.7%).
- 이전 RAG ON과 같은 기준으로 비교한 순증: 3문항, +25.0%p.

91.7%는 이미 알려진 개발 사례와 같은 합성 판단 데이터에서 얻은 단회 회귀 통과율이다.
자유로운 모든 질문, 신규 문서, 실제 물리 인과, 일반 웹 사용 전체의 정확도가 아니다.
기록 관련 8문항은 대상 Run을 미리 선택·첨부한 API 평가였으며, 이름만 적는 입력 흐름은
이 평가에 없었다. 이후 이름 연결을 수정했지만 그 뒤 새로운 실제 모델 정확도를 산정하지 않았다.

새 60문항을 RAG OFF/ON으로 실행하는 120요청 확대 평가는 중지 상태다.
해당 두 전용 DB의 Agent 요청·모델 시도는 각각 0/0이며 이 보고서 성적에 합치지 않는다.

## 2. 평가 범위와 공통 실행 조건

### 2.1 평가 대상

V3 독립 복제본에 이식한 판단 기록 검색과 비용 반려 규칙, 이를 사용하는 계획·도구·저장·표시 경로다.
V1/V2를 덮어쓰거나 서로 다른 버전의 성적을 같은 시험으로 합치지 않는다.
기존 V1 60문항 근거 회수 성적과 이번 V3 12문항 전체 Agent 성적은 대상·분모가 달라 직접 비교하지 않는다.

저장된 수치 Run 150개와 합성 판단 기록 360건을 사용했다. 판단 기록은 실제 사람의 검토나
비용 측정 결과가 아니며, 수치 데이터가 존재한다는 사실이 판단 메모까지 존재함을 의미하지 않는다.
실제 실험 결과·사용자 대화와 판단·DB·비밀값은 공개 평가 자료에서 제외한다.
사용자가 공유를 요청한 평가 질문 12개와 합성 판단 360건의 원문 문장은 [원문 자료](v3-rag-materials/README.md)에 제공한다.

### 2.2 기능 스위치의 뜻

- rulesEnabled: 명시된 비용 사유 반려 기록을 고유 기록 단위로 전수 집계하는 기능.
- ragEnabled: 로컬 임베딩을 이용해 관련 판단 메모 원문과 출처를 찾는 기능.
- 수치·단위·Run 버전·사용자 선택·계획 의미 Decisions는 두 스위치와 별개의 필수 검증이다.
- RAG 검색 결과의 유사도만으로 후보 Run을 제외하지 않는다.
- 비용 집계에서 상위 검색 결과 수나 메모 안의 반복 표현을 별도 반려 건수로 쓰지 않는다.

### 2.3 실제 모델 평가 설정

계획·답변·Decisions 모델은 gpt-6-luna, 계획·답변 reasoning effort는 low였다.
timeout 90초, 계획 의미 검토 ON, 요청 전체 재계획 최대 2회, 답변 재작성 최대 1회,
요청당 모델 시도 상한 13회를 유지했다. 내부 복구는 같은 논리적 요청의 실행이며 새 질문으로 세지 않는다.

검색은 intfloat/multilingual-e5-small의 고정 revision을 로컬에서 사용했다.
최소 유사도 0.78, 상대 차이 0.08, 검색 도구 한 번의 최종 인용 상한 5개를 유지했다.
재정렬 모델과 experimental facets는 사용하지 않았다. 유사도 0.78은 정답 확률 78%가 아니다.
상한 5는 항상 5개를 채우라는 뜻이 아니며, 적합한 근거가 없으면 0개를 반환해야 한다.

평가용 DB·대화·파일 저장소·검색 캐시는 일반 웹과 분리했다. 실제 평가 전 질문·정답·데이터·
코드와 backend jar를 동결하고 문항마다 소스 해시를 검사했다. 시험 중 정답이나 임계값을 바꾸지 않았다.

## 3. 지표와 채점 방법

### 3.1 전체 Agent 엄격 통과율

질문별 필요한 실행·수치·단위·최종 후보·선택 재개·기록 근거·최종 설명을 모두 만족한 문항 수를
전체 문항 수로 나눈다. HTTP 상태 COMPLETED만으로 정답 처리하지 않는다.
구조화된 공식 수치 표와 후보 목록도 사용자 답변의 일부다. 같은 숫자의 산문 반복은 요구하지 않는다.

### 3.2 필요한 근거 회수율

필요한 정답 출처 중 실제 반환한 정답 출처의 비율이다.
예: 정답 근거가 3개인데 2개만 찾으면 2/3이다. 정답 근거가 없는 질문은 이 분모에서 제외한다.
비용 규칙의 전수 집계 증빙은 의미검색 근거와 별도로 계산한다.

### 3.3 검색 정밀도

실제로 반환한 고유 출처 중 필요한 정답 출처의 비율이다.
예: 필요한 3개와 무관한 12개를 함께 가져오면 회수율은 100%라도 정밀도는 3/15다.
근거 없는 질문에서 오인용한 출처도 정밀도 분모에 포함한다.

### 3.4 근거 집합 전체 일치

필요한 출처를 빠뜨리지도 않고 무관한 출처를 추가하지도 않은 양성 문항의 비율이다.
회수율만 높이고 반환 문서를 과도하게 늘리는 방식은 이 지표를 통과할 수 없다.

### 3.5 근거 없음 처리

검색 후 인용이 비어 있는지와, 최종 답변이 질문에 맞춰 확인 불가를 설명했는지를 따로 검사한다.
원문이 없는 금액을 만들지 않는 것은 필요하지만, 질문이 금액을 요구했다면 금액을 확인할 수 없다는
구체적 안내까지 있어야 전체 이행으로 본다. 검색 실패나 기능 오류로 인용이 없는 경우는 올바른 기권이 아니다.

### 3.6 출처 정확성과 중복

기록 ID뿐 아니라 원문, 귀속 역할, Run·버전, 문서 ID, 해시의 일치를 검사한다.
같은 문항의 여러 단계에서 완전히 같은 출처가 반복된 경우 고유 집합으로 계산하되,
반복 호출·중복 표시 횟수는 별도 수치로 공개한다. 단계별 결과를 앞 5개로 잘라 채점하지 않는다.
다른 Run에 귀속되거나 원문이 바뀐 인용은 관련 주제여도 통과시킬 수 없다.

### 3.7 정답 작성과 검토의 한계

최초 12문항과 정답은 구현 결과를 보지 않은 별도 에이전트가 작성·교차 검산했다.
작성자는 프런트엔드 연결 작업에도 참여했고 정답 교차 검산은 같은 작성자가 별도 단계에서 수행했다.
따라서 완전히 독립된 사람 평가나 서로 다른 전문가의 정답 검토로 표현하지 않는다.
질문·정답의 동결 SHA256은 9bcaf2973c545d0c444045f26cce7de195451bef2de70d045b1af644beeb052a다.
이 해시는 비공개 수치 정답을 포함한 원래 파일의 해시다. 부록의 공유 질문 JSON은 정답 필드를 제외했으므로 파일 해시가 다르며, 원문 문장 일치는 별도 manifest로 확인한다.
평가 정답·정답 기록 ID·정답 개수는 모델이나 검색 인덱스에 제공하지 않았다.
다만 실제 사용자 첨부를 대신해 평가 실행기가 대상 Run을 사전에 선택·첨부했으므로,
입력부터 Run을 확정하는 모든 웹 사용 흐름을 평가한 것은 아니다.

답변 내용은 조건 라벨을 가린 독립 AI 검토자가 확인했다. 사람이거나 도메인 전문가인 검토자는 아니다.
내용으로 기능 상태를 짐작할 수 있으므로 완전한 이중 맹검이라고 부르지 않는다.
합성 기록, AI 작성 정답, 알려진 문항의 반복, 모델의 단회 생성 변동이 모두 해석의 한계다.

## 4. 회차 0 — V3 기능 연결·격리와 무료 코드 검사

### 목적

RAG와 비용 규칙이 기존 V3 실행 계획의 정식 도구로 작동하고, OFF 기능이 실행되거나
다른 Run의 근거가 저장되지 않는지 확인했다. 기존 그래프의 11개 노드와 연결은 유지하고
execute_step이 decision_records를 처리하도록 확장했다.

### 확인된 통합 경계와 수정

### 가. 같은 Run의 서로 다른 버전이 중복으로 거절되던 경계가 있었다.

   고유 참조를 Run ID만이 아닌 Run ID·버전 쌍으로 검사하도록 보완했다.
   비용 반려 전수 건수는 여전히 Run ID 단위로 집계한다.

### 나. 모델에 실제로 전달한 기능별 지시·스키마와 입력 예산 검사의 대상이 달랐다.

   최종 조합한 planner/writer 입력을 검사하도록 맞췄다. OFF 기능을 지시문에 남기지 않는다.

### 다. 같은 기록 inventory fingerprint를 가진 단계의 인용 카드를 합치면서 근거가 빠질 수 있었다.

   단계별 snapshot을 유지하도록 보완했다. 같은 inventory여도 질문·범위·action은 다를 수 있다.

### 검증

Python V3 173개, 관련 프런트 28개, 백엔드 V3 단위 16개가 통과했다.
Ruff, 범위 지정 Mypy 52개 소스, 프런트 빌드, backend bootJar를 검사했다.
390/800/1008/1440px에서 버전 선택·스위치·가로 넘침·JS/API 오류와 저장된 결과 표시를 확인했다.
저장 응답의 화면 재생 검사는 새 실제 질문을 보낸 시험이 아니며 모델 호출은 없었다.
Docker 기반 DB 계약 검사 4개는 작성·컴파일했지만 실행하지 않았다.

### 해석과 수정 방향

이 회차는 연결·격리·저장·표시 정합성 검사다. 검색 정확도 상승이나 실제 Agent 통과율로
해석하지 않는다. 다음 회차에서 같은 질문을 실제 모델에 보내 최종 답변과 도구 실행을 함께 확인했다.

## 5. 회차 1 — 실제 모델 동일 12문항 A/B

### 목적·실행

규칙 ON을 고정하고 RAG OFF/ON 차이를 확인했다. 각 조건 12개, 총 24개 실제 Agent 요청이다.
문항별 A→B 여섯 쌍과 B→A 여섯 쌍을 고정 seed로 섞었다. 두 조건은 같은 초기 데이터 사본을 썼다.
논리적 요청 24개에 내부 모델 시도 64회(A 34/B 30)가 기록됐다. 이는 질문 64개라는 뜻이 아니다.

### 결과

| 지표 | 규칙 ON·RAG OFF | 규칙 ON·RAG ON |
| --- | --- | --- |
| 전체 엄격 통과 | 3/12 · 25.0% | 8/12 · 66.7% |
| 양성 의미검색 근거 회수 | 0/9 | 8/9 · 88.9% |
| 무근거 오인용 포함 정밀도 | 해당 없음 | 8/9 · 88.9% |
| 양성 근거 집합 전체 일치 | 해당 없음 | 3/4 |
| 올바른 근거 없음 처리 | 0/2 | 1/2 |
| 비용 규칙 증빙 회수 | 5/6 | 5/6 |
| 비용 규칙 증빙 전체 일치 | 1/2 | 1/2 |

전체 통과의 관측 차이는 +41.7%p다. RAG OFF에서 의미검색 호출은 0회였다.
OFF에서 무인용이라는 이유만으로 근거 없음 처리 통과로 올리지 않았다. 관련 요청이 기능 제한 안내가
아닌 오류로 종료됐기 때문이다. 이 시험은 기록 검색이 필요한 질문이 많은 구성이라 일반 전체
업무의 OFF 기준 성능을 대표하지 않는다.

### 문제 1: 사용자 직접 선택이 시작되기 전에 종료

증상: 전체 등록 목록을 열어 달라는 요청에서 선택 대기까지 도달하지 못했다.
확인한 원인: 계획이 전체 목록 대신 비어 있는 현재 comparison_entries를 후보 출처로 사용했다.
수정 방향: 전체 등록 목록과 현재 선택·선행 검색 후보를 구분하고 잘못된 출처를 실행 전에 거절한다.
          기존 재계획 예산 안에서 고쳐야 하며, 제한된 범위를 전체 목록으로 임의 확장하지 않는다.

### 문제 2: 비용 반려 기록 누락

증상: 명백한 비용 사유 반려 한 건이 집계에서 빠져 후보의 건수와 제외 결과가 틀렸다.
확인한 원인: 연결어가 있는 문장을 전체 UNCLEAR로 분류해 행정적 부연까지 비용 사유를 지웠다.
수정 방향: 문장 전체가 아니라 비용 관련 절의 긍정·부정·해결·미확정 상태를 대조하고,
          Python과 서버가 같은 고유 기록 건수를 독립 계산하게 한다.

### 문제 3: 공동 메모 누락

증상: 실제 공동 메모가 있는데 검색 전에 후보 문서가 제거됐다.
확인한 원인: 개별 메모와 구분하라는 요청을 개별 메모만 읽으라는 뜻으로 해석하고,
           귀속을 추측하지 말라는 금지를 공동 메모 조회 금지로 전파했다.
수정 방향: 읽기·인용 금지와 귀속 추측 금지를 분리한다. 공동 메모를 찾더라도 개별 후보의
          비용 사유로 옮기지 않으며 실제 조회 금지는 유지한다.

### 문제 4: 검증 근거가 아닌 원문을 인과 검증에 사용

증상: 검증 완료된 물리 인과 근거를 요구했지만 단순 성능 반려 메모 한 건이 반환됐다.
확인한 원인: 요청 명제의 인과 사건·방향·검증 상태를 충분히 검사하지 못했고,
           사용하지 말라는 반려 예시를 검색할 주제로 남겼다.
수정 방향: 원문이 요구 명제를 실제로 지지하는지 확인한다. 검증 완료와 미검증·자료 대기·
          단순 분석 완료를 구분한다. 새로운 물리 원인을 만들어 주장한 실패와는 구분한다.

### 추가 문제와 남은 방향

RAG OFF의 기록 관련 질문은 안전한 기능 제한 설명 대신 INVALID_AGENT_REQUEST로 종료되는
경계가 있었다. 이 동작의 안내 개선은 별도 후속 과제다.
또한 구조화된 후보가 같아도 한 조건의 산문이 원문과 후보의 연결을 부정하는 사례가 있었다.
따라서 A/B 차이 전부를 검색 알고리즘의 인과 효과라고 단정하지 않고 생성 변동도 남긴다.

### 실행 증빙의 한계

뒤 20요청은 실제 체크포인트에서 계획 검토 ON과 모드 일치를 직접 관찰했다.
앞 4요청은 완료 뒤 체크포인트가 삭제돼 실행 gate와 모델 시도를 통한 추론 증빙으로 구분했다.
첨부 선택을 준비하지 못한 HTTP 400 거절 1회는 실제 Agent 접수·모델 시도 0임을 확인했다.
이미 접수한 실패 문항을 재실행하지 않았고 준비 거절과 실제 접수 24개를 구분해 보존했다.

## 6. 회차 2 — 정밀도 개선 과정의 구성요소 개발 재검사

### 목적

필터를 완화하기만 했을 때 필요한 기록은 돌아왔지만, 선택 후보 하나만 겹치는 다른 검토의

### 방법 1: 공동 검토 범위 검사

같은 후보 묶음을 함께 검토한 메모를 요청하면 기록의 후보 관계가 해당 묶음을 포함하는지 확인한다.
특정 Run·부분집합·ANY 요청은 따로 보존한다. 조회 범위가 크다는 이유만으로 모든 기록이
그 전체를 동시에 검토했어야 한다고 요구하지 않는다.
메모가 없는 Run도 사용자의 실제 선택 범위에 남겨 두며, 문서에 등장한 Run만으로 범위를 재구성하지 않는다.

### 방법 2: 요청·금지·표시 지시 분리

쉼표로 나열한 금지 예시는 마지막 금지 술어가 전체 목록에 적용되도록 보존한다.
원문을 표시하거나 출처를 구분하라는 지시를 독립적인 사실 검색 OR 조건으로 세지 않는다.
하나의 기록이 여러 조건을 동시에 만족해야 하는 경우와 서로 다른 근거를 각각 요구한 경우를 구분한다.

### 방법 3: 사건과 증거 상태 검사

질문과 원문의 지표, 증감 방향, 원인과 결과의 역할을 문장·절 단위의 명시적 표현으로 대조한다.
미검증·자료 대기 기록 자체를 찾는 질문은 허용하되 이를 검증 완료 근거로 승격시키지 않는다.
별도 유료 분류기나 재정렬 모델은 추가하지 않았고 임베딩·0.78/0.08 임계값·상한 5를 유지했다.
질문 전체 문자열이나 평가 정답 ID를 외운 예외 규칙을 넣지 않았다.

### 방법 4: 비용 절 분류와 정책 버전

cost-regex-2에서 비용 관련 절의 상태를 분류한다. 다른 주제의 불확실성이나 행정 설명이
명백한 비용 사유를 지우지 않게 한다. 같은 심사의 반복 문구는 고유 기록 한 건으로 센다.
Python/Java가 인공 문장 49개를 같은 기준으로 분류하는 계약 검사를 사용했다.
신규 실행 저장은 정책 2로 검증하고, 과거 정책 1의 저장 결과는 그 당시 정책으로 읽는다.
기존 결과를 재라벨링하거나 V1/V2 정책을 바꾸지 않았다.

### 방법 5: 선택 목록 출처를 계획 단계에서 검증

전체 등록 목록에서 새로 고르면 candidates=null을 사용한다.
검색 결과 안에서 고르면 선행 candidates/candidate_group을 사용한다.
잘못된 선택 출처를 도구 실행 전에 거절하고 계획 지시·Decisions의 선택 대상 검토를 함께 보완했다.
선택이 적다는 이유로 전체 목록을 대신 쓰거나, 사용자 선택 전에 임의의 Run을 고르지 않는다.

### 문제 1: 안전한 기권과 질문 전체 이행의 차이

증상: 금액 질문에서 실제 검색 결과와 인용은 0개였고 금액·통화를 날조하지 않았다.

     구체적 답변을 명시하지 않았다.
확인한 원인: 검색 NO_EVIDENCE 상태는 보존됐지만, 최종 문구가 질문의 첫 요구와 충분히 연결되지 않았다.
수정 방향: 요청한 정보가 금액·통화·시점·검증 완료 여부 중 무엇인지 보존해 확인 불가 안내를 작성한다.
          단순 무인용을 성공으로 세지 않고 질문별 확인 불가 이행을 별도 채점한다.
상태: 이 회귀 평가 중 제품이나 정답을 바꿔 재실행하지 않았다. 미달 판정 1개를 유지한다.

### 문제 2: 필요한 출처는 정확하지만 중복 검색·표시가 남음

증상: 고유 의미검색 출처 9개는 모두 정답이었지만, 복합 근거 문항에서 같은 3개 출처가 각각
     세 번 반환돼 raw 인용 15개 중 동일 출처 중복 6개가 발생했다.
확인한 원인: 여러 계획 단계가 같은 질문·범위의 기록 검색을 반복했고 단계별 근거가 각각 표시됐다.
수정 방향: 질문·Run/버전·모드·inventory·정책이 같은 검증된 검색 결과를 재사용하고,
          원문·역할·버전·해시가 같은 인용의 중복 표시를 줄인다. 다른 질문·범위의 근거는
          inventory fingerprint만 같다는 이유로 제거하지 않는다.
상태: 고유 출처 정밀도 100%와 반복 호출 문제를 구분한다. 중복 해결 성적으로 보고하지 않는다.

### 문제 3: 후보 수와 기록 수의 혼동

증상: 메모 인용이 0개여도 유지된 Run 후보가 하나면 하단에 검색 결과 1개가 표시될 수 있다.
원인: 후보 출력의 개수와 판단 기록 검색 개수를 같은 일반 문구로 표시한다.
수정 방향: 조회 Run 수·검색 가능한 문서 수·반환 기록 수·인용 수를 사용자에게 구분해 보여 준다.
          Run이 존재한다는 사실을 판단 기록 한 건이 존재한다는 뜻으로 읽히게 하지 않는다.

### 계획·복구와 모델 시도

재계획 없이 최종 엄격 통과한 문항 9개, 한 번의 재계획 후 최종 통과한 문항 2개,

유효 계획의 Decisions 의미 검토 12회는 모두 PASS였고 답변 재작성은 없었다.
논리적 요청 12개에 내부 모델 시도 30회가 기록됐다.
  최초 계획 12 / 계획 의미 검토 12 / 재계획 2 / 답변 작성 2 / 답변 검토 2.
12개 모두 실제 그래프 상태의 plan_review_enabled=true와 요청 모드 일치를 직접 확인했다.

### 해석 제한

두 회차는 같은 문항·정답 기준이지만 모델의 단회 생성 변동도 포함한다.
따라서 점수 차이 전부를 코드 수정의 순수 인과 효과라고 단정하지 않는다.
100%는 의미검색 고유 출처 9개의 성적이며 전체 Agent 성적은 91.7%다.
이름 입력 경로의 후속 수정 뒤 현재 전체 정확도를 다시 측정한 결과도 아니다.

## 8. 회차 4 — 웹 자유 입력에서 발견한 이름 연결 누락과 무료 연결 검증

### 발견한 입력 방식

사용자가 Run을 첨부하지 않고 등록 이름을 문장에 적어 과거 판단 기록을 요청했다.
기록 관련 기존 8문항은 모두 평가기가 Run 참조를 사전에 첨부했으므로 이 사용 방식을 검사하지 못했다.

### 증상과 확인한 원인

질문의 이름은 실제 DB의 Run·버전 참조로 연결되지 않았고 최초 계획은 빈 selected_runs를 사용했다.
재계획에서도 원문과 다른 선택 대상·개수를 제안하여 검증이 차단했다. 기록 도구 실행 수는 0이었다.
이는 실제 저장 기록의 부재나 유사도 임계값 때문에 근거를 놓친 사례가 아니다.
입력 단계에서 조회할 대상을 확정하지 못한 문제이며, 기존 평가 설계의 범위 누락도 함께 드러났다.

### 수정 방법

서버가 이름을 opaque한 등록 ID로 정확히 대조하고 고정 버전을 제공한다. 이름의 숫자에서
물리 조건을 추정하지 않는다. 명시적으로 첨부한 과거 버전은 유지하고 모호한 이름·버전은 확인 대상으로 남긴다.
namedRunReferences/namedRunBindings를 기존 선택과 분리해 planner·Decisions·도구 바인딩에 전달한다.
원문 이름·고정 참조·인용 구절의 대응을 검사하고 서버도 실행 직전 이름 참조를 다시 인증한다.
이전의 다른 active/candidate Run을 새 이름 대신 조회하지 않는다. 명시된 여러 이름 중 일부를
요청한 원문의 의미는 검토하되 이름이 등장했다는 이유만으로 모두 조회하도록 강제하지 않는다.
알 수 없거나 버전을 확정하지 못하면 모델·도구를 부르기 전에 이름 확인·첨부 안내를 제공한다.

### 무료 검증 결과

- 새 Python 검사 11개를 포함한 전체 V3 358개 통과.
- 새 resolver/service 검사 18개를 포함한 백엔드 V3 단위 40개 통과.
- 미첨부·소문자·문장부호·한국어 조사·복수 이름과 일부 조회·과거 버전·모호성·위조 바인딩·
  이전 선택 보존·다른 Run 혼입 차단을 확인했다.

- 실제 로컬 기록과 설치된 E5로 짧은 이력 질문을 검색하여 관련 기록 3개를 확인했다.
- 별도 DB의 HTTP 요청에 첨부 배열을 비워 제출하고, 서버 이름 확인→claim→전체 그래프→
  실제 E5 검색→원문·출처 검증→저장·최종 snapshot까지 확인했다.

- 알려진 이름은 기록 3개·완료, 미등록 이름은 인용 0개·구체적 확인 안내였다.
  계획 생성·Decisions는 고정 인공 응답이었고 provider API 호출은 0이었다.
  미등록 이름은 고정 인공 모델조차 호출하지 않았다.

- 실제 상태에서 계획 검토 ON과 요청 모드 일치를 확인했다. 기존 데이터·대화·V1/V2와
  그래프의 11개 노드·연결 등록을 보존했다. 임베딩·검색 임계값과 기존 정답은 바꾸지 않았다.

### 검증 준비 오류의 보존

연결 검증기에서 payload 필드명, 비어 있는 초기 체크포인트, 완료 상태명의 계약을 맞추는
과정에서 발생한 검사 오류는 별도 DB와 로컬 증빙에 남겼다. 고정 인공 응답 검사 과정이며,
실제 모델 평가의 실패 문항을 성공할 때까지 재실행한 점수로 합치지 않는다.

### 수정 후 웹에서 기록이 없는 Run을 조회한 사례

이름·버전 확정과 검색은 정상 실행됐으나 선택 범위 문서 0개·인용 0개였다.
별도로 저장된 판단 360건을 확인한 결과 해당 Run에 연결된 기록이 없었다.
이 경우는 검색 전에 대상 확정이 실패한 위 사례와 구분한다. 검색 대상 문서가 유사도 필터
이전부터 0개이고 과거 버전도 포함했으므로, 해당 로컬 데이터에서 실제 기록 부재가 확인된 경우다.
이 단일 사용자 사례를 전체 정확도 점수로 환산하지 않는다.

### 해석과 남은 검증

이름이 같은 Run·버전으로 연결된 뒤에는 기존 RAG 검색 로직을 사용한다.
하지만 이름 해석·범위 확정의 성공까지 포함한 자유 입력 전체 성적이 기존 91.7%와 같다고
확정할 수는 없다. 이 경로는 수정·연결 검증 완료로 기록하며 새 실제 모델 성적으로 재라벨링하지 않는다.

## 9. 다음 수정과 평가 방향

### 가. 질문별 NO_EVIDENCE 안내

금액·통화·시점·검증 완료 여부 등 요청 정보가 무엇인지 보존해 구체적으로 확인 불가를 설명한다.
평가에서는 인용 0개와 질문 전체 이행을 별도 채점하고, 오류 중단을 올바른 기권으로 올리지 않는다.

### 나. 중복 검색과 인용

동일 질문·Run/버전·모드·기록 snapshot·정책의 검증된 결과만 재사용한다.
캐시를 쓴 경우 원문·버전·귀속 해시를 다시 확인하며 다른 범위의 정당한 근거를 합치지 않는다.
고유 정밀도와 raw 인용·중복 호출을 같이 보고한다.

### 다. 입력 흐름 평가 범위 확장

사전 첨부 질문과 이름만 입력한 질문을 구분하고, 짧은 구어체·이어 질문·다른 이전 선택·
등록되지 않은 이름·모호한 버전·일부 이름 제외·기록 없는 Run을 포함하는 평가가 필요하다.
같은 Run에 도달한 뒤의 검색 결과와, 입력부터 도달하기까지의 전체 성공률을 분리한다.
현재 문서는 이 평가를 실행했다고 주장하지 않는다.

### 라. 사용자 표시

조회 Run 후보 수와 기록 문서·반환·인용 수를 구분하고, 빈 검색과 대상 확정 실패의 안내도 나눈다.
모의 판단 기록임을 유지하고 물리 원인이나 비용 측정이 검증됐다는 뜻으로 표시하지 않는다.

### 마. 기능 OFF 경로

비활성 기능을 실제로 호출하지 않는 격리는 유지하면서, 해당 요청을 지원하지 않는 이유를
사용자에게 명시하는 경로를 검증한다. 필수 수치·계획 검증을 OFF 스위치와 함께 끄지 않는다.

### 바. 새 문항 평가

실행 전 질문·정답·문서·버전·코드·모델 설정을 고정하고 알려진 12문항과 분리한다.
회수율과 정밀도·전체 일치·근거 없음 처리를 함께 확인하며, 성공할 때까지 실패 질문을 재실행하지 않는다.
최초 계획 경로와 재계획 후 복구, 실제 모델 호출과 인공 모델 검사를 구분한다.
중지한 60문항·120요청을 포함한 추가 실제 모델 평가는 자동 재개하지 않는다.
