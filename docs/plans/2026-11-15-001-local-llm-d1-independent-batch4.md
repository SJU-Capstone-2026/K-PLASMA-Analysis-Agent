# d1 독립 4개 GPU 배치와 Docker 1.5GiB 구현 계획서

> 구현 시 `superpowers:executing-plans`에 따라 단위별로 진행한다. 이 문서는 계획이며, 코드 변경·Docker 설정 적용·실제 모델 평가 결과가 아니다.

**Goal:** d1 검사항목의 독립성을 유지하면서 최대 4개를 GPU 배치로 계산하고, Docker VM을 1.5GiB로 제한한 동일 환경에서 기존 개별 처리와 정확도·시간·메모리를 비교한다.

**Architecture:** 기존 d1 전용 MLX 서비스 안에서 각 검사를 별도 singleton pack으로 만든다. 하나의 모델 가중치를 공유하고 여러 pack을 별도 배치 행으로 계산하며, 결과는 기존 검토 파서에 그대로 반환한다. LangGraph·도구·검토 지침·최종 응답 양식은 유지한다.

**Tech Stack:** Apple M4 Pro 24GB, 기존 Qwen/llama.cpp, d1-2B BF16, Python 3.12, MLX 0.32.4, 고정 mlx-decision 1.3.0 소스 `2527a733c97a3fd5e0de54ea19f74fd362ed1ad2`, Docker Desktop VM 1536MiB.

**Spec:** 2026-11-15 사용자 요청과 [기존 v2.3 계획](2026-11-14-004-local-llm-v2.3-qwen-analysis-d1-joint.md), [기존 구현·검증 기록](../verification/2026-11-14-local-llm-v2.3-qwen-d1-joint.md)을 따른다. 이전의 여러 검사를 한 입력에 넣는 묶음 후보를 독립 행 배치로 대체하는 후속 계획이다.

## 먼저 읽는 요약

1. Docker VM을 **2GiB → 1.5GiB(1536MiB)**로 줄이고, DB와 기존 데이터가 정상인지 먼저 확인한다.
2. 검사를 하나씩 독립 입력으로 만든다. 검사 11개라면 보통 **4개 → 4개 → 3개**를 계산한다.
3. 같은 조건에서 현재 Q8 개별, MLX 개별, MLX 독립 4개 배치를 비교한다.
4. 결과표에 정답 여부·개별 방식과의 판정 차이·시간·메모리·스왑을 각각 기록한다.
5. 빠르더라도 검토 결과가 달라지거나 메모리 검증에 실패하면 적용을 보류한다. 기존 모델 자체의 오답도 숨기지 않는다.

이번 요청은 **계획서 작성**까지다. 실제 설정 변경·서비스 재시작·구현·평가는 후속 구현 단계에서 수행한다.

## 고정 조건

- v2_localLLM만 변경한다. 보호 대상 그래프 검증·제품 수정은 범위에 넣지 않는다.
- 기존 그래프의 노드·간선, `submit_plan`, 계획 필드, 검토 지침·선택지·집계 규칙, 최종 응답·스트리밍을 유지한다.
- 설정과 평가 그래프 상태의 `plan_review_enabled=true`를 확인한다. 요청 전체 재계획 최대 2회, 필요한 답변 검토와 재작성 최대 1회를 유지한다.
- Qwen 모델·엔진·생각 예산·샘플링·context 24576·batch/ubatch 256·호출 제한을 바꾸지 않는다. Qwen 캐시도 시작 시 확인한 동일 설정을 모든 비교에 사용한다. 현재 문서상 공용 기본값은 OFF다.
- d1 BF16 가중치 revision·tokenizer·calibration·MLX 라이브러리는 기존 pin을 유지한다. 정밀도·확률 임계값·지침을 함께 조정하지 않는다.
- Qwen과 d1은 기존 lease로 교대 실행한다. 모델을 여러 벌 로드하거나 같은 모델 인스턴스를 여러 스레드에서 호출하지 않는다.
- 개발 메모리 정책의 warning 허용·critical/미지 상태 차단을 유지한다. critical은 일시 회복해도 실패 기록을 남긴다. swap은 증가량과 시간에 미친 영향을 보고한다.
- 추론은 인증된 loopback·로컬 모델 파일만 사용한다. 외부 상용 모델 fallback·외부 tracing·원문 전송을 추가하지 않는다. 맥 전체 인터넷 차단은 하지 않는다.
- 원시 입력·모델 응답·DB·사용자 기록·세션은 Git 제외 로컬 경로에만 보관한다. 공개 문서에는 소프트웨어 평가 집계만 적는다.
- 기존 미커밋 변경을 보존한다. 공용 모델 기본값 승격·commit/push·PR은 이 계획의 자동 후속 작업에 포함하지 않는다.

## 현재 확인한 사실과 한계

### 독립 배치가 의미하는 것

| 구분 | 입력과 계산 | 이번 용도 |
|---|---|---|
| A: 기존 Q8 개별 | llama.cpp에서 검사마다 별도 연산 | 현재 방식과의 비교 기준 |
| B: MLX BF16 개별 | 동일 본문+검사 하나를 순차 연산 | 병렬 처리 효과를 분리하는 직접 기준 |
| D: MLX BF16 독립 배치 | 본문+검사 하나를 각 행에 넣어 최대 4행 계산 | 새 구현 후보 |
| 과거 C: MLX 공동 입력 | 한 입력에 여러 검사를 넣어 공통 상태를 계산 | 이번 실제 비교에서 제외 |

기존 기록의 C와 혼동하지 않도록 새 후보는 D라고 부른다. A→D에는 엔진·정밀도 변경도 포함되고, **B→D만 독립 배치의 직접 비교**다.

엔진의 `D1Lfm3Backend.hidden_states()`·`rows_hidden()`은 별도 `Packed`를 배치 행으로 처리한다. 행 사이 attention은 섞이지 않는다. 현재 서비스는 `for native, tokens in groups`에서 `backend.score()`를 순차 호출해 이 경로를 활용하지 않는다.

### Docker 1.5GiB는 아직 적합 판정이 아니다

[과거 DB·Docker 측정](../verification/2026-11-13-v2-local-llm-docker-3gib.md)에서 웹 평가 DB의 캐시 포함 피크는 1.060GiB였다. 별도 DB 사본의 복원·동시 조회 10개까지 진행한 시점에는 컨테이너 시작 후 누적 커널 피크 **1.608GiB**가 기록됐다. 이는 동시 부하를 가정한 별도 검사이며, 현재 순차 작업의 필수 부하나 최소 메모리 요구량으로 사용하지 않는다. 최근 Docker 2GiB 웹 평가의 DB cgroup 피크는 약 120~130MiB였다([기록](../verification/2026-11-14-local-llm-development-memory.md)). 측정 구간·캐시 상태가 달라 같은 값으로 해석하지 않는다.

1536MiB는 **Docker Linux VM에 배정하는 메모리**다. DB 컨테이너 전용 상한이나 호스트 Docker 프로세스 RSS 상한이 아니다. Linux·Docker 엔진에도 메모리가 필요하며 VM의 실제 가용량은 별도로 확인한다. 0.5GiB 설정 감소가 호스트 RAM 0.5GiB 회수를 보장하지 않는다([Docker 공식 설명](https://docs.docker.com/desktop/settings-and-maintenance/settings/)).

**1536MiB에서 실제 순차 사용에 해당하는 DB 동작·OOM·응답 시간을 확인한 뒤 모델 비교에 진입**하고, 이후 모델 비교 중에도 DB 메모리를 관측한다. DB 동시 조회 10개는 이번 필수 검사에서 제외한다. d1 독립 배치의 4개 행은 이미 구성된 검토 입력의 GPU 계산이며 DB 조회 4개를 동시에 실행하는 기능이 아니다.

### 메모리 추정과 실측을 구분한다

d1 텍스트 가중치는 약 3.22GiB이며 배치 행끼리 공유한다. 이전 약 4K 토큰 입력 관측과 가중치 외 작업 메모리의 선형 증가 가정으로 계산한 4행 예산은 약 5.64GiB, 개별 대비 +1.82GiB/약 47%였다. 이것은 **활성 할당량의 단순 계산 시나리오**로, 예측 보장·전체 RAM·할당기 캐시 포함 총량이 아니다.

기존 MLX `peak_bytes`는 요청마다 초기화하지 않은 서버 실행 중 누적 피크다. 새 비교에서는 요청별로 초기화해 계측한다. `get_peak_memory()`의 누적 범위와 재사용 메모리인 allocator cache를 구분한다([피크 문서](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.get_peak_memory.html), [캐시 문서](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.get_cache_memory.html)).

## 변경 설계

### 1. 검사는 하나씩, GPU 계산만 최대 4개씩

현재 검토 요청의 전체 `state`, 검사 ID, 지침, 선택지와 순서를 그대로 보존한다. 각 검사를 공식 singleton encoder로 인코딩해 **한 pack에 질문 하나만** 넣는다. 가중치·tokenizer·calibration 파일과 학습 시 `d1_set_size=16`은 수정하지 않는다.

기존 `group_size`는 한 pack에 넣는 검사 수다. 이를 4로 바꾸면 과거 공동 입력의 작은 묶음이 되므로 사용하지 않는다. 별도의 최소 설정 하나를 추가한다.

- `D1_INDEPENDENT_BATCH_SIZE=1`: MLX 기존 개별 경로. 기본값은 1.
- `D1_INDEPENDENT_BATCH_SIZE=4`: 새 독립 배치 경로. `D1_ENGINE=mlx`, `D1_GROUP_SIZE=1`일 때만 허용한다.
- Q8나 `D1_GROUP_SIZE=16`과 독립 배치 4의 조합은 설정 오류로 거부한다. 기존 Q8 및 과거 공동 입력 프로필의 의미는 바꾸지 않는다.
- 서비스 로컬 설정 키는 `independent_batch_size`이며, 설정 파일·worker 프로필·실제 서비스 값이 일치해야 한다.

singleton pack들을 현재 순서로 모으고 다음 두 조건을 모두 만족하도록 결정적으로 나눈다.

1. 한 GPU 배치의 행 수 **최대 4**.
2. `행 수 × 가장 긴 행의 전체 토큰 수 ≤ 32768`.

각 행 자체도 기존 전체 입력 한도 **16000토큰**을 만족해야 한다. 초과 행은 자르거나 요약하지 않고 기존 입력 초과 오류로 종료한다.

약 4.5K 토큰 검사 4개는 약 18K로 한 번에 처리할 수 있다. 약 15.5K 토큰 검사 4개는 32K 배치 한도를 넘으므로 2개+2개로 나눈다. 이는 사전에 정한 입력 분할이며, 메모리 오류 뒤 조용히 2개 방식으로 재시도하는 fallback이 아니다. 실제 행 수·분할 사유를 기록해 모두 4개로 실행한 것처럼 보고하지 않는다.

배치 행은 가장 긴 행에 맞춰 오른쪽을 패딩하고 원래 길이·질문 span을 보존한다. 공식 `SetLayout`·attention mask·계산 경로를 재사용한다. 가중치 한 벌로 계산하고 질문 ID별 hidden state를 공식 `question_features()`·`read_out()`에 전달한다. calibration·선택지 토큰·softmax·최대 확률 선택·tie 처리 규칙을 재작성하지 않는다.

별도 엔진 fork나 설치된 site-packages의 직접 수정 대신 `service.py`의 작은 `score_independent(backend, singletons, max_rows)` 연결 함수를 사용한다. 결과는 기존 `BackendOutput`과 HTTP 반환 계약으로 합친다. 입력한 검사 ID마다 결과가 정확히 하나여야 하며 누락·추가·중복·비정상 확률·잘림·오류는 기존 오류 경로로 보낸다.

`/v1/count`의 기존 `group_counts`·`group_question_ids`는 singleton 단위를 유지한다. 배치 스케줄 정보를 내부 진단에 추가하더라도 원래 질문별 토큰 계수와 바꾸지 않는다. usage는 실제 singleton pack 토큰 수의 합이며, padding 포함 계산량은 별도 진단값으로 기록한다.

### 2. 상태·준비 검사와 해제

실제 독립 배치 크기·배치 토큰 예산·실행 정책 버전을 기존 MLX 프로필과 config fingerprint에 연결한다. `/runtime`·기동 설정·라이브러리 hash·모델 hash·입력 계수·준비 증거가 서로 맞아야 한다. 기존 B/C/Q8의 보고서를 새 D 프로필의 준비 증거로 재사용하지 않는다.

공통 런타임의 프로필 검증·계수 소비자·메모리 증거 생성자와 소비자를 함께 갱신한다. 기존 응답 본문과 그래프 판정 계약은 유지하며 새 배치 진단은 기존 내부 계측 영역에 둔다.

계산 후 GPU 동기화, 모델 참조 제거, GC, allocator cache 해제와 빈 런타임 기준 복귀를 확인한다. 실패하면 Qwen을 다시 깨우지 않는다. 성공하면 기존 Qwen 재개·필요한 계획/답변 검토 경로를 유지한다. 같은 HTTP 요청 안에서는 가중치를 검사마다 재로드하지 않는다.

### 3. 공정한 계측

A/B/D 모두 같은 1536MiB Docker, Qwen 설정·캐시 상태, DB·백엔드·웹 대기 상태와 동일 원본 검토 입력을 사용한다. 한 번에 평가 프로필 하나만 실행하고 소유한 실험 서비스만 종료한다. 다른 앱은 임의로 종료하지 않는다.

MLX B/D 모두 동일한 새 계측 코드를 사용한다. 요청 시작 전 GPU 동기화 후 피크를 초기화하고 로드·각 계산 배치·해제 경계를 기록한다. 배치별 초기화가 필요하면 요청 피크는 각 구간 피크의 최댓값으로 보존한다. 로드/계수/계산/해제 시간을 구분하고 계측 추가 비용도 포함한 전체 시간을 비교한다.

| 지표 | 보고 방법 |
|---|---|
| d1 전체 검토 시간 | 입력 계수·전환·로드·계산·파싱·해제 확인까지, Qwen 계획 생성 시간 제외 |
| d1 내부 시간 | 로드·인코딩/스케줄·계산·해제를 분리, B/D 동일 경계 |
| 정확도 | 기대 정답과 최종 상태 일치 수, 항목별 선택, 잘못된 PASS·잘못된 거절·이유의 타당성 |
| 동등성 | B/D의 입력 digest·singleton token IDs/span·검사별 선택·최종 상태·확률 최대 차이 |
| MLX 활성 피크 | 요청/측정 구간별 native high-water mark |
| MLX 할당기 캐시 | 단계/배치 경계 표본 최대. 관측하지 않은 순간 피크로 표현하지 않음 |
| 프로세스 메모리 | RSS와 가능할 때 footprint 표본 최대. 누적 ru_maxrss와 구간 표본을 구별 |
| 호스트 상태 | active+wired+physical compressor 지표·pressure·swap 시작/끝/피크 증가 |
| Docker/DB | VM 설정·실제 MemTotal, DB working set·캐시 포함 cgroup current/peak, OOM/kill·VM swap 가용 시 |

호스트·RSS·GPU·DB는 다른 회계다. 서로 합산하거나 `24GiB − 호스트 지표`를 가용 RAM으로 계산하지 않는다. allocator cache는 Qwen 지시서 KV 캐시와 별개다. 이번 비교에서 allocator cache 정책도 양쪽 동일하게 유지하며 새 상한 조정 효과를 배치 효과와 섞지 않는다.

## 구현 단위와 검증 순서

### U1. Docker 1536MiB 적용과 데이터 보존

**변경 위치:** 로컬 Docker Desktop 설정과 Git 제외 실행 기록. 설정 예시·실행 설명은 `docs/development/agent-v2-local-llm.md`에 반영한다. 기존 로컬 Docker 설정 변경 절차를 재사용하고 새 범용 관리 도구는 만들지 않는다.

- [ ] 시작 시 실제 MemoryMiB·실행 VM 메모리·컨테이너/볼륨·요청 처리 중 여부를 확인한다. 기존 150 Run/150 version과 과거 대화의 개수·행 hash를 보관한다. 이미 다르면 현재 원본을 기록하고 임의 복원하지 않는다.
- [ ] 진행 중 요청을 끝낸 뒤 DB를 정상 정지하고 Docker 설정을 1536MiB로 변경·재시작한다. 볼륨 삭제·DB 초기화·마이그레이션·컨테이너 DB 상한 추가는 하지 않는다.
- [ ] DB health, 실제 적용값, 데이터 동일성, 실제 순차 사용에 해당하는 조회/저장/재시작 복구, OOM/kill 카운터를 확인한다. 기존 계측 절차를 재사용하되 조회를 인위적으로 10개 동시 실행하지 않는다. 제품 데이터 검증은 읽기 전용, 쓰기 검사는 소량의 인공 기록으로만 수행하고 사전 기록과 구분한다. 별도 사본이 필요한 검증은 공용 DB와 동시에 실행하지 않는다.
- [ ] 1536MiB에서 DB 오류·OOM·데이터 불일치·지속 비정상 상태면 모델 비교를 중단한다. 복구 목적으로 원래 2048MiB로 되돌리고 복구 결과를 보고한다. 2GiB 평가 결과를 1.5GiB 결과로 대체하지 않는다.

**완료 근거:** 설정·실제 VM·DB 피크·응답 시간·OOM·데이터 보존 기록. 1.5GiB 적합성은 실측 후 판정하며 기존 피크만으로 선승인하지 않는다.

### U3. 실제 메모리 준비 검사

**재사용:** `agent/python/evals/local_llm_measure.py`의 인공 검사 본체, 기존 lease·메모리 판정·필요 시 동일 설정의 기존 캐시 왕복 검사. 생성 보고서를 `runtime.py`의 기존 준비 검증으로 다시 읽는다.

1.5GiB에서 공유 DB 옆에 검사 DB를 추가로 띄우지 않는다. 기존 `scripts/agent/measure-local-llm.mjs`는 별도 스택을 만드는 진입점이므로 그대로 실행하지 않고, 같은 Python 검사 본체를 기존 공유 스택의 연결 정보와 함께 사용한다. 실제 웹 화면 준비를 확인한 경우에만 `stack-ready` 증거를 만든다. 공유 연결을 그대로 사용할 수 없는 검사가 있으면 공용 DB를 정상 정지한 뒤 사본 스택만 실행하고 종료 후 원복한다. 두 스택을 동시에 실행한 수치를 단일 스택 메모리로 보고하지 않는다.

- [ ] U1/U2 통과 후 A/B/D 각각 기존 인공 7종을 한 세트씩 실행한다. Qwen·d1의 교대, 큰 입력, 모델 해제와 다음 모델 진입을 관측한다. 총 21검사 행이며 본 정확도 대조 요청과 별도 집계한다.
- [ ] 기존 7종의 d1 인공 입력은 검사 3개라서 실제 4행을 검증하지 못한다. B/D 각각에 **독립 검사 4개·행당 약 4K 토큰**과 **독립 검사 4개·행당 약 15.5K 토큰**을 한 번씩 추가한다. 총 **4개 준비 검토 요청**이며, 전자는 D의 실제 4행 계산, 후자는 2행+2행 분할을 확인한다. 입력·기대 선택은 B/D에서 동일한 인공 값으로 고정한다.
- [ ] B/D에서 실제 행 수·행 토큰 수·padding 토큰 수·분할 원인·가중치 한 벌 상주·요청별 GPU 피크를 확인한다. 토큰 예산 때문에 2행이 된 경우 그 사실을 명시한다.
- [ ] pressure·swap·RSS·MLX active/cache·DB cgroup·OOM을 공통 간격과 같은 단계 표기로 기록한다. 입력 한도/해제/critical/미지 상태/DB 오류가 생기면 이후 모델 단계에 진입하지 않는다.

**완료 근거:** 1536MiB와 각 실제 프로필에 연결된 새 준비 증거. 추가 4검사 준비 결과는 기존 7행의 개수·의미를 바꾸지 않고 별도 증거 필드로 저장하며, D의 준비 판정에서는 이 증거도 필수로 검증한다. warning과 swap 증가는 development 규칙에 따라 기록하며 숨기지 않는다. 메모리 준비 통과와 무스왑 안정성은 구별한다.

### U4. 고정 입력의 정확도·시간·메모리 비교

**재사용/변경:** `agent/python/evals/local_llm_d1_joint_probe.py`의 `review_cases()`, native 변환·입력 digest·기존 파서·메모리 감시를 재사용한다. 새 `agent/python/evals/local_llm_d1_independent_probe.py`에 A/B/D 비교 진입점과 집계를 두고, `agent/python/tests/v2_local_llm/test_d1_independent_probe.py`에서 고정 개수·쌍대 비교·실패 보존·계측을 검사한다. 기존 과거 A/B/C 집계 의미는 바꾸지 않는다.

**입력 8종:** 정상 조회, 정상 전체 후보 비교, 정상 선택 확인 후 비교, 경계 변경, 단위 변경, 비교 누락, 요청하지 않은 설명 추가, 필요한 선택 생략. 기존 인공 입력·정답·검사 지침·선택지를 그대로 고정한다. Qwen으로 계획을 다시 만들지 않으므로 d1의 차이를 분리할 수 있다.

- [ ] 실행 전에 설정과 평가 그래프의 검토 ON, 모델/라이브러리/서비스 식별값·Docker 1536MiB·현재 Qwen 캐시 상태·예산을 확인한다. 스탠드얼론 d1 비교는 그래프 전체를 실행한 웹 평가가 아님을 보고서에 적는다.
- [ ] 고정 8종 × 3회 반복 × A/B/D = **72개 검토 요청**을 한도로 실행한다. 프로필 순서는 반복마다 A→B→D, B→D→A, D→A→B로 교대한다. 동시에 모델을 올리지 않는다.
- [ ] 순서에 따른 영향은 11검사인 정상 선택 확인 사례를 B/D에서 각각 한 번씩 실제 역순으로 입력해 확인한다. **추가 2개**, 본 대조와 합계 최대 **74개**다. 숨은 워밍업·자동 재접수·실패 후 성공할 때까지 반복은 하지 않는다.
- [ ] 각 반복의 모든 입력 digest와 B/D singleton token IDs/span이 같아야 한다. 중간 실패·누락·UNAVAILABLE는 그대로 결과에 포함하고 같은 입력을 자동 재호출하지 않는다. critical/해제 실패는 나머지 실행을 중단한다.
- [ ] case별 3회 기록, 같은 case의 중앙값, 8개 case 중앙값의 프로필 간 비교, 최대값·평균·전체 요청 중앙값을 함께 보고한다. 속도 개선율은 같은 집계끼리 `(기준−후보)/기준`으로 계산한다. 3회로 신뢰구간·보편 성능을 주장하지 않는다.
- [ ] PASS/ISSUE 최종 상태뿐 아니라 모든 검사 선택·확률·구체적 지적 이유를 비교한다. 선택이 같아도 이유가 틀린 사례는 별도 표시한다. B 자체의 반복 간 불안정과 B→D 차이를 구별한다.
- [ ] A→D는 현재 Q8 경로 대비 효과, B→D는 병렬 처리 효과로 따로 보고한다. 이전 Docker 2GiB·누적 GPU 피크·과거 13.849초를 새 실측 baseline으로 복사하지 않는다.

**실제 추론 범위:** U3 인공 7종×3세트(21검사 행)와 추가 4개 준비 검토 요청, U4 최대 74검토 요청이다. 준비 실패 시 후속 횟수는 줄어들며 이유를 기록한다. 캐시 ON 준비 왕복의 부가 호출만 기존 절차대로 별도 집계한다. 상용 API 호출·40문항·실제 웹 문항 제출은 이번 계획에 넣지 않는다. 전체 그래프의 웹 품질 검증과 d1 고정 계획 검증을 섞지 않는다.

이 계획은 성능 비교 후보를 만드는 작업이다. 검토 정확도 개선·모델 교체·지침 변경·확률 임계값 조정·실제 웹 비교는 이번 결과를 본 뒤 별도로 정한다.

## 보고·복귀·산출물

구현 시 U1~U4별로 **무엇을 바꿨는지 → 실제 결과 → 문제/중단 원인 → 다음 단계**를 중간 보고한다. 최종 표에는 최초 고정 계획 판정·검사별 오류·복구 없음 여부와 반복 수를 적는다. 고정 계획 대조에는 재계획을 실행하지 않으며 이를 Agent의 복구 후 정답률로 포장하지 않는다. 실제 그래프 준비에서 복구가 발생하면 최초/Decisions 지적/재계획 후 결과를 분리한다.

원시 기록은 Git 제외 `.local/runtime/d1-independent-batch4/`에 둔다. 모델 원문·질문·확률·메모리 시계열·프로필·DB 보존 증거를 로컬로 연결하고, 공개 요약은 새 `docs/verification/2026-11-15-local-llm-d1-independent-batch4.md`에 적는다. 날짜는 실제 실행일에 맞춘다.

실패하면 소유 실험 서비스만 정리하고 원래 Q8 개별·동일 Qwen 캐시 설정으로 복귀한다. Docker 1536MiB는 U1에서 검증됐다면 유지한다. Docker 자체가 실패 원인이면 서비스 복구를 위해 2048MiB로 되돌린 사실을 명시한다. 설정과 실제 서비스가 맞지 않는 옛 준비 증거로 worker를 ready 처리하지 않는다. 1536MiB에서 Q8도 준비를 통과하지 못하면 검증되지 않은 ready 대신 중단 상태와 원인을 보고한다.

## 계획 자체 검토

- 요구사항 대응: 독립 최대 4행=U2, Docker 1.5GiB=U1, 정확도·시간·메모리 대조=U3/U4, 기존 그래프·응답 유지=고정 조건/U2.
- 특히 검토한 위험: 마지막 나머지 배치, 긴 행 때문에 4개가 안 들어가는 경우, 서로 다른 행의 ID/판정 혼선, 누적 메모리 피크 오해, 기존 모델 오답을 동등성 통과와 혼동하는 경우. 각 항목을 구현 검사 또는 실제 비교에 연결했다.
- 모델 실행·Docker 설정 변경·제품 테스트는 이 문서 작성 단계에서 수행하지 않았다. 메모리 추정·속도 목표는 아직 실측 결과가 아니다.
