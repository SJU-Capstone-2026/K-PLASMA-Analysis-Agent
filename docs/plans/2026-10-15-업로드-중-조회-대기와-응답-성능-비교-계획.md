# 업로드 중 조회 대기·응답 성능 B/C 비교 계획

## Goal Capsule

**150개 Run을 등록하는 동안 기존 실험의 조회 요청을 함께 보내, 파싱 중 DB 연결을 놓아주는 C가 B보다 조회를 덜 기다리게 하는지 확인한다.**
DB 연결 획득 시간과 사용자가 기다리는 HTTP 응답 시간을 따로 측정한다.
연결이 충분한 설정에서 차이가 없다면 그것도 결과로 기록한다.

- 이번 산출물은 테스트 계획이다. 추가 계측 구현·부하 테스트는 아직 실행하지 않았다.
- 선행 근거: [파일 업로드 성능 개선 검증](../verification/2026-10-15-파일-업로드-성능-개선.md).
- 이번에는 A를 다시 측정하지 않는다. B/C 각각 조회만 하는 기준선, 업로드만 하는 기준선, 업로드와 조회가 겹치는 결과를 비교한다.
- 실제 백엔드 HTTP·파서·PostgreSQL을 사용하며 LLM 호출·토큰 비용은 없다.
- 서비스 DB와 원본을 건드리지 않고 전용 DB·저장소를 사용한다. Redis·Kafka·작업자 병렬화·쿼리 튜닝은 이번 변인이 아니다.

## Product Contract

### Evidence and Hypothesis

선행 인공 데이터 150개·B/C 각 10회 평균에서 DB 연결 점유 합계는 **25.649→3.323초, 87.04% 감소**했다.
반면 업로드 클라이언트 전체 시간은 **34.433→34.473초**로 추가 단축이 관측되지 않았다.
이는 업로드가 쓰던 연결 자원을 빨리 돌려준 결과이며, 다른 조회의 응답이 빨라졌다는 증거는 아직 아니다.

| 확인한 현재 구조 | 이번 실험에서의 의미 |
| --- | --- |
| B는 파싱·계산을 등록 트랜잭션 안에서 수행 | SQL을 실행하지 않는 동안에도 연결을 점유할 수 있음 |
| C는 준비 트랜잭션 → 연결 반환 후 파싱 → 게시 트랜잭션 | 조회가 사용할 수 있는 연결이 늘어날 가능성 |
| 업로드 작업자는 하나, 선행 벤치마크 풀 크기는 2 | B에서도 남은 연결로 조회가 즉시 끝날 수 있음 |
| `application.yml`은 풀 최대 크기 미지정, 연결 획득 제한은 3,000ms | 기본값과 실제 실행 시 덮어쓴 설정을 구분해야 함 |
| 보존 C JAR의 HikariCP는 7.0.2, 최대 연결 기본값은 10 | 설정을 덮어쓰지 않은 제품 비교군은 10으로 명시해 재현 |
| 기존 계측 HTTP 필터는 업로드 POST만 추적 | 조회의 연결 획득·SQL·응답 구간 계측을 추가해야 함 |

가설은 **같은 부하에서 연결 부족이 발생할 때 C의 연결 획득 시간과 조회 p95가 줄어든다**는 것이다.
p95는 전체 요청 중 95%가 이 시간 안에 끝났다는 뜻이다.
연결이 충분하면 차이가 작을 수 있고, CPU·파일 I/O·JSON 처리 병목이 우세하면 연결 반환만으로 HTTP 지연이 줄지 않을 수도 있다.

### Requirements

- R1. B/C의 제품 차이는 기존 트랜잭션 분리로 제한하고, 새 계측은 양쪽에 동일하게 적용한다.
- R2. 조회 응답 데이터·순서·SQL·인덱스·요청 빈도·환경을 고정한다.
- R3. 연결 획득, SQL 호출, 연결 점유, 서버 응답, 클라이언트 응답을 구분하고 오류·시간 초과·미발행 요청을 함께 기록한다.
- R4. 제품 설정, 선행 풀 2개 설정, 풀 1개 경합 실험의 결과를 분리한다.
- R5. 조회 지연뿐 아니라 업로드 완료 시간과 정합성을 확인한다.
- R6. 효과 없음·악화도 그대로 보고하고, 실제 동시 조회의 개선율을 기존 점유 감소율로 대체하지 않는다.

### Scope

핵심 조회는 **실험 상세 조회 `GET /api/run-versions/{id}`**다.
`RunController.version → RunQueryService.getVersion → RunRepository.version`에서 고정 버전의 `full_run` 한 건을 읽고 응답한다.
업로드와 같은 DataSource를 사용하며, 현재 SQL은 `select full_run from run_version where id=?`다.

업로드 중 늘어나는 전체 목록 API(`/api/runs`, `/api/catalog`)는 핵심 측정에서 제외한다.
조회 데이터 양이 변하면 연결 대기와 응답 크기의 영향을 구분하기 어렵기 때문이다.
Agent context API는 요청 생성·claim·manifest 저장 등의 영향도 있으므로 별도 후속 범위다.
따라서 이번 결과를 **Agent 전체 응답 개선**이나 **모든 조회 API의 개선율**이라고 표현하지 않는다.

## Planning Contract

### Comparison Design

| 비교군 | 제품 기준 커밋 | 동작 |
| --- | --- | --- |
| B | `ddf0e07584127d7b2ad68fc674c97ffd5eb12ad3` | 연속 처리 적용, 파싱 중에도 등록 트랜잭션 유지 |
| C | `1b1bcf49f756bf6cea7ce8ab5d397bc03736c82a` | B + 파싱과 준비·게시 트랜잭션 분리 |

보존 B/C JAR는 기존 결과 재현용으로 유지한다.
조회 계측을 추가할 때는 두 기준 커밋에 **동일한 계측 패치**를 적용해 별도 JAR를 만들고 기준 SHA·패치 diff·JAR SHA-256을 기록한다.
C만 새 계측을 사용하거나, 새 B 결과를 과거 C 결과와 직접 비교하지 않는다.
조회 코드·파서·스키마·인덱스에 의도하지 않은 차이가 없는지 확인한다.
현재 업로드 작업 브랜치에서 계획 문서를 보관하고, 후속 계측·실행은 그 변경과 구분되는 커밋으로 관리한다.

### Data and Controls

- 업로드: 선행 실험과 동일한 인공 신규 Run 150개, 2,175파일, 총 1,545,005,295바이트의 폴더 업로드. 파일 생성·압축은 측정 밖이다.
- 조회: 별도 인공 Run 3개의 고정 버전을 미리 등록한다. 업로드할 150개와 P/S/B·Run ID·source가 겹치지 않게 한다.
- 조회용 3개는 소형·대표 크기·큰 상세 응답을 포함하도록 고르고, 선택 기준·샘플 수·응답 바이트를 사전 manifest에 고정한다. 작은 빈 JSON만 조회하지 않는다.
- 요청은 3개 버전을 같은 순서로 반복한다. 전체 지표와 버전별 지표를 함께 내며 B/C에서 응답 해시·버전·바이트가 같아야 한다.
- 매회 전용 DB·storage를 조회용 seed 상태로 복원한다. 신규 업로드가 DUPLICATE로 바뀌지 않아야 하며 종료 후 조회용 3개 + 신규 150개를 검증한다.
- 작업자 1개, drain 32, idle 500ms, 상태 polling 1초, 연결 제한 3,000ms를 유지한다. 풀 비교군 안에서 minimumIdle도 maximumPoolSize와 같게 고정하고 풀 준비 완료 후 시작한다.
- Java 21, heap 256MiB~2GiB, PostgreSQL 18.6-alpine3.24, DB CPU 2개·메모리 3GiB 등 선행 환경을 유지한다. 실제 적용값·Tomcat 설정·k6 버전·OS·자원 상태를 기록한다.
- 본 측정 중 빌드·JFR·다른 벤치마크를 동시에 실행하지 않는다. OS 캐시를 비우지 않는 warm-cache 비교이며 냉시작 성능으로 발표하지 않는다.

### Test Matrix

조회는 **초당 5개 요청**을 기본으로 고정한다.
이는 실제 사용자의 클릭 빈도라고 주장하는 값이 아니라, B/C에 동일한 조회 부하를 가하고 표본을 확보하기 위한 실험값이다.
가상 사용자 수와 실제 사용자 수는 같지 않다.

| 설정 | 풀 최대 연결 | 조회만 기준선 | 업로드 + 조회 | 해석 범위 |
| --- | ---: | --- | --- | --- |
| P: 제품 기본 설정 | 10 | B/C 각 60초 × 3회 | B/C 각 10배치 | 기본 설정에서 실제 조회 지연 개선이 있는지 |
| H: 선행 벤치마크 설정 | 2 | B/C 각 60초 × 3회 | B/C 각 10배치 | 기존 점유 측정과 같은 연결 제약에서의 효과 |
| D: 경합 확인용 | 1 | B/C 각 60초 × 3회 | B/C 각 5배치 | 업로드가 유일한 연결을 보유할 때의 대기 원리 확인 |

업로드만 기준선은 같은 seed·신규 계측 환경에서 각 풀·B/C별 **3배치**를 별도로 측정한다.
과거 업로드 시간은 참고만 하고, 이번 조회 부하에 따른 업로드 지연 증가량은 새 기준선과 비교한다.
정식 측정 전에는 각 풀·비교군의 전체 볼륨 워밍업 1회를 제외한다. JVM 재시작 시 다시 워밍업한다.
B/C 순서는 고정 난수 seed로 BC/CB를 균형 배치하고 결과를 본 뒤 순서를 바꾸지 않는다.

풀 1은 **배포 권장 설정이 아니며**, 제품 설정 결과와 합쳐 개선율을 계산하지 않는다.
제품 실행에 외부 설정이 있다면 비밀값을 제외한 실제 Hikari 설정을 확인한다. 기본값 10과 다르면 P를 그 값으로 고정하고 계획·환경 기록을 먼저 갱신한다.
효과를 얻기 위해 사후에 요청 빈도를 계속 올리는 방식은 사용하지 않는다. 더 높은 처리량 실험은 별도 계획으로 남긴다.

### Execution Window

1. 준비된 서버와 seed에서 조회 응답 정합성·실제 풀 크기·열린 연결 수를 확인한다.
2. k6 조회 부하를 90초 동안 실행하고, 시작 10초 후 기존 Python harness로 150개 신규 업로드를 시작한다.
3. 조회는 이전 응답 완료와 관계없이 200ms 간격을 목표로 시작한다. 업로드 상태 polling은 별도 클라이언트에서 1초마다 수행하고 조회 지표와 분리한다.
4. 업로드 요청 진입·접수 commit·첫 job·개별 parse·게시·마지막 terminal commit을 서버의 같은 단조 시계로 기록한다.
5. 90초 후 새 조회 발행을 마치고 진행 중 조회는 HTTP timeout 10초 범위에서 수집한다. 업로드가 80초 시점까지 끝나지 않으면 불완전 관측 실행으로 보존하고 정상 비교에서 분리한다.
6. 업로드·조회 값과 해시를 검증하고 원시 로그를 보관한 뒤 다음 배치를 준비한다. 실패 실행을 삭제하거나 성공할 때까지 재시도해서 대체하지 않는다. 진행 중인 HTTP·worker가 모두 끝나거나 자기 서버를 종료한 뒤에만 seed를 복원한다. 미완료 job이 저장 중인 DB·파일을 초기화하지 않는다.

**핵심 비교 창은 서버 업로드 요청 진입부터 마지막 terminal commit까지**다.
조회가 이 창 안에서 서버에 진입했으면 완료가 창 뒤로 넘어가더라도 포함한다.
서버의 요청 ID와 시작·종료 시각으로 HTTP 표본을 연결해, k6 통계 전체에 업로드 전후의 빠른 조회가 섞이는 것을 방지한다.

전체 창 외에 접수 단계, worker 처리 단계, 조회 시작 시 파싱과 겹친 경우를 나눠 보고한다. phase 그룹은 겹칠 수 있으므로 합산하지 않는다.
파싱 중 연결 반환은 worker의 변경이다. 접수 파일 처리 중의 지연까지 모두 C의 효과로 설명하지 않는다.
업로드 시간이 달라지면 겹친 조회 수가 달라질 수 있으므로 배치별 창 길이·표본 수·발행률을 표시한다.
서버 진입 전에 실패한 요청도 클라이언트 기록에 남기고 누락하지 않는다. 서로 다른 프로세스의 단조 시계 값을 직접 빼지 않는다.

### Measurements

| 지표 | 측정 경계·방법 | 주의점 |
| --- | --- | --- |
| DB 연결 획득 시간 | 조회별 `DataSource.getConnection()` 시작→성공 또는 예외 | 풀 대기와 호출·검증 비용을 포함한다. 전부 순수 대기라고 부르지 않는다 |
| 조회별 연결 획득 합계 | 한 HTTP 요청에서 발생한 획득 시도 합계 | 시도 횟수·실패 횟수도 보관해 다중 획득을 숨기지 않는다 |
| 풀 경합 보조 지표 | Hikari active/idle/total/pending을 100ms 간격 관측 | pending은 연결을 기다리는 스레드 수. 짧은 경합은 표본 사이에서 놓칠 수 있음 |
| JDBC SQL 호출 | 조회별 execute 구간·호출 수 | 결과 읽기·JSON 역직렬화 전체를 DB 엔진 실행 시간으로 부르지 않는다 |
| 연결 점유 | 획득 성공→close | 파싱 중 반환 여부 및 업로드·조회 각 점유를 분리 |
| 서버 응답 시간 | 조회 HTTP 필터 진입→응답 처리 반환 | 서버 내부 측정이며 TCP·브라우저 렌더 시간은 아님 |
| 클라이언트 응답 시간 | k6 HTTP 호출 전후 경과, `http_req_duration`도 별도 기록 | 호출 경과에는 연결 준비 등이 포함될 수 있음. duration은 sending+waiting+receiving |
| 오류·실제 처리율 | 성공/오류 코드, timeout, 발행/완료 수, dropped iterations | 목표 5req/s가 실제 발행됐는지 확인 |
| 업로드 전체·파싱·DB 점유 | 기존 업로드 계측과 harness | 조회를 빠르게 하느라 업로드가 느려지는지도 확인 |
| 자원 상태 | Java/DB/k6 CPU·메모리, GC, 디스크 I/O | 대기가 아닌 CPU·I/O 간섭을 분리해 해석 |

각 지표는 평균·중앙값·p95·최댓값·표본 수를 내고, timeout 포함 오류율을 병기한다.
성공 요청만의 응답 시간 표는 전체 실패율과 함께 제공하며, timeout을 0ms나 정상 완료로 계산하지 않는다.

**k6의 `http_req_blocked`는 클라이언트의 TCP 연결 준비 대기이며 DB 연결 풀 대기가 아니다.**
또한 PostgreSQL `wait_event`는 DB 내부 잠금·I/O 등이지 Java 풀에서 기다린 시간은 아니다.
DB 연결 대기 개선은 조회별 획득 시간과 풀 pending·업로드 연결 점유 구간을 연결해서 판단한다.
중첩된 SQL·점유·HTTP 시간을 더해 전체 시간을 만들지 않는다.

### Tools

| 도구 | 이번 용도 |
| --- | --- |
| k6 로컬 실행 | `constant-arrival-rate`로 초당 5개 조회, HTTP 지연·오류·발행 누락 수집. Grafana Cloud는 필요 없음 |
| 기존 Python 업로드 harness | 실제 대용량 multipart·상태 polling·seed 복원·정합성 검증·k6 실행 조율 |
| 기존 Java/JDBC 계측 확장 | 조회 요청과 DB 획득·SQL·연결 점유를 요청 ID로 연결 |
| Hikari MXBean | in-process 읽기 전용 풀 상태 관측. 원격 JMX 포트·공개 관리 API는 만들지 않음 |
| PostgreSQL 통계 | `pg_stat_statements` 호출·실행 시간 차이, 별도 관측 연결의 `pg_stat_activity`로 잠금/I/O 보조 확인 |
| Python 집계 | 시간 창별 필터, 요청 ID 결합, 배치별 통계·전후 차이·그래프·보고서 |

현재 저장소에는 k6 harness가 없고 로컬 `k6` 실행 파일도 확인되지 않았다.
구현 시 로컬 실행 도구를 준비하고 버전을 고정한다. 계측을 위해 Prometheus·Redis·Kafka를 추가하지 않는다.
`pgbench`는 DB만 측정하므로 이번 HTTP+연결 풀 경합의 주 도구로 쓰지 않는다. Phoenix도 LLM 호출이 없는 이번 경로의 주 계측 도구는 아니다.

k6는 반복 1회에 조회 1개만 보내고 sleep으로 빈도를 조절하지 않는다.
5req/s·HTTP timeout 10초를 감당할 수 있게 VU 60개를 사전 확보하고 실행 중 자동 증가는 사용하지 않는다.
요청 ID는 별도 상세 로그로 보관하며 고유 ID마다 metrics tag를 만들지 않는다.
발행 누락이 있으면 원인과 수를 보존한다. 부하 도구 자원 부족은 환경 문제로 분리하고, 서버 지연 때문에 발생했다면 서비스 한계의 일부로 보고한다.

### Interpretation Rules

- 배치가 독립 반복 단위다. 같은 배치의 조회 수백 건을 각각 독립 실험처럼 취급하지 않는다.
- B/C 배치별 평균·p95의 분포와 차이를 제시한다. 전체 표본 p95는 보조로만 제시하고 배치 p95 평균과 이름을 구분한다.
- 감소량은 `B−C`, 감소율은 `(B−C)/B×100`이다. B가 거의 0이면 백분율을 강조하지 않고 ms 차이를 적는다.
- 주 비교군은 짝지은 배치 차이와 배치 단위 bootstrap 95% 구간을 함께 낸다. 0을 포함하거나 실행 편차와 차이가 비슷하면 뚜렷한 개선으로 단정하지 않는다.
- 업로드 없는 기준선에 비해 B/C 각각 얼마나 느려지는지도 적는다. 기준선과 다른 시점의 결과를 단순히 빼서 순수 풀 대기라고 부르지 않는다.
- **기본 설정에서 차이 없음 / 풀 2에서 차이 없음 / 풀 1에서 개선**도 유효한 결론이다. 이 경우 “연결 부족 상황의 대기 완화”까지만 주장한다.
- 풀 획득 시간은 줄었는데 HTTP 응답이 그대로라면 JSON 처리·CPU·전송 등의 영향이 남은 것으로 조사한다. 이번에 자동으로 추가 최적화하지 않는다.
- 조회 때문에 업로드가 늘어난 시간과 실패율도 같은 비중으로 보고한다. 개선율 목표를 미리 정해 통과 여부를 맞추지 않는다.

## Implementation Units

### U1. Query and Pool Timing

**Goal / Requirements:** 조회의 연결 획득·응답 시간을 구분해 수집한다. R1, R3.
**Dependencies:** 없음. B/C 기준 커밋·동일 계측 패치 원칙을 먼저 고정한다.

**Files:**

- 수정: `backend/src/main/java/com/kplasma/analysisagent/ingestion/ImportTimingFilter.java`, `backend/src/main/java/com/kplasma/analysisagent/ingestion/ImportTimingRecorder.java`, `backend/src/main/java/com/kplasma/analysisagent/ingestion/ImportSqlTimingConfiguration.java`.
- 추가: `backend/src/main/java/com/kplasma/analysisagent/ingestion/ImportPoolTimingSampler.java`.
- 테스트 추가: `backend/src/test/java/com/kplasma/analysisagent/ingestion/ImportQueryTimingTest.java`.

**Approach:** 기존 opt-in 계측에서 지정한 조회 endpoint·상태 polling을 각기 다른 kind로 추적한다. 헤더의 실험 요청 ID는 길이·문자 집합을 제한하고 본문·SQL 파라미터·비밀값은 기록하지 않는다. trace에 HTTP 상태·획득 실패를 연결한다. 업로드 worker의 큐 조회처럼 trace 밖인 SQL은 별도로 식별해 계측 coverage를 명시한다. 풀 관측은 기존 단일 업로드 scheduler를 막지 않는 별도 경량 관측 실행기로 수행한다.

**Test scenarios:**

1. 정상 상세 조회의 요청 ID·HTTP 상태·획득·SQL·반환이 연결되고 응답 내용은 계측 off와 동일하다.
2. 없는 버전/잘못된 UUID/DB 획득 timeout도 기록된다. 실패한 획득을 연결 점유로 기록하지 않는다.
3. 서로 다른 동시 요청의 ThreadLocal trace가 섞이지 않으며 기존 업로드·job 로그도 유지된다.
4. 계측 off에서는 파일·관측 스레드·추가 SQL이 없고, on에서도 관측용 애플리케이션 SQL이 늘지 않는다.

**Verification:** 독립 풀 1개를 latch로 잠깐 점유하는 소형 통합 테스트로 계측의 인과 순서와 timeout을 검증한다. 이것은 측정기 검증이며 실제 성능 결과에 포함하지 않는다.

**Goal / Requirements:** 같은 조회·업로드 부하를 B/C에 재현한다. R2, R4, R5.
**Dependencies:** U1.

**Files:**

- 추가: `scripts/performance/upload_query_load.js`, `scripts/performance/upload_query_benchmark.py`.
- 재사용·필요한 부분만 확장: `scripts/performance/upload_benchmark.py`, `scripts/performance/generate_upload_fixture.py`.
- 테스트 추가: `scripts/performance/test_upload_query_benchmark.py`.

**Approach:** 기존 업로드 경로를 복제하지 않고 조회용 seed 보존·신규 150개 검증을 지원한다. manifest·서버 환경·풀 크기·요청 순서·비교 순서를 원시 결과와 함께 남긴다. DB 초기화는 기존 전용 DB 방어를 유지하고 실행 중 서비스 DB·사용자 storage를 대상으로 삼지 않는다.

**Test scenarios:**

1. seed 조회 결과가 고정되고 업로드 150개는 모두 신규이며 조회 3개를 사후 업로드 검증에서 잘못 집계하지 않는다.
2. k6 성공·timeout·발행 누락·비정상 종료를 기록하고 실패 실행을 보존한다.
3. 워밍업/본 측정/비교군/풀별 출력 경로가 겹치지 않는다. 서비스 DB 지정과 빈 seed·충돌하는 P/S/B는 실행 전에 거부한다.
4. 진행 중 요청의 완료가 업로드 창을 넘어가도 포함되고, 창 앞뒤 요청·polling은 구분된다.

**Verification:** 작은 인공 파일로 end-to-end smoke 후 전체 볼륨 측정으로 넘어간다. 본 측정에서는 sleep·가짜 SQL 지연·가짜 파싱 시간을 삽입하지 않는다.

## Verification Contract

### Preflight and Overhead

- 모든 B/C JAR의 공통 계측 패치와 제품 diff를 검토한다. 세션 중 다른 쿼리/인덱스 변경을 섞지 않는다.
- 조회만 및 업로드+조회에서 계측 off/on을 B/C 각 3회, 풀 2 기준으로 비교한다. on은 사전 지정한 첫 3회 본 측정을 사용하고 실행 순서를 기록한다.
- 새 계측으로 평균 또는 p95가 5% 이상 증가하거나 변동이 커 원인 분리가 어려우면 측정기부터 검토한다. 짧은 응답에서는 절대 ms 차이도 함께 본다.
- JDBC 호출 수·응답 값·등록 상태가 동일해야 한다. 수집 로그가 누락되면 DB 구간 분해를 성공했다고 주장하지 않는다.
- PostgreSQL 보조 관측은 애플리케이션 풀을 빌리지 않는 별도 연결로 수행하며 빈도·오버헤드를 B/C에서 같게 유지한다.

### Validity and Stop Conditions

제품 수치·버전·원본 해시 불일치, seed 충돌, 서비스 DB 접근, 비교군 설정 혼입은 즉시 중단 사유다.
HTTP 오류·획득 timeout은 자동 폐기하지 않고 결과에 포함한다. 업로드가 완료되지 않은 실행은 완료 지연 평균에서 따로 표시한다.
관측 창 부족·로그 손실·발행 부하 불일치가 있으면 해당 한계를 공개하고, 원인을 고친 뒤 양쪽 비교군을 같은 조건으로 다시 측정한다.

기능 검증은 backend JUnit/Testcontainers와 새 harness 단위 테스트로 수행한다.
벽시계 성능 수치를 CI의 고정 임계값으로 삼지 않는다.
제품 기본값은 바꾸지 않고 계측을 끄면 기존 동작으로 돌아가야 한다. 제품 UI·API 응답 계약·데이터 스키마는 변경하지 않는다.

| 클라이언트 응답 평균 / p95 | 미측정 | 미측정 | 미측정 | 미측정 |
| 서버 응답 평균 / p95 | 미측정 | 미측정 | 미측정 | 미측정 |

## Definition of Done

- B/C 공통 계측과 고정 조회·업로드 재현 harness가 있다.
- P/H 각 10배치, D 각 5배치 및 정해진 기준선·워밍업·계측 제어 실험을 수행하고 불완전/실패 실행까지 남긴다.
- 조회 대기·HTTP 지연·업로드 영향·오류·정합성 결과를 분리해 보고한다.
- 평소 설정에서 개선이 없을 때도 그 결론을 명확히 남긴다.
- 코드·소량 인공 테스트·집계 보고서는 PR로 공유하고, 입력 파일·DB·전체 응답·원시 로그·실제 데이터는 `.local/performance/upload-query/` 등 Git 제외 경로에 보관한다.
- 실행이 끝나면 자기 벤치마크 프로세스만 종료한다. 이전 업로드 결과와 서비스 데이터는 보존한다.
