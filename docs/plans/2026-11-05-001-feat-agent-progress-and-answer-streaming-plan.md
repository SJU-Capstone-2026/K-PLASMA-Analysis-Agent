# Agent 진행 기록과 실시간 답변 표시 구현 계획

## Goal Capsule

사용자가 기다리는 동안 현재 수행 중인 작업을 짧은 실행 기록으로 보여준다. 작업이 끝나면 기록을 접고 `2분 8초 동안 작업함`과 구분선을 답변 위에 표시한다. 일반 개념 답변과 실험 해석은 모델이 생성하는 동안 화면에 이어서 표시한다.

이 문서는 두 계획을 함께 다룬다.

1. 실제 실행 단계에 맞춘 진행 기록과 완료 후 소요 시간 표시.
2. 최초 답변과 수정 답변의 실시간 스트리밍.

현재 대화에서 확정한 결정, 현재 코드와 운영 문서, 이 계획의 순서로 요구를 해석한다. 이번 작업의 산출물은 구현 계획서다. 제품 변경과 실험 실행은 후속 구현 단계에 해당한다.

## Product Contract

### Requirements

진행 화면과 답변 표시 요구는 다음과 같다.

| ID | 사용자에게 제공할 동작 |
|---|---|
| R1 | 실제로 시작한 작업을 짧고 자연스러운 문장으로 표시한다. 도구와 작업 대상에 따라 문구가 달라진다. |
| R2 | 대기 UI는 답변과 같은 바닥에 작은 회색 실행 기록으로 표시한다. 현재 작업과 최근 완료 작업을 구분한다. |
| R3 | 완료 후 진행 기록을 기본으로 접고, 작업 시간과 가로 구분선 아래에 답변을 표시한다. |
| R4 | 모델이 답변을 생성하는 동안 공개 가능한 본문을 순차 표시한다. 일반 개념과 실험 해석을 모두 지원한다. |
| R5 | 검토에서 수정이 필요하면 이를 표시하고, 해석 영역을 수정문으로 다시 스트리밍한다. |
| R6 | 실제 측정값·단위·참조 검증과 기존 Decisions 검토 및 복구 한도를 유지한다. |

대화 유지와 실행 정책 요구는 다음과 같다.

| ID | 사용자에게 제공할 동작 |
|---|---|
| R7 | 다른 채팅방으로 이동해도 작업은 원래 방에서 계속되며, 돌아오거나 새로고침해도 올바른 진행 상태와 결과를 복원한다. |
| R8 | 최신 대화를 따라 읽는 경우에만 답변 증가에 맞춰 스크롤한다. 과거 대화를 읽는 경우에는 기존 아래 화살표를 사용한다. |
| R9 | 단순 조회·수치 비교·그래프 표시에 답변 작성 LLM을 추가하지 않는다. v1 기본 대화와 v2 대화 모두 처리 상태를 표시한다. |
| R10 | 입력 대기·조회 0건·데이터 비가용·실행 실패·연결 복구를 서로 다른 상태로 안내한다. |

### 사용자와 확정한 결정

- D1. 진행 기록은 질문 확인, 검색, 비교, 작성처럼 현재 작업을 알려준다. 단계가 지나가면 해당 작업의 완료 사실을 남긴다. `session-settled: user-directed`
- D2. 완료 시 기본 화면은 소요 시간과 구분선, 답변으로 정리한다. `session-settled: user-directed`
- D3. 최초 해석도 생성 즉시 스트리밍하고, 수정이 필요하면 수정문도 스트리밍한다. 검토 완료까지 본문 전체를 숨기는 방식은 사용자가 대기 시간이 길어지는 이유로 제외했다. `session-settled: user-approved`
- D4. 수정할 때 해당 해석 영역을 비우고 같은 위치에서 새 문장을 표시한다. 진행 기록에 `해석을 수정하는 중`을 표시해 변경을 알아볼 수 있게 한다. 위 확정에 따른 표시 동작이다.
- D5. 작업 설명은 실행 이벤트와 확인된 입력·결과를 조합해 코드가 만든다. 진행 문구 작성을 위한 별도 LLM 호출은 추가하지 않는 설계다.

### 계획 1. 진행 기록과 작업 시간

분석이 진행될 때 최근 완료 기록 3개와 현재 작업 1개를 기본으로 보여준다. 필요하면 이전 기록을 펼칠 수 있다. 이 표시 개수는 초기 디자인 제안값이다. 현재 작업에는 작은 움직이는 표시, 완료 작업에는 작은 체크와 옅은 색을 사용한다. 실행하지 않은 미래 작업을 추정해 진행률을 표시하지 않는다.

진행 중 화면 예시는 다음과 같다. 아래 건수는 화면 동작을 설명하기 위한 인공 예시다.

```text
✓ 사용자 질문과 선택한 Run 확인
✓ 검색 조건과 단위 확인
✓ 조건에 맞는 실험 7개 확인
◌ 찾은 7개 실험의 압력과 이온 플럭스를 비교하는 중
```

해석 작성이 시작되면 기록 아래에서 본문이 늘어난다. 생성·검토 중인 해석에는 `작성 중` 또는 `검토 중`을 표시한다. 요청 저장까지 끝나면 아래 형태가 된다.

```text
38초 동안 작업함  ›
────────────────────────────────────────────
비교 표·그래프
최종 해석
```

시간 문구를 누르면 공개 실행 기록을 펼칠 수 있도록 제안한다. 기본 상태는 접힘이다. 여기의 선은 영역 구분선이며 진행률 막대가 아니다.

#### 도구와 단계별 문구 목록

문구를 같은 순서로 항상 재생하지 않는다. 실제로 통과한 경로의 항목만 표시한다. 조건·지표명은 검증된 입력에서, 건수는 확정된 결과에서 가져온다.

| 작업 코드 | 표시 예시 | 표시가 시작되는 근거 |
|---|---|---|
| `QUEUED` | 분석을 시작할 준비 중 | 요청 접수 후 worker 실행 전 |
| `QUESTION_CHECK` | 질문과 선택한 Run을 확인하는 중 | 문맥 확인 단계 진입 |
| `PLAN` | 요청에 맞는 작업 순서를 정리하는 중 | 최초 계획 모델 호출 허가 확인 |
| `PLAN_VALIDATE` | 검색 조건·단위와 작업 연결을 확인하는 중 | 계획 코드 검증 시작 |
| `FORWARD_LOOKUP` | 압력·전력 조건에 맞는 실제 실험을 조회하는 중 | `forward_lookup` 실제 실행 시작 |
| `REVERSE_SEARCH` | 평균 이온 에너지 범위에 맞는 실험을 찾는 중 | `reverse_search` 실제 실행 시작 |
| `SEARCH_COMPLETE` | 조건에 맞는 실험 7개를 찾았어요 | 저장·검증된 검색 결과의 후보 수 |
| `SEARCH_EMPTY` | 해당 조건에 맞는 실험은 없어요 | 정상 완료된 검색 결과가 0건 |
| `COMPARE_RUNS` | 찾은 7개 실험의 압력과 이온 플럭스를 비교하는 중 | 해석된 입력 Run 목록으로 비교 실행 시작 |
| `COMPARE_OUTPUTS` | 선택한 실험의 전위 파형 비교값을 확인하는 중 | 실제 요청한 출력의 DB 조회 시작 |
| `COMPARE_IEAD` | 실험별 IEAD 최대 강도와 피크 위치를 비교하는 중 | 해당 지표가 지정된 비교 실행 |
| `DERIVE` | 앞선 결과로 다음 검색의 기준값을 계산하는 중 | 최댓값·평균·비율 등 실제 내부 연산 시작 |
| `RESULT_VALIDATE` | 측정값·단위와 비교 결과를 확인하는 중 | 실행 결과의 코드 검증 시작 |
| `REUSE_RESULT` | 저장된 결과를 이어서 사용하는 중 | 실행·모델 결과가 이미 저장된 상태로 확인됨 |
| `NEEDS_RUNS` | 비교할 실험을 선택해 주세요 | Run 선택 HITL 상태 저장 |
| `NEEDS_BASELINE` | 비교 기준으로 사용할 Run을 골라 주세요 | 기준 Run HITL 상태 저장 |
| `NEEDS_CONDITIONS` | 조회에 필요한 조건을 확인해 주세요 | 조건 확인 HITL 상태 저장 |
| `RESUMED` | 선택한 실험으로 분석을 이어가는 중 | 사용자 입력을 수락하고 재개 |
| `REPLAN` | 중간 결과를 반영해 남은 작업을 조정하는 중 · 1/2 | 실제 재계획 모델 호출 시작 |
| `GENERAL_ANSWER` | 질문에 맞는 설명을 작성하는 중 | 일반 개념 답변 모델 호출 시작 |
| `INTERPRET` | 확인된 실험 결과를 해석하는 중 | 실험 해석 모델 호출 시작 |
| `REVIEW` | 해석이 근거에 맞는지 검토하는 중 | Decisions 실제 호출 시작 |
| `REWRITE` | 검토 결과를 반영해 해석을 수정하는 중 | 기존 규칙에 따른 답변 수정 시작 |
| `COMMIT` | 답변을 저장하는 중 | 최종 답변 저장 진입 |
| `RECOVERING` | 저장된 처리 상태를 확인하고 이어가는 중 | worker 복구 또는 결과 확인 경로 |

파형 원본을 웹이 나중에 불러오는 작업은 해당 그래프 영역에서 `그래프 데이터를 불러오는 중`으로 표시한다. 이 경우 모델이 파형 원본을 읽고 있다는 문구를 만들지 않는다. v2 단순 조회는 작성·Decisions 단계 없이 결과 확인과 저장으로 이어진다.

#### 작업 시간의 정의

초기 표시값은 서버가 관측한 `RUNNING` 구간의 누적 시간으로 정한다. 요청 실행, 도구 처리, 작성·검토·재계획 시간을 포함한다. 실행 전 큐 대기와 사용자 선택 대기 시간은 별도 상태로 구분한다.

- 첫 claim에서 구간을 시작한다. heartbeat는 lease만 갱신한다.
- 사용자 입력 대기, 완료, 실패, 취소 때 현재 구간을 닫는다.
- lease가 만료된 worker를 다시 claim할 때 기존 구간은 이전 lease 만료 시각까지 정산한다. 새 구간을 열어 이어간다.
- 최종 시간은 첫 유효한 완료 시 확정하고, 같은 완료 요청의 재전송과 새로고침에는 같은 값을 돌려준다.
- `1초 미만`, `38초`, `2분 8초` 형태로 표시한다. 실패·취소에는 해당 상태를 함께 표기한다.
- 기존 대화에 계산 근거가 없으면 시간을 새로 추정하지 않는다. 새 요청부터 기록한다.

현재 v2 `budget.active_elapsed_seconds`는 일부 모델·도구 호출 구간을 합산한다. UI의 전체 작업 시간으로 그대로 사용하지 않는다. 기존 `updated_at`도 heartbeat와 재개 때 바뀌므로 전용 시간 필드를 둔다.

### 계획 2. 최초 답변과 수정 답변 스트리밍

| 답변 종류 | 화면에 나타나는 방식 |
|---|---|
| 일반 개념 설명 | 모델의 실제 출력 조각에서 문장을 추출해 즉시 표시한다. |
| 조회·수치 비교·그래프 | 검증된 결과 블록을 준비되는 시점에 표시한다. 기존 코드 렌더러를 사용한다. |
| 실험 결과 해석 | 참조와 수치 처리가 가능한 본문부터 `작성 중`으로 표시하고, 이어서 Decisions 검토 상태를 보여준다. |
| 수정 해석 | `수정 중`을 표시하고 기존 해석 영역을 비운 뒤, 새로운 본문을 같은 위치에 스트리밍한다. |

실험 해석의 흐름은 다음과 같다.

```text
도구 결과 검증 → 표·그래프 표시
                  ↓
해석 스트리밍 · 작성 중 → 코드 검증 → Decisions · 검토 중
                                             ↓
                                필요하면 해석 수정 스트리밍
                                             ↓
                                  코드 검증 → Decisions
                                             ↓
                         최종 저장 → 작업 시간·구분선·확정 답변
```

스트리밍 중의 해석은 검토 전 초안이다. 이 상태를 화면에서 식별할 수 있게 한다. 검토 결과가 수정 요구일 때 수정되는 해석 영역과 진행 상태를 함께 갱신한다. 최종 확정 상태로 바뀌는 기준은 백엔드의 답변 저장 완료다.

이 변경의 직접적인 목표는 첫 본문을 기다리는 시간을 줄이는 것이다. 모델의 첫 출력 전 처리 시간과 이후 Decisions 검토 시간은 여전히 존재한다. 전체 완료 시간이 반드시 줄어든다고 가정하지 않고 첫 본문 표시 시간과 최종 완료 시간을 따로 측정한다.

v2 재계획 최대 2회, 답변 수정 최대 1회, 수정 후 다시 검토하는 현재 규칙을 따른다. 두 번째 검토에 이슈가 남아도 현재 정책대로 최종 저장 대상 답변을 표시하며 검토 통과 상태를 새로 만들어내지 않는다. 확률은 기존처럼 기록 용도로 둔다.

| 답변 모델 | `model_client.py`의 `_request`가 현재 전체 응답을 기다린다. 설치된 OpenAI Python SDK는 잠금 파일 기준 2.54.0이다. |
| 답변 구조 | v1 일반 답변에는 텍스트 경로가 있다. v2는 `GeneralAnswerDraft` 또는 `DataAnswerDraft` JSON을 만든다. |
| 수치 처리 | `v2/composition.py`가 근거 ID·허용 값·단위를 확인하고 `{{value:…}}`를 실제 값으로 채운다. |
| 화면 본문 | `V2AnswerView.tsx`는 해석·전제·한계를 나눠 표시한다. `GeneralAnswerCard.tsx`의 `AnswerMarkdown`이 수식·Markdown 렌더러다. |
| 최종 저장 | `AgentRequestService.finalizeRequest`가 완료 답변을 요청에 기록된 방의 turn으로 저장한다. |
| 대화 복원 | `AgentRequestRepository.messages`, `WorkspaceRepository`와 `AgentPage`의 메시지/turn 연결을 사용한다. |

### 공통 전송 방식

현재 PostgreSQL과 Spring MVC 안에 공개 진행 이벤트를 추가하고, 웹은 SSE로 받도록 설계한다. Spring MVC의 `SseEmitter`를 사용할 수 있다. SSE 응답을 유지하는 동안 DB 연결이나 요청 행 잠금을 계속 점유하지 않는다. [Spring 공식 문서](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-async.html)

새 마이그레이션은 구현 시 다음 미사용 번호를 확인해 `V13__agent_public_events.sql`로 추가하는 안이다.

- `agent_public_event`에 `request_id`, 요청별 `seq`, `event_key`, `type`, 제한된 `payload`, 서버 `occurred_at`을 저장한다.
- `(request_id, seq)`를 기본 키로, `(request_id, event_key)`를 중복 방지 키로 사용한다.
- 요청 행을 짧게 잠근 같은 트랜잭션에서 순번을 할당하고 이벤트를 기록한다. 한 요청 안의 커밋 순서와 재생 순서를 보장한다.
- `agent_request`에 누적 실행 시간, 열린 실행 구간 시작 시각과 최종 종료 시각을 추가한다. 필요한 계산은 서버 시계를 사용한다.

#### 공개 이벤트 계약

다음은 계약 방향을 설명하는 예시이며 제품 코드가 아니다. 후보 수 7은 인공 예시다.

```json
{
  "schemaVersion": 1,
  "requestId": "request-id",
  "workspaceEpoch": 1,
  "conversationEpoch": 24,
  "requestRevision": 0,
  "seq": 12,
  "occurredAt": "2026-11-05T10:00:00Z",
  "type": "activity",
  "payload": {
    "activityId": "compare_1:start",
    "code": "COMPARE_RUNS",
    "phase": "started",
    "stepId": "compare_1",
    "runCount": 7,
    "metricIds": ["pressure", "ionFlux"]
  }
}
```

| 이벤트 | 전달 내용 |
|---|---|
| `activity` | 현재 단계, 시작/완료/재사용 상태, 필요한 건수·지표·재계획 번호 |
| `results.ready` | 현재 계획에서 유효한 검증 결과 묶음의 버전과 실행 ID. 본문은 공개 결과 조회로 가져온다. |
| `answer.start` | 답변 시도 ID와 `answerRevision`, 표시할 블록 종류 |
| `answer.delta` | 해당 답변 버전·블록에 추가할 공개 텍스트와 조각 번호 |
| `answer.reset` | 수정·실패·복구로 이전 임시 본문을 무효화하는 이유와 대상 |
| `request.state` | 입력 대기·완료·실패·취소 상태, 최종 turn ID, 확정 시간 |

진행 문구는 코드·검증된 건수·지표명에서 만든다. 공개 payload는 허용 필드만 직렬화한다. 모델 내부 추론 이벤트, 전체 계획 JSON, 임의 원문 오류, 인증 정보와 로컬 경로는 공개 필드에 포함하지 않는다.

#### API와 순서 보장

- worker가 공개 이벤트를 쓰는 내부 endpoint를 추가한다. 현재 worker 토큰과 `claimGeneration`, `requestRevision`, 유효 lease 검사를 적용한다.
- 공개 읽기 endpoint는 기존 요청 조회와 동일한 로컬 단일 workspace 접근 정책을 따른다. 초기화·삭제된 요청의 이벤트와 본문은 과거 URL로도 반환하지 않는다. 새 사용자 계정·권한 체계는 이번 범위에 추가하지 않는다.
- 같은 `event_key`와 같은 payload 재전송은 같은 결과를 반환한다. 같은 키의 다른 내용은 충돌로 처리한다.
- 작업 ID와 중복 방지 키에는 요청 revision과 실제 실행·모델 attempt를 포함한다. 같은 도구를 재계획 후 다시 실행한 경우와 전송만 반복한 경우를 구분한다.
- 접수·claim·HITL·resume·실패·취소·최종 완료는 상태 갱신과 이벤트 기록을 같은 트랜잭션에서 처리한다. heartbeat 주기마다 화면 기록을 추가하지 않는다.
- 모델·도구의 `started`는 호출 허가와 저장 결과 유무를 확인한 뒤 기록한다. 캐시 재사용과 결과 불명 상태는 별도 코드로 표시한다.
- `GET /api/agent/requests/{id}/events`가 `text/event-stream`으로 이미 커밋된 행부터 순서대로 보낸다. 최초 구현은 짧은 주기 조회 기반의 tailer를 사용하고, 구독을 닫을 때 전용 자원을 정리한다.
- SSE `id`는 요청별 `seq`다. 재연결 시 `Last-Event-ID`를 받고, 새 구독에는 `after` 커서도 받는다. 브라우저 표준이 재연결 때 마지막 이벤트 ID를 전달한다. [HTML 표준](https://html.spec.whatwg.org/multipage/server-sent-events.html)
- 완료 뒤 연결한 클라이언트도 저장된 최종 상태를 확인한다. 마지막 순번까지 이미 받은 완료 구독은 종료하고 반복 재연결을 막는다.
- 상태 조회 API에도 최신 공개 진행·미리보기와 `lastEventSeq`를 제공한다. SSE가 끊기면 동일 이벤트를 페이지로 조회해 커서 뒤부터 복원한다. 재구독은 기존 요청의 수신을 재개한다.
- 최초 공개 snapshot과 `lastEventSeq`는 동일한 DB 읽기 시점 기준으로 만든다. 웹은 그 순번까지의 상태를 한 번 적용하고 이후 이벤트만 합친다. HITL 재개로 요청 revision이 증가할 때는 서버의 상태 전환 이벤트 또는 같은 시점 snapshot을 먼저 적용하며, 임의의 오래된 delta가 revision을 바꾸게 하지 않는다.
- 브라우저의 현재 채팅방, 요청 ID, 요청 revision, 답변 revision과 순번을 확인한 후 화면에 적용한다. 대화 전환은 수신만 중지하며, 원래 방의 서버 작업은 이어간다.
- 초기화는 공개 이벤트와 임시 본문도 기존 요청 내용 정리와 함께 삭제하고, 이전 worker의 추가 기록을 차단한다.

### 검증된 결과의 선공개

현재 공개 `answerSnapshot`은 최종 저장 전에는 없고, v2 단계 결과 조회는 worker용이다. 따라서 텍스트 delta만 추가해서는 해석 전에 표·그래프를 보여줄 수 없다.

- 단계의 코드 검증과 결과 저장이 성공한 뒤, worker는 현재 계획에서 유효한 `executionId` 목록을 공개 결과 묶음으로 확정한다. backend는 같은 요청에 실제 저장된 결과인지, Run 고정 버전과 결과 계약이 일치하는지 확인한다.
- 결과 묶음 확정과 `results.ready` 기록은 같은 트랜잭션에서 처리한다. `resultRevision`은 이 이벤트의 요청별 순번으로 정하고, 이벤트에 현재 유효한 실행 ID 목록을 저장한다. 별도 결과 버전 카운터나 결과 본문의 중복 저장은 만들지 않는다.
- `GET /api/agent/requests/{id}/results?resultRevision=…`는 해당 이벤트의 실행 ID와 불변 저장 결과를 결합해 공개 필드만 반환한다. 상태 snapshot에도 현재 결과 버전을 포함한다. 이벤트가 가리킨 버전은 이후 계획이 바뀌어도 같은 내용을 반환한다.
- 현재 `savedResults` 전체를 그대로 공개하지 않는다. 이전 계획에서 무효화된 결과가 섞이지 않도록 그래프의 현재 유효 실행 연결만 사용한다. 재계획은 이 연결을 갱신하고 새 결과 버전을 발행한다. 기존 유효 결과는 유지하고 영향받은 결과만 대체한다.
- 공개 결과는 `stepId`, `executionId`, 정확한 Run 참조와 기존 도구 카드가 사용하는 `toolResult` 계약으로 구성한다. 내부 계획·모델 원문과 파형 원본 배열을 덧붙이지 않는다. 분포·파형 원본은 기존 DB 조회 경로에서 해당 그래프가 필요할 때 가져온다.
- 웹은 기존 조회·비교 카드의 표시 부분을 재사용한다. 완료 전에는 `확인된 결과`로 표시하고 최종 turn이 필요한 판단 기록 저장 등의 동작은 비활성화한다. 임시 turn을 만들어 저장된 답변인 것처럼 취급하지 않는다.
- 해석 수정은 결과 묶음을 지우지 않는다. 최종 저장 뒤에는 현재 카드와 본문을 같은 실행 ID의 확정 turn에 연결하고 중복 표시하지 않는다. HITL 화면의 후보 목록은 기존 선택 계약을 유지한다.

### 호환성과 연결 오류

배포 순서는 추가형 DB 마이그레이션과 backend, worker, frontend 순서로 둔다. 새 공개 계약은 선택 필드와 별도 endpoint로 추가해 기존 클라이언트가 기존 상태 조회를 계속 사용할 수 있게 한다. 기능을 끄면 기존 비스트리밍 경로로 돌아가고, 이미 저장한 최종 답변과 이벤트를 파괴적으로 되돌리지 않는다.

진행 이벤트 전송만 실패하면 같은 중복 방지 키로 제한된 전송 재시도를 하며 모델·도구를 다시 호출하지 않는다. 일시적인 조각 전송 장애는 제한된 버퍼로 처리하고, 지속되면 미리보기를 중단한 뒤 기존 최종 저장·조회 경로로 결과를 전달한다. 저장되지 않은 조각을 저장된 것으로 표시하지 않고 수신 상태를 안내한다. 이는 도구 실행 재시도 정책과 별개다.

### 답변 조각의 처리

실제 모델 출력에는 Responses 스트리밍을 사용한다. 공식 문서는 응답 생성 중 출력 조각을 처리하는 방식과 구조화된 출력 스트리밍을 안내한다. 설치된 SDK에서는 `response.output_text.delta`와 누적 원문을 받을 수 있지만, 응용 프로그램의 중간 JSON 필드 처리가 추가로 필요하다. [OpenAI 공식 스트리밍 문서](https://developers.openai.com/api/docs/guides/streaming-responses), [구조화된 출력 문서](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)

1. 기존 작성 호출에 스트리밍 observer를 연결한다. 모델, 추론 수준, strict schema, 출력 한도, usage·추적, 호출 예산을 유지한다. SDK의 `text.format`과 `text_format`을 동시에 지정하지 않는다.
2. v1 일반 개념의 텍스트 답변은 본문 조각을 바로 투영한다. v1의 다른 구조화 작성 경로는 현재 답변 계약별 허용 본문 필드 adapter를 두고, 기존 코드가 확정하는 수치를 그대로 사용한다. v2 JSON은 `paragraphs[i]`, 해석 `text`, `assumptions[i]`, 한계 `text`만 공개 본문으로 추출한다. 공개 본문이 없는 정상 결과에는 가짜 문장을 생성하지 않는다.
3. 스트리밍 decoder는 JSON 경로, 문자열 escape와 필드 종료를 추적한다. `O1`까지 도착한 근거 ID가 `O12`로 이어질 수 있으므로, 중간 문자열을 확정된 참조로 사용하지 않는다.
4. writer용 스키마에서는 근거 목록이 본문보다 먼저 나오도록 속성 순서를 조정하는 안을 우선 검증한다. 실제 생성 순서가 달라도 참조가 확정될 때까지 해당 수치 표현은 대기한다. 저장된 답변의 필드 의미와 기존 호환성은 유지한다.
5. 수치 참조 처리 함수를 현재 `assemble_answer`에서 공용 순수 함수로 분리해 미리보기와 최종 조립이 같이 사용한다. 근거 존재, 인용 목록 포함, 요청 값 부분 존재와 단위 형식 검사를 유지한다.
6. `{{value:…}}`가 닫히고 인용 근거가 확정되면 코드가 실제 수치로 바꾼 뒤 공개한다. 미완성 참조부터 이어지는 문장 조각은 버퍼에 둔다. 이로 인해 수치가 많은 일부 구간은 묶여 나타날 수 있다.
7. worker와 backend 사이의 텍스트 전달은 약 50~100ms 단위로 모으는 것을 초기 목표로 삼고, 이벤트 크기와 DB 쓰기량을 측정해 조정한다. 모델 출력 전체 완료를 기다려 타이핑 효과를 재생하는 방식으로 성공 판정하지 않는다.
8. 모델 출력 종료 후 현재의 JSON 파싱, Pydantic 검증, 근거 치환, Decisions 경로를 수행한다. refusal, incomplete, 오류, 중간 EOF는 기존 오류 코드로 처리하고 해당 초안 상태를 무효화한다.

진행 설명을 위한 모델 호출은 추가하지 않는다. v2 정상 경로의 호출 구성은 단순 데이터 요청의 계획 1회, 일반 개념의 계획+작성 2회, 실험 해석의 계획+작성+검토 3회를 기준으로 보존한다. 기존 한도 안의 재계획·수정 호출은 실제 발생한 경우에만 늘어난다.

### 수정과 최종 저장

- 최초 작성은 `answerRevision=1`이며, 수정이나 재계획 후 새 본문을 시작할 때마다 증가한다. 시도 ID도 기존 모델 attempt와 연결한다. 이 표시 버전은 재계획·답변 수정 예산과 별개이며 기존 횟수 제한을 바꾸지 않는다.
- 수정이 결정되면 `REWRITE`와 `answer.reset`을 먼저 기록한다. 해석 영역에 `수정 중`을 표시하고, 수정 모델의 텍스트 조각을 새 버전으로 받는다. 검증된 표·그래프는 기존 결과 블록에서 관리한다.
- 늦게 도착한 이전 버전 조각은 새 해석에 붙이지 않는다. 검토·재계획으로 무효화된 본문도 같은 규칙을 적용한다.
- 수정 도중 실패하면 그 임시 본문을 확정하지 않는다. 현재 그래프가 선택한 마지막 코드 유효 답변 또는 확인된 결과를 최종 저장 대상으로 사용한다.
- 모델 완료 이벤트는 작성 단계의 종료다. 최종 `request.state=COMPLETED`는 DB에 turn과 답변을 기록한 트랜잭션이 끝난 뒤 전달한다.
- 웹은 최종 turn을 확인해 임시 본문을 기존 `V1AnswerView` 또는 `V2AnswerView`로 넘긴다. 본문을 중복 추가하지 않는다.
- 최종 시간과 기록 요약은 `AgentMessage`/요청의 선택적 `executionSummary`로 전달한다. 과거 answer snapshot 본문은 재작성하지 않는다.

### 렌더링과 스크롤

- 임시 본문도 기존 `AnswerMarkdown`, 한글 강조, GFM, LaTeX 정규화와 KaTeX 구성을 사용한다.
- 닫히지 않은 수식은 해당 수식 조각을 버퍼링하고, 구분자가 완성되면 렌더링한다. 저장 원문에 구분자를 임의로 추가하지 않는다.
- 닫히지 않은 코드 블록과 표, 잘못된 수식, HTML 유사 문자열을 스트리밍 분할 위치별로 검증한다. 기존 안전한 텍스트 처리 정책을 유지한다.
- 화면 갱신은 짧은 묶음 또는 animation frame으로 합치고, 현재 미리보기 영역만 갱신한다. 과거 turn의 memoization을 유지한다.
- 수정으로 본문이 잠시 줄어들 때도 위쪽 대화를 읽는 사용자의 스크롤 기준점을 보존한다. 최신 답변을 따라 읽는 경우에는 같은 해석 영역과 입력창 위의 간격을 유지한다.
- 자동 스크롤 기준에 현재 본문 높이 변화를 추가한다. 위로 스크롤한 상태에서는 위치를 보존하고 첫 새 본문 도착 시 작은 아래 화살표를 표시한다.
- `aria-live`에는 단계 변경을 알리고, 본문 전체를 토큰마다 다시 읽게 하지 않는다. 움직임 감소 설정과 키보드 조작을 지원한다.

## Verification Contract

구현자는 다음 완료 근거를 남긴다.

1. backend 통합 검사에서 순서·멱등성·lease·작업 시간·방 소속·최종 저장을 검증한다. SSE 연결을 열어둔 상태에서도 일반 상태·Run 조회를 처리할 수 있어야 한다.

3. 프론트엔드 타입 검사와 관련 단위 검사에서 이벤트 reducer, 요청/방 경계, 답변 버전 전환과 기존 렌더러 호환성을 검증한다.
4. 브라우저는 390 / 800 / 1008 / 1440px에서 진행 기록·HITL·입력·그래프·수식·자동 스크롤·아래 화살표·가로 넘침을 확인한다.

6. SSE 단절과 재접속은 같은 요청을 복원해야 한다. 새 질문 제출, 모델 재호출, 도구 재실행과 최종 turn 중복 저장이 생기면 실패다.
7. 재시작·복구 중에는 기존 호출 결과 불명 정책을 따른다. 저장 여부를 모르는 모델 작업을 이벤트 복원을 이유로 다시 호출하지 않는다.
8. 공개 이벤트와 최종 답변의 실제 데이터는 로컬 검증 경로에 보관한다. 저장소에는 계약·코드·인공 테스트 데이터와 요약 결과만 남긴다.

## Definition of Done

- 두 계획이 일반 개념, 데이터 전용, 실험 해석, 수정, 사용자 확인 경로에서 실제로 동작한다.
- 진행 문구가 실제 실행 사실·검증된 건수와 맞고, 완료 후 작업 시간과 구분선으로 정리된다.
- 최초 답변과 수정 답변이 제공자 출력 완료 전에 화면에 나타나는 것이 제어 스트림과 실제 웹에서 확인된다.
- 수치 참조가 코드에서 해소되고, 최종 저장 답변의 기존 정확성·복구 한도·검토 정책이 유지된다.
- 대화 이동·새로고침·재연결·취소·초기화에서 다른 방이나 이전 시도의 텍스트가 섞이지 않는다.
- 기록된 최종 시간이 다시 열어도 같으며, 사용자 입력 대기를 작업 시간에 합산하지 않는다.
- 타입·계약·관련 단위/통합 검사와 네 화면 크기 검증이 통과하고, 실제 측정 결과가 기록된다.

## 실행 시 확인할 항목

- 현재 모델 endpoint의 strict JSON 스트리밍 지원과 실제 속성 출력 순서는 U4 시작 시 확인한다.
- 텍스트 묶음 간격, 기록 노출 개수, Markdown·KaTeX 갱신 비용은 UX/부하 측정으로 조정한다. 첫 본문이 나오기 전 모델 처리 시간도 함께 보고한다.
- 기존 완료 답변에는 확실한 작업 시간 자료가 없을 수 있다. 과거 시간을 추정해 채우는 데이터 이관은 포함하지 않는다.
- 현재 확인된 범위에서는 추가로 결정해야 구현을 시작할 수 있는 제품 선택은 없다. 첫 초안과 수정문 모두 실시간 표시하는 방식은 사용자의 후속 답변으로 확정됐다.
