# 기존 업로드 실험 조건 복원 B/C 재측정 — 2026-10-16

사용자 요청: 제품 B/C 트랜잭션 차이만 비교하도록 기존 실험의 요청 도구·조회 시점·서버 상태 정책을 복원한다.

## 사전 고정
- 제품: 이전 B.jar/C.jar 그대로. ZIP entry 해시 차이는 ImportWorker.class 및 내부 클래스뿐이며, 보존한 소스 diff는 tx.process를 tx.prepare → 트랜잭션 밖 파싱 → tx.publish로 나눈 변경이다. 저장 시 중복 재확인도 이 변경에 포함된다.
- worker/관리자 8개, Hikari maximum/minIdle=10, 총150 Run·2,175파일·1,545,005,295바이트, 동일 원본·파티션·seed DB·기존 버전 조회.
- 부하 발생: 기존 measured-harness의 k6 스크립트 및 requestSlot을 바이트 단위 그대로 복사한다. 기존 iteration 순서별 조회 대상 배분도 유지한다. Node 도구나 새 VU별 매핑으로 바꾸지 않는다.
- 동일 k6 v2.3.0, 100 VU가 5초마다 동시 조회. 첫 예약 묶음+5초에 업로드 시작. 비교 조회는 cohort2(부하 시작+10초), 즉 업로드 시작 약5초 후로 고정. 7초 후로 이동하지 않는다.
- 기존 서버 재사용/예열 정책: B1 새 JVM+8Run 예열 → C1 새 JVM+예열 → C2 C1 서버 재사용 → B2 새 JVM+예열 → B3 B2 서버 재사용 → C3 새 JVM+예열. B/C 각각 fresh2회/reuse1회로 집계는 균형이며, 개별 B2/C2와 B3/C3는 warm 상태가 같지 않다는 제한을 명시한다. 매 시행 DB와 업로드 저장소는 같은 seed로 복원한다. 호스트/OS 캐시 상태를 완전히 동일하게 만들지는 않는다.
- 실행 범위만 기존 worker 1/2/4/8 전체에서 이번 요청 대상 worker8 블록으로 제한한다. 순서와 나머지 스크립트는 그대로다. 원본 함수 schedule만 런처에서 worker8 순서로 덮어쓴다.
- 외부의 가벼운 시계 관측 스레드는 time.time_ns와 monotonic_ns를 100ms마다 기록할 뿐 부하 예약/HTTP 시간/제품을 변경하지 않는다. 두 군 동일 적용. 기존 HTTP elapsedMs와 k6 durationMs를 함께 확인한다.

## 집계와 중단
- 대표 결과는 고정 cohort2의 모든 100건을 각 시행에서 집계한 뒤 B/C 각3회 평균으로 제시한다. 지연이 크거나 개선이 없다는 이유로 제외하지 않는다. 업로드 점유와 완료 시간은 전체150개 처리 구간이다.
- 기존 60.6%와 연결하기 위한 보조 결과: 양쪽 cohort2의 평균 활성 worker>=6인 쌍만 별도로 집계한다. 이때도 고정 cohort2만 사용하고 다른 회차를 골라 유리한 수치를 만들지 않는다. 포함/제외는 원시 결과와 함께 공개한다. B의 실제 worker 연결 보유 시점으로 거른 기존 규칙도 별도 감사하되 대표 전체 묶음을 덮어쓰지 않는다.
- 전송 폭·예약 지연·조회 대상별 개수·실제 worker/연결 점유는 모두 기록한다. 기존 조건 재현을 위해 새 실험의 발송<=5ms 게이트를 소급 적용해 표본을 제거하지 않는다. 부하 불일치가 발견되면 제한으로 보고한다.
- 시계 offset의 시행 내 변동 또는 wall/monotonic upload elapsed 차이가5ms 초과하면 타이밍 이상으로 구분한다. 데이터 오류·요청 누락도 별도 실패다. 성능 평균에 유효한 것처럼 섞지 않는다. 오류가 있으면 도구를 바꾸지 않고 해당 원시 기록을 보존한 채 완료 범위를 보고한다.
- 사전 예정은6시행이며 성공 여부·지연에 따라 유리한 추가 반복을 하지 않는다. 기존 대비 평균의 변동 원인을 전부 분리했다거나 인과를 확정했다고 주장하지 않는다.
- 전용 테스트 DB만 사용하고 종료 후 seed 복원 및 서버·테스트 컨테이너 종료. 제품 서버/실데이터/LLM은 사용하지 않는다.
