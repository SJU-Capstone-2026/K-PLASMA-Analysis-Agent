# 업로드 worker 확대와 DB 연결 점유 B/C 비교 테스트 계획

## 1. 무엇을 확인하나

**관리자와 업로드 worker를 함께 1 → 2 → 4 → 8개로 늘렸을 때, 파싱 중 DB 연결을 반환하는 C 방식이 B보다 조회 대기와 응답 시간을 줄이는지 확인한다.**
DB 연결은 서버 전체에서 공유하는 **10개**, 전체 업로드량은 **150 Run**으로 고정한다.
현재 문서는 테스트 계획이며, 병렬 worker 구현·테스트·벤치마크 실행은 아직 하지 않는다.

- **B:** 작업 사이 불필요한 대기는 제거했지만, 파일 파싱 중에도 트랜잭션과 DB 연결을 유지하는 방식.
- **C:** 준비 → 트랜잭션 밖 파싱 → 게시로 나누어, 파싱 중에는 DB 연결을 반환하는 방식.
- **관리자:** 업로드를 요청하는 클라이언트. 실제 계정·로그인 부하를 뜻하지 않는다.
- **worker:** 서버에서 한 번에 Run 하나를 처리하는 작업 실행 슬롯. DB 연결 수와 같지 않다.

[앞선 VU 1~100 실험](../verification/2026-10-15-동시-사용자-조회와-업로드-트랜잭션-비교.md)에서는 worker 1개에서 연결 점유 합계가 약 88% 줄었지만, 조회 응답 개선은 반복마다 달랐다.
이번에는 [합의한 후속 범위](2026-10-15-동시-사용자-조회와-업로드-트랜잭션-비교-계획.md)를 구체화해, 여러 업로드 작업이 동시에 실행될 때의 차이를 본다.
효과가 크게 나오는 조건을 찾는 것이 아니라, 고정한 조건에서 효과와 비용을 함께 검증한다.

## 2. 비교할 조건

| 단계 | 관리자 역할 클라이언트 | 서버 worker | 서버 전체 DB 풀 | 전체 업로드 | 동시에 조회하는 VU |
| --- | ---: | ---: | ---: | ---: | ---: |
| W1 | 1 | 1 | 10 | 150 Run | 100 |
| W2 | 2 | 2 | 10 | 150 Run | 100 |
| W4 | 4 | 4 | 10 | 150 Run | 100 |
| W8 | 8 | 8 | 10 | 150 Run | 100 |

- 조회는 **100 VU가 5초마다 함께 요청**한다. 평균 목표는 약 20건/초이며, 매번 100건이 몰리는 가정이다. 앞선 실험에서 연결 대기가 관측된 대표 조건 하나를 사용하고 VU 전 단계를 다시 반복하지 않는다.
- 백엔드는 **JVM 한 개·DataSource 한 개**다. 서버를 8개 띄워 풀을 80개로 늘리는 실험이 아니다. Hikari 최대 연결과 최소 유휴 연결은 모두 10으로 고정·검증한다.
- worker는 관리자별로 고정 배정하지 않고 같은 서버의 공통 큐에서 작업을 가져온다. 관리자 8명과 worker 8개가 일대일로 연결되는 구조는 아니다.
- 각 단계에서 관리자 수, worker 수, 입력 분할, 조회 방식과 환경을 동일하게 두고 B/C를 비교한다.
- 단계 간에는 관리자 수와 worker 수가 동시에 변한다. W1→W8의 차이를 worker만의 독립 효과로 표현하지 않는다.
- 조회만 하는 대조 실험, Redis·Kafka 도입, SQL·인덱스 최적화, 파일 복사·파서 최적화, 서버 장애 복구 확대는 포함하지 않는다.

## 3. 입력과 환경을 어떻게 맞추나

| 항목 | 고정 방법 |
| --- | --- |
| 입력 | 기존 인공 150 Run·2,175파일·1,545,005,295바이트. 입력·파일 SHA-256 기록 |
| 초기 DB | 매 반복 동일 seed 복원. 147개 신규·3개 갱신, 완료 시 current Run 150개·불변 버전 153개 |
| 업로드 | FOLDER multipart, 관리자마다 독립 요청·idempotency key. 관리자들의 전송 시작을 공통 barrier로 맞춤 |
| 조회 대상 | 기존 seed의 불변 버전 3개를 동일하게 순환. `GET /api/run-versions/{id}` 응답 전체 해시 검증 |
| 런타임·자원 | 앞선 실험과 같은 Java·PostgreSQL·k6 버전, JVM 256 MiB~2 GiB, DB 컨테이너 2 CPU·3 GiB. 실행 전 실제 버전·설정 기록 |
| 처리 설정 | backlog 연속 처리·빈 큐 대기 500ms·drain 한도 32의 의미를 B/C 동일하게 유지. 기본 제품 worker는 1개 유지 |
| 계측 | B/C 동일 계측. Hikari 상태 100ms, OS/DB 자원 약 2초 표본. 제품 기본 계측 비활성 유지 |
| 완료 확인 | 클라이언트 폴링 1초. 서버 terminal commit 시각을 별도로 수집해 폴링 오차와 구분 |

150 Run을 통째로 복제하지 않고 관리자별로 **중복 없이 분할**한다.
Run에 속한 파일 묶음은 쪼개지 않는다. 예상 개수는 1명 150개, 2명 75개씩, 4명 37~38개씩, 8명 18~19개씩이다.
개수 차이는 최대 1개로 제한하고 파일 바이트·기존 파싱 비용이 가능한 한 균등하도록 고정 분할표를 만든다.
분할표는 B/C와 모든 반복에서 재사용하며 관리자별 Run 수·바이트·예상 파싱 비용을 기록한다. 부가 파일도 한 번만 포함해 전체 파일·바이트 수가 보존되어야 한다.
각 관리자는 한 요청을 보내고 완료를 기다린다. 관리자가 늘어도 전체 업무량은 150개다.

## 4. 본 측정 전에 반드시 확인할 것

기존 코드를 그대로 두고 스레드 수만 늘려서는 유효한 비교가 되지 않는다. 아래는 **실행 전 준비 요건**이며, 이번 문서 작성 단계에서 구현하지 않는다.

| 현재 코드에서 확인한 점 | 실행 전 준비·검증 |
| --- | --- |
| `ImportExecutionConfiguration`은 스케줄러 크기 1이며 단일 `worker::poll` 작업을 등록 | 독립된 worker 실행 슬롯을 W개 구동. 스케줄러 풀 숫자만 변경한 것을 병렬 실행으로 간주하지 않음 |
| `ImportWorker.poll()`은 먼저 첫 QUEUED ID를 읽고, `process()`에서 해당 ID를 `FOR UPDATE SKIP LOCKED`로 점유 | 작업 선택·점유 경합과 공유 `backlog` 상태 검토. 여러 worker가 같은 첫 작업만 반복 선택하지 않고, 각 job을 정확히 한 번 처리하는 공통 실행 경로 확보 |
| 접수는 `ImportRepository.lockIntake()`의 전역 advisory lock 사용 | 여러 접수 요청이 이 잠금 때문에 기다릴 수 있음. 접수와 worker의 연결 획득·점유를 별도로 기록하고 기존 잠금을 이번 비교에서 임의로 제거하지 않음 |
| batch 진행 상태 갱신은 `import_batch` 행을 잠금 | 같은 batch의 여러 worker가 갱신할 때 진행률·최종 상태 정확성 및 잠금 대기 검증 |
| `summarize_events()`는 작업이 겹치지 않는다고 가정하고 음수 작업 간격을 거부 | 병렬 구간을 처리할 별도 집계 경로 필요. 순차 집계의 assertion만 삭제하거나 기존 시간 합산식을 재사용하지 않음 |
| 기존 B/C JAR은 worker 1개 기준 | B/C에 **같은 병렬 실행·계측 보완**을 적용한 새 비교용 빌드 생성. 소스 기준 커밋·공통 변경·트랜잭션 차이·JAR 해시 기록 |

새 빌드를 `B-parallel`, `C-parallel`로 식별한다. 보고서의 B/C는 이 새 비교 쌍을 뜻한다고 명시한다.
W1도 새 빌드로 다시 측정하며, 이전 보고서 수치를 이번 결과의 직접 기준선으로 가져오지 않는다.
병렬화 준비 과정에서 트랜잭션 범위 외 알고리즘·락 정책을 한쪽에만 바꾸면 비교를 시작하지 않는다.

**정확성 사전 검증**

1. 소량 인공 입력과 테스트 barrier로 2·4·8개 작업의 파싱이 실제로 겹치고 설정 한도를 넘지 않는지 확인한다. 본 성능 측정에 인위적인 sleep·SQL 지연은 넣지 않는다.
2. 여러 worker가 경쟁해도 job 누락·이중 실행·영구 QUEUED가 없어야 한다. batch 진행 수와 terminal 상태가 실제 job 집계와 일치해야 한다.
3. 동일 원본의 동시 등록은 기존 정책대로 버전 하나와 중복 결과로 수렴해야 한다. 같은 조건의 다른 원본은 불변 버전과 유효한 현재 버전 포인터를 유지해야 한다. 현재 코드가 보장하지 않는 도착 순서를 새로 보장했다고 주장하지 않는다.
4. 한 job 파싱 실패·게시 rollback이 다른 job이나 기존 성공 버전을 훼손하지 않아야 한다. 중복·충돌·실패 검증은 150개 처리량 측정에 섞지 않는다.
5. B의 파싱 중 트랜잭션 활성, C의 파싱 중 비활성을 실제 실행으로 확인한다. worker별 trace가 올바른 job·batch와 연결되는지 검증한다.
6. 기본 worker 1개 동작 회귀와 병렬 집계 검증을 통과한 뒤 본 실험에 들어간다. 성능 계측의 동기 로그 기록이 새 병목이면 결과를 분리하고, 한쪽만 계측을 줄이지 않는다.

## 5. 측정 순서와 시간 제한

**본 비교는 W1 / W2 / W4 / W8에서 B/C 각각 3회, 총 24회**다. 각 반복은 초기 DB·스토리지를 복원하고 새 업로드를 보낸다.

- 단계는 W1→W2→W4→W8로 진행한다. 단계별 실행 순서는 B1→C1→C2→B2→B3→C3로 고정한다. 첫 두 쌍의 선후를 바꿔 한쪽이 항상 먼저 실행되는 상황을 줄인다.
- 같은 변형·worker 단계의 연속 반복은 JVM을 재사용한다. 변형 또는 worker 단계가 바뀌어 재기동하면 소량 고정 입력으로 워밍업하고 seed를 복원한다. 워밍업은 본 통계에서 제외한다. 반복별 JVM 시작 여부를 기록한다.
- k6 부하를 먼저 시작하고 5초 뒤 관리자들의 업로드를 함께 시작한다. 예정 시각·실제 전송 시작 시각 차이를 기록한다.
- 모든 관리자 요청의 202 응답만으로 완료 처리하지 않는다. **전체 150개 job의 최종 commit과 모든 batch의 성공**을 확인한다.
- 조회는 업로드 전체 완료 후 다음 5초 조회 묶음까지 유지하고 종료한다. 비교 지표에는 아래에서 정한 업로드와 겹친 조회만 포함한다.
- 배치당 업로드 관측 상한은 60초, k6 부하는 시작 전 5초와 종료 여유를 포함해 최대 70초로 제한한다. 실제 요청 수·예정 조회 누락·timeout을 기록한다.
- 본 측정 목표는 준비 완료 후 약 20~30분이며 **30분부터 새 배치를 시작하지 않고 35분에 종료**한다. 코드 준비·빌드·정확성 검증·문서 작성 시간은 별도다. 미실행 단계와 중단 이유를 남기고 자동 추가 반복하지 않는다.

worker가 많아 업로드가 빨리 끝나면 겹치는 조회 묶음 수도 적어진다.
표본 수와 묶음 수를 함께 보고하고, 겹친 묶음이 3개 미만인 배치는 p95 해석이 약하다고 표시한다.
표본을 늘리려고 업로드량·조회 간격을 도중에 바꾸거나 업로드를 인위적으로 지연시키지 않는다.

## 6. 무엇을 어떤 기준으로 측정하나

**측정 구간**

- **전체 업로드 창:** 서버가 첫 업로드 요청을 받은 때부터 전체 batch의 마지막 job terminal commit까지.
- **접수 이후 worker 창:** 마지막 batch의 접수 commit부터 마지막 job terminal commit까지. 접수 잠금 영향을 덜 포함하는 보조 분석이며, 앞선 batch에서 이미 처리된 작업이 있으므로 전체 worker 처리 비용이라고 부르지 않는다. 빈 구간이면 N/A로 남긴다.
- 각 창 안에서 시작된 조회를 포함하고, 창 밖에서 끝나더라도 완료·오류까지 수집한다. B/C의 전체 창과 길이가 더 짧은 두 창의 공통 경과시간 구간을 함께 집계해 서로 다른 요청 묶음 수의 영향을 확인한다. 창을 잘라 실패나 느린 요청을 제외하지 않는다.

| 지표 | 정의·보고 방식 |
| --- | --- |
| DB 연결 획득 | 조회·업로드 접수·worker별 `getConnection()` 평균/p95/실패. 순수 큐 대기 외 연결 확인 비용도 포함 |
| 실제 연결 상태 | Hikari active·idle·pending 표본, 최대 대기 요청 수, pending>0 표본 비율. 설정 10개와 실제 상태를 함께 확인 |
| 업로드 연결 점유 | 접수와 worker를 구분한 연결 보유 시간 합계(connection-seconds), 150 Run 전체·Run당 값. 조회 연결 점유는 별도 |
| 조회 응답 | HTTP 평균·p95·최대, 오류·응답 해시 불일치, 요청 시작 지연·발행 누락. 연결 획득 시간은 이 안에 포함되므로 더하지 않음 |
| 업로드 전체 완료 | 관리자 공통 시작부터 마지막 관리자 완료 확인까지의 실제 경과시간. 서버 전체 창 길이도 별도 표시 |
| 개별 작업 대기 | 각 job의 QUEUED commit→성공한 claim까지 대기 평균/p95. 공유 큐가 비어 worker가 쉬는 시간과 구분 |
| 파일·파싱·DB 처리 | worker/job/batch별 구간 합계, 원본 파일·바이트 수, SQL 실행·commit 횟수와 시간. 중첩 phase를 이중 합산하지 않음 |
| 다른 병목 | Java/DB/k6 CPU·RSS·GC·파일 I/O·메모리 압박, PostgreSQL 잠금·I/O 대기 |
| 처리 정확성 | 150 READY, current 150·version 153, 전체 scalar/graph golden parity, 원본 SHA, 과거 조회 응답 해시 |

**병렬 집계에서 지킬 규칙**

- 4개 worker가 각 5초 작업하면 작업 시간 합계는 20초일 수 있지만, 실제 경과시간이 20초라는 뜻은 아니다. 단계 합계를 전체 완료 시간에서 빼서 “나머지 시간”을 만들지 않는다.
- 대기는 job별 준비·claim 시각으로 계산한다. 순차 처리 때 사용한 “직전 job 종료→다음 job 시작” 간격은 쓰지 않는다.
- worker 수만으로 DB 점유 개수를 추정하지 않는다. JDBC close 계측 시각이 약간 겹칠 수 있으므로 span 겹침의 최대치를 실제 연결 수라고 표시하지 않고, Hikari의 실제 상태 표본을 사용한다.
- Hikari 100ms·자원 약 2초 표본은 짧은 포화를 놓칠 수 있다. pending 표본이 0이라고 대기 자체가 없었다고 단정하지 않는다.
- 각 배치의 평균/p95를 먼저 계산한 뒤 3회 평균·최솟값·최댓값을 제시한다. 반복별 값과 B→C 방향도 공개하며 수천 건의 요청을 수천 회 독립 반복으로 세지 않는다.
- 감소율은 `(B−C)/B×100`, 시간 차이는 `B−C`다. 음수는 악화이고 기준값 0이면 비율은 N/A다. 평균 p95는 “배치 p95의 평균”으로 표기한다.

## 8. 중단 기준과 결과 판정

- **즉시 중단:** 제품/공용 DB에 연결, 입력·결과 불일치, job 유실·이중 게시, worker 또는 풀 설정 불일치, 데드락·OOM·서버 종료. 실패한 배치와 이미 얻은 자료는 보존한다.
- **배치 종료 후 조사:** 60초 내 미완료, 연결 획득 timeout, 요청 오류·누락, 부하 발생기 지연. 정상 평균에서 숨기지 않고 실패·관측 하한을 보고한다. 원인이 해결되기 전 상위 단계로 진행하지 않는다.
- 개선이 없거나 C가 느리다는 이유로 중단·제외·자동 재측정하지 않는다. 수정 때문에 재측정해야 하면 영향받은 B/C 모두 같은 조건으로 다시 측정하고 이전 실패를 남긴다.
- 동시 실행 준비 검증에서 의도한 W개 worker가 겹치지 않으면 유효한 W단계 결과라고 부르지 않는다. 본 측정에서는 실제 최대·평균 활성 worker와 큐 길이를 보고해 접수·스케줄링 제약을 구분한다.

| 관측 결과 | 가능한 결론 |
| --- | --- |
| 연결 점유만 줄고 조회 시간이 비슷함 | DB 연결 자원 효율 개선 확인. 조회 응답 단축은 확인하지 못함 |
| B에서 풀 대기, C에서 점유·획득·HTTP 시간이 반복적으로 감소 | 해당 worker·조회 부하 조건에서 대기/응답 완화 증거. 실제 서비스 전체·Agent 응답 개선율로 확대하지 않음 |
| C의 조회는 빨라지지만 업로드는 느려짐 | 조회와 업로드 사이의 비용 교환을 두 수치로 함께 보고 |
| CPU·I/O·접수 잠금이 지배함 | 연결 부족과 다른 병목. 트랜잭션 분리 효과만으로 설명하지 않음 |
| 반복마다 방향이 다름 또는 조회 묶음이 너무 적음 | 관측 평균과 범위만 보고. 안정적인 개선 확정이나 유의성 주장 보류 |

조회 단독 대조군을 제외했으므로 업로드가 추가한 지연을 독립적으로 산출했다고 주장하지 않는다.
관리자당 한 번의 150개 분할 업로드를 측정하는 실험이며, 무한 큐·장시간 지속 부하·실제 사용자 수용 한도를 검증하지 않는다.
