# Agent v2 의사결정 기록 활용 설계

## 1. 목표

Agent v1에 연결한 판단 기록 활용(`RECORD_REUSE`)을 Agent v2의 계획 단계로도 쓸 수 있게 한다. 이렇게 하면 v1이 지원하지 못하는 다음 같은 복합 질문을 처리할 수 있다.

> "에너지 30 eV 이상 후보를 찾되 비용 때문에 반려된 건 빼고, 남은 후보끼리 플럭스를 비교해줘"

```
s1 후보 탐색 → s2 비용 반려 제외 → s3 남은 후보 비교
```

- 판단 규칙은 v1과 **같은 코드**(`domain/decision_records.py`)를 사용한다. 비용 판별, 건수 집계, 제외 결과는 v1과 같아야 한다.
- 메모 원문은 계획·답변 작성·의미 검증 모델과 Phoenix로 보내지 않는다.
- v1의 기본값, 과거 대화, 진행 중인 요청은 바꾸지 않는다.

## 2. 전제와 범위

| 항목 | 결정 |
| --- | --- |
| 선행 작업 | v1 연결 PR(판단 규칙 포함)이 `main`에 병합된 뒤 시작한다 |
| 자동 제외 사유 | v1과 같이 **비용 사유만** |
| 기준 건수와 안내 문구 | v1·프로토타입과 같다 |
| v1·v2 기본값 | 바꾸지 않는다(v2 설계 D10-R) |
| v3와의 관계 | 팀 합의(2026-11-08)에 따라 v3는 **이 규칙 도구가 들어간 v2를 복사**해 만들고 RAG 도구만 추가한다(§2.1) |
| v2 소유 | v2 그래프는 담당 팀원과 합의한 뒤 변경한다. 합의한 결정은 §11에 기록한다 |
| 범위 밖 | 제외 되돌리기, 사유 태그·RAG, 병렬 실행 |

### 2.1 v3(RAG) 계획과의 순서

팀은 v2를 복사해 RAG를 추가한 v3를 만들고, v2(규칙)와 v3(규칙 + RAG)를 같은 질문으로 비교하기로 했다. 두 버전의 차이가 RAG뿐이어야 하므로 규칙 도구는 **v2에 먼저** 넣고, 그다음 v2를 복사한다.

```
v2에 규칙 도구 추가(이 문서) → v2를 복사해 v3 생성 → v3에 RAG 도구 추가 → v2·v3 비교 평가
```

- v3를 먼저 복사하면 같은 규칙 도구를 두 번 구현해야 하고, 두 구현이 달라질 위험이 있다.
- v3 RAG 설계는 별도 문서로 작성한다. 이 문서는 v2·v3에 공통인 규칙 도구만 다룬다.
- v1(규칙)과 v3(RAG)를 직접 비교하면 그래프 차이와 RAG 효과가 섞이므로, RAG 효과는 v2와 v3로 비교한다.

## 3. 지원 흐름

| ID | 질문 예시 | v2 계획 |
| --- | --- | --- |
| V1 | "이 후보들의 과거 기록 보여줘" | `records(view, 확인된 후보)` |
| V2 | "이 후보 중 비용 반려 1건 이상 제외해줘" | `records(exclude, 확인된 후보)` |
| V3 | "에너지 30 eV 이상 찾되 비용 반려 제외" | `search → records(exclude, 검색 후보)` |
| V4 | V3 + "남은 후보끼리 비교해줘" | `search → records → compare(남은 후보 전체)` |
| V5 | V3 + "그중 두 개 골라 비교" | `search → records → await(run_selection, 남은 후보) → compare` |

| V7 | "성능 때문에 반려된 건 빼줘" | 제외하지 않고 비용 사유만 지원한다고 안내 |
| V8 | 제외 뒤 남은 후보가 없음 | `run_if`로 비교를 건너뛰고 확인된 결과만 답변 |

## 5. 설계 선택

### 5.1 v2에 넣는 방식

| 방식 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| A. 탐색 단계 옵션(`exclude_cost_rejections`) | v1과 같은 정렬 전 제외, 단계 수 적음 | 탐색에만 쓸 수 있고 조회·확인된 Run·보기에는 못 씀 | 제외 |
| **B. 독립 단계 `decision_records`** | 탐색·조회·확인된 Run 어디에나 연결, 보기·제외 모두 지원, 결과를 다음 단계에 전달 | 계획 검사·후보 출처 규칙 확장 필요 | **채택** |
| C. A와 B를 모두 지원 | 각 경우에 맞는 방식 사용 | 같은 기능이 두 경로라 검증 부담이 두 배 | 제외 |

**B의 정렬 동등성.** v2에서는 탐색 뒤에 제외하므로 v1(탐색 전 제외)과 순서가 다르다. 하지만 `search_reverse`의 공통 순위는 Run마다 독립적으로 계산한 키로 정렬한다(목표 키 → 근접도 → 표시 점수 → Run ID). 그래서 정렬된 목록에서 Run을 빼도 남은 Run의 순서는 처음부터 빼고 정렬한 결과와 같다. 이 성질은 테스트로 고정한다(§10). 다른 점은 중간 탐색 카드의 조건별 탭에 제외 전 결과가 남는다는 것뿐이고, 이는 §8에 차이로 기록한다.

### 5.2 기준 건수를 정하는 주체

| 방식 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| 계획 모델이 리터럴로 채움 | 단계마다 다른 기준 가능 | 모델이 숫자를 지어낼 위험, v1과 판정 차이 | 단독 사용 제외 |
| 계획에 `await_input` 확인 단계 추가 | 기존 확인 구조 재사용 | "많은"을 모델이 감지해야 함 | 제외 |
| **코드가 원문으로 결정, 모델 값은 대조만** | v1과 같은 판정(`parse_request`), 재현 가능 | 한 질문에 기준 하나 | **채택** |

규칙:
1. 코드가 원문 질문에 `parse_request`를 적용한다. 결과가 정수 N이면 N을 기준으로 쓴다.
2. 모델이 `threshold` 리터럴을 넣었으면 인용 구절과 값이 코드 결과와 같아야 한다. 다르면 계획 오류로 재계획한다.
3. 결과가 "많은"처럼 모호하면 실행 중 확인 요청을 띄운다(§6.4).
4. 한 질문에서 기록 단계가 여러 개여도 기준은 하나다. 서로 다른 기준이 필요한 질문은 §12의 한계로 둔다.

### 5.3 안내문(NOTICE) 처리

v1은 안내문을 별도 답변 상태로 표시한다. v2는 단계 결과와 최종 답변이 분리돼 있다.

| 방식 | 판단 |
| --- | --- |
| 계획 검사에서 거부하고 재계획 | 제외. 사용자 요청 문제를 계획 오류로 다뤄 재계획 횟수를 낭비함 |
| **기록 단계가 `failed`와 안내 코드를 반환하고 답변 단계가 문구 표시** | **채택**. 기존 실패 → 답변 작성 경로를 그대로 사용 |

안내 코드와 문구는 v1과 같다.

| 코드 | 조건 | 문구 |
| --- | --- | --- |
| `RECORD_NOTICE:COST_ONLY` | 제외 요청인데 비용 언급이 없음 | 현재 시연에서는 비용 사유가 명확한 반려 기록만 자동 제외합니다. 다른 사유는 기록 원문을 확인해 주세요. |
| `RECORD_NOTICE:THRESHOLD` | 기준이 1 이상의 정수가 아님 | 제외 기준은 1건 이상의 정수로 입력해 주세요. 후보를 제외하지 않았습니다. |
| `RECORD_NOTICE:SCOPE` | 대상 Run이 없음 | 먼저 후보 탐색을 실행하거나 결과의 전체 후보를 질문 대상으로 선택해 주세요. |

안내문으로 끝난 요청의 답변 `executionStatus`는 **`PARTIAL`**로 표시한다(§11 결정 3). 요청은 해석했지만 제외를 실행하지 않았다는 뜻이며, 실행 오류인 `FAILED`와 구분한다. 기록 단계 하나만 있는 계획에서도 `PARTIAL`이 되도록 테스트로 고정한다.

v1의 `NUMERIC` 안내(수치 조건 미해석)는 v2에 두지 않는다. v2에서는 수치 조건을 탐색 단계로 계획하고, 해석하지 못하면 기존 계획 검사와 재계획이 처리한다.

## 6. 계약

### 6.1 계획 단계

```python
class DecisionRecordInputs(ClosedModel):
    action: Literal["view", "exclude"]
    runs: Binding                     # 대상 Run 집합
    threshold: LiteralInput | None = None


class DecisionRecordStep(StepBase):
    kind: Literal["tool"]
    tool: Literal["decision_records"]
    inputs: DecisionRecordInputs
```

`ToolName`과 `StepSpec`에 추가한다. `runs`에 허용하는 출처:

| 출처 | 바인딩 | 예 |
| --- | --- | --- |
| 탐색·조회 결과 전체 | `result_ref(step, "candidates", candidate_group)` | V3 |
| 다른 기록 단계의 남은 후보 | `result_ref(step, "candidates", candidate_group)` | 연속 적용 |
| 사용자 확인 선택 | `result_ref(confirm, "selection", scalar)` | V5 변형 |
| 확인된 문맥 | `context_ref("selected_runs")`, `context_ref("activeRun")`, `context_ref("candidate_references")` | V1, V2 |

리터럴 Run ID는 허용하지 않는다(비교와 같은 규칙).

현재 v2 문맥(`_binding_context`)은 `selected_runs`, `activeRun`, `selectedRunRef`만 제공한다. v1의 대상 우선순위(첨부 Run → 현재 후보 그룹 → 활성 Run)를 맞추려면 요청 문맥의 `candidateReferences`를 `candidate_references` 키로 추가해야 한다. 이 키는 기록 단계에서만 허용한다.

### 6.2 계획 검사 추가

`validate_plan`에 다음을 추가한다.

1. `runs` 출처가 위 표에 있는지 확인한다.
2. `candidate_group` 범위를 쓸 수 있는 생산 단계에 `DecisionRecordStep`을 추가한다. 그러면 `compare_runs.runs`와 `await_input(run_selection).candidates`가 기록 단계의 `candidates`를 읽을 수 있다.
3. `threshold` 리터럴이 있으면 §5.2 규칙으로 대조한다.
4. **누락 검사:** 원문에 제외 요청이 있으면(`parse_request(...).exclude`) 계획에 `action="exclude"`인 기록 단계가 하나 이상 있어야 한다. 없으면 `InvalidPlan`으로 재계획한다. v1의 "다른 도구로 보낸 제외 요청 보정"에 해당한다. 재계획 2회 뒤에도 없으면 `RECORD_STEP_MISSING`으로 확인된 결과만 답변하고, 제외하지 않았다고 알린다.

### 6.3 단계 결과

```text
StepResult(
  status   = "verified" | "empty" | "failed",
  outputs  = {
    "toolResult": DecisionRecordsResult,   # v1과 같은 계약(kind="decision_records")
    "candidates": [RunRef, ...],           # 남은 Run. 입력 순서 유지
    "excluded":   [RunRef, ...],
  },
  runRefs  = 남은 Run + 제외된 Run,
  groupId  = "records",
  reason   = resultStatus 또는 RECORD_NOTICE:*
)
```

- `toolResult`는 v1 `DecisionRecordsResult`를 그대로 사용한다. 따라서 Java 검증과 프론트 카드도 재사용한다.
- `candidates`는 **입력 순서를 유지**한다. 탐색 결과를 받으면 탐색 순위가 그대로 남는다.
- 남은 Run이 없으면 `empty`다. 기존 `run_if candidate_count`로 후속 단계를 건너뛸 수 있다(V8).
- `view`는 `candidates`=입력 전체, `excluded`=[]다.

### 6.4 기준 건수 확인

기준이 모호하면 실행기가 `blocked`와 `MISSING_INPUT:record_threshold`를 반환한다. `wait_for_input`은 v1과 같은 확인 요청을 만든다.

```json
{"type": "decision_threshold", "message": "제외할 기록 건수를 선택해 주세요.",
 "options": [{"label": "1건", "input": {"type": "decision_threshold", "threshold": 1}},
             {"label": "2건", "input": {"type": "decision_threshold", "threshold": 2}}]}
```

- 답(버튼 또는 "3건" 입력)은 v1의 `_threshold_reply`로 해석하고, 모델을 다시 호출하지 않는다.
- 해석한 값은 대기 단계의 확인 결과(`selection:<stepId>`, `outputs.value`)로 저장하고 같은 단계를 다시 실행한다.
- 잘못된 값은 `RECORD_NOTICE:THRESHOLD`로 끝난다.
- 현재 v2 대기는 실행 선택(`run_selection`)·비교 옵션(`comparison_options`)·텍스트(`text`)만 구분하므로 `wait_for_input`에 네 번째 종류인 `decision_threshold` 분기를 추가한다. 화면 형식은 v1과 같다(§11 결정 4). 서버 재개 API는 이미 일반 입력을 허용한다.

### 6.5 서버 API

새 엔드포인트를 추가한다.

```
POST /internal/agent/requests/{id}/steps/{executionId}/decision-records
→ {"records": [...]}      # v1 /decision-records와 같은 투영
```

| 검사 | 내용 |
| --- | --- |
| 인증·fence | 기존 v2 단계 API와 같음 |
| 단계 | 활성 예약이 있고, 그 단계가 `tool="decision_records"`인지 확인 |
| 대상 Run | 예약 입력의 `runs`가 확인된 문맥, 저장된 탐색 결과, 또는 앞선 기록 단계의 `candidates`에 속하는지 확인(`matchesSearchCandidates` 확대) |
| 고정 | 요청에서 처음 읽은 기록을 v1과 같은 `manifest.decisionRecords`에 저장해 요청 단위로 고정한다(§11 결정 5). 같은 요청의 다른 단계·재계획·재시작에서도 같은 기록을 쓴다 |
| 투영 | v1 `reuseEvidence`와 같은 필드만 반환. 작성자·목표·측정값 제외 |

`V2ExecutionRepository.TOOLS`에 `decision_records`를 추가하고, 도구 실행 예산(요청당 12회)에 포함한다. 비교 단계가 기록 단계의 `candidates` 전체를 받을 때도 같은 출처 검사를 적용한다.

### 6.6 답변 근거와 메모 보호

모델(계획·작성·검증)에 가는 입력:

| 항목 | 모델 입력 | 이유 |
| --- | --- | --- |
| Run별 비용 반려 건수 | ✅ `Evidence(field="costRejections", value=N, runRef)` | 답변 문장에 인용 |
| 남은·제외 Run ID | ✅ `Evidence(field="candidates"/"excludedRuns")` | 결과 설명 |
| 적용 기준, 정책 버전 | ✅ | 적용 조건 명시 |
| 메모, 공통 코멘트, 당시 질문 | ❌ | 메모 비전송 원칙 |
| 사유 분류(`reason`) | ❌ | 메모 내용을 간접 노출할 수 있음 |

- `collect_evidence`는 `toolResult`를 건너뛰므로 메모는 기본적으로 빠진다. 기록 단계 전용 근거 함수를 추가해 위 표의 값만 만든다.
- 회귀 테스트는 고유 문자열을 메모에 넣고 계획·작성·검증 payload와 trace 어디에도 나오지 않음을 확인한다. 트레이스 마스킹(`note`, `comment` 등)은 v1 PR의 `_scrub`를 그대로 쓴다.
- 메모 원문은 화면의 기록 카드에서만 사용자에게 보인다(v1과 같음).

### 6.7 공개 결과

`AgentPublicResultProjection.tool`에 `decision_records`를 추가한다. 검증은 v1 `AnswerV2Validator`의 기록 검사를 재사용하고, 공개 필드는 v1 결과 계약과 같다. 프론트의 v2 결과 화면은 단계 카드 목록에 v1 UI PR의 기록 카드를 재사용한다.

## 7. 계획 지침 추가안

`PLAN_INSTRUCTIONS`에 다음 내용을 추가한다. 문구는 v2 담당자와 맞춘다.

```
과거 판단 기록 확인과 비용 반려 제외는 decision_records 단계로 계획한다.
action은 기록 보기면 view, 후보에서 빼라는 요청이면 exclude다.
제외 대상은 앞 검색·조회의 candidates(candidate_group) 또는 확인된 선택을 runs로 연결한다.
제외 뒤 비교·선택은 decision_records 단계의 candidates를 읽는다. 검색 결과를 직접 읽지 않는다.
기준 건수는 원문에 'N건 이상'이 있을 때만 threshold 리터럴로 인용한다. 없으면 null이다.
수치 조건은 reverse_search에 두고 decision_records에는 넣지 않는다.
메모 내용으로 판단하지 않는다. 사유 판정은 코드가 한다.
```

## 8. v1과의 차이

| 항목 | v1 | v2 | 이유 |
| --- | --- | --- | --- |
| 제외 시점 | 탐색 전 `source` 필터 | 탐색 뒤 기록 단계 | 단계 결과 연결. 공통 순위는 같음(§5.1) |
| 중간 탐색 카드 | 없음 | 제외 전 결과 표시(접힘) | v2 설계 D10-O |
| 안내문 | 답변 상태 `NOTICE` | 단계 실패 + 답변 문구 | v2 구조 |
| 다른 도구로 보낸 제외 요청 | 도구 보정(`record-guard`) | 계획 누락 검사 + 재계획 | v2 구조 |
| 기준 확인 | `decision_threshold` | 같은 형식, 실행 중 대기 | 동일 UX |
| 복합 질문 | 미지원 | 탐색·제외·선택·비교 연결 | 이번 목적 |
| 결과 문구 | 고정 문구 | 모델이 작성, 수치는 코드가 채움 | v2 답변 방식 |

## 9. 복구와 정합성

- 기록은 요청 단위로 고정해 재시작·재계획 뒤에도 같은 결과를 낸다.
- 재계획으로 기록 단계 입력이 바뀌면 v2의 기존 무효화 규칙으로 그 단계와 이후 단계를 다시 실행한다.
- 답변 inventory에는 제외된 Run도 포함한다.
- 도구 목록과 계획 지침이 바뀌므로 배포 시 진행 중인 v2 요청은 기존 버전 불일치 정책을 따른다.

## 11. 팀 결정 사항

v2 담당자와 확인하려던 질문을 2026-11-08 팀에서 다음과 같이 정했다.

| # | 질문 | 결정 |
| --- | --- | --- |
| 1 | 기록 처리를 v2에 넣는 방식 | **독립 단계 `decision_records`**(§5.1 B). 탐색 단계 옵션으로 넣지 않는다 |
| 2 | 기준 건수를 정하는 주체 | **코드가 원문에서 결정**(§5.2). 모델이 쓴 값은 대조만 하므로 "리터럴은 원문 인용" 원칙과 충돌하지 않는다 |
| 3 | 안내문일 때 `executionStatus` | **`PARTIAL`**(§5.3) |
| 4 | 기준 건수 확인 대기 | `wait_for_input`에 **`decision_threshold` 종류를 추가**하고 형식은 v1과 같게 한다(§6.4) |
| 5 | 요청 단위 기록 고정 위치 | **`manifest.decisionRecords`**(§6.5). v1과 같은 저장 위치를 쓰고 v2 전용 저장소는 만들지 않는다 |

## 13. 알려진 한계

- 한 질문에서 기준 건수는 하나다. "A 후보는 1건, B 후보는 2건 기준으로"처럼 단계마다 다른 기준은 지원하지 않는다.
- 제외 되돌리기는 v1 UI PR의 방식을 확정한 뒤 v2에 적용한다.
- 사유 판별의 한계(정규식 표현 범위, `N건 이상`만 기준으로 인식)는 v1과 같다.
- 실제 모델이 기록 단계를 정확히 계획하는지는 평가(5단계)로 확인하기 전까지 보장하지 않는다.
