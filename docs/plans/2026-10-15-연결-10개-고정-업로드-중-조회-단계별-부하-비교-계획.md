# 연결 10개 고정 — 업로드 중 조회 부하 B/C 비교 계획

**연결 수는 제품 기본값인 10개로 유지하고, 조회 요청만 늘려 지연이 시작되는 구간에서 B와 C를 비교한다.**
모든 부하를 여러 번 반복하지 않는다. 먼저 B로 짧게 탐색하고, 지연이 시작된 단계와 바로 아래 단계만 새로 반복 측정한다.
이번 문서는 후속 테스트 계획이며 아직 실행 결과가 아니다.

## 1. 목적과 선행 결과

[선행 실험](../verification/2026-10-15-업로드-중-조회-대기와-응답-성능-비교.md)에서 연결 10개·초당 5건의 조회는 연결 대기가 관측되지 않았다. B→C의 연결 점유는 약 88% 감소했지만 조회 평균은 3.192→3.291ms로 빨라지지 않았다.
이번에는 **기본 풀에서도 조회가 많아지면 B의 긴 연결 점유가 대기를 유발하는지, C가 이를 완화하는지** 확인한다. CPU·파일 I/O·부하 발생기가 먼저 한계에 도달할 가능성도 검증한다.

확인할 질문은 세 가지다.

- 어느 요청량부터 조회 응답 또는 DB 연결 획득이 느려지는가?
- 같은 요청량에서 C의 조회 평균·p95·연결 획득 시간은 B보다 줄어드는가?
- 조회를 빠르게 하는 대신 150 Run 업로드 완료가 느려지는 등 상충 효과가 있는가?

고부하는 가정한 상황이다. 운영 트래픽이나 서비스 전체 처리 한계로 일반화하지 않으며, 차이가 없다는 결과도 그대로 보고한다.

## 2. 고정 조건

| 항목 | 적용 조건 |
| --- | --- |
| 비교군 B | 연속 처리 적용, 파일 파싱도 DB 연결을 보유한 트랜잭션 안에서 수행 |
| 비교군 C | 동일한 연속 처리, 준비·게시만 트랜잭션으로 처리하고 파일 읽기·파싱 중 연결 반환 |
| 서버 DB 풀 | `maximum-pool-size=10`, `minimum-idle=10`, 연결 획득 제한 3초. 시작 시 실제 설정과 풀 상태 검증 |
| 업로드 처리 | worker 1개, drain 32, idle 500ms, 완료 상태 폴링 1초로 고정 |
| 업로드 입력 | 기존 인공 150 Run·2,175파일·1,545,005,295바이트 재사용 |
| 초기 상태 | 각 배치마다 전용 DB·보관소를 seed 3건으로 복원. 업로드는 **147건 신규 + 3건 갱신**, 완료 시 current Run 150개·버전 153개 |
| 조회 대상 | seed의 불변 버전 3개를 같은 비율로 순환하는 `GET /api/run-versions/{id}`. 응답 SHA-256 검증 |
| 실행 환경 | 기존 Java·PostgreSQL·힙·DB CPU/메모리 제한·인덱스·SQL·워밍업 조건 유지. 실행 버전·JAR 해시 기록 |
| 변경하는 변수 | 조회 요청률과 B/C 구현만 변경. LLM·Agent·프론트·추가 캐시·업로드 병렬화 제외 |

제품 설정 위치는 [application.yml](../../backend/src/main/resources/application.yml)이다. 기존 설정은 풀 크기를 명시하지 않아 Hikari 기본값 10을 사용하며, 이번 테스트 프로세스에는 10을 명시해 환경 차이를 막는다. 제품 설정을 변경하거나 풀을 1·2개로 줄이지 않는다.
보존한 B/C 계측 JAR을 선행 보고서의 해시와 대조해 재사용한다. 해시가 다르면 동등한 소스·계측인지 확인하기 전 측정을 시작하지 않는다.

## 3. 짧은 탐색과 집중 비교

### 3.1 B에서만 요청량 탐색

**20 → 50 → 100 → 200 → 400건/초**, 각 단계에서 150 Run 업로드를 1회 수행한다. 먼저 나타난 지연 또는 부하 발생 한계에서 증량을 멈춘다.
기존 초당 5건 결과는 시작점을 정하는 참고이며, 이번 전후 개선율의 기준 데이터로 재사용하지 않는다.

단계마다 새 업로드 배치를 사용한다. 하나의 업로드 도중 요청률을 올리면 낮은 부하는 접수 단계, 높은 부하는 파싱 단계와 겹칠 수 있으므로 사용하지 않는다.

다음 기준은 **탐색 중단용 기준**이며 제품 SLO나 성능 목표가 아니다.

| 관측 | 다음 행동 |
| --- | --- |
| 업로드 worker 구간의 조회 연결 획득 p95 ≥ 5ms이며, 같은 구간에서 Hikari pending > 0을 100ms 표본 3개 이상에서 관측 | DB 연결 경쟁 후보. 해당 요청률과 바로 아래 요청률을 확정 |
| 조회 HTTP p95 ≥ 50ms 또는 HTTP 오류율 ≥ 1% | 증량 중단. 획득·SQL·CPU·I/O를 함께 보고 연결 경쟁인지 다른 병목인지 구분 |
| 실제 요청 시작률이 목표의 95% 미만이거나 `dropped_iterations` 발생 | 증량 중단. VU 부족·k6 자원 부족·서버 지연에 따른 VU 점유를 구분. 이를 곧바로 DB 한계로 해석하지 않음 |
| 400건/초까지 위 현상 없음 | 탐색 종료. 400건/초 한 단계만 B/C 비교하며 상한을 자동으로 늘리지 않음 |

20건/초부터 지연이 나타나면 아래 비교 단계는 5건/초로 잡아 **새로 측정**한다.
발행 누락이 발생한 요청률은 목표 부하를 달성한 결과로 사용하지 않는다. 추가 증량 없이 마지막 정상 발행 단계만 비교하고, 누락 단계는 한계 진단으로 별도 표시한다.

### 3.2 선택한 최대 두 단계만 B/C 비교

- 탐색 종료 후 **C 결과를 보기 전에** 비교 요청률과 선정 이유를 파일로 확정한다.
- 선택한 요청률마다 **B 3회 + C 3회**를 새로 측정한다. 탐색 수치를 본 비교에 섞지 않는다.
- 실행 순서는 B 1차 → C 1·2·3차 → B 2·3차로 구성해 서버 재기동을 줄이면서 B를 C 앞뒤에 배치한다. 두 요청률의 순서도 반복마다 바꾼다.
- JVM 시작마다 동일한 150 Run 워밍업 1회 후 seed를 복원한다. 탐색에 사용한 첫 B JVM은 본 측정 1차까지 재사용한다.
- 선택한 최고 요청률에서 B/C 각각 조회만 30초씩 1회 측정한다. 이는 업로드가 없을 때도 느린지 확인하는 진단용이며, 반복 비교의 개선율에 섞지 않는다.

최대 구성은 **탐색 5배치 + 본 비교 12배치 + JVM 워밍업 3배치 = 업로드 20배치**, 조회만 진단 2회다. 두 번째 비교 단계가 불필요하거나 한계가 빨리 나타나면 더 줄어든다. 선행 110배치 실험을 다시 실행하지 않는다.

### 3.3 시간 제한

한 배치는 조회 부하 60초, 부하 시작 5초 후 업로드, 요청 종료 대기 최대 10초로 제한한다. 업로드가 부하 시작 후 55초까지 끝나지 않으면 `완료 시간 ≥ 관측 시간`으로 기록하고, 시간을 늘려서 계속 기다리지 않는다.
중단 시에는 해당 테스트의 부하 발생기와 서버를 종료한 뒤 전용 DB·보관소를 복원한다. 정리가 끝나기 전 다음 배치를 시작하지 않는다.

**측정 환경 준비 후 워밍업·복원·재기동을 포함해 약 20~30분을 목표**로 한다. 25분이 지나면 새 배치를 시작하지 않고, 30분에는 진행 중 측정을 종료하고 정리한다. 도구 수정·빌드 시간은 이 측정 예산과 구분해 알린다. 시간 때문에 못 한 반복은 미실행으로 표시하며, 자동으로 추가 실험을 붙이지 않는다.

## 4. 부하 도구와 측정 지표

k6의 `constant-arrival-rate`로 응답이 느려져도 정해진 요청률로 요청을 시작한다. 요청률은 동시 사용자 수와 다르며, 한 반복에서 HTTP 조회를 1회 수행한다. [k6 공식 설명](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-arrival-rate/)

VU는 선행 실험과 같은 60개를 사전 할당하고 최대치도 60으로 고정한다. 이는 k6의 요청 실행 슬롯이며 DB 연결 수 10개와 별개다. 이번 상한인 400건/초에서 평균 요청 시간이 150ms이면 약 60개 슬롯이 필요하므로, 정상 응답부터 초기 지연 구간을 탐색하는 데 여유를 두되 부하 발생기 메모리를 과도하게 늘리지 않는다. 실제 반복에는 해시 계산 등도 포함되므로 시작률·VU 사용량·누락을 함께 확인하고 측정 중 자동 증설하지 않는다. [VU 할당 원리](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/arrival-rate-vu-allocation/)

| 측정 대상 | 도구·지표 | 해석 |
| --- | --- | --- |
| 조회 체감 시간 | k6 요청별 HTTP 평균·p50·p95·최대, 오류율, 실제 시작/완료 건수 | 연결 획득만이 아닌 전체 HTTP 경로 비교 |
| DB 연결 획득 | 기존 JDBC 계측의 `DataSource.getConnection()` 평균·p95·실패 | 연결 검증 비용도 포함하며 순수 대기 시간과 같다고 표현하지 않음 |
| 풀 경쟁 | Hikari MXBean 100ms 간격 active·idle·pending, pending 관측 비율·최대 | DB 연결을 추가로 빌리지 않고 수집. 짧은 대기는 표본에서 빠질 수 있음 |
| DB 실행 | 조회 SQL 횟수·실행 시간, `pg_stat_activity` 대기 종류 | 연결 대기와 느린 SQL·잠금 대기를 구분 |
| 업로드 영향 | 클라이언트 완료, 서버 마지막 job commit, 대기·복사·파싱·DB 저장, 연결 점유 합계 | 조회 개선과 업로드 지연을 따로 보고 |
| 다른 자원 병목 | Java와 **k6** CPU·RSS, DB 컨테이너 CPU·메모리·I/O, 호스트 메모리 압박 | 이전에 빠진 k6 자원도 측정. 단일 코어 사용률과 호스트 전체 사용률을 구분 |

핵심 집계는 **업로드 서버 진입부터 마지막 job terminal commit 사이에 시작된 조회**이며, 해당 요청은 업로드 종료 뒤 완료돼도 포함한다. 접수·worker·파싱과 겹친 조회도 나눠 본다. 파싱 그룹은 worker의 부분집합이다.
요청 ID로 클라이언트·서버 계측을 연결하며, 오류 요청과 발행 누락도 전체 분모에 별도로 표시한다. 완료되지 않은 업로드는 정상 완료 평균에서 제외하되 실패·중단 건수와 관측 하한을 반드시 함께 제시한다.

## 5. 실행 전에 보완할 측정 코드

제품 로직은 변경하지 않는다. 기존 측정 도구의 고정값과 집계만 확장한다.

- [upload_query_load.js](../../scripts/performance/upload_query_load.js): 현재 고정된 `rate=5`를 입력값으로 받도록 하고 양의 정수·400건/초 상한을 검증한다. VU는 60으로 유지한다. 단계별 실제 발행 수·누락·오류를 보존한다.
- [upload_query_benchmark.py](../../scripts/performance/upload_query_benchmark.py): 요청률·VU·탐색/본 측정·반복 번호를 메타데이터와 배치 이름에 포함한다. 현재 600초 업로드 대기·고정 요청률 메타데이터·조회 단독 60초를 이번 시간 제한에 맞게 매개변수화한다. k6 PID 자원 수집과 중단 후 정리를 추가한다.
- [analyze_upload_query_benchmark.py](../../scripts/performance/analyze_upload_query_benchmark.py): 요청률·단계별로 집계한다. 부하 때문에 생긴 HTTP 오류·중단·발행 누락을 계측 실패와 구분하고, 성공 요청만 골라 전체가 빨라진 것처럼 계산하지 않는다.
- 작은 실행 제어 스크립트로 단계 선정·최대 배치 수·전체 시간 제한을 적용한다. 실행 계획을 먼저 저장하고 B/C 결과에 따라 유리한 단계로 바꾸지 않는다.

기존 [실행 도구 테스트](../../scripts/performance/test_upload_query_benchmark.py)와 [집계 테스트](../../scripts/performance/test_analyze_upload_query_benchmark.py)에 요청률별 출력 충돌 방지, 단계 선정, 시간 종료, 관측 중단, 오류 포함 집계를 검증한다. 실행 전 해당 Python unittest와 k6 옵션 로딩만 확인하고 제품 전체 테스트를 불필요하게 반복하지 않는다.

고부하에서는 응답 해시 계산·요청별 로그·서버 계측 자체도 비용이 된다. 동일 계측을 B/C에 적용하되, 로그 저장이나 k6 자원이 병목이면 그 한계를 기록하고 이번 결과로 제품 최대 처리량을 주장하지 않는다. 계측 on/off 대규모 재실험은 이번 짧은 범위에 추가하지 않는다.

## 6. 결과 판정과 산출물

각 요청률에서 배치별 평균·p95를 구하고 **B/C 3회 각각의 값, 평균, 범위, 대응 반복의 차이**를 제시한다. 서로 다른 요청률을 합쳐 하나의 개선율로 만들지 않는다. 감소율은 `(B−C)/B × 100`이며 음수는 악화로 표시한다.
3회는 짧은 확인 실험이다. 작은 차이를 유의한 개선이라고 단정하거나 수천 개 HTTP 요청을 독립 반복 수로 간주하지 않는다. 탐색만 지연이 있었고 본 비교에서 재현되지 않으면 재현되지 않았다고 적는다.

보고서에는 다음을 남긴다.

1. 요청률별 B/C 조회 평균·배치 p95, 연결 획득 평균·p95, pending, 실제 처리량·오류·발행 누락 표.
2. 같은 요청률에서의 150 Run 완료 시간과 단계별 시간, DB 연결 점유 합계. 조회 이득과 업로드 손해를 분리한 결론.

원시 계측·인공 입력·DB는 Git에서 제외한 `.local/performance/` 아래에 두고, 문서와 합성 실행 시간 집계만 저장소에 기록한다. 기존 보고서는 유지하고 `docs/verification/`에 이번 후속 결과를 별도로 작성한다.
