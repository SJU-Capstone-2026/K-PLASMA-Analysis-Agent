# LocalLLM_v2.2 선행 출력 조건 개선 Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans. 아래 승인된 범위를 직접 구현하고 마지막에 전체 변경을 한 번 검토한다.

**Goal:** 로컬 계획의 모호한 `requires`를 `required_prior_outputs`로 바꾸고 의미·선행 관계를 지시서와 스키마에 설명한다.

**Architecture:** 로컬 PlanDraft의 새 표준 필드명을 변경하고 Pydantic AliasChoices로 과거 `requires` 입력을 읽는다. 새 출력·재계획·d1 문맥은 새 이름을 사용한다. 기존 그래프 노드·간선·실행 규칙·최종 응답과 과거 DB 기록은 유지한다.

**Tech Stack:** 기존 Python/Pydantic/LangGraph와 native submit_plan, 기존 Java 계획 journal. 새 의존성 없음.

**Spec:** 사용자의 2026-11-14 지시: “1번부터 개선”, “지시서랑 필드명 좀 더 직관적이게”, 캐시는 별도 지시 전 제외. 앞선 대화에서 합의한 필드명과 설명 보강 범위를 따른다.

## Global Constraints

- 이번 구현은1번만 수행한다. 캐시·모델·생각 예산·메모리 기준·batch·입력 한도·공통 서버 배포는 변경하지 않는다.
- 원본 보호 대상 그래프와 초기 복제 증거를 수정하지 않는다. 로컬 그래프의 알고리즘과 최종 답변 schema를 유지한다.
- 과거 `requires` 계획은 호환 읽기만 제공한다. 기존 DB·대화·답변·계획을 일괄 수정하지 않는다.
- 두 이름을 동시에 넣은 모호한 입력은 거부한다. 자기 참조·미래/비선행 참조·존재하지 않는 출력·단위/개수 검사는 유지한다.
- 기존 enum·추가 필드 거부·정확한 원문 조건·최대 재계획2회·d1 검토를 유지한다.
- 소프트웨어 검증과 실제 모델 품질 검증을 구분한다. 준비 실패를 우회하거나 실제 질문을 반복해 성공으로 바꾸지 않는다.
- commit/tag/push는 별도 요청 전 수행하지 않는다. 기준 커밋은 LocalLLM_v2.1의 `7803b29`다.

## Review Focus

1. 기존 저장 계획을 읽어 새 이름으로 직렬화해도 입력 원본과 기존 DB 행은 바뀌지 않아야 한다.
2. 새 이름이 최초 계획뿐 아니라 rejected/previous plan·d1 검토 경로·오류 경로에서도 일치해야 한다.
3. 이름 변경이 잘못된 자기 참조를 코드로 지워 통과시키는 수리가 되어서는 안 된다.
4. 도구 schema와 입력 계수는 같은 실제 요청을 사용하고 enum·nullable·strict 제약을 유지해야 한다.
5. 필드 설명 추가가 최종 답변·writer 지침·검토 선택지·원본 그래프를 바꾸지 않아야 한다.

## 실행 판단

Ruling: 이번 대화의 필드명·설명 보강 논의와 사용자의 실행 지시를 승인된 spec으로 사용한다. 추가 승인 대기로 멈추지 않는다.
Ruling: 별도 변환용 계획 모델을 추가하는 대신 Pydantic의 alias 읽기 기능을 사용한다. 새 계획은 새 이름으로 일관되게 저장하고 과거 DB는 변경하지 않는다.
Ruling: 계획 schema의 의미와 backend 버전2 보존 API는 유지한다. 로컬 계획 문서를 별도로 내보내고 native 프로토콜 식별자로 새 계약을 구분한다.
