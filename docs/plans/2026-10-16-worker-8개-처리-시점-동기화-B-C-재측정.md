# worker 8개 처리 시점에 맞춘 업로드 B/C 비교 — 2026-10-16

## 요청과 단일 변경
업로드 후 고정 5초 대신 B/C 각각 worker 8개가 파일 처리 중일 때 조회 100개를 발송한다. 기존 B/C JAR, 데이터, DB 풀, 관리자 수, k6, JVM·DB 설정과 서버 예열/재사용 순서는 유지한다. 제품 worker를 정지·지연하거나 DB 연결을 인위적으로 점유하지 않는다.

## 고정 조건
- pool max/minIdle10, 관리자·worker8, 전체150 Run/2175파일/1,545,005,295바이트, 기존 동일 원본·partition·seed·조회 대상3개.
- 동일 B.jar/C.jar와 k6 v2.3.0 사용. 첫 조회 묶음(cohort0), 5초 뒤 묶음(cohort1), 첫 묶음+5초 업로드 시작을 유지한다.
- cohort2의 발송만 worker 처리 신호로 전환한다. cohort3 이후는 해당 발송 시각+5초 주기로 이동한다. 조회 목표는 원본처럼 iteration 순서로 배분한다.
- B1,C1,C2,B2,B3,C3 총6시행. B1/C1/B2/C3은 새 JVM+같은8 Run 예열, C2/B3은 직전 서버 재사용. 기존 정책을 그대로 유지하므로 각 군 fresh2/reuse1이나 개별2·3회차의 재시작 상태 차이는 제한으로 공개한다.
- Python이 기존 timing 로그를1ms 간격으로 증분 읽는다. job.claimed~job 사이를 활성 job으로 계산하고, source.load 이후 parse.graph 완료 전인 job이8개일 때 신호를 낸다. 100 VU는 제품 밖 로컬 HTTP 신호 서버에서 대기하며 같은 신호를 받은 뒤 원래 GET을 보낸다. gate 요청은 조회 응답 시간에 포함하지 않는다.
- 로그는 버퍼링되므로 신호가 충분조건이라고 가정하지 않는다. 사후 실제 Java job/parse 구간과 요청 시작을 대조한다. 제품 계측 코드와 로그 flush 정책은 변경하지 않는다.

## 판정·집계
- 대표표는 각 시행 cohort2 전체100건의 평균을 구해 B/C 각3회 평균을 계산한다. HTTP, 연결 획득, 업로드 누적 점유, 업로드 완료 시간을 분리한다.
- 처리 단계 일치 여부는 양쪽 첫 조회의 서버 진입 시 활성 job8개인지로 판정한다. 100개 각각의 활성 job·파싱 개수와8개였던 비율·최소/평균을 함께 공개한다. worker가 작업 사이를 전환하더라도 개별 요청을 골라 제외하지 않는다.
- 요청 수100·응답해시·조회 대상별 건수, 요청 발송 폭, gate→HTTP 지연, 서버 진입 폭, 시계 변동을 확인한다. 발송 폭25ms 초과 또는 쌍간 차10ms 초과면 동시 부하 불일치로 분리한다. 지연값이 크거나 개선이 없다는 이유로 제외하지 않는다.
- 오류/단계 불일치는 원자료를 남기고 분리하며 예정6회를 넘어 유리한 결과가 나올 때까지 반복하지 않는다. gate가55초 안에 열리지 않으면 시행 실패다.
- 동일150 Run/153버전, pool10/worker8 상한, 과거 버전 payload, B/C JAR해시 확인. 전용 테스트 DB만 사용하고 종료 후 seed 복원·서비스 종료한다.

## 측정 도구 사전 시행 기록
첫 B 시행은 HTTP 신호를100개 스레드로 전달해 발송 폭44ms가 발생했고, 소수점 예약 시각보다 일찍 깬 VU가 다음 묶음을 누락하는 문제가 확인됐다. 해당 experiment/ 원자료는 보존하고 성능 비교에서 제외한다. 비동기 단일 이벤트 루프로 신호를 전달하고 예약 시각까지 기다리도록 수정했다. 제품 JAR/DB는 바꾸지 않았다. 최종 비교는 measured/ 아래 사전 순서6시행 전체를 새로 실행하며 결과에 유불리한 추가 반복은 하지 않는다.

## 공통 발송 시각 보완 — 최종 비교 전 확정
비동기 신호 전달로 처리 단계8개는 확인했지만 첫 쌍의 실제 HTTP 호출 폭이 B2ms/C17ms여서 사전 쌍간차10ms 기준을 벗어났다. measured/6시행은 변경 없이 완료·보존하며 조건 불일치 기록으로 따로 보고한다. 신호 응답에 공통 dispatchEpochMs(감지 시각을 밀리초로 올림+100ms)를 넣어 모든 VU가 같은 정수 밀리초에 발송하도록 한다.100ms는 클라이언트 출발 준비 시간이며 제품 worker/DB를 멈추거나 지연시키지 않는다. 실제 발송·서버 진입 때에도 worker8개가 처리 중이었는지 사후 검증한다.
최종 synchronized/6시행은 동일 B1,C1,C2,B2,B3,C3 및 기존 나머지 조건으로 한 번만 진행한다. 동시 발송 판정은 이전 원본 수준인 각 묶음 호출 폭5ms 이하·B/C 폭 차3ms 이하로 강화한다. 측정 결과가 좋지 않더라도 보존하며 이 이후 성능값을 이유로 재시행하지 않는다. 이전 단계 감지 시행과 이 최종 시행의 평균은 합치지 않는다.

## 측정 후 집계 기준 확정

사용자와 결과를 검토해 최종 `synchronized/`의 B/C **1·2·3회차 전체를 유효 표본으로 포함**한다. 6시행 모두 worker 8개가 파일을 처리하는 신호를 확인했고, 100건 발송 폭은 2~9ms였다. 앞서 강화한 정확히 8개·5ms·쌍간 3ms 기준은 작업 교대와 짧은 발송 편차를 지나치게 엄격하게 구분하므로 제외 기준에서 해제하고 진단 이력으로 보존한다. 이는 측정 후의 집계 판단 변경이며 최초 계획·원자료·진단 결과를 소급 수정하지 않는다.

대표값은 각 시행의 처리 중 첫 100건 평균을 구한 뒤 3회 평균으로 집계한다. 같은 시행의 전체 업로드 완료·연결 누적 점유도 함께 비교한다. 최종 보고서와 PR·folio는 이 전체 3쌍의 수치로 통일한다.
