# 동시 사용자 조회와 업로드 트랜잭션 B/C 비교

## 목적과 확정 조건

사용자 요청에 따라 DB 연결 10개를 유지하고, 150개 실험 업로드 도중 가상 사용자 1 / 10 / 20 / 50 / 100명이 **5초마다 함께 조회**하는 상황에서 B/C를 비교한다. 조회만 실행하는 기준 실험은 사용자 요청으로 제외한다.

B는 파싱 중에도 트랜잭션과 연결을 유지한다. C는 준비·게시 구간만 트랜잭션으로 묶고 파싱 중 연결을 반환한다. 단일 업로드 배치와 작업자 1개를 유지한다. 여러 사용자의 동시 업로드나 파싱 병렬화는 이번 범위가 아니다.

실제 이용 로그로 정한 트래픽이 아닌, 다수가 함께 새로고침하는 가정이다. 실험 중 개선 유무에 따라 요청량·간격을 바꾸지 않는다. 이전 400건/초 실험과 요청 분포가 다르므로 개선율의 기준으로 섞지 않는다.

| VU | 5초마다 발생하는 조회 | 장기 평균 목표 조회량 |
| ---: | ---: | ---: |
| 1 | 1건 | 0.2건/초 |
| 10 | 10건 | 2건/초 |
| 20 | 20건 | 4건/초 |
| 50 | 50건 | 10건/초 |
| 100 | 100건 | 20건/초 |

VU는 계정 생성 수나 항상 실행 중인 SQL 수가 아니다. k6의 `constant-vus`로 고정 VU를 실행하고, 시나리오 시작 시각 기준 0 / 5 / 10초 등 공통 시각에 조회한다. 운영체제 스케줄링으로 완전히 같은 순간에 도착하지 않을 수 있어 각 묶음의 실제 요청 시작 시각 편차, 동시 HTTP·서버 조회 개수를 기록한다. 응답이 느리면 과거 요청을 몰아서 따라잡지 않고 지난 구간을 건너뛴다. 실제 처리량·누락된 예정 조회 수를 보고한다.

## 실행과 시간 제한

- 같은 인공 150 Run·2,175파일·1,545,005,295바이트, seed 불변 버전 3개, 기존 B/C JAR과 해시·인덱스·SQL을 재사용한다.
- 각 배치 seed 복원 후 147건 신규·3건 갱신. 모든 원본 응답 해시와 업로드 후 150 READY·전체 golden parity를 검증한다.
- 조회는 기존 `GET /api/run-versions/{id}`이며 3개 seed 버전을 순환한다. 한 VU의 1회 행동은 HTTP GET 한 번이다. 실제 브라우저 렌더링·로그인·사용자별 워크스페이스·LLM은 포함하지 않는다.
- Hikari 최대/최소 유휴 연결 10, 업로드 worker 1, drain 32, idle 500ms, 완료 폴링 1초 고정. 실제 풀 설정을 각 배치에서 검사한다.
- 각 VU 단계 B/C 각각 **2회**, 총 비교 20회. 순서는 B1 오름차순 → C1 오름차순 → C2 내림차순 → B2 내림차순. JVM 시작마다 업로드 워밍업 1회씩 총 3회 추가한다.
- 한 배치 조회 50초, 부하 시작 5초 뒤 업로드. 업로드 관측 제한 40초, 조회 종료 유예 10초. 시간 초과·실패는 원시 결과와 관측 하한을 남기고 정상 평균에서 숨기지 않는다.
- 측정 약 20~25분을 목표로 하며 25분부터 새 배치를 시작하지 않고 30분에 종료한다. 테스트 도구 준비·문서 작성 시간은 별도다. 미실행 단계는 명시하고 자동 추가 반복하지 않는다.
- 전용 로컬 DB만 사용한다. 종료 시 테스트 Java와 부하 프로세스를 종료하고 seed를 복구한다. 제품 DB와 실제 실험 데이터는 사용하지 않는다.

## 지표·도구·판정

| 대상 | 도구와 지표 |
| --- | --- |
| VU와 요청 | k6 constant-vus, 공통 5초 스케줄, 요청별 시작·종료·VU·묶음 번호·HTTP 시간·상태·해시 |
| 연결 경쟁 | 기존 JDBC 계측 `getConnection()` 시간·획득 실패, Hikari MXBean 100ms 간격 active/idle/pending |
| DB·서버 처리 | 조회 JDBC 실행·연결 점유 시간, PostgreSQL pg_stat_statements 및 pg_stat_activity |
| 업로드 | Python HTTP 클라이언트, 서버 단계 계측의 대기·복사·파싱·DB 저장·연결 점유·완료 시간 |
| 다른 병목 | Java/k6 CPU·RSS, Docker DB CPU·메모리·I/O, 메모리 압박 |

집계는 서버 업로드 시작부터 마지막 terminal commit 사이에 시작된 조회를 기준으로 한다. 파싱 도중 시작된 조회도 별도로 비교한다. 연결 획득 시간은 순수 큐 대기만이 아니라 연결을 빌리는 비용을 포함한다. 100ms 표본에 pending이 없더라도 그보다 짧은 대기가 없었다고 단정하지 않는다.

각 VU의 배치별 결과와 두 반복의 평균·범위를 제시한다. VU가 작은 단계는 조회 표본도 작아 p95와 미세한 차이를 확정적인 성능 개선으로 해석하지 않는다. 수천 개 요청을 독립 반복 수로 부풀리지 않는다.

B에서 연결 획득 지연과 pending이 생기고 C에서 줄어드는지 확인한다. HTTP 시간·업로드 시간의 악화도 함께 제시한다. 조회만 하는 대조군이 없으므로 조회 자체 한계와 업로드의 추가 영향을 완전히 분리했다고 주장하지 않는다. 개선이 없어도 완료된 결과로 기록한다.

## 실행 결과

확정 조건의 B/C 비교 20회와 워밍업 3회를 완료했다. 조회 7,240건의 상태·해시 검증을 통과했으며, 수치·반복 편차와 한계는 [결과 보고서](../verification/2026-10-15-동시-사용자-조회와-업로드-트랜잭션-비교.md)에 기록했다. 아래 여러 관리자·worker 범위는 미실행이다.

## 후속 검토 — 여러 관리자의 업로드와 서버 병렬 처리

2026-10-15 사용자 합의: 이번 단일 관리자·worker 1개 실험 이후, **관리자 수와 업로드 작업자 수를 함께 1 → 2 → 4 → 8로 늘리는 조건**을 검토한다. DB 풀은 모든 단계에서 10개로 유지한다. 아직 구현하거나 측정한 범위가 아니다.

| 단계 | 업로드 관리자 역할의 클라이언트 | 서버 업로드 worker | DB 풀 |
| --- | ---: | ---: | ---: |
| 기준 | 1 | 1 | 10 |
| 2 | 2 | 2 | 10 |
| 3 | 4 | 4 | 10 |
| 4 | 8 | 8 | 10 |

- 관리자 수는 업로드를 보내는 클라이언트 수, worker 수는 서버가 동시에 처리하는 실험 수다. 관리자를 늘리는 것만으로 현재의 직렬 파싱이 병렬화되지는 않는다. 서버 worker 확장은 후속 구현·검증이 필요한 별도 변경이다.
- 전체 업로드량은 동일한 150 Run으로 고정하고 관리자들에게 중복되지 않게 분할한다. 개별 파일 크기 차이도 고려해 바이트·파싱 비용이 가능한 한 균등하도록 배분한다. 사람마다 150개씩 늘려 총 작업량이 달라지는 비교와 구분한다.
- 각 단계 안에서 관리자·worker·조회 VU·5초 조회 간격·입력·DB 연결 수를 고정하고 B/C만 비교한다. 단계 간 차이는 관리자와 worker가 함께 변한 상황이므로 두 변수 각각의 독립 효과라고 주장하지 않는다.
- 동시 실행에서도 중복 등록·현재 버전 갱신·job claim·실패 처리가 유지되는지 먼저 검증한다. 동일 Run을 동시에 갱신하는 충돌 시나리오는 처리량 실험과 별도다.
- 핵심 지표는 실제 DB 연결 active·idle·pending, 업로드와 조회 각각의 연결 점유 시간·획득 시간, 조회 HTTP 평균·p95·실패, 150 Run 전체 완료 시간이다. 작업자 8개를 연결 점유 8개로 간주하지 않는다.
- CPU·파일 I/O·메모리 병목도 함께 측정한다. 풀 부족이 아닌 자원 경합으로 느려졌다면 구분해 기록한다.
- 조회 VU 전 단계를 관리자 단계마다 전수 반복하지 않는다. 이번 결과를 본 뒤 대표 조회 부하와 반복 수·시간 상한을 별도 계획으로 확정한다.
