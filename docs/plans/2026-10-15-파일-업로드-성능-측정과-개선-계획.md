# 150 Run 파일 업로드 단계별 측정·성능 개선 - Plan

## Goal Capsule

150개 Run의 **업로드 시작부터 등록 완료까지** 걸리는 시간을 대기·파일 처리·파싱·DB 저장으로 구분해 측정하고, 한 가지 변경씩 적용해 개선 효과를 비교한다.
현재는 계획 작성 단계이며 **성능 테스트·제품 코드 변경은 아직 실행하지 않았다.**

- 근거: 사용자의 150개 업로드 단계별 측정 및 개선 전후 비교 요청.
- 우선순위: 기존 수치·원본·중복 등록·버전 갱신 규칙 보존 → 재현 가능한 A 기준선 → 측정된 병목 개선.
- 실행 환경: 격리한 PostgreSQL·저장소에서 실제 HTTP 업로드와 실제 스케줄러·파서·등록 코드를 실행한다.
- 중단 기준: 원본 해시, 수치, 상태, 버전 연결이 달라지면 해당 개선안의 성능 비교를 중단하고 원인을 해결한다.
- 산출물: 계측·인공 데이터 생성기·벤치마크·회귀 테스트·검증 보고서. 실제 데이터의 입력·출력·원시 로그와 개인 folio는 Git에서 제외한다.
- 이번 문서는 계획이다. 구현·테스트 실행·PR 생성은 다음 작업이다.

## Product Contract

### Problem and Current Evidence

대상은 backend/src/main/java/com/kplasma/analysisagent/ingestion/ 및 run/ 패키지다.
조사 기준은 origin/main의 bbe01beb021cf2a12cce2812d0fad1be474ea559다.
실행 직전에 실제 적용 대상 커밋·스키마를 고정하고, 진행 중인 다른 성능 개선을 비교 중간에 섞지 않는다.

| 확인한 구조 | 코드 근거 | 측정할 영향 |
| --- | --- | --- |
| Run 하나 처리 후 기본 500ms 대기, 스케줄러 1개 | ImportWorker.poll, ImportExecutionConfiguration | 연속 작업 사이 빈 시간 |
| multipart 파일을 자체 임시 파일로 쓰고 staging에 재복사·해시 계산 | ImportController.accept, SourceStore.stage/copy | 중복 읽기·쓰기 비용 |
| 보관은 같은 저장소 내 atomic move로 게시 | ImportIntakeService.move | 복사와 구분한 이동 비용 |
| source 잠금 트랜잭션 안에서 파싱·등록 | ImportWorker.process | SQL 시간과 별개인 연결·잠금 점유 |
| 해시·요청 키 기반 중복 방지, 파일 메타데이터 batch insert가 이미 있음 | ImportIntakeService, ImportRepository | 신규·중복·갱신 경로 차이 |
| 작업 시작·완료마다 batch 전체 작업 집계 | ImportWorker.refresh | 집계 SQL 호출·누적 비용 |

기본 설정에서 150개 작업이 계속 대기한다면 작업 사이 fixed delay는 149 × 500ms = 약 74.5초다.
**코드로 계산한 값이며 실측값이 아니다.** 최초 대기·파일 처리·파싱·DB 시간은 별도다.
실행 시 설정 덮어쓰기 여부를 기록한다.

### Requirements

**측정·비교**

- R1. 150개 신규 Run의 클라이언트 전체 완료, 접수 응답, 서버 등록 완료 시간을 구분한다.
- R2. 대기·파일 처리·파싱·DB 저장을 분리하고 중첩 시간을 중복 합산하지 않는다.
- R3. 계측만 추가한 A를 먼저 보존하고 모든 비교군에 동일한 계측을 사용한다.
- R4. 입력 바이트·DB 초기 상태·인덱스·자원을 고정하고 반복 결과·편차·성공/실패·개선율을 함께 보고한다.

**동작 보존**

- R5. 동일 원본은 기존 버전을 재사용하고, 같은 P/S/B의 변경된 원본은 현재 버전 갱신으로 처리한다.
- R6. 실패한 새 결과가 이전 정상 버전을 덮어쓰지 않으며 미게시 원본 정리 정책과 버전·현재 포인터·완료 상태의 DB 원자성을 유지한다.
- R7. 단위·정밀도·Bias-off null/비가용·원본 샘플·수렴 판정·업로드 제한·경로 검증을 유지한다.

**개선**

- R8. backlog가 남은 작업 사이 인위적 대기를 제거하고 빈 큐의 반복 조회는 제한한다.
- R9. 파일 파싱과 DB 게시 트랜잭션을 분리하되 게시 시 source 유효성·중복을 재확인한다.
- R10. 중복 파일 복사 통합은 실제 비용이 확인된 경우 독립 비교군으로 검증한다.

### Scope Boundaries

150개 신규 등록이 핵심이다.
1개 등록·동일 원본 재업로드·같은 조건 갱신·일부 실패도 검증한다.
LLM·Agent 답변·Redis·Kafka·UI 재설계·물리 계산 변경·신규 장애 복구 체계는 포함하지 않는다.
기존 복구·오류 처리는 유지한다.

### Deferred to Follow-Up Work

- 작업자 2개·4개의 제한 병렬화는 B/C 이후에도 파싱·I/O 병목이 남으면 별도 실험한다.
- 동일 Run ID 처리 순서·현재 버전 갱신을 보장하기 전에는 병렬 처리를 기본값으로 켜지 않는다.
- 상태 집계 SQL·등록 batch화는 실제 병목으로 확인되면 별도 비교한다.
- 여러 사용자 동시 업로드·k6 처리량 검증은 단일 150개 등록 기준선 확정 후 진행한다.

## Planning Contract

### Decisions

- KTD1. 현재 PostgreSQL 작업 큐와 API를 유지한다. 처음 올리는 서로 다른 파일은 결과 캐시로 생략할 수 없으므로 큐·I/O를 먼저 측정한다.
- KTD2. A→B→C를 누적 비교하고 A→최종 종합 개선율과 단계별 관측 감소량을 구분한다.
- KTD3. B/C의 작업자는 1개다. 대기 제거에 병렬화 효과를 섞지 않는다.
- KTD4. 재업로드는 별도 시나리오다. 중복 생략 시간을 신규 150개 등록의 개선율로 쓰지 않는다.
- KTD5. DB SQL 시간과 트랜잭션 점유를 구분한다. A의 트랜잭션에는 파싱도 포함된다.
- KTD6. 순·역방향 개선의 projection·검색 인덱스가 있다면 모든 비교군에 동일하게 유지해 등록 쓰기 비용을 통제한다.
- KTD7. 소형 테스트 파일 150개 복제는 harness 검증용이다. 실제 파일 볼륨을 반영한 입력과 구분한다.

### Comparison Groups

이번 A/B/C는 업로드 비교군이며 선행 순·역방향 실험의 A/B/C와 구분한다.

| 비교군 | 변경 | 고정 항목 | 비교 목적 |
| --- | --- | --- | --- |
| A | 기존 방식 + 공통 계측 | 500ms fixed delay, 작업자 1개 | 개선 전 기준선 |
| B | backlog가 남으면 연속 처리 | 파일·파서·트랜잭션·SQL·작업자 수 | A→B 대기 제거 |
| C | 파싱을 게시 트랜잭션 밖으로 이동 | 파일 복사·파서 결과·작업자 수 | B→C 연결·잠금 점유 및 전체 시간 |
| I — 조건부 | C의 중복 임시 복사 통합 | 검증·파서·등록 정책 | C→I 파일 처리 독립 효과 |
| P2/P4 — 후속 | 채택 버전에서 작업자 수만 2/4로 변경 | 큐·파일·DB 구조·동일 Run 순서 정책 | 병렬화 이득과 연결·잠금 대기 |

C가 단일 작업자에서 전체 시간을 줄이지 않을 수도 있다.
연결·트랜잭션 점유 감소를 별도로 평가하고 비용 대비 이득이 없으면 채택을 보류한다.
I도 실측 후 판단하며 검증을 생략해 성능을 얻지 않는다.

### Processing Flow

~~~mermaid
flowchart TD
  A["실제 HTTP 업로드"] --> B["multipart 수신·임시 저장"]
  B --> C["자체 임시 복사·staging·해시"]
  C --> D["원본 게시·중복 확인·작업 DB 저장"]
  D --> E["접수 commit: 작업 실행 가능"]
  E --> F["큐 대기·작업 claim"]
  F --> G["원본 메타데이터·스칼라/그래프 파싱"]
  G --> H["중복 재확인·Run/버전·완료 상태 저장"]
  H --> I["완료 commit"]
  I --> J{"대기 작업 있음"}
  J -->|"A: 500ms 후 / B·C: 연속"| F
  J -->|"없음"| K["빈 큐 대기"]
~~~

C에서는 G의 파일 파싱을 쓰기 트랜잭션 밖에서 수행한다.
H에서 source 및 같은 Run ID를 보호하고 현재 버전·검색 데이터·완료 상태를 함께 commit한다.
I를 적용해도 multipart 계층의 임시 저장까지 제거했다고 표현하지 않는다.

### Measurement Boundaries

| 지표 | 경계·포함 항목 | 해석 |
| --- | --- | --- |
| 클라이언트 접수 | POST 시작 → 202 수신 | 전송·multipart·검증·접수 저장·응답 포함 |
| 클라이언트 전체 | POST 시작 → 전체 150개 terminal 관측 | 사용자 대기, polling 지연 포함 |
| 서버 전체 | 요청 진입 → 마지막 terminal commit | 클라이언트 전송 이전 시간·최종 polling 제외 |
| 큐 대기 | 작업 실행 가능 commit → 해당 작업 claim | 앞선 작업 처리 대기도 포함 |
| 작업 사이 빈 시간 | 직전 처리 종료 → 다음 claim 시도/시작 | backlog가 유지된 구간의 휴식·scheduler 지연 |
| 파일 처리 | controller 복사, staging 복사·해시, ZIP 검사·해제, atomic move 각각 | 읽기/쓰기 바이트·이동 건수 병기 |
| 파싱·계산 | 스칼라 / 그래프 파서 각각 진입 → 반환 | 내부 파일 읽기·단위 변환·검증·샘플 계산 포함 |
| DB 처리 | JDBC 실행 횟수·소요 시간, 연결 획득 대기, commit 호출 시간 | JDBC에는 DB 잠금·왕복 포함, 엔진 실행 시간과 구분 |
| 트랜잭션 점유 | 시작 → commit/rollback 완료 | A는 파싱 포함, 다른 지표와 중첩 |
| 기타 | 입력 발견·JSON 구성·상태 집계·응답 구성 등 | 설명 안 된 잔여 시간을 DB에 귀속하지 않음 |

- 접수 commit 전후와 after-commit 관측을 기록한다. DB job 생성 시각은 commit 전일 수 있어 큐 대기 시작으로 그대로 사용하지 않는다. commit 직후 다른 스레드가 먼저 claim한 경계 표본은 관측 오차 범위를 표시하고 음수를 임의로 0으로 바꾸지 않는다.
- 202 전달 전에 작업자가 실행될 수 있다. 접수 시간과 후처리 시간을 단순히 더하지 않고 실제 이벤트 구간으로 전체를 산출한다.
- 서버는 단조 시계를 사용한다. 클라이언트·서버 시계를 직접 빼지 않고 batch/job 식별자로 연결한다.
- Run별 큐 대기 합계는 전체 대기가 아니다. 각 Run이 앞선 처리 시간을 함께 기다려 중복되기 때문이다.
- 상위 구간과 내부 SQL·파일 구간은 별도로 저장하고 전체 시간에는 겹치지 않는 구간만 합산한다.
- 복사와 해시는 같은 loop이므로 기본 지표는 복사+해시다. 버퍼·행마다 타이머·로그를 추가하지 않는다.
- 로그는 비교군·batch/job·구간·바이트·행 수·SQL 종류별 횟수를 기록한다. 업로드 업무 SQL·빈 큐 polling·상태 확인용 읽기 SQL은 별도로 센다. 실제 원본 본문·비밀값·경로는 공개하지 않는다.

## Test Design

### Inputs

1. 소형 인공 1개·150개로 테스트와 harness부터 검증한다.
2. 성능용 인공 150개는 실제 원본의 파일 수·크기·행 수·격자 분포를 로컬에서 조사해 생성한다. 원본 물리 수치는 복제하지 않고 seed·생성기 버전·데이터셋 해시를 고정한다.
3. 실제 150개는 접근 가능한 기존 원본을 읽기 전용으로 복사해 별도 DB·저장소에서 A/최종을 비교한다. 입력·출력·상세 로그·folio는 비공개 로컬에만 보관한다.

지원 조합은 Pressure [2,4,6,8,10] × Source [100,200,300,400,500] × Bias [0,200,400,600,800,1000] = 150개다.
폴더명만 바꾼 동일 조건 150개를 만들지 않는다.
INI·solver·폴더 조건을 맞추고 Bias-off 25개·Bias-on 125개의 파일·비가용 규칙을 반영한다.
기존 SyntheticRunFiles는 Bias-off 소형 1개 위주라 성능용 그래프 입력 생성이 필요하다.

폴더와 ZIP은 해제 후 같은 경로·파일 바이트·source 해시를 갖게 한다.
fixture·ZIP 생성은 업로드 시간에서 제외하고 압축 크기·해제 후 크기를 기록한다.
실제 입력·볼륨이 없으면 인공 데이터 결과라고 명시하고 실제 150개 성능이라고 발표하지 않는다.

### Scenarios

### Repetition and Controls

- S1은 각 비교군에서 워밍업 1회 후 **본 측정 10회**다. A/B/C 필수, I는 채택 후보일 때 추가한다.
- S2~S4는 A/최종에서 워밍업 1회 후 본 측정 각 5회다. S5~S7은 정합성 테스트로 검증한다.
- 계측 오버헤드는 동일 A의 계측 off/on 각 3회 예비 비교한다. 추가 SQL이 없어야 하며 5% 이상 차이가 반복되면 계측을 줄여 A를 다시 만든다. 5%는 계획상 점검 기준이다.
- 매회 전용 DB·저장소를 해당 초기 상태로 복원한다. 신규 시나리오가 재업로드로 바뀌는 것을 막는다.
- JVM·DB 옵션·연결 풀·인덱스·파일 시스템·multipart 제한·scheduler·단일 업로드 요청 수를 고정한다.
- 작업 선택 규칙은 동일하게 유지하되 랜덤 UUID 때문에 달라질 수 있는 실제 처리 순서를 기록한다. A/B/C 실행을 블록별 교대하고 전원·절전·백그라운드 작업을 기록한다. OS 파일 캐시는 강제 초기화하지 않으며 디스크 cold 성능으로 표현하지 않는다.
- 상태 polling은 동일하게 1초다. 서버 terminal commit과 클라이언트 관측 사이 지연도 별도 기록한다.
- 예비 A의 완료 시간으로 본 측정 timeout을 고정하고 모든 군에 동일 적용한다. 실패·timeout을 성공 평균에서 숨기지 않는다.
- batch 전체는 평균·중앙값·최소·최대·표준편차·성공 횟수를 보고한다. 10회 p95로 SLA·최대 처리량을 주장하지 않는다.
- Run별 통계는 batch 내 종속 표본이다. 10회 업로드를 1,500개 독립 실험으로 해석하지 않는다.

### Result Interpretation

전체 개선율 = (A 평균 전체 완료 시간 − 최종 평균 전체 완료 시간) / A 평균 전체 완료 시간 × 100.
클라이언트 전체와 서버 전체의 개선율은 별도다.
단계별 감소는 직전 비교군과 비교하고 중첩 지표를 억지로 합산하지 않는다.

| 결과 표 | 필수 항목 |
| --- | --- |
| 전체 | 비교군·입력 크기·성공/실패·접수·전체 평균/중앙값·감소 ms/% |
| 대기 | 최초 claim·Run별 큐 대기·backlog 중 작업 사이 빈 시간·실제 설정 |
| 파일 | 단계별 시간·읽기/쓰기 바이트·ZIP 해제 크기·atomic move 건수 |
| 파싱 | 스칼라/그래프 시간 합계·분포·원본 행/격자 수 |
| DB | SQL 횟수·JDBC·commit·연결 대기·트랜잭션 점유·상태 집계 비중 |
| 정확성 | 150개 수치/상태/해시·중복/갱신/실패/멱등성 |

B는 정책상 500ms 휴식을 제거한다. 실제 scheduler·DB 대기가 0ms라는 뜻은 아니다.
C의 트랜잭션 감소를 DB 엔진 계산 단축으로 표현하지 않는다.
새로운 동시 요청 수용량·Agent 응답 속도·최대 사용자 수는 이번 결론에 포함하지 않는다.
