# 실험 선택 화면 DB 검색·페이지 조회 개선 계획

## 2026-10-22 사용자 변경 합의 — 사본 없는 최신 목록 조회

기존 전체 후보·버전 고정 정책을 사용자 요청으로 대체한다. 목록은 매번 원본 run/run_version에서 최신 현재 버전을 검색·정렬해 30개만 반환한다. 선택한 버전과 명시적으로 첨부한 버전만 요청 상태에 보관한다. 전체 선택은 사용자가 직접 누른 시점의 일치 버전을 저장하며 이후 신규 등록을 자동으로 추가하지 않는다.

- 준비 API는 선택 세션과 첨부 K개만 생성한다. 목록 조회·검색·페이지 이동은 후보 행을 저장하지 않는다.
- 원본의 기존 registration_sequence로 안정적인 별칭을 만들고 첨부 별칭을 예약한다. 목록 갱신으로 선택한 과거 버전을 교체하지 않는다.
- 원본 현재 목록과 첨부 과거 버전의 각 분기에 정렬·커서·LIMIT 31을 먼저 적용한 뒤 합친다. PostgreSQL이 UNION 전체를 정렬하며 원본 인덱스를 사용하지 않는 계획을 피하고, 최종 31개로 제한한 뒤 조건·버전 정보를 읽는다. 목록·검색용 인덱스는 원본 테이블에 둔다. 인덱스/검색 열의 등록 시 갱신은 원본 등록 작업에 포함되며 요청마다 전체 사본을 만드는 작업은 없다.
- 3글자 이상 검색은 일치 식별자를 먼저 구하고 Run ID·버전 ID 쌍으로 기존 Run PK에 연결한 뒤 정렬한다. 희소/일치 없는 검색에서 정렬 인덱스 순으로 전체 버전을 반복 대조하는 실행 계획을 피한다. 두 글자 검색은 정렬 경로를 유지한다.
- 목록은 전체 건수 COUNT를 기다리지 않고 먼저 표시한다. 건수는 별도 API에서 뒤에 갱신하며, 재측정에서도 COUNT 지연을 별도로 기록한다. 전체 복사 제거로 run_selection 준비 전용 180초 timeout은 제거하고 기본 timeout을 사용한다.
- V10으로 이전 요청의 미선택 사본을 정리하고 선택/첨부는 보존한다. V11이 원본 정렬 B-tree·부분 문자열 GIN을 추가한다. 이전 마이그레이션은 수정하지 않는다.
- 150 / 1만 / 10만 / 100만 건, 동일 JVM 8GB·DB 6GB에서 새로운 B(직접 조회, 보조 인덱스 제외)와 C(같은 코드+V11)를 다시 측정한다. A 기존 기준선과 이전 사본 B/C 결과를 덮어쓰지 않는다.
- seed/마이그레이션 시간은 요청 측정에서 제외하고, 준비 HTTP·첫 페이지·준비된 API·브라우저를 각각 보고한다. 준비 직후 저장 행 수 0(첨부 없는 경우), 선택 2개 후 2행, K개만 비교 전달을 검증한다. 전체 화면 지연에서 초기 준비를 누락하지 않는다.

아래 본문은 이전 전체 후보 고정 설계의 이력이다. 이 변경 합의가 충돌하는 항목보다 우선한다.

## Goal Capsule

**비교 대상을 고르는 추가 입력 화면에서 전체 실험 목록을 한꺼번에 전송하지 않고, DB에서 검색·정렬한 결과를 30개씩 보여준다.**
검색·페이지 이동 중 선택과 기준 Run을 유지하고, 선택 화면을 처음 준비했을 때의 후보·버전을 끝까지 유지한다.
현재 페이지 선택, 검색 결과 전체 선택, 전체 실험 선택을 구분해서 제공한다.

사용자가 선택한 버전 정책은 **“아직 선택하지 않은 실험도 처음 시점의 버전을 보여준다”**이다.
따라서 전체 후보를 고정하는 일 자체를 없애지 않는다.
고정 목록을 DB 안의 전용 테이블로 옮겨 Java·Python·HTTP·브라우저가 전체 목록을 반복 처리하는 비용을 줄인다.
**최초 고정에는 여전히 전체 후보 수에 비례하는 DB 작업이 필요하다.** 이 비용까지 포함해 개선 전후를 비교하며, 최초 조회가 무조건 일정 시간에 끝난다고 가정하지 않는다.

구현·A/B/C 측정 완료 기록은 [성능 비교 보고서](../verification/2026-10-22-실험-선택-페이지-조회-성능-비교.md)에 정리했다. 아래는 구현 전에 확정한 계획이며, 자원 한도·측정 표본 등 실제 실행 조정은 보고서에 별도로 기록했다.
그래프 캐시 공용 락은 후속 검토로 남긴다.

### Scope

- 대상: `compare_runs`가 비교할 실험을 확정하지 못해 `run_selection` 추가 입력을 띄우는 화면과 관련 API·저장 경로.
- 포함: 목록 고정, 페이지 검색, 선택 상태, 비교 재개 계약, 관련 삭제·취소·구버전 요청 호환성, 성능 실험.
- 제외: 역방향 결과 카드의 페이지 조회, 실험 관리 카탈로그 전체 개편, 일반 대화 기록 전체 조회 개선, 그래프 병렬 계산·캐시 락, Redis·Kafka, LLM 모델·프롬프트 변경.
- 기존 순방향·역방향 검색과 비교 계산·그래프 수치는 바꾸지 않는다. 비교 후보 전체를 임의의 상위 몇 개로 축소하지 않는다.

### User Flow

1. 실험 선택이 필요해지면 서버가 해당 추가 입력의 후보·버전을 한 번 고정한다.
2. 목록 첫 30개를 보여준다. 검색 시 DB가 고정 목록에 조건을 적용하고 첫 페이지를 반환한다.
3. 다음 페이지나 다른 검색어로 이동해도 선택한 실험과 기준은 유지된다.
4. 전체 선택 메뉴에는 현재 페이지, 검색 결과 전체, 전체 실험을 구분해 표시한다.
5. ‘선택한 실험으로 계속’을 누르면 서버가 저장된 선택을 검증하고 그 버전으로 비교를 재개한다.

예: 화면 준비 시 A-v1·B-v1이 존재하고 이후 A-v2·B-v2·신규 C가 등록되어도, 해당 화면은 A-v1·B-v1을 계속 사용하고 C는 추가하지 않는다.
이미 태그한 과거 버전은 기존처럼 후보에 포함한다.
원본 버전이 삭제되면 최신 버전으로 교체하지 않고 비가용으로 표시한다.

현재 검색은 전체 로딩 후에는 브라우저 안에서 끝나므로, 서버 검색으로 바꾼 뒤 모든 검색 응답이 더 빠를 것이라고 미리 결론 내리지 않는다.

### KTD1. Freeze Options Inside the Database

새 마이그레이션 `V8__run_selection_snapshots.sql`에서 아래 두 관계형 테이블을 만든다. 구현 시 번호 충돌이 있으면 다음 번호를 쓴다.

| 테이블 | 주요 내용 | 수명·크기 |
| --- | --- | --- |
| `agent_run_selection` | snapshot ID, request ID, pending ID, 요청 revision·epoch, 선택 revision, 기준 별칭, 후보 수·선택 수, 생성 시각 | 추가 입력당 1행 |
| `agent_run_selection_option` | snapshot ID, 고정 별칭·ordinal, Run ID·버전 ID, 공정 조건과 단위, 최초 선택 가능 여부·사유, 검색 문자열·정렬 키, 선택 여부 | 고정 후보 N개와 별도로 첨부한 과거 버전 |

- `(request_id, pending_input_id)`를 유일하게 만들어 재시도해도 동일한 목록을 사용한다.
- DB의 `INSERT ... SELECT`로 고정한다. Java로 전체 summary를 읽어 행별 INSERT하는 방식은 사용하지 않는다.
- 현재 후보와 명시적 과거 참조를 **동일한 SQL 문장 스냅샷**에서 합치고 정확한 버전으로 중복 제거한다. 후보 생성과 개수 기록·NEEDS_INPUT 전이는 하나의 준비 트랜잭션에서 완료한다. N에 따른 이 트랜잭션의 실행·잠금 시간을 측정한다.
- 기존 첨부 별칭을 먼저 예약하고 나머지 별칭을 고유하게 배정한다. `R1` 등이 검색·정렬·페이지마다 다른 실험을 가리키면 안 된다.
- 저장할 것은 선택에 필요한 최소 정보다. 결과 지표 전체, `full_run`, 그래프, 원본 파일 목록은 넣지 않는다. 최초 고정이 실패하면 새 pending을 반쪽 상태로 공개하지 않는다.
- 요청 `context_snapshot`에는 format version과 snapshot ID만 넣는다. Python state·manifest·체크포인트에는 후보 목록이 들어가지 않는다.
- 사용자가 입력을 고민하는 동안 DB 트랜잭션이나 연결을 유지하지 않는다.
- 옵션 행의 버전 참조는 원본 삭제를 막는 외래 키로 만들지 않는다. 삭제 후에도 고정된 표시 정보는 남기고 실제 버전 존재 여부를 조회해 비활성화한다.

이 설계는 **전체 후보의 DB 복사를 남기는 대신 전체 목록의 애플리케이션 전송·직렬화를 없애는 절충안**이다.
N이 커질 때 최초 INSERT·인덱스 유지·WAL·정리 비용이 늘어날 수 있다.
전체 목록을 검색 시점의 최신 값으로 바꾸거나 긴 DB 스냅샷 트랜잭션을 유지하는 대안은 사용자가 선택한 정책과 운영 비용 때문에 채택하지 않는다.
공유 카탈로그 이력·리비전으로 고정 목록 복사까지 없애는 작업은 최초 준비 비용이 실제 병목으로 남을 때 후속 검토한다.

### KTD2. Search and Pagination

- 기존 검색 대상인 고정 별칭, Run ID, 버전 ID, 압력·소스·바이어스의 값·단위로 검색 문자열을 만든다. 현재 표시의 대소문자 무시·부분 문자열 검색 의미를 보존한다.
- 검색 문자열은 후보 고정 시 한 번 생성한다. 매 조회마다 전체 summary JSON을 읽거나 브라우저에 전체 문자열을 보내지 않는다.
- `%`, `_`, 역슬래시는 사용자가 입력한 문자로 검색하고 SQL 바인딩·LIKE escape를 적용한다. SQL 정렬식은 허용 목록만 사용한다.
- 페이지는 `LIMIT pageSize + 1`로 다음 페이지 여부를 판단하고 최대 pageSize개만 반환한다.
- 큰 OFFSET을 반복해서 건너뛰지 않고 **마지막 정렬 키 이후부터 찾는 커서 방식**을 사용한다.
- 순서는 `(natural_sort_key, run_id, run_version_id)`로 고정한다. 숫자가 포함된 이름의 현재 자연 정렬 동작과 대소문자·동률 정책을 테스트로 명세하고, 고정 목록 생성 시 재현 가능한 정렬 키를 만든다.
- 커서는 snapshot ID, pending ID, 요청 revision, 검색 조건, 정렬 방향, 마지막 키를 묶는다. 다른 검색어·방향·요청의 커서를 재사용하면 거부한다. 클라이언트 커서로 접근 범위를 넓힐 수 없다.
- 검색·정렬 변경은 첫 페이지로 돌아간다. 이전 페이지는 커서 이력으로 돌아갈 수 있다. 후보는 고정되어 있으므로 등록·갱신으로 페이지가 흔들리지 않는다.
- `후보 전체 N개`는 생성 시 얻은 수를 재사용한다. 검색 일치 수는 DB 집계로 제공하되 목록 응답과 분리하고, 같은 snapshot·검색 조건에서는 재사용한다. 삭제 여부에 따라 달라지는 ‘현재 선택 가능 수’는 이 고정 수와 구분하고 일괄 선택 시 다시 확인한다. 입력할 때마다 브라우저가 전체 목록을 받아 개수를 세지 않는다.
- 삭제·선택 가능 여부 확인은 반환 페이지의 버전들을 한 번에 조회한다. 옵션 한 행마다 별도 SQL을 실행하지 않는다.

PostgreSQL은 큰 OFFSET도 내부에서 건너뛸 행을 처리하며, LIMIT에는 고유한 정렬이 필요하다고 설명한다. 이 때문에 커서와 고정 정렬을 사용한다. [LIMIT/OFFSET 공식 문서](https://www.postgresql.org/docs/18/queries-limit.html)

### KTD3. Indexes and Search Cost

B 비교군은 위 구조와 검색용 필드를 만들되 아래 보조 인덱스는 넣지 않는다. C 비교군에서 `V9__run_selection_search_indexes.sql`로 추가한다. PK·유일성 제약은 B/C 모두 동일하게 유지한다.

| 인덱스 | 용도 |
| --- | --- |
| B-tree `(snapshot_id, natural_sort_key, run_id, run_version_id)` | 고정 목록 안에서 이름 정렬·다음 페이지 조회 |
| B-tree `(snapshot_id, ordinal) WHERE selected` | 선택한 항목만 페이지 조회·재개 시 검증 |
| GIN `(search_text gin_trgm_ops)` | 기존 부분 문자열 검색을 유지하면서 검색 후보를 줄임 |

`(snapshot_id, alias)` 유일성 제약과 버전 식별 제약으로 정확한 선택 항목을 찾는다.
GIN 검색에는 snapshot 조건을 반드시 결합한다. 여러 세션을 읽어 합친 결과를 반환하지 않는다.
공정 수치의 범위 검색은 이번 자유 검색 계약에 새로 넣지 않는다. 기존 순·역방향 B-tree를 이 화면에 억지로 적용하지 않는다.

B-tree는 정렬·동등·범위 검색에 적합하지만 일반적인 `%검색어%`를 모두 해결하지 않는다. 부분 문자열에는 PostgreSQL `pg_trgm`의 GIN 지원을 사용한다. [인덱스 종류](https://www.postgresql.org/docs/18/indexes-types.html), [pg_trgm](https://www.postgresql.org/docs/18/pgtrgm.html)
한두 글자처럼 추출할 trigram이 적은 검색은 인덱스 이득이 작을 수 있으므로 별도 시나리오로 측정한다.
`pg_trgm`은 개발·테스트·배포 DB의 확장 설치 권한을 확인하고 Flyway로 관리한다. 사용할 수 없으면 부분 검색을 몰래 접두사 검색으로 바꾸지 않는다.

### KTD4. Selection State and Bulk Actions

선택은 현재 페이지 배열이 아니라 **고정 옵션의 ID·버전을 기준으로 서버에 보존**한다. 브라우저는 보이는 페이지와 선택 요약만 유지한다.
체크·해제는 먼저 화면에 반영하고 순서대로 저장한다. 저장 중 표시와 실패 시 해당 동작의 되돌리기·재시도를 제공한다.
검색·페이지 조회 실패가 선택 상태를 초기화해서는 안 된다.

| 동작 | 적용 범위 | 기존 선택 |
| --- | --- | --- |
| 현재 페이지 선택 | 현재 표시 중인 선택 가능한 옵션 | 추가 합집합 |
| 검색 결과 전체 선택 | 고정 목록에서 현재 검색 조건에 맞는 선택 가능한 옵션 전체 | 추가 합집합 |
| 전체 실험 선택 | 검색어와 관계없이 고정 목록의 선택 가능한 옵션 전체 | 추가 합집합 |
| 개별 해제 | 해당 고정 옵션 | 다른 선택 유지 |
| 선택 해제 | 전체 선택 및 기준 Run | 모두 해제 |

- ‘전체’의 범위를 버튼·완료 안내에 표시한다. 30개만 골랐는데 전체 선택이라고 표시하지 않는다.
- 일괄 선택은 DB에서 조건부 UPDATE로 수행하고 변경 수·전체 선택 수·선택 revision만 반환한다. 브라우저가 모든 페이지를 자동 순회하거나 모든 ID를 한 요청에 담지 않는다.
- 일괄 선택의 재시도는 같은 멱등 키로 처리한다. 같은 작업이 뒤늦게 다시 실행되어 사용자가 해제한 항목을 재선택하지 않게 한다.
- 일반 선택 저장도 `expectedSelectionRevision`과 멱등 키로 순서를 검증한다. 여러 탭에서 수정 충돌이 나면 서버 상태를 읽고 알리며 조용히 덮어쓰지 않는다.
- 기준 Run은 선택 집합 안에 있어야 한다. 기준을 해제하면 기준 지정도 해제한다.
- 선택한 항목이 많으면 선택 수와 일부 태그를 먼저 보여주고 선택 목록도 페이지 조회한다. 전체 선택 때문에 다시 수만 개의 DOM을 만들지 않는다.
- 선택한 항목이 삭제되면 비가용 표시를 유지하고 비교 재개를 막는다. 삭제 항목을 자동으로 빼서 다른 비교를 실행하지 않는다.
- `NEEDS_INPUT` 중에는 선택하지 않은 후보 삭제만으로 요청 전체를 취소하지 않는다. 재개 후 실제 비교 참조가 삭제되는 경우에는 기존 비교 요청 무효화 정책을 유지한다.

### KTD5. API and Agent Boundary

아래 계약 이름은 구현 기준이며 기존 OpenAPI·TypeScript·Java 계약과 함께 확정한다.

| 경로·행동 | 입력·출력 요지 |
| --- | --- |
| `GET /api/agent/requests/{id}/run-options` | format=2, pending ID, query, sort, cursor, pageSize. 응답: format=2, snapshot ID, request revision, options 한 페이지, nextCursor·hasMore, 후보 수·선택 revision |
| `GET .../run-options/count` | 같은 snapshot·검색 조건의 일치 수·선택 가능 수. 행 목록을 반환하지 않음 |
| `GET .../run-selection` | 선택 수·기준·선택 revision 및 선택된 옵션 한 페이지 |
| `POST .../run-selection` | expected request/selection revision, pending ID, 멱등 키, 추가·해제·기준·페이지/검색/전체 선택 동작 |
| 기존 `POST .../resume` | format=2 선택은 snapshot ID·selection revision으로 제출. 서버가 저장된 선택 K개를 읽어 `comparisonReference` 구성 |

- `NEEDS_INPUT` 생성 시 snapshot ID와 선택 API 형식을 pending에 포함한다. Python이 전체 옵션을 가져오거나 해석하지 않는다.
- 페이지 GET은 요청 존재·소유 범위·epoch·revision·pending 상태를 검사하되 `workspace.lock()`의 전체 대화 로딩과 요청 전체 JSON 파싱을 호출하지 않는다. 이 화면에 필요한 최소 메타데이터 조회를 추가한다.
- 모든 선택 관련 API는 같은 요청·pending 범위 검증을 공유한다. snapshot ID나 별칭만 안다는 이유로 다른 요청의 목록을 읽거나 선택을 변경할 수 없다. query·cursor 길이, pageSize, 현재 페이지 선택의 항목 수에는 서버 검증을 둔다.
- 선택 변경·재개는 기존 workspace → request 잠금 순서를 지키고 선택 revision을 검사한다. 요청 상태 변경·취소·삭제와 경합해도 오래된 화면이 새 요청에 적용되면 안 된다.
- 실제 비교 재개는 최소 2개, 기준 포함, 정확한 버전 존재·비교 가능 여부를 K개 기준으로 일괄 검증한다. 기존 `READY` 판정 의미를 임의로 더 엄격하게 바꾸지 않는다.
- 일반 선택 저장이 모두 끝난 뒤 재개한다. `requestRevision`은 실제 추가 입력 재개에만 증가하고 페이지·체크 변경으로 추가 입력 횟수를 소비하지 않는다.
- 재개 결과의 별칭·정확한 참조·순서는 기존 계산 계약에 맞춰 서버에서 만든다. 클라이언트가 `comparisonReference`를 직접 제출하지 않는다.
- 기존 20,000자 입력 제한을 풀어 거대한 ID 배열을 받는 방식으로 해결하지 않는다. 대량 선택도 작은 제출 본문을 사용한다.
- 최종 비교에는 K개의 선택이 필요하므로 K가 커지면 비교 자체의 처리·저장 비용은 남는다. ‘전체 선택’과 ‘100만 개 파형 비교를 완료할 수 있음’을 같은 성과로 주장하지 않는다.

### KTD6. Compatibility and Lifecycle

- 기존 `comparisonOptions` JSON이 있는 진행 중 요청은 같은 고정 목록을 전용 테이블로 한 번 변환한다. 현재 카탈로그에서 새로 생성하지 않고 과거 별칭·버전·삭제 상태를 보존한다.
- 새 프론트는 format=2를 명시한다. 형식 없이 전체 목록을 기대하는 이전 클라이언트에는 일부 페이지를 전체인 것처럼 반환하지 않고 `CLIENT_REFRESH_REQUIRED`와 새로고침 안내를 반환한다. 전환 기간 기존 `runKeys` 제출은 서버가 고정 목록의 별칭으로 검증할 수 있게 유지한다.
- 재개 트랜잭션에서 선택 K개를 신뢰 가능한 입력 이벤트와 비교 문맥으로 남긴 다음 고정 후보 목록을 정리한다. 같은 재개 멱등 키의 재요청은 이미 저장된 이벤트로 응답한다.
- 취소·새 대화·전체 초기화·해당 요청의 최종 실패 등 선택 세션이 종료되는 경로에서 임시 테이블을 정리한다. `NEEDS_INPUT` 대기 중인 세션은 임의 TTL로 지우지 않는다.
- 정리 실패는 관측 가능한 재시도 대상으로 남기며 완료된 요청의 임시 목록이 계속 쌓이지 않도록 점검한다. 큰 목록 삭제 시간·WAL도 측정한다.
- 기존 저장 답변과 판단 기록은 수정하지 않는다. 원본 Run 삭제 정책을 약화하거나 임시 목록 때문에 삭제가 영구 차단되지 않게 한다.

## Verification Contract

### Comparison Groups

| 구분 | 내용 | 해석 |
| --- | --- | --- |
| A | 현재 전체 JSON 고정·전송·브라우저 검색 | 변경 전 제품 기준선 |
| B | DB 관계형 고정 목록 + 서버 검색·페이지 + 서버 선택 상태, 검색 보조 인덱스 없음 | 구조 변경의 종합 효과 |
| C | B + 정렬·선택 B-tree 및 부분 검색 GIN | 보조 인덱스의 추가 효과 |

**A→B는 같은 SQL의 개선만이 아니라 저장·전송·UI 경로 변경의 효과**다.
**B→C는 동일 구조에서의 인덱스 효과**이고, B-tree와 GIN 각각의 기여를 주장하려면 해당 검색 유형의 실행 계획과 별도 인덱스 제거 실험이 필요하다.
최종 제품 효과는 A→C로 기록한다.

### Data and Controls

- N=150 / 1만 / 10만 / 100만의 인공 Run 목록을 격리 DB에 준비한다. 150도 실제 Run 수에 맞춘 인공 데이터이며 실데이터 성능이라고 표기하지 않는다.
- 현재 Run 수 N과 과거 버전 수 V를 구분한다. 동일 조건의 중복 Run을 만들어 수를 부풀리지 않는다. 서로 다른 인공 조건·고유 Run ID를 만들고 일부 갱신 이력·비가용 항목·명시적 과거 참조를 추가한다.
- 검색용 최소 summary·단위·버전·상태 구조는 제품과 같게 만든다. 거대한 파형 파일은 이 화면 테스트에 필요하지 않으며 생성하지 않는다.
- A/B/C는 같은 DB seed, 서버/JVM·PostgreSQL 버전, CPU·메모리·Hikari 설정, 브라우저 버전·화면 폭·네트워크 조건을 사용한다. 후보 고정이 필요한 실험마다 새 요청으로 시작한다.
- 초기 선택 상태와 과거 첨부 참조도 동일하게 맞춘다. 업로드·다른 성능 실험은 동시에 돌리지 않는다. 상태 폴링 주기는 같게 유지하고 폴링으로 추가된 대기도 기록한다. 인위적인 저장·네트워크 지연은 넣지 않는다.
- LLM은 호출하지 않는다. 테스트 harness가 실제 요청 생명주기로 동일한 `run_selection` 상태에 도달하게 한다. 내부 API 인증 우회용 제품 엔드포인트를 추가하지 않는다.
- 최초 고정 비용과 이미 고정된 목록의 재검색 비용을 섞지 않는다. 워밍업 후 캐시 상태를 맞추되 이를 OS·DB 캐시가 비워진 ‘콜드’ 측정이라고 부르지 않는다.
- 비교 순서를 번갈아 실행하고 각 규모의 워밍업 2회·독립 세션 10회 이상을 기본으로 한다. 준비 시간이 큰 규모는 완료/실패·표본 수를 그대로 기록하고 작은 표본의 p95를 안정적인 서비스 지표로 과장하지 않는다.
- 준비된 세션의 API는 시나리오별 최소 100요청을 3블록으로 반복해 평균·중앙값·p95·최댓값·오류율을 기록한다. 브라우저 시나리오는 기본 20회, 대규모는 최소 10회로 표본 수를 명시한다.
- 첫 검증은 VU=1이다. 현재 단일 workspace 제약을 고려해 동시 사용자를 꾸며내지 않는다. 같은 옵션을 여러 클라이언트가 읽는 작은 동시성 검사는 보조 실험으로 구분한다.
- 브라우저 전체 시간은 한 브라우저의 단조 시계로 재고 서버 세부 구간은 요청 ID로 연결한다. 서로 다른 프로세스의 상대 시각을 그대로 빼서 지연을 계산하지 않는다.
- 안전한 시간·메모리·디스크 한도를 미리 동일하게 정하고 넘으면 중단 사유를 기록한다. A가 실패한 규모는 성공한 C와의 개선율 대신 성공 여부·처리 가능한 범위로 보고한다.

| 선택·재개 | 선택 저장 시작 → 확인, 재개 입력 → 다음 실행 준비 | API·JDBC·고정된 Agent 테스트 |
| 종료 정리 비용 | 임시 고정 목록 삭제·정리 시간과 남은 행 | SQL·Java 계측 |

k6는 HTTP API 측정에 사용하며 LLM 요청·DB seed 생성·브라우저 렌더링을 측정하지 않는다.
Playwright는 실제 첫 화면·검색·선택 유지·반응형 UI를 확인한다.
기존 A에는 검색 API 호출이 없으므로 A의 ‘검색 API 지연’을 만들어 비교하지 않는다. A/B/C 검색 체감은 브라우저로, B/C 검색 API 성능은 k6로 나눠 보고한다.
`EXPLAIN`은 DB 내부 실행 경로를, JFR은 Java 객체 할당·직렬화·GC가 실제로 줄었는지를 확인한다.
Phoenix는 Agent 연결 확인에 이미 활성화된 경우 보조 추적으로 사용할 수 있지만 이 화면의 주 계측 도구는 아니다.
이번 실험에서 pgbench를 필수로 추가하지 않는다. 같은 SQL의 독립 처리량이 필요할 때 별도 보조 시험으로 사용한다.

계측 구간이 중첩되면 합산하지 않는다. 응답 감소율은 `(A-B)/A×100` 같은 같은 범위끼리 계산하고 B→C도 별도로 기록한다.
표에는 N·V·K, 성공/실패·표본 수, 전후 ms·바이트·감소율을 함께 적는다.
DB 테이블 전체 크기를 줄였다고 주장하려면 JSON만 비교하지 말고 새 옵션 테이블·인덱스·정리 비용까지 포함한다.

## Definition of Done

- 처음 고정한 후보·별칭·버전과 기존 검색 결과 의미를 보존한다.
- 검색·정렬·페이지 이동·새로고침·재시도에도 선택과 기준 Run이 유지된다.
- 세 선택 범위가 명확하고 대량 선택 때문에 전체 옵션을 브라우저로 전송하지 않는다.
- 페이지 응답은 제한된 행만 반환하고, 문맥·manifest·체크포인트에 비선택 후보 목록이 없다.
- 삭제·취소·멱등·revision·구 요청 전환·임시 목록 정리를 검증한다.
- A/B/C의 동일 결과, 최초 준비를 포함한 사용자 흐름, 전송·메모리·DB 추가 저장 비용을 함께 보고한다.
- 개선율은 측정 후 작성한다. 일부 검색이 느려지거나 초기 고정 비용이 증가하면 그 구간도 결과에 남긴다.
- 제품 코드·계약·마이그레이션·테스트·검증 문서는 같은 기능 PR로 연결한다. 필수 검증과 저장소의 리뷰 요건을 따른다.
- 원시 성능 자료·DB·실제 실험 정보는 `.local/performance/run-selection/` 등 Git 제외 경로에 보관한다. 공개 보고서에는 인공 데이터의 집계와 재현 방법만 포함한다.
