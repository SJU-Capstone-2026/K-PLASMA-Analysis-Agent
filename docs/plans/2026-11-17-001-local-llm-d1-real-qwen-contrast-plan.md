# LocalLLM v2.5 — 실제 Qwen 계획의 인용·실행값 대조를 위한 d1 실험 계획
Created: 2026-11-17 (Asia/Seoul)

**핵심:** 기존 Qwen이 실제 생성한 정상 계획 5개를 고른다. 질문·조건별 인용·단위·연산자·지시서·선택지는 보존하고, 각 계획을 복사해 실행 수치 하나만 바꾼 오류 계획 5개를 만든다. d1이 정상은 통과시키고 오류는 정확한 검사 항목과 `value_changed`로 잡는지 확인한다.

**범위:** 정상5+오류5=10계획, 현재 후보 구조 기준56개 검사·56회 singleton 추론. Qwen 신규 호출0, 웹/API 문항 평가0. Q8+MLX 단일 처리·Docker1.5GiB·d1 검토ON·기존 그래프/응답 양식 유지. 이번 문서는 계획이며 구현·실제 추론은 시작하지 않는다.

## 1. 실험을 다시 설계하는 이유

- 이전 정상5·오류5는 사람이 만든 고정 계획이었다. 인용문20개 모두 질문 전체였으므로 그 결과는 서로 다른 조건별 인용을 제외하는 영향까지 검증한 것이 아니다.
- 실제 기록은 다르다. 기존 DB의15요청·18계획 응답(최초15/재계획3)에서8개 응답은 조건별 일부 구절을 인용했다. 인용문63개 중45개는 질문 전체와 정확히 같고,18개는 달랐다. 이 중17개는 문장 끝 구두점 차이를 넘어선 부분 인용이다.
- 반복 웹 실행과 재계획이 포함되므로18개 응답을18종 질문으로 세지 않는다. 확보한 질문 문자열은5종이며, 작업 구성은 순방향 조회3종·범위 검색1종·하한 검색1종이다.
- 직전 축약 코드는 중복 여부를 비교하지 않고 정해진 인용 필드를 제외했다. 이를 일반적인 ‘중복만 제거’로 설명한 것은 부정확하다. 그 축약 결과는 역사적 비교로 보존하고 이번 기준 입력에 적용하지 않는다.

## 2. 이번에 답할 질문과 선택한 방법

**질문:** 원문과 조건 인용이 맞는 상태에서 실제 실행 숫자가 달라지면, 현재 d1이 그 차이를 정확한 오류로 분류하는가?

| 방법 | 판단 |
|---|---|
| 실제 Qwen 계획에서 인용을 보존하고 실행값 하나만 바꾸기 | 사용자 제안에 따라 채택. 계획 출처와 인용 방식은 실제 기록을 사용하면서 오류 위치를 통제할 수 있다. |
| Qwen을 새로 호출해 다시 계획을 만들기 | 이번 범위에서 제외. 생성 변동·새 비용·재계획이 d1 평가에 섞인다. |
| 인용이 모두 같은 인공 계획으로 계속 비교하기 | 이번 목적의 주자료로 사용하지 않는다. 실제 조건별 인용을 대표하지 못한다. |

이번에는 입력 축약·번역·지시서 재배치·선택지/임계값·모델/정밀도 변경을 함께 실험하지 않는다. 인용을 뺀 구성과의 A/B 비교도 이번56회에 자동 추가하지 않는다.

## 3. 실제 계획의 출처와 선별 기준

현재 확보한 비공개 근거는 `.local/runtime/v2.5-qwen-quote-log-audit/`의 `database-evidence.json`, `quote-audit.json`, `report.md`다.

- 원 응답은 `agent_v2_model_attempt.outcome.data`의 `PLAN_INITIAL`/`REPLAN`이며 부모 요청의 `graph_version=v2_localLLM`이다. 모델명과 응답ID도 확인한다. 저장 계획의 근거 인용15개 세트가 해당 요청의 원 응답과 일치하는 것도 확인했다.
- 평가에는 질문5종에서 각각1개만 고른다. 같은 질문의 OFF/ON 반복이나 재계획을 독립 질문으로 부풀리지 않는다. 최초 계획을 우선하되, 당시 구조 오류가 있었다면 기록상 통과한 실제 재계획을 사용하고 그 출처를 표시한다.
- 옛 `requires` 필드를 가진 저장 계획5개가 있다. 현재 형식에 맞는 실제 저장 계획10개에서5종을 고를 수 있으므로 이번에는 옛 계획을 임의 변환하지 않는다.
- 실제 검토 입력은 기존 `PLAN_REVIEW.outcome.reviewInput`에15건 보존돼 있다. 여기서 당시 원문·이력·확인 문맥을 회수하고 원 응답/저장 계획과 연결한다. 현재 체크포인트0건을 임의의 빈 문맥으로 대신하지 않는다.
- 입력·계획·인용을 재구성하거나 Qwen에게 다시 쓰게 하지 않는다. 문맥이나 출처가 불충분한 사례는 제외 사유를 남긴다.5개를 확보하지 못하면 자료를 만들어 채우지 않고 범위를 다시 보고한다.

요청ID·시도ID·계획revision·모델명·응답ID·원문/계획/인용/원자료 파일hash를 비공개 manifest에 고정한다. 공유 문서에는 실제 질문·계획·Run 참조 원문을 복사하지 않는다.

## 4. 인용이 올바르다는 전제를 먼저 확인한다

Qwen이 적었다는 이유만으로 모든 인용을 정답으로 간주하지 않는다. 아래를 확인한 사례만 이번 평가의 ‘인용이 올바른 기준 계획’으로 채택한다.

1. `message_key`가 실제 원문 메시지를 가리키고 `quote`가 그 메시지에 존재한다.
2. 그 인용이 **현재 입력 필드의 조건**을 뒷받침한다. 다른 조건의 숫자를 인용하거나 원문의 단위·경계를 잘못 짚은 사례는 제외한다.
3. 정상 계획의 실행 수치·단위·연산자와 인용·원문이 의미상 일치한다. 정규화가 있다면 기존 단위 규칙으로 확인한다.
4. 요청한 작업/조건 누락이나 불필요한 작업이 없는 정상 계획인지 별도 확인한다. 옛 d1의PASS만을 정상 정답표의 근거로 삼지 않는다.

기존 `plan_validation.py`의 인용 검사는 주로 원문에 실제 존재하는지 확인한다. **원문에 있는 문장이라는 사실과 해당 조건을 올바르게 가리킨다는 판단은 구분**한다. 조건별 기대 수치·단위·대상 경로·판정 이유를 사전에 사람이 검토한 정답표로 남긴다. 잘못된 원 인용을 수정해서 정상 사례로 만드는 대신 해당 사례를 제외한다.

## 5. 정상5·오류5의 구성

| 쌍 | 실제 로그의 작업 유형 | 오류 사본에서 바꿀 것 | 그대로 둘 것 | 오류 기대 사유 |
|---|---|---|---|---|
| 1 | 순방향 조회 | 압력의 실제 숫자1개 | 질문·모든 인용·단위·나머지 조건 | value_changed |
| 2 | 다른 순방향 조회 | 소스 전력의 실제 숫자1개 | 동일 | value_changed |
| 3 | 조건별 부분 인용이 있는 순방향 조회 | 바이어스 전력의 실제 숫자1개 | 동일 | value_changed |
| 4 | 에너지 범위 검색 | 상한의 실제 숫자1개 | 하한·between 연산자·단위·모든 인용 | value_changed |

- 실제 오류값과 정확한 JSON 경로는 선별한 원 계획을 확인한 뒤 **추론 전에** 고정한다. 숫자는 유한한 허용 타입이며, 범위 상한 변경 뒤에도 하한≤상한이 되게 한다. 구조 검증이 먼저 잡는 모순을 d1 의미 검사의 성공으로 세지 않는다.
- 정상 계획은 원 기록 그대로, 오류 계획은 그 복사본이다. 오류 사본의 **plan 내부 차이는 숫자 leaf1개**여야 한다. 인용·요구사항 설명·출처·단위·연산자·단계/요구사항 연결은 바꾸지 않는다.
- 검토 문맥의hash·program_effects 등 실행 효과 표시는 기존 코드로 다시 만든다. 이 파생 표시가 새 숫자를 반영하는 것은 허용하되, 사람이 정답 힌트나 오류 해설을 덧붙이지 않는다.
- 정답표·오류 주입표는 실행기만 읽는다. d1에는 `normal/bad`, 정답 사유, 바뀐 경로와 기대값, 정상 원본과 오류 사본의diff를 보내지 않는다. d1은 각 계획을 독립적으로 검토한다.

설명용 가상 예시는 아래와 같다. 이 예시값으로 실제 평가 자료를 대신하지 않는다.

| 항목 | 정상 | 오류 사본 |
|---|---|---|
| 원문의 조건과 인용 | ‘소스 전력300 W’ | 그대로 |
| 실행값 |300 W|450 W|
| 기대 판정 |match|value_changed|

이 주 실험은 수치 불일치 분류를 확인한다. 단위·엄격 경계·정렬·비교 대상·기준 Run·조건 누락 검출의 새 성적으로 확대하지 않는다. 관련 실제 계획이 없는 범위를 인공 계획으로 메워 이번 성적에 섞지 않는다.

## 6. d1 입력과 환경 고정

- 입력 기준은 기존 v2.4의 영어축약 `en-compact-no-view`, `d1-wire-en-compact-1`, `per_check/d1-context-2`다. 미채택한 지시서 재구성안이나 `execution-data-focus-v1`을 사용하지 않는다.
- 원문 질문·원래 이력/확인 문맥·요구사항 설명·sources·각literal의source.quote를 **모두 보존**한다. 같은 인용인지 여부로 이번 입력을 바꾸지 않는다.
- v2.4의 도구·지표 설명 선별, 정책, 검사별 지시서/위치·선택지ID/설명/순서·보정값·정규화/계획 검토 파서는 유지한다. 검토를 현재 코드로 조립하므로 과거의 다른 엔진에서 나온 판정은 이번 결과로 재사용하지 않는다.
- d1은 기존 LiquidAI/d1-2B 파생 MLX affine8/group64, 기존 BF16 보존 부분, Metal GPU, `group_size=1`/`independent_batch_size=1`이다. 모델·tokenizer·보정/라이브러리·소스hash를 고정한다.
- Docker1536MiB, 기존development 메모리 정책 유지. warning/swap은 기록하고critical/unknown·입력16000 초과·절단·프로토콜/해제 실패는 중단 사유다. 이를 피하려고 인용을 자르지 않는다.
- 기존 그래프·최종 JSON/SSE·저장·도구 실행 계약과 재계획 최대2/필요시 답변 재작성 최대1 설정은 유지한다. 설정과 실제 그래프 상태의 `plan_review_enabled=true`를 실행 전에 확인한다.

새 Qwen 계획·답변·Run 조회·웹 평가·재계획 복구는 실행하지 않는다. 이번 평가는 이미 고정한 계획에 대한 **최초 d1 검토**다. 원 자료가 과거 재계획에서 나온 경우에도 이번에 재계획 복구를 실행한 것으로 세지 않는다.

## 7. 실행 순서와 호출 예산

1. **자료 확정:** 실제 원 응답/검토 입력을 대조해 정상5개를 선별하고 인용·수치 정답표를 작성한다. 부분 인용과 질문 전체 인용이 실제 기록대로 포함되게 한다.
2. **사본 확정:** 각 정상의 숫자 하나만 바꾼5개를 만들고, plan의단일leaf차이·인용/원문 보존·정답표 비노출·구조 유효성을 CPU에서 검증한다.
3. **입력 확정:** 실제tokenizer로 예산·절단 없음과 같은 검사 종류/선택지를 확인한다. 준비된10개 입력과 모델/소스/환경 manifest를 동결한다. 이 단계까지 모델forward0회다.
4. **준비 확인:** 기존 메모리 증거·가중치/서비스 지문·Docker 한도·검토ON을 확인한다. `Settings.readiness()`처럼 새 계약 추론을 만들 수 있는 호출을 무심코 추가하지 않는다. 증거가 맞지 않으면 멈추고 준비가 필요한 이유를 보고한다.
5. **한 차례 실행:** 정상/오류 쌍을 사전 고정한 순서로 각각 한 번 검토한다. 모든 검사를1개씩 순차 실행하고 각 계획 완료 후 모델/작업 메모리를 해제한다. 정확도가 낮다는 이유로 나머지 사례를 생략하지 않으며, 하드웨어/프로토콜 실패만 중단한다.
6. **분석과 복원 확인:** 모든 원시 선택지 확률을 기존 파서에 통과시켜 기대 항목/사유와 대조한다. 소스·DB·환경·기존 서비스 상태를 확인하고 집계를 기록한다.

현재 형식에 맞는 실제5계획은 검사 수가6+6+6+5+5=28이다. 수치만 바꾼 사본도 같은28개이므로 **총56회**를 계획한다. 최종manifest에서도 이 수와 검사ID를 확인하며, 다르면 실행 전에 변경 이유와 예산을 다시 확정한다. 이를 이유로 검사를 생략해56회에 맞추지 않는다.

Qwen 호출0, 추가모델 대조0, 숨은warmup0, 반복/자동재시도0이다. 프로토콜 준비를 위해 다른 추론이 필요해도 이번56회에 몰래 추가하지 않는다. 중단 시 시도·완료·미완료 수를 따로 남긴다.

공용 worker는 처리 중인 요청이 없음을 확인한 뒤 기존 `model_lease`로 새 모델 작업을 막고, 실행 중 계속 살아 있게 둔다. 이전에 SIGSTOP/재개 후 worker가 종료된 사례가 있어 이번에는 SIGSTOP을 사용하지 않는다. 잠금으로 격리가 불가능하거나 소유 서비스가 바뀌면 중단한다. worker 재시작이나 Qwen 준비 추론을 자동 추가하지 않는다.

| 확률·근거 |목표 검사의 match/value_changed 등 확률과 원문/인용/실행값의 대응을 비공개 원 결과에 남김 |
| 비용·속도 |검사당 입력 토큰, GPU 완료를 동기화한 score 시간, 계획당 합계의 평균/중앙값. 로드/준비/전체 경과 시간은 별도 |
| 메모리 |OS active+wired+compressor 피크, warning/critical/unknown·추가 swap·해제 상태·DB OOM. 다른 회계의 RSS/MLX 할당량과 합산하지 않음 |

사전 기대는 **정상 PASS5/5·목표 오류 항목/사유5/5·엄격 계획10/10**이다. 충족 여부를 그대로 보고한다. 미달하면 실패 사례의 원문·올바른 인용·실행값·선택지 확률·선택 사유 코드·다른 검사의 오판을 나눠 분석한다. 실패 뒤 지시서나 입력을 즉시 바꿔 같은 자료를 반복 실행하지 않는다.

완료해도 이5종 수치 사례의 결과다. 인공 계획에서의1/5→2/5나 과거 웹5/5와 합산하지 않는다. 새 자료에서 성적이 달라졌다는 것만으로 d1 자체가 개선됐다고 주장하지 않는다. 인용 보존의 효과를 인과적으로 비교한 실험도 아니다.
