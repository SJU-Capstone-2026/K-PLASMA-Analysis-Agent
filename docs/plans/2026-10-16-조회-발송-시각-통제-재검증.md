# 요청 발송 통제 재확인 — 측정 전 확정

기존 실험에서 worker4 B2/C2 발송 호출은 1/0ms 폭으로 비슷했으나 서버 filter 진입은 29.193/1.950ms로 달랐다. worker8 C1 cohort2는 예약보다54~56ms 늦게 호출됐다. 기존 로그에는 패킷 발송 시각이 없으며 startEpochMs는 k6 http.get 직전의 1ms 해상도 시각이다. 이 관측을 검증하고 서버 진입 분산을 입력 부하 분산으로 오인하지 않는다.

- 기존 B/C JAR와 인공150Run/2175파일/1545005295바이트, seed3버전, pool10을 재사용한다. 제품 코드는 변경하지 않는다.
- worker/관리자4와8 각각 B/C3쌍. 순서 B1,C1,C2,B2,B3,C3. 모든 시행은 JVM 재시작 후 동일8Run 예열. 조회100VU/5초 동시 묶음, 업로드는 첫 예약묶음+5초에 시작한다.
- VU와cohort로 조회 대상을 결정해 대응 요청의 데이터까지 같게 고정한다. 기존처럼 순서가 바뀌는 iteration 번호로 대상을 고르지 않는다.
- 요청 예정 시각·http.get 직전 시각·HTTP 구성 시간·서버filter 진입/종료·연결 획득·점유를 기록한다. 서로 다른 clock의 절대 값을 빼지 않는다. 요청별 server 외 잔여시간은 왕복HTTP에서 server trace를 뺀 값으로만 정의한다.
- 각B/C쌍의 동일cohort/VU를 비교한다. 각묶음100건, 각100VU, 대상별개수 및VU별대상동일, HTTP200/해시정상을 확인한다.
- 발송 검증: 각묶음 호출 폭<=5ms, 예약지연0~5ms, B/C호출폭차이<=3ms, 평균예약지연차이<=3ms. 오차 허용은 ms-clock 로컬 동시부하의 운용기준이며 완전히 같은 wire-time을 보장하지 않는다.
- 업로드 경합: 조회시점 평균활성worker가 B/C각설정치75%이상, B업로드연결점유도75%이상인 묶음을 선택한다. C의 연결점유는 선택에 쓰지 않는다. 지연/개선율은 선정조건에 쓰지 않는다.
- 조건 미충족 묶음·시행은 삭제하지 않고 이유와 전체값을 보존한다. 3쌍 중 유효묶음이 없는 쌍이 있다면 각worker최대2쌍만 추가 가능. 개선율이 불리한 이유로 추가하지 않는다. 충분한 유효표본을 얻지 못하면 한계로 종료한다.
- 배치별선택요청평균을 먼저 계산한 뒤 배치평균의평균으로 비교한다. 점유합계/업로드완료는 배치전체. 원래 실험 평균과 합치지 않는 별도 재검증이다.
- 도구: k6(조회부하/호출시각/HTTP), Python(병렬업로드·원시trace결합·통제감사), Java기존계측(JDBC/worker), PostgreSQL검증. LLM호출없음. dedicatedDB만 사용하고 종료시 seed복구/서버/DB중지.

## 시계 불안정 발견 후 후속 측정 변경(추가 실행 전)

첫 재측정의 worker4 B/C3쌍은 벽시계-경과시간 차이가 약0.2ms로 안정적이었다. worker8 C1은 -4959.471ms의 차이와 조회cohort3 전체누락으로 실행 검증이 실패했다. 기존worker8 C1도 +53.687ms 차이가 있어 예약지연54~56ms를 순수발송지연으로 확정할 수 없다. 발생 원인(NTP 등)은 확인하지 못했다.

worker4 유효3쌍은 보존한다. worker8은 Node.js의 performance.now 및 타이머로 100연결/5초 동일조회부하를 생성하는 독립 재검증3쌍을 진행한다. k6 currentTestRunDuration은 공식 소스가 UnixNano 차이를 사용하므로 단조 시계 대용으로 채택하지 않는다. k6와Node 결과를 합치거나 도구교체 자체를 제품개선으로 보지 않는다.

기존worker8 B/C의 조회지연을 보지 않고 job 시작/종료구간만 확인했을 때 업로드 시작5초는 worker0개인 구간이었고,6.5~8초는 양쪽8개가 작업 중이었다. 추가worker8에서는 양쪽에 동일하게 upload trigger를 부하발생시작+3초로 고정한다. 따라서cohort2(+10초)는 업로드 시작약7초에 발생한다. worker와트랜잭션을 인위적으로멈추거나sleep을넣지 않는다.

사전 발송허용오차/활성worker/연결점유 기준은 유지한다. Node는 HTTP호출직전·요청쓰기완료·응답완료를 단조시각으로 기록하고, 벽시각도 진단용으로만 보존한다. 단조 예약 검증 전 벽시계 -5초 모의조작에서도 2묶음200HTTP요청이 누락되지 않는지 회귀검증한다. 원시결과는 별도 monotonic-worker8 폴더에 남긴다.
