# Qwen 생각 토큰 예산 비교 계획

작성일 2026-11-19 KST

진행 상태는 보류다. v2.6.2에서 실제로 사용한 생각 토큰 상한은 2,048이다.

## 핵심 요약

v2.6.1을 기준으로 **Qwen 생각 토큰 상한 2,048과 1,024를 비교**한다. 기존 40문항에서 단순 조회 2개와 경계·복합 계획 3개를 골라, 각 조건에서 새 대화로 한 번씩 웹에 제출한다. 첫 비교는 **5문항 × 2조건 = 10건**이다. 최초 계획의 정확도와 재계획 횟수부터 비교하고 같은 품질로 끝난 실행에서 얼마나 빨라졌는지 본다.

현재 상한은 llama.cpp b12317 서버 실행 인자 `--reasoning-budget 2048`이다. Qwen은 상한에 이르기 전에 생각을 끝낼 수 있다. 최근 캐시 적중 웹 평가의 Q01·Q05 전체 생성량은 각각 772·1,181토큰이었다. 이 수치에는 생각과 도구 호출이 함께 들어 있다. 특히 Q01 수준의 생성에서는 1,024 상한이 걸리지 않을 수 있어 복합 문항도 포함한다. [엔진 옵션 설명](https://github.com/ggml-org/llama.cpp/blob/b12317/tools/server/README.md) · [v2.6.1 검증](../verification/2026-11-19-local-llm-v2.6.1-qwen-citation.md)

## 조건과 시험 문항

| 항목 | 고정 조건 |
|---|---|
| 비교 변수 | A의 생각 상한 **2,048**, B의 생각 상한 **1,024**. 최초 계획과 재계획에 적용 |
| 모델과 생성 | 동일 Qwen3.5-9B GGUF Q4_K_M·llama.cpp b12317·현재 가중치 및 템플릿. 계획 생각 ON, 답변 작성 생각 OFF. 계획 전체 출력 상한 6,000, 답변 3,000. temperature 0.6·top_p 0.95·top_k 20·개별 호출 제한 90초 |
| 실행 환경 | 문맥 24,576·batch/ubatch 256·Docker 1.5GiB·기존 메모리 정책과 Qwen/d1 순차 상주 |

| 제품 동작 | v2.6.1의 인용 복원·`submit_plan`·그래프·최종 응답 계약과 동일 DB·검증 기준 |
| 캐시 | 양쪽 모두 ON. 설정별 저장 경로와 검증 증거를 사용하고 각 문항의 첫 계획에서 실제 적중을 확인 |

| 문항 | 확인할 행동 |
|---|---|
| Q01 | 순방향 조회에서 요청 조건·단위가 보존되는지 |
| Q05 | 역방향 조회에서 기준값의 단위와 포함 경계, 전체 후보 요청이 보존되는지 |
| B05 | 요청한 조회만 계획하는지. 자동 채점과 함께 불필요한 설명 단계 추가를 확인 |

각 조건에서 같은 질문과 문맥을 사용한다. C03의 선택 상태도 양쪽에서 일치시킨다. 같은 질문의 이전 계획이나 대화는 새 호출에 포함하지 않는다. 비교 전 기존 문항 은행과 정답 기준을 고정한다. [40문항 검증과 B05 사례](../verification/2026-11-13-v2-local-llm-baseline-40.md)

## 준비와 실행 순서

1. **상한이 실제 실행에 반영되도록 준비한다.** 현재 `config.py`의 실행 기록과 `runtime.py`의 서버 인자·준비 검사가 2,048을 고정한다. 구현 단계에서는 명시적으로 선택한 상한을 정상 설정·실제 서버 인자·실행 기록·캐시 식별값·메모리 프로필에 일치시키는 작은 변경이 필요하다. 기본값은 2,048이다. 시작한 Qwen의 실제 인자와 기록이 다르면 시험 시작 전에 원인을 해결한다. 기본값·값 일치·설정이 다른 캐시와 준비 증거 거부는 기존 `test_config.py`, `test_llamacpp_profile.py`, `test_readiness.py`, `test_prompt_cache.py`에서 검증한다.
2. **각 조건의 메모리와 캐시를 준비한다.** 현재 운영 실행과 캐시를 보존하고 시험용 로컬 프로필을 하나씩 올린다. 예산과 캐시 경로가 일치하는 준비 증거를 확인하고, 필요한 경우 기존 `evals/local_llm_measure.py`와 캐시 왕복 검사로 새 증거를 얻는다. 두 조건에 같은 인공 준비 입력을 써 캐시를 채운다. 준비 호출과 모드 전환 시간은 웹 성적에 별도 표시한다. 평가 전 Docker 1.5GiB, 설정과 실제 그래프의 계획 검토 ON, 모델 준비 상태를 확인한다.
3. **A와 B에서 5문항씩 실행한다.** 한 번에 요청 하나만 진행한다. 문항별 실제 시작 시각·캐시 적중·토큰을 기록한다. 첫 계획의 공통 입력에서 실제 재사용 토큰 수를 대조한다. 캐시 미적중·재사용량 차이·워커 재시작이 섞인 시도는 결과와 원인을 남기고 해당 시간쌍을 따로 표시한다. 메모리 경고는 기존 정책에 따라 기록하고 critical이면 다음 제출을 멈춘다.
4. **두 설정의 성적을 비교한다.** 한 번씩 실행한 결과로 후보를 선별한다. 결과가 유망하면 이후 확인 실행에서는 같은 문항을 B→A 순서로 한 번 더 돌려 순서와 모델 생성 편차를 확인한다. 처음의 10건과 확인 회차를 각각 기록한다. 비교가 끝난 개발 실행의 기준은 현재 2,048·캐시 ON·d1 ON이다.

## 기록할 지표

| 구분 | 문항별 기록 |
|---|---|
| 계획 정확도 | 첫 Qwen 계획의 조회·조건·숫자·단위·비교 대상·단계 연결. 인용 복원 발동 여부, 도구 호출 인자 형식과 잘림 여부 |
| 검토와 최종 정확도 | 첫 d1 결과, 반려 이유, 재계획 횟수, 재계획 뒤 최종 통과, 실제 답변 자동 채점 및 요청 범위 검사. 정상 계획에 대한 d1 오판과 Qwen의 계획 오류는 원인을 구분 |
| 생각과 출력량 | 실제 설정 상한, 생각 토큰, 도구 인자 및 전체 생성 토큰, 종료 이유. 엔진이 생각 토큰을 제공하면 그 계수를 사용하며, 제공하지 않으면 기존 `qwenDiagnostics`의 동일 Qwen 로컬 토크나이저 재계수로 추정한다 |
| 시간 | Qwen의 입력 처리와 전체 생성, d1 검토, 재계획, 워커 실행, 전체 응답. 대기는 전체 응답에서 워커 실행을 뺀 값 |
| 실행 조건 | 첫 계획의 캐시 적중·재사용량, 메모리 압력·추가 swap·Docker OOM 변화, 실제 준비 호출 수 |

처음부터 통과한 수와 최종 통과한 수를 따로 제시한다. 정확도는 전체 5건의 문항별 결과를 공개 가능한 집계로 남긴다. 속도는 동일한 캐시 조건에서 두 설정 모두 정답인 문항의 쌍별 차이와 중앙값을 사용한다. 실패·재계획·시간 초과로 끝난 실행도 건수와 전체 시간을 남긴다.

현재 웹 기록에는 엔진의 생각 토큰 세부 계수가 없다. 같은 진단용 토크나이저를 양쪽에 설정해 생각·도구 인자 개수만 기록한다. 추정치를 절대 상한의 정확한 관측으로 해석하지 않는다. 엔진에 상한 도달 신호가 있으면 별도로 기록한다. 실제 적용 인자와 토큰 분포를 함께 확인하며, 생각 시간은 토큰 비율로 역산하지 않는다. [기존 Qwen 계측 기록](../verification/2026-11-14-local-llm-v2.3-qwen-d1-joint.md)

## 결과를 보고 내릴 결정

- **1,024 우선 후보**는 기준이 맞힌 문항을 모두 유지하고, 복합 계획에서 새 조건 누락이나 단계 연결 오류를 만들지 않으며, 최초 통과·재계획도 악화하지 않는 경우다. 실용적인 시간 개선의 제안 기준은 정답 문항의 쌍별 워커 실행 시간 감소율 중앙값 10%다. 확인 회차에서도 같은 방향인지 본다.
- **상한이 거의 걸리지 않은 경우**에는 이번 문항에서 1,024가 생성량을 실질적으로 제한하지 않았다고 기록한다. 품질을 유지했는데 시간 개선이 작다면 다음 비교 후보는 512다. 512의 성적은 같은 문항·같은 캐시 기준으로 따로 확인한다.
- **속도만 좋아지거나 품질이 불안정한 경우**에는 2,048을 운영 기준으로 둔다. 어떤 질문에서 조건·단계·도구 형식이 무너졌는지 남긴다. 두 설정이 모두 틀린 문항도 별도로 기록해 정확도 판단의 근거를 명시한다.

이 시험은 다섯 문항에서 다음 후보를 고르는 용도다. 전체 40문항이나 선택 확인·결측·설명까지 성능을 확대해서 해석하려면 해당 문항에 대한 추가 검증이 필요하다. 원시 질문·생각·계획·답변·실험 데이터는 로컬에 보관하고 Git에는 집계와 재현 조건을 기록한다.
