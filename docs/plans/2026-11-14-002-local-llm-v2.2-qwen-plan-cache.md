# LocalLLM_v2.2 — Qwen 계획 캐시 저장·복원 구현 계획서

> 상태: **캐시 구현·소프트웨어 검사 완료. 정식 메모리 검사는 경고로 중단되어 웹 OFF/ON 비교와 운영 활성화는 보류했다. 기본 OFF.**
> 실행 결과와 미검증 범위는 [검증 기록](../verification/2026-11-14-local-llm-v2.2-qwen-plan-cache.md)에 남겼다.
> 구현 시 이 문서의 순서대로 직접 진행하고, 마지막에 전체 변경을 한 번 검토한다.

**Goal:** Qwen이 반복해서 읽는 계획 지시서와 `submit_plan` 도구 정의의 계산을 재사용해 입력 처리 시간을 줄인다.

**Architecture:** Qwen의 계획·재계획용 계산 상태를 로컬 파일에 보관하고, 모델을 다시 올린 뒤 복원한다. 기존 그래프 바깥의 모델 연결부에서 처리하며 d1 검토·도구 실행·최종 응답 계약은 유지한다.

**Tech Stack:** 기존 llama.cpp b12317, Qwen3.5-9B GGUF Q4_K_M, Python/httpx와 로컬 파일. 새 서비스·DB·의존성을 도입하지 않는다.

**Spec:** 사용자의 2026-11-14 지시: “일단 Qwen만 캐시 저장하는 걸로 하자. 구현 계획서 작성해줘. 나도 읽기 쉽게 작성해줘.” 앞선 논의의 우선 대상인 **Qwen 계획·재계획용 캐시 1종**으로 범위를 잡는다.

## 1. 먼저 읽는 요약

지금은 Qwen이 작업을 마치고 sleep(모델을 메모리에서 내리는 동작)하면 계산 캐시도 메모리에서 사라진다.
다음 질문에서 같은 계획 지시서와 도구 정의를 다시 읽어야 한다.

이 작업은 **계산해 둔 내용을 파일에 잠깐 보관했다가 다시 사용하는 기능**이다.
새 질문과 실험 데이터는 매번 온전히 전달하고, 계획과 d1 판단도 현재 입력으로 수행한다.

실행 흐름은 다음과 같다. 아래는 연결부의 처리 순서이며 LangGraph 노드를 추가하는 그림이 아니다.

```text
첫 계획:   전체 입력 처리 → Qwen 계획 생성 → 캐시 저장 → Qwen sleep → 기존 d1 검토·실행·답변
다음 계획: 캐시 복원 → 공통 부분 재사용 + 새 내용 처리 → 새 계획 생성 → 캐시 갱신 → 기존 흐름
```

먼저 인공 질문으로 저장·복원이 실제로 작동하는지 확인한다.
그다음 연결부를 구현하고, 메모리 검사를 통과하면 동일한 앞5문항을 캐시 OFF/ON으로 비교한다.
효과가 확인되기 전에는 운영 설정에서 자동으로 켜지 않는다.

## 2. 무엇을 저장하고 무엇을 유지하는가

| 항목 | 이번 계획의 처리 |
|---|---|
| Qwen 계획 지시서 | 반복되는 앞부분의 계산을 재사용하는 주 대상 |
| `submit_plan` 도구 정의 | 필드명·설명·자료형·허용 값 등의 계산을 재사용 |
| 모델 메시지 형식 | 현재 template와 생각모드를 그대로 사용 |
| 새 질문·선택 Run·실험 결과 | 매번 최신 입력을 제공하고, 일치하는 앞부분만 엔진이 재사용 |
| d1 | 기존 전용 API·검토 기준·실행 방법을 유지. 캐시 기능 추가 없음 |
| Qwen 답변 작성 | 별도 캐시를 만들지 않음. 계획용 파일을 답변용으로 복원하지 않음 |
| 그래프·최종 응답 | 노드·간선·처리 규칙·응답 필드·SSE 형식 유지 |

정확히 저장하는 것은 텍스트를 읽으며 계산한 **중간 상태(KV 캐시와 필요한 문맥 체크포인트)**다.
모델·지시서·도구 정의·실행 설정의 식별값도 함께 기록해 다른 조건의 캐시를 잘못 쓰지 않게 한다.

### 파일에 질문도 포함될 수 있다

기본 슬롯 저장 API는 처리 중인 문맥 전체를 저장할 수 있다.
따라서 **“재사용하려는 부분은 고정 지시서”와 “파일에 들어가는 전체 범위”를 구별**한다.
고정 부분만 정확히 잘라 저장할 수 있다고 가정하거나 캐시 파일을 직접 잘라내지 않는다.
이번 최소 구현은 슬롯 저장·복원 기능을 사용하고, 파일 전체를 질문·실험 데이터와 같은 비공개 로컬 데이터로 관리한다.
질문을 포함한 전체 슬롯 파일의 로컬 보관이 맞지 않는다면 고정 부분 전용 저장은 별도 설계로 다룬다.

### 보관 위치 — 프로젝트 안의 Git 제외 폴더

후속 사용자 요청에 따라 기본 저장 위치를 프로젝트 내부로 정한다.

```text
<프로젝트 루트>/.local/cache/v2_localLLM/qwen-plan-cache-KV/
```

저장소의 기존 `.gitignore`에 `/.local/` 규칙이 있어 이 경로는 일반 Git 추적 대상에서 제외된다.
계획 수정 시 현재 작업 사본과 사용자가 지정한 K-PLASMA-Analysis-Agent 프로젝트에서 `git check-ignore`로 규칙 적용을 확인했다. 중복 ignore 규칙은 추가하지 않는다.

프로젝트 루트는 현재 코드가 속한 작업 사본 기준이며 실행 명령을 입력한 현재 디렉터리와 구별한다.
worker와 평가를 서로 다른 디렉터리에서 실행해도 같은 경로로 해결한다.
다른 작업 사본의 프로젝트 폴더에 보관하려면 `AGENT_V2_LOCAL_LLM_QWEN_PLAN_CACHE_DIR`에 해당 로컬 경로를 명시한다. 특정 개발자의 경로는 코드에 하드코딩하지 않는다.

`.gitignore`는 Git 추적을 제외하는 규칙이다. 프로젝트 자체의 iCloud·Dropbox 등 파일 동기화와는 별개이므로 캐시 위치가 동기화 대상에서 제외되는지도 활성화 전에 확인한다. 이 작업이 컴퓨터 전체의 인터넷이나 동기화 설정을 자동으로 바꾸지는 않는다.
구현·검증에서 전용 폴더를 생성했다. 실제 사용자 데이터는 저장하지 않았고 현재 폴더에는 소유 표식만 있다.

## 3. 지킬 조건

후속 사용자 지시로 Docker 배정과 경고 판정은
[Docker2GiB·개발 메모리 계획](2026-11-14-003-local-llm-development-memory.md)으로 대체했다.
아래의3GiB·기준 완화 금지는 그 지시 이전의 승인 조건이며, 모델·그래프·응답 계약 조건은 유지한다.

- 앞선 [선행 출력 조건 개선](2026-11-14-001-local-llm-v2.2-prior-outputs.md)의 `required_prior_outputs`와 지시서를 그대로 사용한다. 캐시 비교를 위해 지시서 내용을 다시 바꾸지 않는다.
- v2/v3 원본, 기존 대화·계획·판단 기록·150 Run을 수정하거나 초기화하지 않는다.
- 계획 입력 한도16K, Qwen context24K, batch/ubatch256, 생각 예산2048, 계획 출력6000, 모델 호출90초를 유지한다. 캐시 적중 토큰도 전체 입력 한도 계산에 포함한다.
- Docker Desktop VM 메모리는 기존 **3GiB(3072MiB)** 제한을 유지한다. 모델·DB·웹을 올리기 전에 설정과 실행 중인 VM의 메모리 배정을 읽기 전용으로 확인한다. 이는 Docker VM의 배정이며 Mac 전체 메모리나 Docker 호스트 프로세스 RSS의3GiB 상한을 뜻하지 않는다.
- Qwen과 d1의 순차 상주, 현재 1초 자동 sleep과 반대 모델의 sleep 확인을 유지한다. 캐시 때문에 두 모델을 함께 올리지 않는다.
- d1 승인·기존 의미 검증·재계획 예산·원문 조건 보존을 유지한다. 캐시 저장 실패를 이유로 모델을 다시 호출하지 않는다.
- 캐시 I/O 시간도 기존 실행 시간 계산에 포함한다. 캐시 때문에 모델 호출 예산이나 전체 시간 예산을 늘리지 않는다.
- 질문과 캐시 파일은 외부로 보내지 않는다. 기존 loopback 인증·프록시 무시·리다이렉트 금지·외부 exporter 비활성화를 유지한다.
- 새 캐시 설정은 기본 OFF다. 인공 검증·새 메모리 증거·웹 비교가 통과한 로컬 프로필에서만 켠다.
- 구현·검증이 끝나도 commit/push·실행 서비스 전환은 별도 사용자 지시를 따른다.

## 4. 순서대로 구현할 작업

### 1단계 — 지금 엔진에서 실제로 되는지 확인

고정된 b12317 실행 파일과 Qwen 모델을 사용한다. 이 단계는 새 엔진 도입이나 모델 교체가 아니다.

- [x] 기존 인공 측정 경로를 따라 캐시 실험용 검사를 준비한다. 실제 질문·Run·DB를 입력받지 않고 인공 문장만 사용한다.
- [x] 유효한 계획을 만든 뒤 슬롯0을 파일로 저장한다. sleep 후 같은 모델을 다시 올려 복원하고, 재사용 토큰 수를 확인한다.
- [ ] 다른 인공 질문과 오류 피드백이 붙은 재계획도 시험한다. 이전 질문의 조건이나 생성 계획이 새 입력으로 섞이지 않아야 한다.
- [x] Qwen sleep → d1 인공 검토 → d1 sleep → Qwen 복원의 실제 왕복도 확인한다. d1 입력·판정 방식은 바꾸지 않는다.
- [ ] 파일 크기, 저장·복원·모델 재로딩·입력 처리 시간, 메모리 피크와 swap 변화를 기록한다. 1초 sleep 직전의 저장 경쟁도 확인한다.

**통과 기준:** 저장 응답의 성공뿐 아니라 복원한 상태에서 공통 앞부분의 계산이 실제 재사용돼야 한다. 문맥 체크포인트가 빠져 매번 처음부터 읽으면 통과로 보지 않는다.

**중단 기준:** 현재 빌드에서 복원이 안 되거나, 1초 sleep 때문에 유효한 저장을 안정적으로 확보하지 못하면 운영 연결로 넘어가지 않는다. 엔진 업그레이드·sleep 변경·메모리 기준 완화를 묶어서 적용하지 않고 원인과 필요한 변경을 보고한다.

다른 질문은 native 예비 실험으로, 오류 피드백 전달은 mock 회귀로 확인했다. 새 파일 관리기의 실제 조건 바인딩·두 번째 d1 검토·피드백 재계획은 정식 메모리 중단으로 미검증이다.

### 2단계 — 로컬 캐시 파일 관리 추가

- [x] `QwenPlanCache`가 인증된 기존 Qwen 제어 client를 사용해 저장·복원한다. 별도 HTTP 경로나 외부 저장소를 만들지 않는다.
- [x] 모델 파일·엔진·template·계획 지시서·도구 정의·context·생각 설정이 맞는 파일만 사용한다. 실행 fingerprint가 달라진 캐시와 답변 역할의 캐시는 무효로 취급한다.
- [x] 정상 캐시1개와 교체용 임시 파일1개만 관리한다. 완전히 저장·확인된 새 파일만 유효한 메타데이터로 공개하고, 실패한 쓰기가 기존 정상 캐시를 덮어쓰지 않게 한다.
- [x] 캐시 없음·손상·설정 불일치·저장 실패는 기록하고 기존 방식으로 계산한다. 복원 오류 뒤 슬롯 상태가 불명확하면 먼저 초기화한다. 안전한 초기화도 실패하면 기존 모델 오류 처리로 중단한다.
- [ ] 파일을 클라우드 동기화 대상이 아닌 로컬 캐시 경로에 보관한다. 디렉터리0700·파일0600, 경로 이탈·심볼릭 링크 거부, Git 제외를 확인한다. 로그에는 질문·계획·캐시 내용·인증값을 넣지 않는다.

폴더·파일 권한, symlink 거부와 Git 제외 검사는 통과했다. 사용자 지정 경로의 외부 동기화 제외 확인은 운영 활성화 전에 남아 있다.

**초기 저장 한도 제안:** 유효 캐시 본문1개당2GiB, 보관 파일과 교체 임시 파일을 합친 운영 목표4GiB 이하. 이는 디스크 보관 정책이며 RAM 상한을 뜻하지 않는다. 최대 입력·출력 범위의 인공 실측에서 넘으면 캐시 적용을 보류하고 상한을 자동으로 늘리지 않는다. 저장 전에 남은 공간을 확인하고, 완료한 파일 크기를 확인해 한도 초과 파일은 유효 캐시로 공개하지 않는다. 기본 API가 쓰기 중 크기를 강제로 제한하지 못할 수 있으므로 임시 쓰기의 관측 피크와 보관 상한을 구별해 보고한다.

**오류 처리:** 캐시 제어 HTTP 요청의 별도 제한은5초로 시작한다. 시간초과 후 늦게 끝난 저장 파일은 완료된 것으로 오인하지 않고 임시 파일로 취급한다. 기존 모델 상태 확인·sleep 대기 한도는 유지한다.

### 3단계 — 계획 호출에만 연결

- [x] Qwen 계획 호출의 기존 입력 검사와 토큰 계수를 유지한다. 한도 초과 입력은 캐시 복원 전에 거부한다.
- [x] Qwen을 다시 올렸거나 같은 슬롯을 답변 작성이 덮은 경우에만 계획 캐시 복원을 시도한다. 메모리에 유효한 계획 캐시가 남은 연속 재계획에는 불필요한 디스크 복원을 하지 않는다.
- [x] 유효한 native `submit_plan` 응답을 받은 직후, 자동 sleep 전에 캐시 저장을 시도한다. 원래 모델 응답·인자·usage·오류를 그대로 기존 파서와 그래프에 전달한다.
- [x] worker·인공 측정·평가가 기존 `model_lease()` 안에서 같은 규칙을 사용하게 한다. 준비 확인용 인공 호출이나 답변 호출이 계획용 파일을 덮어쓰지 않게 한다.

## 5. 문제가 생기면 돌아가는 방법

1. 캐시 사용 설정을 OFF로 돌린다. 기존 입력 계산과 계획 생성 방식으로 동작한다.
2. 필요하면 이 기능이 소유한 로컬 캐시 파일만 지운다. 모델 파일·실험 DB·대화·판단 기록은 건드리지 않는다.
3. 기존 준비 검사를 다시 통과한 프로필로 실행한다. 버전이 다른 checkpoint를 강제로 재개하지 않는다.

캐시 OFF에서도 현재 메모리 경고가 자동으로 해소된다고 보장하지 않는다. 메모리 준비 판정은 별도의 기존 조건이다.

## 7. 확인한 근거와 아직 확인할 점

**코드에서 확인:** 현재 `submit_plan`은 지시서·도구 정의와 전체 문맥을 계수한 뒤 native 도구 호출을 수행한다. Qwen 제어 client와 `model_lease()`는 worker·평가·측정에 이미 있다. 준비 검사의 추가 옵션 허용 목록에는 현재 `--slot-save-path`가 없으므로 기능과 검사를 함께 갱신해야 한다.

**공식 기능:** 고정 버전 문서에 슬롯 캐시 파일 저장·복원 API와 sleep 시 KV 메모리 해제가 명시돼 있다. 공통 접두부 재사용은 가능하지만 수치 계산이 항상 비트 단위로 동일하다고 보장하지 않는다. 따라서 답변 문자열 일치 대신 실제 정답·조건·검토 결과를 확인한다. [llama.cpp b12317 서버 문서](https://github.com/ggml-org/llama.cpp/blob/b12317/tools/server/README.md).

**체크포인트:** 문맥 상태 저장에는 재사용에 필요한 체크포인트가 함께 보존돼야 한다. 성공 응답만으로 Qwen의 실제 재사용을 확정하지 않는다. [고정 버전 서버 소스](https://github.com/ggml-org/llama.cpp/blob/b12317/tools/server/server-context.cpp).

**실행 후 남은 점:** native 예비 실험에서 sleep·d1 왕복 뒤10,217토큰 재사용을 확인했다. 새 파일 관리기의 정식 메모리 검사는 기본 Qwen 호출에서 `LOCAL_MEMORY_PRESSURE`로 중단돼 캐시 왕복에 도달하지 못했다. 웹 정확도와 전체 I/O를 포함한 시간 효과는 미검증이며 기본 OFF를 유지한다.
