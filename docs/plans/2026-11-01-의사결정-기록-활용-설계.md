# 의사결정 기록 활용 설계

## 1. 목표

저장된 판단 기록을 Agent가 다시 읽어 프로토타입 v12.3.1의 `RECORD_REUSE` 흐름을 Python Agent에서 동작하게 한다.

- 판단 기록의 저장, 조회, 기록 화면은 이미 구현되어 있으므로 변경하지 않는다.
- 새로 만드는 범위는 **기록 조회, 비용 사유 판별, 후보 제외, 답변 표시**다.
- 메모 원문은 외부 LLM과 Phoenix로 보내지 않는다.

이 문서는 [Agent v1 계획](../superpowers/plans/2026-10-04-agent-graph-v1-plan.md)에서 후속 범위로 둔 D6의 기록 재사용을 구체화한다. 의사결정 기록 RAG는 여전히 범위 밖이다.

## 2. 확정한 범위

| 항목 | 결정 |
| --- | --- |
| 자동 제외 사유 | 프로토타입과 같이 **비용 사유만** 허용 |
| 사유 판별 | 프로토타입 정규식 규칙을 Python으로 이식 |
| 기록 식별 범위 | `acceptance.md` D4에 따라 **Run ID** 기준. 같은 Run의 과거 버전 기록도 집계하고 버전은 화면에 표시 |
| 데모 기록 | D1 상태 유지. 버튼은 그대로 두고 이번 작업에서 수정하지 않음 |
| 시연 데이터 | 웹 완성 후 팀이 화면에서 직접 입력하고, 발표에서 팀이 만든 시연 기록임을 밝힘 |
| 저장 위치 문구 | 별도 PR(`fix/decision-storage-copy`)에서 처리 |

## 4. 프로토타입에서 유지할 규칙

기준 소스: 프로토타입 `assets/record-reuse.js`, `assets/app.js`의 `executeMemoryQuestion`. 저장소의 이식본은 `agent/src/fallback/record-reuse.js`, `memory-request.ts`다.

### 4.1 사유 분류

`classify(note)`의 정규식과 **검사 순서**를 그대로 옮긴다.

| 분류 | 의미 |
| --- | --- |
| `MISSING` | 메모 없음 |
| `NO_COST` | 비용 문제가 없다는 기록 |
| `UNCLEAR` | 전환 표현이 있거나 판단 불가 |
| `COST` | 비용이 반려 사유로 명확함 |
| `OTHER` | 성능 등 다른 사유 |

### 4.2 근거 연결

- EXP는 후보별 `note`를 쓴다. 공통 코멘트는 **후보가 1개인 기록**에서만 해당 Run의 사유로 본다.
- REV는 `targetRunId`, `decision`, `comment`를 후보 1개처럼 다룬다. 프로토타입 이식본과 같이 REV의 `comparedRunIds`는 근거로 쓰지 않는다.
- 메모에 다른 `RUN-…`가 있으면 `UNCLEAR`로 처리한다.
- 건수는 `REJECT` + `COST`인 **기록 ID의 고유 개수**다.
- 채택과 반려가 공존하면 `mixed`로 표시하며 영구 부적합으로 판단하지 않는다.
- 상태 문구는 `관련 기록 없음`, `비용 반려 N건`, `비용 문제 없음 기록`, `반려 사유 미기록`, `사유 확인 필요`, `비용 반려 근거 없음`을 유지한다.

### 4.3 요청 해석

제외 여부와 기준 건수는 LLM이 아니라 프로토타입 `parse`를 이식한 코드가 원문에서 계산한다.

- 기록 요청: `/(반려|과거 기록|이전.*이유)/`
- 제외 요청: `/제외|빼/`
- 기준: `N건 이상`이면 N, 제외 요청에 `많`이 있으면 미정, 그 외 1
- 처리 순서: 비용 단어 없는 제외 안내 → 잘못된 기준 안내 → 범위 없음 안내 → 기준 선택

제외 기준은 1 이상의 정수다. 0, 음수, 소수는 제외를 실행하지 않고 안내한다.

### 4.4 조회 범위

수치 조건이 없는 요청은 다음 순서로 범위를 정한다.

1. 사용자가 첨부한 참조(`comparisonReference.entries`)
2. 현재 후보군(`candidateReferences`)
3. 기준 Run(`activeRun`)

없으면 "먼저 후보 탐색을 실행하거나 결과의 전체 후보를 질문 대상으로 선택해 주세요."로 안내한다. 수치 조건이 있으면 전체 Run을 대상으로 탐색한다.

## 5. 설계 선택

### 5.1 사유 판별

| 방식 | 재현성 | 표현 대응 | 외부 전송 | 구현 부담 | 판단 |
| --- | --- | --- | --- | --- | --- |
| **프로토타입 규칙 이식** | 높음 | 좁음 | 없음 | 낮음 | **채택** |
| 저장 시 사유 태그 | 높음 | 태그 범위 | 없음 | 중간 | 후속 후보 |
| 외부 LLM 분류 | 중간 | 넓음 | 메모 전송 | 낮음 | 제외 |
| 로컬 임베딩·LLM RAG | 중간 | 넓음 | 없음 | 높음 | 후속 후보 |

### 5.2 Agent 진입 방식

| 방식 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| 정규식으로 LLM 전에 분기 | LLM 호출 없음 | 다른 표현을 놓침 | 제외 |
| 도구 인자를 LLM이 전부 추출 | 표현 대응이 넓음 | 기준 건수를 잘못 만들 위험 | 제외 |
| **도구 선택은 LLM, 조건은 코드** | 표현 대응과 재현성을 함께 확보 | 코드 보정 규칙 필요 | **채택** |

### 5.3 정렬 전 제외 위치

| 방식 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| SQL에 제외 목록 전달 | DB에서 처리 | `ReverseContextQuery` 계약 확대, 긴 목록 | 제외 |
| **Python이 `source`를 탐색 전에 필터링** | 계약 유지, 기존 탐색 함수 재사용 | 기록 전체를 메모리에서 분류 | **채택** |

`search_reverse`는 받은 `source`로 정렬하므로 이 필터는 정렬과 조건별 탭 계산보다 먼저 적용된다. 판단 기록이 크게 늘면 조회 범위 축소를 다시 검토한다.

## 6. 전체 흐름

```text
question
  → select_tool: LLM이 도구 1개 선택
  → guard: 원문 parse, 비용·기준·범위 확인
      ├─ 안내 조건 → present
      ├─ 기준 미정 → wait_input → guard
      ├─ decision_records → gather_records → calculate_records → validate_result → present
      └─ reverse_search + 제외 → gather(source 필터링) → calculate → validate_result → present
```

### 6.1 도구

`TOOL_MODELS`에 다섯 번째 도구 `decision_records`를 추가한다.

```python
class DecisionRecordInputs(StrictModel):
    action: Literal["view", "exclude"]
```

- 수치 조건 없는 기록 조회·제외는 `decision_records`를 선택한다.
- 수치 조건이 있으면 `reverse_search`를 선택하고 수치 조건을 기존처럼 추출한다. `ReverseInputs`는 바꾸지 않는다.
- 도구 설명에 "메모 내용을 추측하지 않는다"를 넣고, 프롬프트에 두 도구의 구분 예시를 추가한다.

### 6.2 guard 보정

LLM 선택과 관계없이 **제외 요청이 조용히 무시되지 않게** 코드가 보정한다.

| 상황 | 처리 |
| --- | --- |
| `reverse_search` + 원문이 비용 제외 요청 | 제외 필터 적용 |
| `decision_records` + 수치 조건 감지 | 수치 해석 실패 안내 |
| 다른 도구 + 원문이 비용 제외 요청 | `decision_records`로 전환 |
| 비용 단어 없는 제외 요청 | 제외 없이 안내 |

`action`과 `parse` 결과가 다르면 제외를 실행하지 않고 기록 조회로 처리한다.

수치 판별은 프로토타입과 같은 정규식을 쓴다. 정렬만 있는 `reverse_search`는 현재 제품이 이미 허용하므로 제외 필터도 적용한다. 프로토타입과의 차이는 8절에 남긴다.

### 6.3 기준 선택

새 pending 형식을 사용해 답변이 LLM을 거치지 않게 한다.

```json
{"type":"decision_threshold","id":"...","message":"제외할 기록 건수를 선택해 주세요.","options":[1,2],"allowCustom":true}
```

```json
{"type":"decision_threshold","threshold":2}
```

`wait_input`은 값을 `state.record_threshold`에 저장하고 `guard`로 돌아간다. 잘못된 값이면 제외 없이 안내 답변으로 끝낸다.

### 6.4 제외 취소

취소는 LLM을 거치지 않는 구조화된 요청이다.

```json
{"text":"제외 취소 · <원래 질문>","recordAction":{"type":"UNDO_EXCLUSION","sourceTurnId":"..."}}
```

- 백엔드는 대상 턴이 현재 대화의 저장된 답변이고 제외 결과를 가졌는지 검증한다. 해당 턴의 도구와 입력을 `context.recordAction`에 넣는다.
- 그래프는 `recordAction`이 있으면 `select_tool`을 건너뛰고 기준 없음으로 다시 실행한다.
- 답변의 `toolSelection.call_id`는 `record-action:<sourceTurnId>`로 둔다.
- 새 턴만 추가하며 판단 기록과 Run, 이전 답변은 변경하지 않는다.

### 7.2 Backend

**기록 조회 API**

```text
POST /internal/agent/requests/{id}/decision-records
{ "claimGeneration": 1, "requestRevision": 1 }
→ { "records": [...] }
```

- 기존 worker 토큰과 claim 검증을 사용한다.
- 처음 호출할 때 현재 기록을 `manifest.decisionRecords`에 고정하고, 재시작 후에는 같은 값을 반환한다. 다른 기록이 저장되어도 진행 중인 요청의 결과는 바뀌지 않는다.
- `context` 호출이 만든 manifest에 추가해야 하므로 **Run 문맥 조회 뒤에** 호출한다.
- 필요한 필드만 반환한다: 기록 ID, 버전, 대상 Run, 판단, 메모, 공통 코멘트, 후보, 당시 질문·조건, 작성 시각.

**기존 코드 변경**

| 파일 | 변경 |
| --- | --- |
| `AgentRequestService` | `operationKind`와 `INTENTS` 허용 값, `recordAction`, 기준 선택 resume, 기록 조회 |
| `AgentWorkerController` | 기록 조회 경로 |
| `DecisionRepository` | Agent용 조회 |
| `AnswerV2Validator` | `decision_records`, 선택 필드 `recordExclusion`, 구조 검증 |

DB 스키마는 변경하지 않는다.

### 7.3 답변 계약

schema 2의 `kind`에 `decision_records`를 추가하고 `intent`는 `RECORD_REUSE`를 사용한다. 기존 답변은 그대로 읽힌다. `reverse_search`는 제외를 적용했을 때만 `result.recordExclusion`을 가진다.

```json
{
  "kind": "decision_records",
  "resultStatus": "RECORDS_READY",
  "action": "exclude",
  "threshold": 1,
  "summaryText": "비용 반려 1건 이상이 확인된 후보 1개를 제외했습니다.",
  "notice": null,
  "remaining": [],
  "excluded": [],
  "canUndo": true,
  "recordPolicyVersion": "cost-regex-1",
  "usedRunRefs": []
}
```

`remaining`, `excluded`의 항목은 `runId`, `runVersionId`, `count`, `status`, `mixed`, `entries`를 가진다. `entries`에는 당시 메모와 질문을 저장한다. 이후 기록이 바뀌어도 과거 답변은 저장 시점의 근거를 유지한다.

`resultStatus`는 `RECORDS_READY`, `EXCLUSION_APPLIED`, `NO_EXCLUSION`, `EXCLUSION_UNDONE`, `NOTICE`다. 문구는 4절과 프로토타입 문구를 따르며 `summary`에는 메모 원문을 넣지 않는다.

수치 탐색에서 제외 목록은 프로토타입과 같이 **수치 조건을 만족했던 Run만** 보고한다. `NO_MATCH`라도 `recordExclusion`을 함께 보여 제외 때문에 결과가 없을 수 있음을 알린다.

갱신할 문서: `docs/contracts/agent-answer-v2.schemas.yaml`, `docs/contracts/agent-v1.openapi.yaml`, `docs/verification/agent-v1.md`.

## 8. 프로토타입과의 차이

| 항목 | 프로토타입 | 이번 설계 | 이유 |
| --- | --- | --- | --- |
| 기준 선택 | 완료된 답변 안의 버튼 | 진행 중 요청의 추가 입력 | 현재 HITL·복구 구조 사용 |
| 기록 위치 | 브라우저 저장소 | 서버 DB, 요청 시작 후 고정 | 서버 구조 |
| 질문 라우팅 | 정규식 | LLM 도구 선택 + 코드 보정 | 다양한 표현 대응 |
| 정렬만 있는 요청 | 현재 후보 범위 사용 | 전체 탐색 후 제외 | 현재 제품의 정렬 탐색 동작 유지 |
| 데모 기록 | 동작 | D1로 차단 | 합의한 보류 상태 |

## 9. 보안

- `select_tool`과 `generate_answer` payload에 판단 기록을 넣지 않는다.
- `recentContext`는 `summary`만 사용하므로 `summary`에 메모를 넣지 않는다.
- 현재 `tracing.node`는 그래프 상태 전체를, `RequestBackend.post`는 요청과 응답을 기록한다. 따라서 `tracing._scrub`에서 `decisionRecords`, `entries`, `note`, `comment`, `overallComment`, `sharedComment`를 값과 관계없이 마스킹한다.
- 질문 원문은 기존과 같이 LLM으로 전송된다. 사용자가 질문에 메모 내용을 직접 쓰면 그 문장도 전송된다.
- 회귀 테스트는 고유 문자열을 메모에 넣고 모델 payload와 trace 출력에 나타나지 않음을 확인한다.

## 10. 복구와 정합성

- 기록은 `manifest`에 고정되어 worker가 재시작해도 결과가 같다.
- 답변 완료·실패 시 기존 정리 절차로 임시 문맥을 제거한다. 턴 스냅샷의 근거는 남는다.
- 대화·전체 초기화 중인 요청은 기존 epoch 검사로 거절한다.
- 답변이 참조한 Run을 `usedRunRefs`에 포함한다. 제외된 Run도 포함한다.
- 프롬프트·도구가 바뀌므로 배포 시 진행 중인 요청은 `RECOVERY_VERSION_MISMATCH`로 끝날 수 있다. 기존 정책을 따른다.

## 13. 알려진 한계와 후속

- 정규식은 정해진 표현만 인식한다. `비용 탓에 탈락`처럼 패턴에 없는 메모는 비용 반려로 세지 않는다.
- 기준 건수는 `N건 이상`만 인식한다. `두 번 이상`은 기준 1건으로 처리되어 더 많이 제외될 수 있다. 프로토타입과 같은 동작이며, 답변에 적용 기준을 표시해 확인할 수 있게 한다.
- 한 질문에 도구 하나라는 현재 구조는 유지한다. `제외 후 상위 2개 비교`처럼 여러 작업을 잇는 요청은 지원하지 않는다.
- 메모 표현이 부족하면 사유 태그, 그다음 로컬 RAG를 평가한다. 이 전환은 시연 메모를 실제로 입력해 본 뒤 판단한다.
