# d1 공통 지침 1·4·5번 조건부 적용 — 두 구성 전후 비교

2026-11-17, Asia/Seoul.

**핵심:** 공통 지침 1·4·5번을 필요한 경우에만 넣어도 정상 계획 통과와 실제 숫자 오류 검출은 개선되지 않았다. 기존 2번 문구에서는 정상 **5/5**, 수정한 2번 문구에서는 **1/5**가 그대로였다. 실제 오류 항목 검출도 두 구성 모두 **3/5**, 정확한 오류 사유까지는 **2/5**로 같았다. 입력은 약 **1.8%** 줄었고, 모델 score 시간은 관측상 약 **1.1~1.5%** 줄었다. 수정한 2번 문구에서는 검사 단위 정답이 **43/56→38/56**으로 낮아졌다. 제품 지침은 변경하지 않았다.

## 실험 구성과 핵심 수치

실험 A는 기존 2번 문구를 유지하고 1·4·5번만 조건부 적용했다. 실험 B는 앞서 정상 통과가 1/5였던 범위 한정 2번 문구를 유지하고, 동일한 조건부 선별을 적용했다.

각각 같은 실제 Qwen 정상 계획 5개와 인용문을 보존한 숫자 오류 사본 5개를 검토했다. 각 구성은 계획 10개·검사 56개다. 아래의 적용 전은 저장된 기존 결과이며 재실행하지 않았다. 이번 새 호출은 A 56회+B 56회, **총 112회**다.

| 구성 | 정상 PASS | 오류 항목 검출 | 항목·사유 모두 정확 | 검사 단위 정답 | 검사당 평균 입력 | 계획당 평균 score |
|---|---:|---:|---:|---:|---:|---:|
| A 기존 2번·조건부 적용 전 |5/5|3/5|2/5|44/56|2,200.29토큰|7.682초|
| A 기존 2번·조건부 적용 후 |**5/5**|**3/5**|**2/5**|**45/56**|**2,159.64토큰**|**7.600초**|
| B 수정 2번·조건부 적용 전 |1/5|3/5|2/5|43/56|2,233.29토큰|7.813초|
| B 수정 2번·조건부 적용 후 |**1/5**|**3/5**|**2/5**|**38/56**|**2,192.64토큰**|**7.694초**|

‘오류 항목 검출’은 실제로 숫자를 바꾼 해당 검사에서 match/unclear 외의 오류를 골랐는지다. ‘항목·사유 모두 정확’은 그 항목에서 정답 사유 value_changed까지 골랐는지다. 다른 항목을 잘못 지적해 전체 ISSUE가 된 경우를 정확한 검출로 세지 않았다.

## 바꾼 지침과 그대로 둔 경계

공통 1번에서 input_history가 비어 있으면 ` and latest input_history`만 생략했다. 원래 질문과 실행 입력·의존성을 대조하라는 부분은 보존했다. 이번 실제 계획은 모두 이력이 비어 있어 56개 검사 전체에 이 생략을 적용했다.

공통 4번의 미래 값 미존재 허용 문장은 현재 검사 대상과 관련 단계·참조·선행 의존성에 result_ref, await_input 또는 미래 출력 guard가 있을 때 유지한다. 공통 5번은 result_ref 설명과 await_input 설명을 분리해 필요한 절만 유지한다. 작업·필터 누락 같은 전체 계획 검사는 전체 계획의 관련 기능을 확인한다. 판별 자료를 해석할 수 없으면 기존 지침을 보존한다.

확인 요청 누락 검사는 await_input이 계획에서 빠진 경우도 찾아야 한다. 따라서 계획 안에 await_input이 없더라도 이 검사 종류에는 4번과 5번의 await_input 절을 유지했다. 이번 각 구성에서 확인 검사 10개가 여기에 해당했다. 나머지 46개는 고정 숫자·단일 단계 계획으로 4·5번을 생략했다. result_ref 절이 필요한 검사는 없었다.

두 구성에서 선별 규칙과 결과는 같았다. A와 B 사이에는 기존부터 비교하던 공통 2번 문구 차이만 남았다. 2·3·6번, 개별 검사 지침, 검사 위치, 선택지 ID·설명·순서와 확률 보정값은 각자의 적용 전과 동일하다. 개별 지침에 이미 있는 미래 참조 관련 예외도 그대로 두었다. 별도의 ‘선택 요청이 없으면 match’ 문구는 추가하지 않았다.

질문·추가 입력·확인 문맥·Qwen 요구사항·인용문·실제 실행 계획·실행 효과·검사 목록·선별된 도구/지표 설명·정책은 변경하지 않았다. corpus도 두 구성과 기준이 동일하다. 112개 native 요청의 state 문자열 및 실제 state token prefix를 기존 자료와 대조했다. 후보 ID는 original-conditional-145-v1과 scoped-conditional-145-v1이며 비공개 manifest에 기록했다. 제품 prompt_version은 변경하지 않았다.

## A: 기존 2번 문구에서의 변화

정상 5개는 모두 최초 검토 PASS였다. 소스 전력과 바이어스 전력의 실제 숫자 변경을 놓치는 문제는 남았다. 에너지 범위의 상한 변경은 기존처럼 boundary_changed로 분류해, 오류 항목을 찾았으나 정답 사유 value_changed와는 달랐다.

검사 선택 5개가 달라졌다. 확인 요청 누락 검사에서 오류 사본의 잘못된 unclear 2개가 match로 수정됐다. 반면 범위 오류 사본의 작업 검사에서 기존 match가 unexpected로 바뀌어 새 오판 1개가 생겼다. 기존에 잘못 missing이라던 정렬 검사 2개는 unclear로 바뀌었으며 여전히 오답이다.

따라서 검사 정답은 44/56→45/56, 수정된 오판 2개·새 오판 1개다. 확인 검사 오판은 2/10→0/10으로 줄었지만 작업·필터 누락 및 정렬의 부수 오판은 남았다. 모든 검사와 사유까지 맞힌 계획은 5/10→5/10이었다.

오류 계획 전체 상태는 ISSUE 4/5, UNCLEAR 0/5, 잘못된 PASS 1/5로 전후가 같았다. 바이어스 숫자 오류가 있는 계획의 ISSUE는 실제 바이어스 오류 검출이 아니라 작업·필터 누락 오판으로 만들어진 상태다.

## B: 수정한 2번 문구에서의 변화

정상 통과는 1/5로 그대로였다. 정상 4개에서 확인 요청 누락 검사의 unclear가 유지됐고, 확인 검사 전체 오판도 9/10으로 같았다.

추가로 필터 누락 검사 4개와 정렬 검사 1개가 match→unclear로 바뀌었다. 이 중 필터 누락 검사 2개는 정상 계획에 생긴 오판이다. 기존 오판을 정답으로 고친 검사는 없었다. 검사 정답은 43/56→38/56이며, 모든 검사와 사유까지 맞힌 계획은 1/10→1/10이었다.

오류 계획 전체 상태는 ISSUE 3/5, UNCLEAR 2/5, 잘못된 PASS 0/5로 전후가 같았다. UNCLEAR로 막힌 것을 실제 숫자 오류를 검출한 것으로 해석하지 않는다.

score는 backend.score 호출부터 GPU 동기화 완료까지의 시간이다. 가중치 로드·프로세스 시작·별도 사전 패킹·실행기 대기·웹 처리는 제외했다. 실행기 wall은 별도 진단값이며 프로세스 시작과 로드·폴링을 포함한다.

기준 시간을 다시 측정하지 않았고 반복·순서 반전도 하지 않았다. 약 1%대 차이는 단회 관측이며, 지침 축약이 그만큼의 속도 개선을 보장한다는 증거로 사용하지 않는다.

전체 입력에서 공통 1·4·5번의 이번 생략 분량이 작아 약 1.8%만 줄었다. 전체 계획·검사 목록·나머지 설명을 줄인 실험이 아니다. 이 정도 축약으로 핵심 오류가 해소되지 않았으므로, 이번 자료로 단순한 지침 길이를 오판의 유일한 원인으로 볼 수 없다. 어떤 표현·입력 구조가 내부 점수에 영향을 줬는지는 이 실험만으로 확정하지 않는다.

## 환경·메모리·유지 상태

M4 Pro 24GiB, LiquidAI/d1-2B의 MLX affine8/group64·일부 BF16 보존, Metal GPU, MLX 0.32.4·mlx-decision 1.3.0을 유지했다. group_size=1·independent_batch_size=1로 각 검사를 독립 실행했다. 전체 계획 10개를 한 모델 입력에 묶지 않았다.

모델 설정과 실제 LangGraph의 plan 이전 중단 상태에서 plan_review_enabled=true를 실행 전후 확인했다. Docker VM은 1536MiB, 메모리는 기존 development 정책을 유지했다. 기존 메모리 증거의 유효성을 확인했으며 별도 메모리 부하 추론을 추가하지 않았다.

| 이번 실행 관측 | A | B |
|---|---:|---:|
| OS active+wired+compressor 피크 |17.717GiB|18.003GiB|
| 표본 수 |188|188|
| warning / critical / unknown 표본 |0 / 0 / 0|0 / 0 / 0|
| 추가 swap |0|0|

OS 피크는 전체 시스템 관측이다. DB OOM 증가는 없었다. 기존 swap 자체가 0이라는 뜻은 아니다.

worker를 종료·일시정지하거나 서비스·모델 프로필을 교체하지 않고 기존 model_lease로 충돌을 막았다. 종료 후 제품 소스·설정·worker 환경·프로세스 ID·DB를 보존했고, d1 서비스가 해제 상태이며 기존 메모리 증거도 계속 유효함을 확인했다.

## 검증과 산출물

- CPU 선별 검사: 구현 전 4실패, 구현 후 4통과. 빈 이력·고정 숫자, 이력 존재, 확인 누락 검사, 미래 결과의 전이 참조, 미확인 검사 보존을 확인했다. 명령은 `agent/python/.venv/bin/python -m pytest .local/runtime/v2.5-d1-conditional-common/test_conditional.py -q`다.
- 실제 tokenizer 패킹은 가중치 로드·추론 0회다. 기존 state token prefix·선택지 token 그룹·보정값이 같고 절단이 없음을 확인했다. 준비 검증은 `verify_inputs.py`로 두 구성 112개 모두 대조했다.
- 실행은 각 구성의 `run_evaluation.py`를 순서대로 호출했다. 완료된 결과만 기존 normalize_response/parse_plan_review에 통과시켜 원시 선택·확률·전체 상태가 일치함을 확인했다.
- 새 d1 의미 검사 112회, 새 Qwen 호출 0회, 준비/warmup 추론 0회, 자동 재시도 0회다. 고정 계획의 최초 검토만 측정했고 재계획·답변 재작성·Run 도구·웹/API 요청 평가는 실행하지 않았다.
- 기준 corpus·입력·결과·패킹·분석 파일은 내용 hash로 보존을 확인했다. 최종 `verify_completion.py`로 실행 환경과 완료 수를 확인했다.
- 실험용 코드와 원시 산출물은 Git 제외 `.local/runtime/v2.5-d1-conditional-common/`에 보관했다. 제품 소스는 변경하지 않았다. 전체 제품 테스트·웹 평가는 추가 실행하지 않았다.
- 기존 worktree Git 메타데이터 오류로 Git diff/branch 확인은 불가능했다. 내용 hash와 공개 문서의 원문·비밀값 미포함을 별도 검증했다. Git 복구·커밋·push·PR·배포는 하지 않았다.

두 후보 모두 자동 채택하지 않았다. A는 검사 정답이 1개 늘었지만 새 오판도 1개 생겼고, B는 새 오판이 5개 늘었다. 제품은 기존 6개 공통 지침과 개별 검사 지침을 유지한다.
