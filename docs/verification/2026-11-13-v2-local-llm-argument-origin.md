# Native 도구 인자 형식 오류의 발생 지점

2026-11-13, Qwen 원문과 LM Studio의 API 결과를 **동일한 생성 1회 단위로** 비교했다.
재현된 JSON 문법 오류는 **Qwen 원문에 이미 존재**했고, LM Studio는 해당 내용을 문자열로
보존해 반환했다. 정상 원문을 변환 과정에서 깨뜨린 사례는 이번 진단에서 발견하지 않았다.

## 방법과 범위

- 실제 Run이나 사용자 질문 원문을 사용하지 않은 인공 진단이다. 웹 40문항을 다시 평가하지 않았다.
- 먼저 인공 입력 4건을 수집했다. 그중 2건에서 JSON 파싱은 되지만 스키마 규칙을 어긴 응답이 나왔다.
- JSON 문법 오류 자체를 확인하라는 후속 요청에 따라, 최대 3건 중 오류 재현 시 중단하는
  추가 진단을 시작했다. 첫 입력에서 재현되어 중단했다. **모델 호출은 총 5건**이다.
- 기존 `_tool_request`와 `call_submit_plan` 경로, 원래 도구 스키마·추론 설정·출력 한도를 사용했다.
  복사 대조 1건 외의 4건은 기존 `PLAN_INSTRUCTIONS`를 그대로 사용했다.
- `lms log stream --source model --filter input,output --json`으로 모델 입력·출력 원문을 받고,
  같은 HTTP 요청의 본문과 native `tool_calls[].function.arguments` 응답을 함께 보관했다.
  각 생성마다 입력·출력 로그 1개씩, 동일 모델 ID와 해당 인공 질문을 확인했다.
- 모델에 전달된 이름·설명·인자 스키마의 제약은 API 요청과 일치했다. 프롬프트에서 생략된
  API 메타데이터는 `function.strict`와 스키마 최상위 `title`뿐이었다. 이 차이를 인자 제약의
  변경으로 취급하거나, `strict` 강제 기능의 내부 구현을 입증한 것으로 해석하지 않았다.

원문 입출력 기록 기능의 의미는 [LM Studio 공식 문서](https://lmstudio.ai/docs/cli/serve/log-stream)도 확인했다.
변환 원인 판정은 문서상의 설명이 아니라 실제 수집한 동일 생성의 원문/API 비교에 근거한다.

## 관측 결과

| 진단 | Qwen 원문 | LM Studio API | 기존 앱 검사 |
| --- | --- | --- | --- |
| 고정 계획 복사 | 정상 JSON 배열, `base_revision`은 `None` | 배열 내용 일치, `None` 문자열 보존 | 기존 호환 처리 후 입력 계획과 정확히 일치 |
| 단순 검색 계획 | 정상 JSON 배열 | 배열 내용 일치 | PlanDraft 형식 통과 |
| 검색·설명 계획 | JSON 배열이지만 `requires` 등에 잘못된 필드 | 원문과 같은 객체·배열 | 스키마 검사 실패 |
| 사용자 선택 계획 | JSON 배열이지만 선택 단계의 필드·형식 오류 | 원문과 같은 객체·배열 | 스키마 검사 실패 |
| 중첩 계산 계획 | `steps` 배열 안에서 닫는 괄호 불일치 | 같은 깨진 본문을 문자열로 반환 | `/steps` JSON 파싱 실패 |

`steps`와 `requirements` 총 10개를 비교했다. 정상 JSON 배열 9개는 API 배열과 값이 정확히
일치했다. 문법이 깨진 `steps` 1개는 양끝 공백을 제외한 본문이 API 문자열과 정확히 일치했다.

재현된 `steps`는 표준 JSON 파서에서 `Expecting ',' delimiter`가 발생했다. 원문 내
문자 위치 817(0부터 시작)에서 배열에 닫는 대괄호가 와야 할 위치에 `}`가 있었다.
즉, API 변환 전 모델 출력 단계에서 이미 JSON으로 해석할 수 없는 내용이었다.
원문이나 운영 인자를 자동으로 고쳐 실행하는 우회 처리는 적용하지 않았다.

관측된 흐름은 다음과 같다.

```text
Qwen이 XML 도구 호출의 steps 안에 잘못된 JSON을 생성
→ LM Studio가 그 내용을 문자열로 보존해 API에 반환
→ 기존 call_submit_plan이 내부 JSON을 읽다가 실패
→ MODEL_OUTPUT_INVALID로 차단
```

따라서 이번에 재현된 오류에서 문자열 반환은 이미 잘못된 원문이 전달된 결과다.
LM Studio가 정상 배열을 잘못된 JSON 본문으로 바꾼 증거는 발견하지 않았다.
별도의 스키마 오류 2건 역시 잘못된 필드가 Qwen 원문에 존재했고 API가 이를 보존했다.

## 보존·검증과 한계

진단 시작 당시 GUI에는 문맥 8,192·parallel 4의 유휴 인스턴스가 적재되어 있었다.
기존 상태를 기록하고 평가 당시 문맥 32,768·parallel 1의 인스턴스로 순차 진단한 뒤,
각 진단 묶음 종료 시 원래 인스턴스 ID·문맥·parallel을 복구하고 API에서 일치 여부를 검사했다.
기존 모델 lease를 사용했고, 원래 인스턴스가 idle·대기 0인 상태에서만 진단을 시작했다.

진단 전후 로컬 namespace의 Python 소스 전체, 최종 응답 JSON Schema, thinking OFF 템플릿의
SHA-256이 일치했다. 그래프·도구 계약·최종 응답 양식·운영 후처리는 변경하지 않았다.
계획을 실제 Run에 실행하거나 d1 의미 판정의 성능을 평가하지 않았다.

비공개 로컬 증거는 원문 입출력 로그, HTTP 본문, `paired-comparison.json`,
`syntax-cause.json`, 복구 확인 파일과 변경 전 소스 해시다. 비교기의 정상/원문 오류/변환 차이
구분은 인공 self-check로 확인했고, 실제 생성 5건의 1:1 대응·값 일치·변경 없음 assert를 실행했다.

과거 40문항의 형식 오류 96건 전부에 대해 원문을 소급 확보한 결과는 아니다. 이번에는
그와 같은 문법 오류 유형을 별도로 재현해 발생 지점을 확인했다. 생각모드·모델 크기·양자화·
샘플링 설정 중 무엇이 오류 빈도에 얼마나 영향을 주는지는 비교하지 않았다.

REA 커넥터를 통한 설치 앱 분석 시도는 앱 소스의 외부 전송 위험으로 자동 승인 검토에서
거부되어 실행되지 않았다. 이후 사용자 지시에 따라 REA를 사용하지 않았다. 변환 원인
판정에는 수집한 입출력 비교만 사용했다.
