# d1 독립 4개 GPU 배치 구현·비교 기록

기준: [구현 계획](../plans/2026-11-15-001-local-llm-d1-independent-batch4.md). 구현·준비 검사·본72회와 역순2회를 완료했다.
**B/D 입력·판정·확률 동등성과 메모리는 통과했지만, 독립 배치의 속도 개선은0.49%로20% 목표에 미달했다. 기본 실행은 기존 Q8로 복구했다.**
실제 입력·모델 응답·프로필·DB hash·원시 시계열은 Git 제외 로컬 경로에 보관한다.

## 구현과 보존

- d1 MLX는 검사마다 전체 본문과 질문 하나를 공식 encoder로 인코딩한다. 최대 4개 pack을 별도 행으로 계산하고 공식 hidden state/readout/calibration을 재사용한다.
- `D1_GROUP_SIZE=1`, `D1_INDEPENDENT_BATCH_SIZE=4`의 조합을 명시적으로 선택한다. 기존 개별 기본값은1이다. 공동 입력4나 모델4벌을 만들지 않는다.
- 행당 전체 입력16000, 배치당 `행 수×가장 긴 행≤32768`을 유지한다. 긴 입력은 미리 분할하며 OOM 뒤 조용히 개별 방식으로 바꾸지 않는다.
- 계수·설정·실제 서비스·프로필·준비 증거를 연결한다. 모델 해제와 빈 런타임 복귀 뒤에만 Qwen을 재개한다.
- 요청별 GPU 피크를 초기화해 과거 누적 피크와 구분한다. singleton pack의 토큰/레이아웃 hash로 B/D 입력 동일성을 확인한다.
- 그래프·계획/최종 응답·스트리밍·검토 지침·선택지·재계획/재작성 한도는 유지한다. 시작 시 hash와 보존 파일을 비교했다.
- 모델 설정과 실제 그래프의 중단된 계획 진입 전 상태에서 `plan_review_enabled=true`를 확인한다. 고정 d1 입력 대조 자체는 전체 웹 Agent 평가가 아니다.

## Docker와 데이터

Docker Desktop VM을2048→1536MiB로 변경했다. 실제 엔진 `MemTotal`은1,538,883,584바이트다.
같은 PostgreSQL 컨테이너·볼륨,150 Run/150 version,기존 대화85개·요청224개를 재시작 전후 hash로 확인했다. 당시 처리 중 요청0, OOM/kill0이었다.
재시작 직후 순차 조회는 약0.056초였고 DB cgroup 피크는115,060,736바이트였다.

DB 동시 조회10개는 실행하지 않았다.1.5GiB는 Docker VM 배정량이며 DB 또는 호스트 Docker RSS 상한과 구별한다.
실제 모델 준비·비교 중에는 공유 DB를 정상 정지하고 인공 데이터 검사 DB 하나만 사용한다. 종료 후 공유 DB와 기존 서비스 상태를 복구·재검증한다.

## 코드 검증

`agent/python`에서 다음 검사를 수행했다.

```sh
.venv/bin/python -m pytest -c pytest-v2-local-llm.ini tests/v2_local_llm \
  tests/test_contracts.py tests/test_answer_v2_wire.py \
  tests/test_answer_stream.py tests/test_eval_graph_versions.py -q
.venv/bin/python -m mypy src
```

로컬 회귀와 공통 계약 합계598개 통과, 초기 복제 전용8개 제외, mypy121개 소스 통과다.
영향 소스·서비스·평가·테스트의 Ruff와 기존 Node 실행 스크립트 테스트8개도 통과했다.
보호 대상 그래프의 실제 평가는 실행하지 않고 소스 보존만 hash로 확인했다.

별도 읽기 전용 코드 검토에서 Critical0/Important3/Minor1을 확인했다.
정상 독립4 응답을 재검증할 때 배치 크기를 누락한 경로, 추가 준비 실패 뒤 캐시 모델 단계 진입, 비교 환경·역순 증거 검증을 각각 실패 테스트로 재현하고 보완했다.
추가 준비의 단계 이름도 보완했다. 수정 후 전체 회귀를 통과했으며 미해결 지적으로 남기지 않는다.

## 메모리 준비 검사

같은 Docker1536MiB, development 정책, Qwen24K·batch/ubatch256·생각ON, Qwen 캐시OFF로 측정했다.
7종에는 Qwen 및 d1의 작은/중간/큰 인공 입력과 큰 계획 제출이 포함된다.

| 프로필 | 기본7종 | 호스트 지표 피크 | warning/critical | 추가 swap |
|---|---:|---:|---:|---:|
| A: 기존 Q8 개별 |7/7|18.171GiB|0/0|0|
| B: MLX BF16 개별 |7/7|18.516GiB|0/0|0|
| D: MLX BF16 독립 최대4행 |7/7|18.457GiB|0/0|0|

B/D에는 각각4검사짜리 인공 입력을 약4K·약15.5K 토큰으로 추가1회씩 실행했다. 총4개 준비 검토 요청이다.
D는 짧은 입력의 실제4행과 긴 입력의2행+2행 계산을 확인했다. 해당 요청의 GPU 활성 피크는 각각 약4.344GiB·5.289GiB였다.
모델 해제 후 MLX active16바이트/cache0의 기존 보정 기준으로 돌아왔으며 준비 증거를 기존 검증기로 다시 확인했다.

호스트 지표는 active+wired+physical compressor 합계다. MLX 활성 피크·할당기 캐시·RSS와 합산하지 않는다.
위 준비 결과는 전체 고정 비교·장시간 운영의 무스왑 안정성을 대신하지 않는다. 실제4행·2+2행 수치는 이전 선형 메모리 추정과 구별한 실측이다.

## 고정 입력 비교 방법

A=기존 llama.cpp Q8 개별, B=MLX BF16 개별, D=동일 MLX BF16 독립 최대4행이다. 과거 공동 입력 후보 C는 재실행하지 않는다.
정상3/오류5의 기존 고정 인공 계획을 방식별3회씩 대조한다. 최대72개 본 검토와 정상 선택 확인 사례의 B/D 실제 역순 각1개, 합계74개다.
반복별 프로필 순서는 A→B→D, B→D→A, D→A→B다. 한 번에 한 모델 프로필만 실행한다.
추가 워밍업 모델 호출 없이 이미 통과한 실제 준비 증거·artifact·live facts·유휴 상태를 평가 진입 전에 검증한다. 제품 worker의 정식 준비 검사는 변경하지 않는다.

입력 digest, 모든 검사 선택과 최종 상태, 확률 차이, B/D singleton pack hash, 공통 Qwen 설정과 B/D 모델·서비스·라이브러리 식별값을 비교한다.
전체 시간에는 입력 검사·전환·로드·계산·파싱·해제 확인이 포함되며 Qwen 계획 생성 시간은 제외한다.
프로필별 비교값은 먼저 각 사례의3회 중앙값을 구하고, 그8개 사례 중앙값의 중앙값으로 계산한다. 사례별 원시 시간과 전체 평균/최대값도 별도로 보존한다.
1차 계획 PASS·검토 지적·복구 후 통과를 합치지 않는다. 이번 고정 계획 대조에는 재계획을 실행하지 않는다.

## 고정 입력 비교 결과

| 방식 | 기대 최종 상태 일치 | 전체 검토 중앙값 | 평균 / 최대 시간 | 비교 구간 호스트 지표 피크 |
|---|---:|---:|---:|---:|
| A: 기존 Q8 개별 |9/24 — 매회3/8|15.367초|19.140 /32.676초|18.124GiB|
| B: MLX BF16 개별 |12/24 — 매회4/8|13.653초|17.179 /29.488초|17.627GiB|
| D: MLX BF16 독립 최대4행 |12/24 — 매회4/8|13.586초|17.087 /29.000초|17.653GiB|

24개는 서로 다른24문항이 아니라 **같은8개 고정 계획을3회 반복한 요청 수**다.
모든 본 입력 digest·공통 실행 조건·B/D 모델과 서비스 식별값이 일치했다.
B/D의 모든 검사항목 선택·최종 상태가24쌍에서 같고 반복 간에도 안정적이었다. 대응 확률의 최대 절대 차이는0이었다.
실제 검사항목11개를 역순으로 실행한 B/D 각1건도 원래 결과와 모든 선택·최종 상태가 같았다. 실제 역순 ID를 확인했으며 요청 수는각1회다.

| 고정 계획 | 기대 상태 | A — 3회 동일 | B — 3회 동일 | D — 3회 동일 |
|---|---|---|---|---|
| 정상 조회 |PASS|PASS|PASS|PASS|
| 정상 전체 후보 비교 |PASS|PASS|PASS|PASS|
| 정상 선택 확인 후 비교 |PASS|ISSUE|ISSUE|ISSUE|
| 경계 변경 |ISSUE|PASS|PASS|PASS|
| 단위 변경 |ISSUE|PASS|ISSUE|ISSUE|
| 비교 누락 |ISSUE|PASS|PASS|PASS|
| 요청하지 않은 설명 추가 |ISSUE|PASS|PASS|PASS|

상태 일치만으로 구체적인 지적 이유까지 맞았다고 보지 않는다. B/D의 단위 변경 사례는 `request.tasks=unexpected`로 지적했고,
정상 선택 확인과 필요한 선택 생략 사례는 모두 `ordering.search=direction_changed`였다.
따라서 단위 오류·선택 누락 자체를 올바르게 검출한 성적으로 확대하지 않는다. 정상 계획의 잘못된 거절도 남아 있다.
이는 기존 MLX 개별의 판정을 그대로 재현한 것이며 새 독립 배치 때문에 생긴 선택 차이는0이었다.
8개 고정 입력과 검사 선택을 과거 B 기록에 대조했을 때도 모두 같았다.

### 시간 판정

- B→D: **0.49% 단축**, 약0.067초 차이로20% 단축 목표 실패다.
- A→D:11.59% 단축이지만 엔진·정밀도 변경이 함께 있으므로 이를 독립 배치의 효과로 해석하지 않는다.
- GPU에서 실제4행을 계산해도 공통 본문을 행마다 독립 계산하는 전체 연산량은 유지된다. 이번 관측에서는 큰 속도 이득이 없었다.
- 개별 입력이 이미 GPU를 충분히 사용하는지, 어떤 커널이 병목인지는 GPU 활용률·커널별 프로파일을 측정하지 않았으므로 확정하지 않는다.

### 메모리 판정

| 비교 구간 지표 | B: MLX 개별 | D: 독립 최대4행 |
|---|---:|---:|
| 요청별 GPU 활성 피크 최대 |3.933GiB|4.466GiB|
| 할당기 캐시 경계 표본 최대 |6.239GiB|4.447GiB|
| 호스트 지표 표본 최대 |17.627GiB|17.653GiB|
| warning / critical |0/0|0/0|
| 각 실행 구간 시작 대비 추가 swap 최대 |0|0|

GPU 활성 피크는 **+0.533GiB/13.55%**였다. 할당기 캐시는 재사용을 위해 남겨둔 비활성 메모리이며 순간 피크가 아닌 요청 끝 경계 표본이다.
활성 피크·캐시 최대·호스트 피크를 서로 더하지 않는다. 캐시 보유량과 다른 앱 상태도 달라 호스트 약0.026GiB 차이를 순수 배치 증가량으로 확정하지 않는다.
Q8의 같은 GPU 할당기 지표는 수집하지 않아 임의 수치를 만들지 않았다. A/B/D 전체 비교 구간과 역순 검사에서 OOM/critical과 추가 swap은 없었다.
준비 검사까지 포함한 호스트 지표 전체 최대는18.516GiB였다.1.5GiB는 계속 Docker VM 설정이며 이 호스트 지표의 상한이 아니다.

## 적용 판정과 복구

독립4 구현은 명시적 실험 프로필로 남기고 자동 기본값 승격은 하지 않았다.
**독립성·동등성·메모리는 통과, 속도 목표 실패, 기존 모델의 검토 품질 문제 지속**으로 판정했다.

소유한 인공 DB·검사 백엔드·프런트엔드·브라우저를 종료하고 공유 DB를 복구했다.
기존150 Run/150 version·대화85개·요청224개와 기존 행 hash가 모두 보존됐고 처리 중 요청0이었다.
소량의 인공 임시 테이블 쓰기·읽기도 확인했으며 실제 제품 테이블의 실험 데이터는 수정하지 않았다.
공유 DB의 OOM/kill은0이다. Docker VM1536MiB와 실제 `MemTotal`1,538,883,584바이트를 유지했다.

기본 Q8 개별·Qwen 캐시OFF·계획 검토ON으로 로컬 worker를 복구하고 새로운 `worker ready: graph=v2_localLLM` 로그를 확인했다.
복구에 필요한 정식 준비 연결 검사의 Qwen3회·d1 1회는 본74개와 구별한 운영 복구 호출이다. 자동 반복 실험은 추가하지 않았다.
기존8080 백엔드와5173 웹 응답은HTTP200이었다. 실제 로그인된 브라우저 세션과 새 사용자 질문의 웹 평가는 재실행하지 않았다.

상용 모델 호출·40문항·실제 웹 문항 제출·OS 인터넷 차단·commit/push는 수행하지 않았다.
