# LocalLLM v2.5 — 발췌 + citation에서 검사 목록만 복구한 평가

## 핵심

**이번 정상 5개·숫자 오류 5개에서는 오류 항목 재현율 5/5를 유지하면서 정상 반려율이 2/5→0/5로 줄었다.** R02·R03의 정상 소스 전력 오판이 해소됐고, 실제 소스 전력 오류도 계속 검출했다. 질문 축소나 다른 조건의 실행값 복구 없이, 숫자 검토 입력의 검사 목록만 복구한 결과다.

다만 R04의 오류 항목은 잡았지만 숫자 변경을 `boundary_changed`로 분류했다. 따라서 오류 사유까지 정확한 결과는 5/5→4/5다. 다른 검사에 남아 있는 부수 오판도 포함하면 전체 검사 정답은 45/56→47/56이며, 모든 검사·사유까지 맞은 계획은 4/10→6/10이다. 전체 검토가 완전히 해결됐다는 뜻은 아니다.

전체 검사당 평균 입력은 1,987.18→2,046.93토큰(+3.01%), 계획당 평균 d1 채점은 6.926→7.062초(+1.96%)였다. OS 관측 메모리 피크는 17.877 GiB였고 경고·위험·추가 스왑·DB OOM 증가는 없었다. 운영 그래프나 응답 형식에는 반영하지 않은 평가용 구성이다.

## 바꾼 것과 유지한 것

- 기준은 [기존 발췌 + citation 평가](2026-11-17-local-llm-d1-citation-name.md)다. 동일한 실제 Qwen 정상 계획 5개와 인용문을 보존한 숫자 오류 사본 5개를 사용했다. 새 Qwen 계획을 만들지 않았다.
- 숫자 검사 22개에서 `state.check_specs`만 복구했다. 현재 검사 항목을 첫 위치에 두고 같은 계획의 나머지 검사 명세를 원래 상대 순서로 추가했다. 순방향은 목록 1개→6개, 역방향은 1개→5개다.
- 복구한 것은 검사 이름·종류·대상 경로 등의 **검사 명세**다. 다른 조건의 실행 숫자나 원본 계획 전체를 복구한 것이 아니다. 판정 요청인 `questions`는 계속 현재 검사 한 개뿐이다.
- 발췌 계획·`citation.quote`·질문 원본·실행값·단위·도구/지표 설명·발췌 표시·지시서·선택지·온도는 그대로 유지했다. 질문은 축소하지 않았다.
- 누락·정렬 검사 34개는 요청과 패킹을 완전히 유지했다. 검사 수 자체도 56개로 같으며, 검사 목록을 복구했다고 실제 호출 수를 늘리지 않았다.
- 기존 2번+조건부 1·4·5번 공통 지침, Q8+MLX 단일 처리(`group_size=1`, `independent_batch_size=1`), Metal GPU, Docker VM 1,536 MiB(1.5 GiB), development 메모리 정책을 유지했다.
- d1은 `LiquidAI/d1-2B`, revision `a6bce774e6dde338dcc3036ceb5d91f78bf4c19e`, affine 8비트/group 64 구성이다. 기존 BF16 유지 계층도 그대로이며, 엔진은 mlx-decision 1.3.0이다. 정밀도나 보정값을 새로 조정하지 않았다.
- 실행 전 설정과 실제 그래프 상태의 `plan_review_enabled=true`를 확인했다. 기존 그래프·최종 JSON/SSE·저장 계약·작업자 환경·공유 웹/백엔드/DB는 변경하지 않았다.
- 계획마다 모델을 적재해 검사 5~6개를 하나씩 독립 채점하고 해제했다. 실제 d1 추론은 56회, 반복·예열·재시도·추가 Qwen·Run 실행·REPLAN·답변 재작성은 0회다. 기존 그래프의 최대 2회 재계획·최대 1회 재작성 설정은 유지했지만 이번 고정 계획 실험에서는 실행하지 않았다.

## 정확도 비교

오류 항목 재현율은 **실제로 바꾼 숫자의 검사에서 오류를 검출했는지**로 센다. 무관한 검사 때문에 계획 전체가 ISSUE가 된 것을 정답으로 세지 않는다. 정상 반려율은 정상 계획이 PASS가 아닌 비율이며 ISSUE와 UNCLEAR를 함께 센다.

| 지표 | 기존 발췌 + citation | 검사 목록 복구 |
|---|---:|---:|
| 실제 오류 항목 재현율 | 5/5, 100% | **5/5, 100%** |
| 정상 계획 반려율 | 2/5, 40% | **0/5, 0%** |
| 정상 계획 최초 PASS | 3/5 | **5/5** |
| 오류 항목·사유까지 정확 | 5/5 | **4/5** |
| 오류 계획 전체 ISSUE | 5/5 | 5/5 |
| 오류 계획 전체 UNCLEAR | 0/5 | 0/5 |
| 오류 계획의 잘못된 PASS | 0/5 | 0/5 |
| 숫자 검사 정답 | 19/22, 86.36% | **21/22, 95.45%** |
| 누락·정렬 검사 정답 | 26/34 | 26/34 |
| 전체 검사 정답 | 45/56, 80.36% | **47/56, 83.93%** |
| 모든 검사·사유까지 엄격 일치한 계획 | 4/10 | **6/10** |

엄격 일치한 계획은 정상 5개와 R02 오류 사본이다. 나머지 오류 사본은 실제 오류 항목은 모두 검출했지만 부수 검사 또는 사유 분류가 틀렸다. 복구 후 통과를 최초 통과에 합산하지 않았다.

| 사례 | 정상 계획: 기존→복구 | 실제 오류 항목 | 오류 목표 판정: 기존→복구 | 복구 후 오류 계획 |
|---|---|---|---|---|
| R01 | PASS→PASS | 압력 | value_changed→value_changed | ISSUE |
| R02 | ISSUE→PASS | 소스 전력 | value_changed→value_changed | ISSUE |
| R03 | ISSUE→PASS | 바이어스 전력 | value_changed→value_changed | ISSUE |
| R04 | PASS→PASS | 에너지 범위 상한 | value_changed→**boundary_changed** | ISSUE |
| R05 | PASS→PASS | 플럭스 하한 비교값 | value_changed→value_changed | ISSUE |

### 소스 전력 오판과 남은 사유 오판

| 검사 | 기존 선택·점수 | 복구 후 선택·점수 |
|---|---|---|
| R02 정상 소스 전력 | unexpected 46.86%, match 16.23% | **match 45.29%**, missing 31.58% |
| R03 정상 소스 전력 | missing 46.16%, match 23.41% | **match 50.94%**, missing 36.34% |
| R02 실제 소스 전력 오류 | value_changed 34.58%, match 16.41% | **value_changed 57.04%**, match 9.52% |
| R04 실제 상한 숫자 오류 | value_changed 28.19%, boundary_changed 24.87% | **boundary_changed 27.89%**, value_changed 25.18% |

판정이 바뀐 검사는 총 4개다. R02 정상 소스, R03 정상 소스, R03 오류 사본 안의 정상 소스라는 기존 오판 3개가 고쳐졌고, R04 오류 사유 1개가 틀렸다. 변경하지 않은 누락·정렬 34개의 선택과 모든 선택지 점수는 기준과 정확히 같다.

숫자 오류 사본에 남은 부수 오판은 R01 작업·필터 검사의 unclear 2개, R03 작업·필터 검사의 missing 2개, R04 작업 검사의 unexpected·정렬 검사의 unclear 2개, R05 작업·정렬 검사의 unclear 2개다. 합계 8개이며 이번에 입력을 바꾸지 않은 검사들이다. R04 사유 오판을 더해 전체 오답은 9개다.

이번 고정 입력에서는 검사 목록만으로 소스 전력의 정상·오류 구분이 함께 개선됐다. 검사 범위에 관한 문맥이 판정에 영향을 준다는 근거지만, 모델이 내부적으로 왜 그렇게 해석했는지는 확정하지 않는다. 선택지 점수는 정확도나 실제 정답 확률이 아니며, R01 오류의 value_changed 33.95%와 unclear 32.77%처럼 근소한 차이도 남아 있다.

## 검증과 로컬 보관

- 입력 준비 assert로 22개 요청의 `check_specs`만 바뀌고 나머지 34개가 완전히 같음을 확인했다. 원문 질문·발췌·인용·숫자·단위·지시서·선택지 보존을 검사했다. R02·R03 정상 소스 입력은 이전 검사 목록 복구 단위 실험과도 정확히 같다.
- 실제 tokenizer 사전 검증은 모델 추론 0회다. 선택지 token 그룹·보정값이 같고 변경된 22개만 토큰이 늘었으며 다른 34개 패킹은 완전히 같았다.
- 완료한 56개 판정을 기존 `normalize_response`와 `parse_plan_review`로 읽어 원시 선택과 전체 검토 상태가 일치함을 확인했다.
- 소스 지문·프로필·환경 파일·DB 스냅샷·등록 프로세스 ID·Docker 한도·검토 활성화가 전후 유지됐다. 작업자는 계속 실행 중이며 d1 서비스 모델은 해제된 상태다. 기존 메모리 검사 증거도 유효했다.
- 원시 질문·실제 계획·인용·입력·점수·파서 결과·로그는 Git 제외 `.local/runtime/v2.5-d1-checklist-10/`에 보관했다. 폴더 권한은 700, 원시 JSON은 600이다. 기존 평가 산출물은 덮어쓰지 않았다. 이 문서에는 실제 질문·인용문·물리 실험 수치를 넣지 않았다.

## v2.5 최종 채택 — 2026-11-18

`per_check`·`en-compact-no-view`의 MLX 검사 경로에 위 구성을 연결했다. v2.4의 설명 선별, 원본 2번+조건부 1·4·5번, 독립 숫자 필터 발췌, 인용 키 `citation.quote`, 현재 검사가 첫째인 전체 검사 목록 순으로 적용한다. 발췌 대상의 값이 비어 있거나 다른 단계에 의존하면 원본 계획을 사용한다. 원본 실행 계획과 저장·응답 형식은 기존 계약을 따른다. [실행 구성과 적용 조건](../development/agent-v2-local-llm.md#v25-d1-숫자-검토-입력).

저장된 10개 계획을 실제 MLX 서비스의 `pack_requests`로 다시 구성해 **56/56 요청**을 기존 실험과 대조했다. 상태 JSON, 질의, 선택지와 순서가 일치했고 숫자 발췌 22개·기타 34개로 나뉘었다. 저장된 모델 판정을 기존 파서에 넣은 전체 결과도 10/10 일치했다. 이 대조는 모델을 다시 호출하지 않았다.

같은 10개에 v2.4 입력을 사용한 [실제 Qwen 계획 기준](2026-11-17-local-llm-d1-real-qwen-contrast.md)은 정상 5/5, 실제 오류 항목 3/5, 오류 사유 2/5였다. 최종 v2.5는 각각 5/5, 5/5, 4/5다. 같은 자료의 검사당 입력은 2,200.29→2,046.93토큰(-6.97%), 계획당 d1 채점은 7.682→7.062초(-8.08%)였다. 검사 목록 유무만의 비용은 위 표의 직전 발췌 기준으로 비교한다.

`d1-context-3`의 준비 기록을 새로 생성해 공용 로컬 워커를 연결했다. 인공 입력 메모리 검사 7/7, 표본 96개, OS 피크 18.958 GiB, 경고·위험·추가 스왑 0이었다. 로컬 워커 연결 검사 4회와 메모리 검사 7회는 10개 계획의 정확도 평가와 별개다. 5173 웹·8080 백엔드 `/api/health`는 HTTP 200, MLX 계수 경로는 새 입력 해시와 일치했다. Docker 1.5 GiB와 DB 스냅샷, Q8 단일 처리와 검토 활성화도 확인했다.
