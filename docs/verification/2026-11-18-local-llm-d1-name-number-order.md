# LocalLLM v2.5 — R02·R03 명칭·숫자·조건 순서 교차실험

## 핵심

기준 4개와 정상 반사실 입력 12개, 총 16개 d1 검사를 완료했다. **두 사례를 공통으로 정상화하는 단일 명칭·숫자·조건 순서 변경은 없었다.** 숫자 교환·공통값 통일·‘소스 전력→소스 파워’ 표현 변경은 두 사례 모두 오판을 해소하지 못했다.

R02는 현재 숫자 구절을 바이어스 역할로 바꾸거나 소스 조건을 맨 앞으로 옮기면 MATCH로 바뀌었다. R03은 같은 변경에서도 오판했다. 특히 **R03은 현재 검사 필드를 bias_power로 바꾸고 인용과 질문의 역할명까지 맞춰도 missing이었다.** 따라서 현재 source_power 필드나 특정 숫자 하나만으로 두 오판을 설명할 수 없다.

이번 결과는 의미가 맞는 정상 조건의 표현·위치 변화에도 판정이 달라지는 문맥 민감성을 보여준다. 내부 사고 과정이나 유일한 원인을 증명한 결과가 아니며, 새 입력 구성을 운영에 적용하지 않았다.

## 범위와 고정 조건

- 기존 실제 Qwen 정상 R02·R03의 발췌 + citation 입력에서 출발했다. 소스 검사와 실제 바이어스 검사를 각 사례의 기준으로 둬 4개 기준을 실행했다.
- 사례별로 명칭 2개·숫자 2개·순서 2개를 바꾼 검토용 복사본을 만들었다. 모두 해당 검사에서 원문 조건과 실행값이 일치하도록 보존했고 예상 선택은 match다. 실제 질문·실행 계획·Run 데이터를 수정하거나 새 Run을 조회하지 않았다.
- Q8+MLX, group_size=1·independent_batch_size=1, Metal GPU, Docker VM 1536 MiB(1.5 GiB), development 메모리 정책을 유지했다. 실행 전 모델 설정과 실제 그래프 상태에서 plan_review_enabled=true를 확인했다.
- 일반 지침 문장과 선택지 ID·설명·순서·보정 온도는 고정했다. 역할명 교환에서도 새 지시서를 작성하지 않고 기존 바이어스 검사의 질문 객체를 그대로 사용했다. 검사 위치 참조만 해당 역할을 가리킨다.
- 원본 질문의 범위를 줄이거나 다른 실행값·검사 목록·실행 요약을 복구하지 않았다. 각 요청의 계획 입력은 검사 대상 한 개다.
- 그래프·최종 JSON/SSE·저장 계약·공유 웹/백엔드/DB·작업자 환경은 변경하지 않았다. 실제 추론은 정확히 16회, 예열·재시도·새 Qwen·Run 도구·REPLAN·답변 재작성·추가 웹/API 평가는 0회다.
- 검사 한 개마다 모델을 별도 프로세스에 적재·채점·해제했다. 요청 간 상태나 모델 상주가 이어지지 않게 기존 단일 처리 실행기를 사용했다.

## 변경한 한 가지 요인

| 요인 | 구성 | 고정한 내용 |
|---|---|---|
| 기준 | 기존 소스 검사, 기존 바이어스 검사 | 이전 입력과 완전히 동일 |
| 명칭: 표현 | 질문·인용에서 소스 전력을 소스 파워로 변경 | source_power 키·숫자·단위·조건 위치 |
| 명칭: 역할 | 현재 숫자 구절의 소스·바이어스 역할명을 일관되게 교환 | 검사 중인 숫자·단위·구절 위치·나머지 일반 규칙 |
| 숫자: 교환 | 두 사례의 소스값을 서로 교환 | 역할명·단위·구절 순서 |
| 숫자: 통일 | 소스값을 동일한 공통값으로 통일 | 역할명·단위·구절 순서 |
| 순서: 맨 앞 | 소스 조건 구절을 첫 번째로 이동 | 각 조건의 역할·숫자·단위·문장 후반부 |
| 순서: 맨 뒤 | 소스 조건 구절을 마지막으로 이동 | 각 조건의 역할·숫자·단위·문장 후반부 |

역할명 교환은 단어 하나를 잘못된 입력 키에 붙인 실험이 아니다. 질문과 인용의 소스·바이어스 명칭, 선택한 plan.inputs 키, check_specs의 name·metric·paths, review_view의 검사 참조와 기존 questions 키를 일관되게 맞췄다. 두 역할의 단위는 W로 같다. 현재 숫자 구절의 위치와 값은 고정했지만 소스·바이어스라는 물리적 역할의 배정은 바뀐다. 따라서 source_power 키의 철자 효과와 한국어 역할 표현 효과를 따로 분리한 실험으로 해석하지 않는다.

숫자 변경은 질문·인용·실행 숫자에 동일하게 적용했다. 이는 오류 계획 생성이 아니라 특정 수치 자체가 정상 오판을 만드는지 확인하는 대조다. 실행 숫자만 바꾸는 오류 계획은 이번에 사용하지 않았다.

순서 변경에서 R02의 인용문은 원래 질문 전체여서 함께 재정렬해 출처를 유지했다. R03의 인용문은 해당 조건 부분이므로 본문은 그대로 유지했다. 모든 인용이 새 question의 실제 부분 문자열인지 검증했다. 이 때문에 R02의 순서 변경은 질문과 전체 인용의 순서 효과를 함께 측정하며 두 위치의 기여를 각각 분리하지 않는다.

## 결과

표의 퍼센트는 match 선택지의 정규화 점수이며 정확도나 실제 정답 확률이 아니다.

| 구성 | R02 판정 | R02 MATCH 점수 | R03 판정 | R03 MATCH 점수 |
|---|---|---:|---|---:|
| 기존 소스 기준 | unexpected | 16.23% | missing | 23.41% |
| 기존 바이어스 기준 | match | 45.48% | match | 77.88% |
| 소스 파워 표현 | unexpected | 16.86% | missing | 22.40% |
| 현재 구절을 바이어스 역할로 교환 | **match** | **45.73%** | missing | 22.60% |
| 소스값 서로 교환 | unexpected | 15.18% | missing | 22.54% |
| 소스값 공통값 통일 | unexpected | 18.21% | missing | 22.19% |
| 소스 조건 맨 앞 | **match** | **52.91%** | unexpected | 17.14% |
| 소스 조건 맨 뒤 | missing | 25.15% | missing | 27.40% |

기준 4개의 선택과 일곱 선택지 점수는 이전 기록과 부동소수점 값까지 정확히 같았다. 따라서 같은 기준을 다시 실행해 달라진 현상은 아니었다.

R02의 역할명 교환은 MATCH를 29.50%p, 맨 앞 이동은 36.68%p 올려 최상위 선택지를 바꿨다. 다만 점수는 45.73%·52.91%여서 두 정상 사례를 안정적으로 해결하는 공통 규칙으로 채택할 근거는 없다.

R03은 기존 바이어스 검사는 match지만, 기존 소스 구절의 값과 위치를 고정한 채 바이어스 역할로 바꾸면 missing이었다. 이는 현재 검사 이름을 bias_power로 바꾸는 것만으로 같은 문맥의 오판이 해소되지 않음을 보여준다.

숫자 변형 4개는 모두 기존 오류 종류를 유지했다. 이번에 사용한 수치 범위에서는 숫자 하나만이 원인이라는 가설을 지지하지 않는다. 소스 파워 표현 변경도 두 사례를 해결하지 못했다. 조건 순서는 R02의 판정에 영향을 줬지만 R03에서는 오류 종류만 바뀌거나 오판이 유지돼, 가운데 위치만으로 두 사례를 공통 설명할 수 없다.

## 확인된 것과 남은 것

확인된 것은 문맥에 따른 비일관성이다. 같은 지침·선택지를 쓰고 현재 숫자와 조건의 일치 관계를 유지해도, 역할 표현이나 조건 위치에 따라 선택이 달라졌다. 특정 값·소스라는 한국어 표현·현재 source_power 필드·가운데 위치 중 하나를 두 사례의 유일한 원인으로 확정하지 않는다.

R02와 R03은 질문 후반의 요청 내용과 인용문의 범위가 다르다. 이번에는 이 둘을 고정했으며, 그 차이와 개별 요인의 상호작용은 분리하지 않았다. 바이어스→소스의 역방향 역할 교환이나 기계 필드명 철자만 바꾸는 실험도 하지 않았다. 모델이 어떤 조건을 누락으로 생각했는지의 자유 서술 사유는 출력되지 않는다.

의미를 보존하는 조건 순서 변경만으로 R02가 오판에서 MATCH로 바뀌는 것은 검토기의 문맥 민감성을 드러낸다. 원래 사용자 질문을 다시 쓰면 실사용 정확도가 개선된다는 증거나, 숫자 오류 검출까지 유지된다는 증거로 확대하지 않는다.

## 토큰·메모리·검증

- 실제 tokenizer로 16개 요청을 미리 배치했고 모델 추론은 0회였다. 기준 4개의 전체 token ID·선택지 그룹·온도는 이전 요청과 정확히 같았다.
- 총 입력은 25,914토큰, 최대 1,632토큰이며 절단은 없었다. 표현·숫자·순서 변경 요청은 각각 같은 사례의 소스 기준과 토큰 길이도 같았다. 역할명 교환은 기존 바이어스 기준과 같은 길이였다.
- 각 실제 채점에서도 frozen 입력 hash·token 배치·예상 검사 이름·확률 합을 다시 확인했다. 사후 입력 변환을 재실행해 모든 frozen 후보와 같음을 CPU에서 검증했다.
- OS 메모리 피크 15.799 GiB, 96표본, warning/critical/unknown 0, 추가 swap 0, DB OOM 증가 0이었다.
- 전후 소스 지문·프로필·환경 파일·DB 스냅샷·등록 프로세스 ID·Docker 제한이 같았다. 로컬 작업자는 계속 실행 중이며 d1 서비스는 모델 미적재·해제 상태이고 기존 메모리 검사 증거도 유효했다.

## 보관과 재현

원시 질문·인용·파생 계획·전체 점수·토큰·실행기·manifest는 Git 제외 `.local/runtime/v2.5-d1-name-number-order/`에 비공개로 보관했다. 폴더 700·JSON 600 권한을 확인했으며 공개 문서에 원본 질문·인용문·물리 실험 수치를 싣지 않았다.

실행한 주요 명령은 다음과 같다. 기존 산출물이 있으면 자동 반복하지 않는다.

```text
agent/python/.venv/bin/python .local/runtime/v2.5-d1-name-number-order/prepare.py
agent/python/.venv/bin/python .local/runtime/v2.5-d1-name-number-order/capture.py
agent/python/runtimes/d1_mlx/.venv/bin/python .local/runtime/v2.5-d1-name-number-order/engine_probe.py --engine mlx-q8 --preflight
agent/python/.venv/bin/python .local/runtime/v2.5-d1-name-number-order/run_evaluation.py
```

운영 코드·그래프·최종 응답 양식 반영, 정상 5개·오류 5개 재평가, 웹 평가, 커밋·push·PR·배포는 하지 않았다.
