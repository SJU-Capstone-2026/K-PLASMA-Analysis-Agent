# LocalLLM v2.4: 모든 검사 선별 설명 구현·평가

2026-11-15. [후속 구현 계획](../plans/2026-11-15-005-local-llm-d1-all-check-context.md)의 사용자 승인에 따라, 항상 생성하는 3개 검사는 고정 설명 묶음을 사용하고 나머지 10종류에도 설명 선별 정책을 적용했다.

**결과:** 같은 정상 5개·오류 5개의 모든 62개 검사가 실제 추론에서 `selected`였다. 전체 설명 유지와 fallback은 **0개**다. 계획당 d1 검토는 평균 **8.928초**, 검사당 입력은 **2,140.89토큰**이었다. 이전 부분 선별보다 각각 **22.72%·22.52% 감소**했다. 부분 선별 대비 62개 판정은 전부 동일했고 새 회귀는 없었다. 그러나 의도한 오류 항목·사유 검출은 **1/5**로 미해결이다.

사용자 지시에 따라 현재 공용 로컬 워커는 **`per_check` / `d1-context-2`** 상태로 유지했다. 전체 설명으로 되돌리지 않았다. 기존 full/부분 선별 결과와 원시 기록은 그대로 보존했다.

## 변경 범위

- `request.tasks`: 모든 도구의 역할·입출력 설명과 등록된 32개 지표의 label/unit/plotId를 고정 제공한다. 긴 지표 정의와 정의 참조는 출력 검사에서 다룬다.
- `request.filter_coverage`: 조회·검색·값 참조 계약과 검색 가능한 6개 지표 정의를 고정 제공한다. 현재 계획에 없는 요청 필터도 검토할 자료를 유지한다.
- `request.confirmation_coverage`: 사용자 확인·비교 대상/기준 연결·참조 계약을 고정 제공한다. 전체 지표 정의는 넣지 않는다.
- `outputs`: 비교·그래프 계약과 등록된 32개 지표 정의를 모두 남기고 무관한 도구 설명을 제외한다. 계획에 있는 지표만 선택하지 않는다.
- `ordering`: 정렬 목표가 비어 있어도 6개 검색 지표와 검색/정렬 계약을 제공한다. 이전의 `unresolved_metric` 6건이 전체 설명으로 돌아가지 않는다.
- `filter`, `targets`, `baseline`, `trend_axis`의 지표군·단위·선행 참조 보호를 유지한다. 계산·선택 개수·선택 대상·실행 조건에도 선별 정책을 적용한다. 지표가 필요 없는 리터럴 계산은 지표 설명 없이 필요한 연산·참조 계약을 제공한다.

규칙은 기존 구조화된 설명에서 항목·필드를 복사한다. 지시서·선택지·정책·원문 질문·이력·전체 계획·문맥·원본 snapshot/digest는 변경하지 않았다. 새 LLM·질문 파서·번역·요약·임베딩은 추가하지 않았다. 검사 생성 조건, 그래프·HITL·도구 실행·`submit_plan`·최종 응답·SSE·v2/v3는 그대로다.

알 수 없는 계약/지표/참조의 안전한 전체 fallback은 일반 요청에 계속 남긴다. 다만 이번 평가는 호출 전 CPU preflight에서 **62개 전부 selected**를 요구하고, 실제 count·추론에서도 selected·동일 state hash를 다시 확인한다. 하나라도 full/fallback이면 전체 선별 평가의 성공으로 처리하지 않는다.

## 조건과 호출 수

기존 frozen corpus SHA-256 `c27853259c724b75e8851af094974b5b3b4ef0256c728f8182510e1136a98c87`의 동일 10사례·62개 검사를 사용했다. 사례 순서·질문·계획·정답·검토 지침·선택지를 바꾸지 않았다.

Q8+MLX 단일 처리, `group_size=1`, `independent_batch_size=1`, `en-compact-no-view`, Docker VM **1536MiB**, development 메모리 정책, Qwen 캐시 OFF, 기존 Qwen GGUF Q4_K_M·llama.cpp 설정을 유지했다. 모델 설정과 실제 그래프의 `plan_review_enabled=true`를 확인했고, Qwen sleep→d1 load/review/unload의 순차 상주를 유지했다. 재계획 최대 2회·답변 재작성 최대 1회는 코드에서 보존했다.

## 토큰·시간

| 지표 | 이전 full | 이전 부분 선별 | 이번 전체 선별 |
|---|---:|---:|---:|
| 선별된 검사 | 0/62 | 22/62 | **62/62** |
| 전체 유지 또는 fallback | 62/62 | 40/62 | **0/62** |
| 입력 토큰 합계 | 200,545 | 171,319 | **132,735** |
| 검사당 평균 입력 | 3,234.60 | 2,763.21 | **2,140.89** |
| 계획당 평균 d1 검토 | 13.467초 | 11.553초 | **8.928초** |
| 계획당 중앙값 | 10.855초 | 9.680초 | **7.244초** |
| 10사례 검토 합계 | 134.668초 | 115.530초 | **89.280초** |
| 요청 합계/62개 검사 | 2.172초 | 1.863초 | **1.440초** |

이번 결과는 저장된 full 대비 **시간 33.70%·입력 토큰 33.81% 감소**, 저장된 부분 선별 대비 **시간 22.72%·입력 토큰 22.52% 감소**다. 토큰은 같은 tokenizer의 native packed 입력과 실제 모델 usage를 대조한 값이다. 이전 10개 요청의 native 원본 body와 이번 10개 요청의 body가 같고, 모델이 읽는 각 검사 입력에서는 `tool_contracts`만 바뀌었음을 확인했다.

항상 3개 검사는 10사례에서 30개 고정 묶음을 사용하고, 나머지 32개 검사도 선별 경로를 사용했다. 부분 선별 대비 P10.good/bad의 정렬 검사는 누락 가능성을 보존하도록 6개 지표를 남겨 1,919→1,994토큰으로 각각 75토큰 증가했다. 두 검사도 full보다 짧고, 전체 입력은 감소했다.

도구 설명 JSON만 독립 계수한 검사당 평균은 **830.29토큰**이었다. 고정 3종의 설명 부분은 작업 1,597 /필터 누락 783 /확인 누락 440토큰으로 사례마다 같았다. 부분 JSON 토큰을 전체 native 입력의 가산 가능한 분해로 간주하지 않는다.

새 실행의 count HTTP 합계는 0.605초, backend 추론 합계는 87.050초, 그중 load 4.494초, release는 별도 0.753초였다. 준비·재시작·워커 시작 시간은 의미 검토 시간에 넣지 않았다. 모든 사례를 포함했다.

이전 기록과의 비교이므로 시간대·호스트 상태가 완전히 같은 동시 A/B는 아니다. 모델·라이브러리·지침·사례가 같은 단회 관측값이며 일반적인 속도·정확도 동등성을 주장하지 않는다. 위 시간은 **d1 계획 검토** 시간으로 전체 채팅 응답 시간이 아니다.

## 메모리·보존·현재 실행 상태

다른 메모리 지표를 합산하지 않는다. OS 피크는 다른 앱의 영향도 포함한다. 모델 해제는 실제 allocator/cache 상태로 확인했다.

평가 전후 **150 Run /150 version /85 turn /224 request**, 진행 중 요청 0과 원본·과거 기록의 보존 hash가 같았다. 제품 소스 identity와 frozen corpus도 유지됐다. 소유한 유휴 로컬 워커만 평가 동안 정지했고, 마지막에는 새 per_check 워커로 교체했다. 공용 5173/8080·DB·Qwen 서버와 v2/v3는 그대로 사용했고 다른 앱은 종료하지 않았다.

추가 모델 호출 없이 새 워커 실행, 새 메모리 증거와 runtime identity 일치, `per_check` / `d1-context-2`, 계획 검토 ON, d1 released, frontend/backend HTTP 200, Docker 1536MiB를 확인했다. 선별 모드는 사용자의 개발 설정 선택이며 오류 검출 정확도 인증을 의미하지 않는다.
