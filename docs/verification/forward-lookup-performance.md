# 순방향 조회 접근 방식 벤치마크

측정일: 2026-10-10–11 (KST). 네 규모의 벤치마크와 별도 오류 진단을 완료했다. 자원 한도로 완료하지 못한 경로도 아래에 포함한다.

## 목적과 비교 범위

전체 Run 요약을 가져온 뒤 Python에서 찾는 비용과, DB에서 후보를 제한하는 비용을 분리했다. **제품 조회 코드를 변경한 전후 측정이 아니라, 같은 테스트 연결 경로에서 세 접근 방식을 비교한 결과**다.

| 방식 | DB 조회 | Python에 전달하는 요약 |
|---|---|---|
| A | 모든 현재 Run과 버전의 요약 조회 | N개 |
| B | 압력·소스·바이어스 `WHERE` 조회 | 정확히 일치하는 1개 |
| C | 정규 조건으로 Run ID를 구성하고 기존 기본 키 조회 | 정확히 일치하는 1개 |

각 방식은 동일한 `lookup_forward`와 결과 재검증을 거치고, 별도로 생성한 기대 Run·버전·조건·수치와도 비교했다. 모든 성능 입력은 정확 일치하며 모든 Run이 적격이다. 근접 탐색·전역 제외 목록·비가용 데이터까지 B/C로 구현한 것은 아니다.

C는 `run_pkey`와 `run_version_pkey`를 활용한다. 새 인덱스를 추가하지 않았으며 **B→C 차이를 복합 인덱스 추가 효과라고 해석하면 안 된다.** SQL 조건식과 탐색 키가 함께 바뀐 비교다.

## 조회 구간 M2

측정 경계는 Python 요청 시작 → 실제 Java/JDBC → HTTP JSON → Python 선택·검증 완료다. LLM·대화 저장·전체 catalog 고정은 포함하지 않는다. p95는 성공 표본을 정렬한 `ceil(0.95 × n)`번째 값이다.

| Run 수 | A 평균 / p95 ms | B 평균 / p95 ms | C 평균 / p95 ms | 성공 표본 |
|---:|---:|---:|---:|---|
| 150 | 5.434 / 8.153 | 1.893 / 2.466 | 1.292 / 1.883 | 각 200/200 |
| 10,000 | 245.273 / 265.626 | 35.684 / 40.792 | 1.348 / 2.024 | 각 200/200 |
| 100,000 | 2,428.514 / 2,610.343 | 313.390 / 326.474 | 1.801 / 2.800 | 각 200/200 |
| 1,000,000 | 준비 요청 중 Java heap OOM | 3,160.539 / 3,298.172 | 1.803 / 3.147 | B/C 각 200/200; A 본 측정 불가 |

평균 / p95 감소율은 `(이전 − 이후) / 이전 × 100`이다.

| Run 수 | A→B 감소율 | B→C 감소율 | A→C 감소율 |
|---:|---:|---:|---:|
| 150 | 65.17% / 69.76% | 31.73% / 23.63% | 76.22% / 76.90% |
| 10,000 | 85.45% / 84.64% | 96.22% / 95.04% | 99.45% / 99.24% |
| 100,000 | 87.10% / 87.49% | 99.43% / 99.14% | 99.93% / 99.89% |
| 1,000,000 | 산출 불가 | 99.94% / 99.90% | 산출 불가 |

세 방식이 모두 완료된 규모에서는 매 라운드 평균이 A > B > C였고, 100만 건 보충 측정에서는 매 라운드 B > C였다. 총 2,200개의 M2 본 측정이 모두 정확성 검증을 통과했다. 네 규모를 섞어 하나의 개선율로 만들거나 Agent 전체 응답 개선율로 사용하지 않는다.

| Run 수 | A 응답 바이트 | B/C 평균 응답 바이트 | 반환 행 A → B/C |
|---:|---:|---:|---:|
| 150 | 144,987 | 약 976 | 150 → 1 |
| 10,000 | 9,687,116 | 약 979 | 10,000 → 1 |
| 100,000 | 96,873,857 | 약 979 | 100,000 → 1 |
| 1,000,000 | 완료 응답 없음 | 약 979 | A 미완료; B/C 1 |

10만 건 A의 평균 2,428.5ms는 HTTP 수신 1,572.8ms, Python JSON 해석 471.4ms, 선택 192.9ms, 검증 191.5ms로 나뉘었다. Java fetch 1,374.2ms와 직렬화 145.6ms는 HTTP 구간 안에 포함되므로 별도로 더하지 않는다. Java 매핑 265.2ms도 fetch에 포함된 중첩 구간이다.

100만 건 A는 첫 준비 요청 26,717ms 후 `RemoteProtocolError`를 반환했고 JVM 로그에서 `OutOfMemoryError: Java heap space`를 확인했다. 이어진 B/C 준비 요청은 종료된 서버에 연결하지 못했다. 이 두 접속 실패는 조회 전략의 실패율로 해석하지 않고, 같은 데이터·heap·입력·제품 기준 커밋의 새 JVM에서 B/C만 200회씩 보충 측정했다. 준비 요청 5회도 다시 수행했고 B/C 순서는 기존 5라운드 순서에서 A만 제외했다. 원 실패 기록은 보존했다. A의 평균·p95 및 A를 기준으로 한 100만 건 개선율은 계산하지 않는다.

## DB 실행 계획 M1

대표 입력 5개에 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`을 실행했다. 실행 계획의 `cost`를 ms로 읽지 않았으며, 중첩 scan의 행 수를 합쳐 고유 검사 행 수로 표현하지 않았다.

- 150건에서는 C도 `run` 테이블에 Seq Scan을 선택했다. 작은 테이블에서의 정상적인 계획이며 인덱스 사용을 강제하지 않았다.
- 1만·10만·100만 건의 B는 `run_version` Seq Scan에서 각각 9,999 / 99,999 / 999,999행을 제외하고 1행을 반환했다. 연결되는 `run`에도 Seq Scan이 있었다.
- 같은 규모의 C는 `run_pkey`와 `run_version_pkey`의 Index Scan으로 각각 1행을 찾았다.
- **M2 조회 SQL은 세 방식 모두 1회였다.** 이번 A/B/C 차이는 SQL 호출 횟수 감소보다 반환량·탐색 범위·JSON 처리 비용의 차이다. 이를 N+1 해결이라고 부르지 않는다.

| Run 수 | A SQL 실행 평균 ms | B SQL 실행 평균 ms | C SQL 실행 평균 ms |
|---:|---:|---:|---:|
| 150 | 1.102 | 0.732 | 0.081 |
| 10,000 | 99.819 | 33.399 | 0.092 |
| 100,000 | 644.747 | 308.659 | 0.101 |
| 1,000,000 | 11,386.482 | 3,277.017 | 0.399 |

100만 건 A도 **DB 안의 실행 계획 측정은 완료**됐다. Java가 전체 결과를 객체로 만드는 M2의 OOM과 다른 경계다. 100만 건 A의 대표 계획 루트에는 temp read 506,119 / written 506,189 blocks도 관측됐다. 이는 임시 버퍼 접근량이지 임시 파일의 최대 크기가 아니다.

M1 서버 실행 시간에는 Java 매핑·HTTP 전송·Python 처리가 없다. shared read는 PostgreSQL 버퍼 밖의 읽기이며 물리 디스크 읽기와 동일한 지표가 아니다.

## pgbench와 메모리

pgbench는 같은 사용자 SQL과 40개 입력 목록으로 1연결·1스레드·simple protocol, 60초 × 3라운드를 수행한다. DB 컨테이너 내부에서 실행하므로 클라이언트 CPU도 같은 2 CPU 한도를 공유하며, 호스트 HTTP 경로의 M2와 직접 비교하지 않는다. 단일 연결 처리율을 최대 동시 사용자 처리량으로 표현하지 않는다.

RSS는 별도 실행에서 Java/Python을 매번 새로 시작하고 5회 준비 조회 후 100ms 간격으로 관측한다. 방식별 3회이며 짧은 피크를 놓칠 수 있으므로 최대 관측값이다. 기존 A가 확보한 heap을 B/C의 메모리로 잘못 집계하지 않도록 프로세스를 분리했다.

아래 지연은 3라운드의 평균 지연 중 중앙값이며, 처리율은 라운드별 처리율의 평균이다. 네 규모 × 세 방식 × 3회 모두 완료했고 실패 트랜잭션은 0건이었다. 100만 건 A는 전체 3라운드에서 완료한 트랜잭션이 19건으로 적으므로 정밀한 꼬리 지연 추정에 사용하지 않는다.

## 현재 Agent 경로 M3

실제 요청 제출·claim·LangGraph·checkpoint·manifest·답변 저장을 실행했다. **도구 선택 LLM만 고정된 정상 입력으로 대체했다.** 각 요청마다 새로운 Java/Python 프로세스와 빈 대화에서 시작하므로 준비된 M2와 같은 지연 경계가 아니다.

- 150건: 10회 완료, 평균 448.5ms. 대표 요청에서 체크포인트 저장 15회, 요청 제출부터 최종 확인까지 JDBC SQL 실행 165회가 관측됐다. 대화 초기화는 측정에서 제외했다. 체크포인트·상태 검증을 포함한 전체 경로의 횟수이며 Run당 N+1로 단정하지 않는다.
- 1만 건: 첫 요청이 체크포인트 저장 단계에서 `INVALID_AGENT_REQUEST`로 실패했다. 별도 재현에서 `checkpoint payload is too large`를 확인했다. `AgentRequestService.saveCheckpoint`의 직렬화된 payload 길이 제한은 **16,000,000자**다. 재현 요청의 HTTP body는 약 23.1MB였으며 HTTP 바이트 수와 payload 문자 수는 서로 다른 값이다.
- 10만 건: 첫 체크포인트 전송은 230,339,089bytes였고 HTTP 400 `INVALID_UPLOAD`로 거절됐다. 이어진 저장 시도도 460,662,300bytes에서 같은 오류가 났다. 별도 진단에서 `Mutation.payload.saver`의 문자열을 읽는 Jackson `StreamConstraintsException`과 **100,000,000자** 제한을 확인했다. 파일 업로드가 아닌 `/internal/agent/requests/.../checkpoint` 호출인데도 공통 `ImportController.Errors`의 파싱 오류 처리에서 업로드 오류 코드로 매핑됐다.
- 100만 건: `backend.context`가 30초 제한에 도달했고, 같은 요청의 JVM 로그에서 heap OOM도 확인했다. 완료 시간 대신 31,104.6ms 시점의 `BACKEND_UNAVAILABLE` 실패를 기록했다. 실패한 각 규모는 첫 실패 뒤 나머지 9회 반복을 중단했다.

로컬 span 이름·시간과 테스트용 JDBC 계측을 사용했다. Phoenix Cloud 전송을 주 측정에 포함하지 않았다. span에는 부모·자식 중첩이 있으므로 시간을 모두 합산하지 않는다.

주 측정 이후 150건 인공 데이터로 대표 요청 한 건을 Phoenix Cloud `K-PLASMA` 프로젝트에 전송했다. REST 조회로 trace `884372285a7cc9c8ea927ab69aa119ef`의 26개 span 도착을 확인했고 모두 `OK`, `benchmark.synthetic=true`였다. 도구 선택 → guard → gather/context → calculate → validate → present/finalize와 중간 checkpoint 흐름을 확인했다. 이 진단의 시간은 M2와 기본 M3 통계에 합치지 않았다.
