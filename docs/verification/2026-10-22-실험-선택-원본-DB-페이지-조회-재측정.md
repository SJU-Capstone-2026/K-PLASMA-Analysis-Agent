# 실험 선택 화면: 사본 없는 원본 DB 페이지 조회 재측정

**전체 후보 사본을 없애고 원본 DB에서 30개씩 조회하도록 변경했다.** 100만 건의 선택 화면 준비는 이전 사본 C의 평균 **75.23초 → 새 C의 4.76ms**로 줄었다. 선택 전 후보 저장 행은 네 규모 모두 **0개**, 두 개 선택 후에는 **2개**였다.

## 변경과 비교군

목록은 조회 시점의 최신 현재 버전을 보여주고, 선택한 실험과 명시적으로 첨부한 실험만 정확한 버전으로 보존한다. 선택 후 원본이 갱신돼도 선택 버전은 바꾸지 않는다. 페이지·검색·새로고침은 전체 후보를 저장하지 않는다. 현재 페이지/검색 결과 전체/전체 실험의 세 선택 범위를 유지하며, 명시적 일괄 선택만 클릭 시점의 선택 대상 K개를 저장한다.

| 비교군 | 구조 | 인덱스 차이 |
| --- | ---: | ---: |
| A (기존 기준선 재사용) | 전체 후보 JSON 저장·전송, 브라우저 검색 | 기존 main |
| B (이번 재측정) | 원본 최신 목록 검색·keyset 페이지 + 선택 K개 저장 | 기존 PK·UNIQUE·선택용 인덱스 유지 |
| C (이번 재측정) | B와 같은 코드·계약·데이터 | 원본 run 정렬 B-tree, run_version 검색 GIN 추가 |

V10은 이전 요청의 미선택 사본을 정리하고 선택·첨부를 보존한다. V11은 원본 테이블의 공유 인덱스를 추가한다. 검색 문자열·정렬 키는 원본 등록 시 생성되는 필드이며 요청별 후보 사본이 아니다. `snapshotId`는 선택 상태 식별자로만 사용한다. 전체 건수는 별도 API에서 갱신하여 첫 30개 표시를 막지 않는다.

## 환경과 도구

- 150 / 1만 / 10만 / 100만 건 모두 동일 조건 중복이 없는 인공 데이터. 실제 데이터·서비스 DB·LLM은 사용하지 않았다. 데이터 입력(seed), 원본 검색 열 생성과 인덱스 작성/마이그레이션 시간은 요청 측정에서 제외했다. 이미 DB에 데이터와 인덱스가 있는 조회 상황이다.
- Apple M4 Pro / RAM 24GB, Java 21, PostgreSQL 18.6 / CPU 2개·메모리 한도 6GB, Hikari 풀 10개. 모든 비교의 JVM은 `-Xms512m -Xmx8g`다. 메모리는 벤치마크 설정이며 제품 기본 설정 변경이 아니다.
- 각 규모 서버 재시작·seed 후 워밍업 2회, 독립 선택 요청 준비/첫 조회 10회. B/C는 같은 bootJar에서 V11 파일만 제외/포함하고 나머지 ZIP 항목의 바이트 일치를 검증했다.
- k6: 1VU 직렬 HTTP 지연 측정. 150~10만 건은 유형별 100회 × 3블록, 100만 건은 10회 × 3블록이다. 동시 사용자 부하 테스트가 아니다.
- Playwright/Vite: 실제 React 선택 패널과 Spring API를 연결해 첫 체크박스 활성화·paint, 검색 입력→결과 표시, DOM 노드를 측정했다. 150·1만 건은 20회, 10만·100만 건은 10회이며 검색에는 제품의 300ms 입력 대기가 포함된다.
- Python `perf_counter`: 실제 submit→claim→needs-input 흐름 중 준비 HTTP, 이후 첫 목록 HTTP, K=2 선택·재개·정리를 측정했다. `EXPLAIN (ANALYZE, BUFFERS)`·`pg_stat_statements`·JFR로 DB/서버 근거를 보존했다.
- A는 기존 커밋 `5c5e82f9515e390202392673a92c89b7671518de`의 동일 자원 기준선을 재사용했다. A와 새 B/C는 측정 시점이 다르고, 최신 목록 정책도 사용자 승인으로 바뀌었다. 이전 사본 B/C는 현행 B/C와 섞지 않았다. 측정 중 다른 빌드·테스트·부하를 병행하지 않았다.

## 1. 초기 준비와 첫 페이지

각 10회 평균, 단위 ms다. 준비는 needs-input 처리부터 선택 세션 저장·상태 전이 응답까지이고, 첫 조회는 그 직후 별도 GET이다. 합계는 두 HTTP 구간의 합이며 브라우저 렌더링이나 전체 Agent/LLM 응답 시간이 아니다.

| 규모 | B 준비 | C 준비 | B 첫 조회 | C 첫 조회 | C 준비+첫 조회 | 선택 전 저장 행 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 150건 | 4.42 | 4.44 | 5.19 | 5.04 | 9.48 | 0 |
| 1만 건 | 4.61 | 4.50 | 7.21 | 5.58 | 10.08 | 0 |

이전 사본 C의 준비 시간과 비교하면 다음과 같다. 이전 측정은 미선택 후보까지 최초 버전으로 고정했고, 새 측정은 선택한 버전만 고정하므로 준비 정책 변경을 포함한 결과다.

B/C 모두 네 규모의 준비·첫 조회 **40/40회**를 완료했다. 100만 건 A는 기존 증설 실험에서도 전체 JSON 저장 중 실패했으므로 성공 평균/개선율을 만들지 않았다.

준비된 세션의 첫 목록/페이지 HTTP 평균이다. A는 N개 전체, B/C는 최대 30개를 반환하므로 A→B는 DB 처리·전송·반환 구조의 종합 효과다. B→C는 같은 요청·코드에서 V11 인덱스만 다른 비교다. 단위 ms.

## 실행 계획·진단

최신 목록과 첨부 과거 버전을 UNION한 뒤 한 번에 정렬하던 중간 구현에서는 원본 정렬 인덱스를 사용하지 못했다. 각 분기에 커서·정렬·LIMIT 31을 먼저 적용하고 합친 뒤 다시 최대 31개로 제한했다. 아래 실행 계획은 이 분기 구조·정렬·버전 JOIN을 유지한 진단 SQL이며 SELECT 표시 필드만 축약했다. HTTP 평균과 다른 단일 DB 표본이다. 중간 진단 측정은 별도 로컬 디렉터리에 보존하고 최종 B/C 평균에서 제외했다.

- B 10만 건: Seq Scan  / 100000.0행. DB 실행 37.16ms.
- B 100만 건: Seq Scan  / 1000000.0행. DB 실행 278.26ms.
- C 10만 건: Index Only Scan run_picker_order_idx / 31.0행. DB 실행 9.09ms.
- C 100만 건: Index Only Scan run_picker_order_idx / 31.0행. DB 실행 8.82ms.

희소/일치 없는 검색에서도 정렬 인덱스 순으로 모든 버전을 검사하는 계획이 관측돼, 3글자 이상 검색은 일치하는 Run ID·버전 ID를 먼저 확정한 뒤 기존 Run PK로 연결하고 정렬했다. 두 글자 검색은 기존 정렬 경로를 유지한다. 검색용 중간 집합은 SQL 실행 중의 식별자 집합이며 DB에 요청별 후보 행을 저장하지 않는다.

공유 원본 인덱스의 저장 공간도 따로 확인했다. 아래는 기존 원본 인덱스를 포함한 run + run_version 인덱스 합계다. 추가 인덱스는 원본 등록 시 갱신되며 화면 요청마다 복사되는 공간이 아니다.

| 규모 | B 원본 인덱스(MiB) | C 원본 인덱스(MiB) |
| --- | ---: | ---: |
| 10만 건 | 18.85 | 53.12 |
| 100만 건 | 182.36 | 518.52 |

원본의 조건·버전 정보는 페이지 후보가 제한된 뒤 읽는다. DB 내부의 31개 버전 PK JOIN은 애플리케이션이 SQL을 31번 보내는 N+1과 다르다. 정확한 전체 건수 집계와 사용자가 명시한 대규모 전체 선택은 여전히 데이터/선택 수에 비례하며 별도 작업으로 남는다.
