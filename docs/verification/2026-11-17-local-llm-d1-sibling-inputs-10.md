# LocalLLM v2.5 — 같은 단계의 실행값을 함께 제공하는 2번 방식 평가

## 핵심

정상 5개·숫자 오류 5개의 전체 d1 검토를 실행했다. 같은 단계의 압력·소스 전력·바이어스 전력 실행값을 함께 주자 **정상 통과는 3/5→5/5로 개선됐지만, 실제 오류 항목·사유 검출은 5/5→2/5로 낮아졌다.** 순방향 조회의 압력·소스·바이어스 숫자 변경 세 건을 모두 match로 놓쳤다.

전체 검사 정답은 45/56으로 같았다. 정상 소스 전력의 기존 부수 오판 세 개를 고친 대신 실제 숫자 오류 검사 세 개가 오답으로 바뀌었다. 따라서 정상 두 사례에서 MATCH가 높아졌다는 사실을 오류 검출까지 유지되는 개선으로 확대할 수 없다.

## 적용한 구성과 유지 조건

- 기존 실제 Qwen 정상 계획 5개와 인용문을 보존한 숫자 오류 사본 5개를 사용했다. 새 Qwen 계획을 만들지 않았다.
- 순방향 조회의 숫자 검사 18개에서 현재 인자 하나만 있던 검토 복사본에 같은 단계의 다른 두 리터럴을 추가했다. 현재 인자는 첫 위치에 유지하고 나머지를 추가했다.
- 실제 판정 대상·검사 경로·questions 객체·선택지·온도는 계속 한 항목씩이다. 세 숫자의 판정을 한 번에 요청하거나 묶음 처리하지 않았다.
- 인용문·원본 질문·실행 숫자·단위는 변경하지 않았다. 추가한 리터럴의 출처 객체도 기존 citation 표기로 맞췄다. 오류 사본의 바뀐 숫자는 세 검토 복사본 모두에 그대로 보존했다.
- requirements 설명·다른 검사 목록·program_effects는 복구하지 않았고, review_view도 기존 값을 유지했다. 전체 계획 구성으로 되돌린 실험이 아니다.
- 누락·정렬 34개와 역방향 숫자 검사 4개는 입력과 토큰을 완전히 유지했다. 역방향 두 사례는 원래 constraints 하나와 goals 빈 배열이어서 추가할 같은 단계의 조건이 없었다.
- 공통 지침은 기존 2번+조건부 1·4·5번이다. Q8+MLX, group_size=1·independent_batch_size=1, Metal GPU, Docker VM 1536 MiB(1.5 GiB), development 메모리 정책을 유지했다.
- 실행 전 설정과 실제 그래프 상태에서 plan_review_enabled=true를 확인했다. 원래 그래프·최종 JSON/SSE·저장 계약·작업자 환경·공유 웹/백엔드/DB는 변경하지 않았다.
- 계획마다 모델을 적재해 검사 5~6개를 독립적으로 하나씩 채점한 뒤 해제했다. 실제 추론 56회가 모두 완료됐고 예열·재시도·추가 Qwen·Run 도구·REPLAN·답변 재작성·웹/API 전체 질문 평가는 0회다.

## 정확도 비교

기준은 [기존 발췌 + citation 평가](2026-11-17-local-llm-d1-citation-name.md)다. 같은 입력을 반복한 [3회 평가](2026-11-17-local-llm-d1-citation-repeat3.md)에서도 기준 판정과 점수는 정확히 같았다.

| 지표 | 기존 발췌 + citation | 2번 방식 |
|---|---:|---:|
| 정상 계획 최초 PASS | 3/5 | **5/5** |
| 실제 오류 항목 검출 | 5/5 | **2/5** |
| 오류 항목·value_changed 사유 정확 | 5/5 | **2/5** |
| 오류 계획 전체 ISSUE | 5/5 | 3/5 |
| 오류 계획 전체 UNCLEAR | 0/5 | 1/5 |
| 오류 계획의 잘못된 PASS | 0/5 | **1/5** |
| 숫자 검사 정답 | 19/22 | 19/22 |
| 누락·정렬 검사 정답 | 26/34 | 26/34 |
| 전체 검사 정답 | 45/56 | 45/56 |
| 모든 검사·사유까지 엄격 일치한 계획 | 4/10 | 5/10 |

새 구성의 엄격 일치 5개는 정상 계획 5개다. 오류 사본은 목표 오류 검출 또는 부수 판정에서 적어도 하나씩 틀렸다. 이번에도 복구 후 통과와 최초 통과를 합치지 않았으며 재계획 자체를 실행하지 않았다.

## 사례별 결과

| 사례 | 정상 계획 | 바꾼 숫자 종류 | 오류 목표 검사: 기존→2번 | 오류 계획 전체 상태 |
|---|---|---|---|---|
| R01 | PASS | 압력 | value_changed→**match** | UNCLEAR |
| R02 | PASS | 소스 전력 | value_changed→**match** | **PASS** |
| R03 | PASS | 바이어스 전력 | value_changed→**match** | ISSUE |
| R04 | PASS | 에너지 범위 상한 | value_changed→value_changed | ISSUE |
| R05 | PASS | 플럭스 하한 비교값 | value_changed→value_changed | ISSUE |

R01은 실제 압력 오류를 match로 놓쳤으며 작업·필터 누락 검사의 unclear 때문에 전체 UNCLEAR가 됐다. R02는 실제 소스 전력 오류와 나머지 검사까지 모두 match라서 잘못 PASS했다. R03은 바이어스 오류를 match로 놓쳤지만 다른 작업·필터 누락 검사에서 missing을 지적해 전체 ISSUE가 됐다. 따라서 R03의 전체 ISSUE를 올바른 오류 검출로 세지 않는다.

| 놓친 오류 목표 검사 | MATCH 점수 | value_changed 점수 |
|---|---:|---:|
| R01 압력 | 54.30% | 20.17% |
| R02 소스 전력 | 50.15% | 20.80% |
| R03 바이어스 전력 | 52.42% | 14.14% |

선택지 점수는 정확도나 실제 정답 확률이 아니다. d1은 최대 점수 선택지를 반환하므로 세 오류 모두 match를 선택했다. 원시 입력에서 오류 숫자·올바른 원문 인용이 보존됐음을 별도로 확인했다. 자료가 늘어났을 때 왜 불일치를 덜 민감하게 판정했는지의 내부 사유는 모델이 출력하지 않아 확정하지 않는다.

바뀐 선택은 총 6개다. R02 정상 소스, R03 정상 소스, R03 오류 사본 안의 정상 소스라는 기존 오판 3개는 고쳐졌다. 반대로 R01 압력·R02 소스·R03 바이어스의 실제 오류 검출 3개는 놓쳤다. 변경하지 않은 38개 요청의 선택과 모든 선택지 점수는 기준과 정확히 같았다.

## 토큰과 시간

| 측정 | 기존 발췌 | 2번 방식 | 관측 차이 |
|---|---:|---:|---:|
| 전체 입력 토큰 | 111,282 | 113,134 | +1,852 / +1.66% |
| 전체 검사당 평균 입력 | 1,987.18 | 2,020.25 | +33.07 |
| 숫자 검사당 평균 입력 | 1,630.64 | 1,714.82 | +84.18 |
| 계획당 평균 모델 채점 | 6.926초 | 7.072초 | +0.146초 / +2.10% |
| 전체 검사당 평균 채점 | 1.2368초 | 1.2628초 | +0.0260초 |
| 숫자 검사당 평균 채점 | 0.9954초 | 1.0573초 | +0.0618초 |

최대 입력은 기존과 같은 3,110토큰이며 절단은 없었다. 계획 처리 wall 평균은 7.969초다. 모델 채점은 backend.score 호출부터 GPU 동기화 완료까지이고 모델 적재·프로세스 시작·별도 패킹·폴링·웹 처리는 제외한다. wall도 Qwen 계획 작성이나 최종 응답을 포함하는 웹 전체 시간은 아니다.

이번 후보는 1회 실행이고 기준은 저장된 이전 결과다. 작은 시간 차이를 일반적인 속도 차이로 단정하지 않는다. 동일한 기준 구성의 최근 3회 평균은 6.904초였으나 이번에는 그 구성을 다시 호출하지 않았다.

## 메모리와 검증

- OS 메모리 피크 18.256 GiB, 176표본, warning/critical/unknown 0, 추가 swap 0이었다. DB OOM 증가는 없었다.
- MLX 할당 피크는 2,917,167,217 bytes(약 2.717 GiB)다. OS 전체 관측과 범위가 다르므로 더하지 않는다.
- 입력 준비 assert로 변경 요청 18개·그대로인 요청 38개, 현재 검사와 질문/인용/오류 숫자의 보존을 확인했다. 이전 R02·R03 restore_siblings 실험의 정상 소스 요청과도 정확히 같았다.
- 실제 tokenizer 사전 검증은 추론 0회다. 선택지 token 그룹·보정값이 같았고 변경된 18개만 토큰이 늘었다. 다른 38개 패킹은 완전히 같았다.
- 56개 원시 결과를 기존 normalize_response/parse_plan_review로 읽어 선택·확률·전체 검토 상태가 일치함을 확인했다.
- 전후 소스 지문·프로필·환경 파일·DB 스냅샷·등록 프로세스 ID·Docker 한도·검토 활성화가 유지됐다. 작업자는 계속 실행 중이고 d1 서비스는 모델 미적재·해제 상태이며 기존 메모리 검사 증거도 유효했다.

## 로컬 보관과 실행 근거

원시 질문·실제 계획·인용·입력·점수·파서 결과·실행 로그는 Git 제외 `.local/runtime/v2.5-d1-sibling-inputs-10/`에 보관했다. 이전 산출물은 덮어쓰지 않았다. 공개 문서에는 실제 질문·인용문·물리 실험 수치를 넣지 않았다.

실행한 주요 명령은 다음과 같다. 기존 파일이 있으면 자동 반복하지 않는다.

```text
agent/python/.venv/bin/python .local/runtime/v2.5-d1-sibling-inputs-10/prepare.py
agent/python/.venv/bin/python .local/runtime/v2.5-d1-sibling-inputs-10/capture.py
agent/python/runtimes/d1_mlx/.venv/bin/python .local/runtime/v2.5-d1-sibling-inputs-10/engine_probe.py --engine mlx-q8 --preflight
agent/python/.venv/bin/python .local/runtime/v2.5-d1-sibling-inputs-10/run_evaluation.py
agent/python/.venv/bin/python .local/runtime/v2.5-d1-sibling-inputs-10/analyze.py
agent/python/.venv/bin/python .local/runtime/v2.5-d1-sibling-inputs-10/compare.py
agent/python/.venv/bin/python .local/runtime/v2.5-d1-sibling-inputs-10/verify_completion.py
```

이번에는 평가용 입력에만 2번 방식을 적용했다. 정상 반려 개선과 실제 오류 검출 저하를 함께 기록했으며, 운영 입력 정책 반영·전체 웹 평가·커밋·push·PR·배포는 하지 않았다.
