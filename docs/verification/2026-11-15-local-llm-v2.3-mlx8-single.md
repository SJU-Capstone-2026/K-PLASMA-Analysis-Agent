# LocalLLM v2.3: MLX Q8 개별 검토와 입력 축약 실험

2026-11-15. [최신 구현 계획](../plans/2026-11-15-003-local-llm-v2.3-mlx8-single.md)의 결과다.

## 결과와 해석

요청한 Q8 MLX 개별 실행, 고정 지침 영어화, 중복 설명 축약, 전송용 실행 정리표 제거를 구현했다. Q8 기존 입력 대비 최종 입력 토큰은 **19.59%**, 검토 시간은 **19.35%** 감소했다. 그러나 이번 인공 계획의 PASS/ISSUE 판정 일치는 **3/5에서 2/5**, 의도한 오류 항목·사유까지 맞힌 건수는 **2/5에서 1/5**로 줄었다. **정확도 유지 조건을 만족한 개선으로 채택할 수 없다.** 요청한 최종 구성은 실험용 설정으로 남기며 이 결과를 성공으로 바꾸거나 자동으로 재평가하지 않았다.

이는 실제 Agent 5문항 웹 평가의 성공률이 아니다. 고정된 인공 계획을 d1에 주고 계획 의미 검토만 비교한 소규모 진단이며, Qwen의 새 계획·실제 Run 조회·최종 답변은 생성하지 않았다.

## 같은 입력으로 비교한 5개 구성

인공 계획 5개는 올바른 단일 조회, 올바른 검색 후 비교, 숫자를 잘못 바꾼 검색, 요청하지 않은 설명을 추가한 계획, 지표 정의를 잘못 고른 비교다. 모델 설정과 실제 LangGraph 중단 상태의 `plan_review_enabled=true`를 실행 전에 확인했다. 계획별 검사항목 수는 6/9/5/5/7개로 총 32개다. 각 검사는 다른 검사의 결과나 질문을 입력에 합치지 않고 **MLX에서 하나씩 순서대로** 판단했다.

각 구성을 1회씩 실행했다. 총 **25개 d1 검토 HTTP 요청, 160개 단일 검사**이며 순서 뒤집기·숨은 warmup·72건 재평가는 없다.

| 구성 | 입력 토큰 / 검사 | 시간 / 검사 | 계획 검토 평균 | PASS/ISSUE 일치 | 의도한 사유까지 일치 |
|---|---:|---:|---:|---:|---:|
| BF16 + MLX, 기존 한국어 입력† | 4,092.94 | 2.518초 | 16.115초 | 3/5 | 2/5 |
| Q8 + MLX, 기존 한국어 입력 | 4,092.94 | 2.683초 | 17.174초 | 3/5 | 2/5 |
| Q8 + 고정 지침 영어화 | 3,605.03 | 2.387초 | 15.276초 | 1/5 | 1/5 |
| Q8 + 영어화 + 중복 축약 | 3,452.81 | 2.282초 | 14.603초 | 1/5 | 1/5 |
| Q8 + 영어화 + 중복 축약 + 정리표 제외 | **3,291.22** | **2.164초** | **13.851초** | **2/5** | **1/5** |

검사당 평균 토큰은 `5개 요청의 실제 input_tokens 합 / 실제 검사 수 32`다. 단순히 5개 요청의 토큰 평균을 검사당 값으로 표기하지 않았다. MLX native pack의 전체 지침·상태·선택지·특수 토큰을 포함하며 선택 판정이므로 출력 생성 토큰은 0이다. 시간은 gateway의 준비·실제 토큰 계수·HTTP·가중치 로딩·검사·해제를 포함한 벽시계 시간 합을 32로 나눴다. 실제 GPU forward만의 시간이나 전체 웹 응답 시간이 아니다.

유효한 비교 기준은 Q8 기존 입력이다. 최종 단계는 검사당 **801.72토큰**, **0.519초**를 줄였다. 영어화에서 487.91토큰, 중복 설명·전송용 해시 축약에서 추가 152.22토큰, 실행 정리표 제외에서 추가 161.59토큰이 줄었다. 지표 32개 중 일부를 임의로 빼거나 질문·계획·근거를 잘라낸 결과가 아니다.

† BF16 5회 측정 중 작업자가 `intentional-differences.json`을 갱신해 마지막 전체 프로필 일치 검사가 `LOCAL_RUNTIME_PROFILE_MISMATCH`로 실패했다. 이 오류를 원시 결과에 보존했다. 요청별 토큰 계수/전송 동일성과 수치·판정·메모리 기록은 남았지만, BF16 행은 **전체 프로필 검증을 통과한 기준이 아닌 참고 측정**이다. 이를 통과로 보정하지 않았으며 25회 범위를 지키기 위해 모델을 다시 호출하지 않았다. 이후 네 Q8 구성은 프로필 일치 검사와 메모리 감시를 모두 통과했다.

## 판정이 어떻게 달라졌는가

| 인공 계획 | 기대 | BF16 기존† | Q8 기존 | Q8 영어 | Q8 축약 | Q8 정리표 제외 |
|---|---|---|---|---|---|---|
| 올바른 단일 조회 | PASS | PASS | PASS | PASS | PASS | PASS |
| 올바른 검색 후 전체 비교 | PASS | PASS | PASS | UNCLEAR | UNCLEAR | UNCLEAR |
| 숫자를 잘못 바꾼 검색 | ISSUE | ISSUE | ISSUE | PASS | PASS | PASS |
| 불필요한 설명 추가 | ISSUE | PASS | PASS | PASS | PASS | PASS |
| 지표 정의를 잘못 고른 비교 | ISSUE | PASS | PASS | PASS | PASS | ISSUE |

- BF16과 Q8 기존 입력의 32개 선택은 모두 같았다. 선택지 확률의 최대 차이는 약 0.03094였다. 이번 표본에서는 양자화 직후 판정 저하가 관찰되지 않았다. 1회 표본이므로 일반적인 동등 정확도를 입증하지는 않는다.
- 기존 입력의 잘못된 숫자 검색은 ISSUE였지만 `filter.search.pressure=value_changed` 대신 `request.tasks=unexpected`를 골랐다. 오류를 올바른 이유로 찾은 성공으로 합치지 않았다.
- 영어화 직후 정상 비교의 `trend_axis.compare`가 `unclear`로 바뀌고, 잘못된 숫자를 넣은 계획은 통과했다. 따라서 영어가 무조건 더 잘 맞는다는 가정은 이번 입력에서 성립하지 않았다.
- 정리표를 뺀 최종 구성은 잘못된 지표 계획을 ISSUE로 바꿨지만, 기대한 `outputs.compare` 대신 `baseline.compare=unexpected`를 골랐다. 이 역시 올바른 사유 검출로 세지 않았다.
- 중복 축약만 추가한 단계는 영어화 단계와 같은 판정이었다. 문구 변경·중복 참조·정리표 제거에 대한 모델의 민감도를 보여주며, 이 표본만으로 각 문장의 근본 원인이나 일반 정확도를 확정할 수 없다.

실제 그래프를 돌려 재계획한 평가가 아니므로 모든 행은 최초 고정 계획 검토다. REPLAN 후 복구·최종 통과·답변 재작성 수치를 섞지 않았다. 기존 최대 2회 재계획·최대 1회 답변 재작성은 코드에서 유지했다.

## 메모리와 구현 범위

같은 원본 revision `a6bce774e6dde338dcc3036ceb5d91f78bf4c19e`의 d1을 로컬에서 변환했다. affine 8비트/group64로 153개 Linear 가중치를 양자화했고, 공식 선택지 readout이 직접 읽는 tied embedding과 norm·conv kernel은 BF16으로 보존했다. GGUF Q8_0 파일을 MLX에서 그대로 연 것이 아니며, 임의의 다른 d1 revision이나 calibration으로 바꾸지 않았다.

- 모델 파일: BF16 **3.220GiB → Q8 1.940GiB**, 약 **39.75% 감소**.
- 5개 비교 중 MLX allocator 최대값: BF16 참고 **3.896GiB**, Q8 기존 입력 **2.676GiB**, Q8 최종 입력 **2.774GiB**. 전체 macOS 사용 메모리·GPU 전용 VRAM과 동일한 값이 아니다.
- 변환과 25개 비교에서 관찰한 memory pressure warning/critical 표본은 모두 0, 비교 중 swap 증가도 0이었다. Docker VM 제한 **1536MiB**, DB OOM kill 0을 전후 확인했다.
- d1은 매 검토 요청이 끝나면 backend·cache를 해제한다. Qwen sleep 확인 후 d1을 로드하고, d1 해제 확인 후 Qwen을 쓰는 기존 순서를 유지한다.

최종 Q8 설정의 별도 인공 입력 메모리 준비 검사 **7/7도 통과**했다. Qwen 4회, d1 3회이며 토큰 목표 256/4,096/15,500과 생각모드 계획 제출을 확인했다. 해당 d1 세 요청은 각각 독립 검사 3개를 순서대로 처리한다. 실제 입력 계수와 모델 usage가 같았고, d1 해제 후 active 16바이트·cache 0을 확인했다. 이 준비 검사에서 관찰한 OS 활성·wired·압축 메모리 합의 피크는 **17.825GiB**, pressure warning/critical·swap 증가는 0이었다. 샘플링된 프로세스 RSS 피크는 Qwen 6.536GiB, d1 2.384GiB, d1 native MLX 피크는 3.033GiB였다. RSS와 MLX allocator는 서로 다른 지표이므로 합산하지 않는다. 모델 로딩 전후 instance fingerprint도 같았고 준비 증거 검증을 통과했다.

기존 공용 5173 웹·8080 백엔드·DB를 유지하고 로컬 워커를 새 설정으로 재기동했다. 워커 자체 프로토콜 준비 검사 4회(Qwen 계획/본문/stream 3회, d1 1회)를 포함해 이번 작업의 추론 요청은 **25 + 7 + 4 = 36회**다. `worker ready: graph=v2_localLLM` 로그, 실제 그래프 검토 ON, MLX Q8 정밀도·단일 검사 설정·모델 해제, 웹/백엔드 HTTP 200을 확인했다. 기존 Run 150개·Run version 150개·대화 turn 85개·요청 224개와 Run/version/turn 원본 집계 해시는 전후 같았고 대기 요청은 0개였다. 추가 웹 질문을 제출하거나 실제 Run 데이터로 정확도를 재평가하지 않았다. 연결 준비 통과가 의미 정확도 통과를 대신하지 않는다.

고정 검토 지침·선택지 설명·도구/지표 설명·정책만 영어화했다. 원본 질문·대화·확정 문맥·원본 계획·인용·실행 근거는 그대로다. `plan_digest`, `input_digest`, `execution_view`는 전송용 사본에서만 제외하며 원본 snapshot·결과 매칭·거절 근거는 원본을 사용한다. 반복 지표 정의는 공통 사전과 참조로 전달하고 32개 지표 의미를 모두 보존한다. 알 수 없는 고정 문구는 영어화가 된 척하지 않고 오류로 처리한다.

기본은 `D1_PRECISION=q8`, `D1_INPUT_PROFILE=en-compact-no-view`다. BF16 단일 실행은 같은 MLX 서비스의 `bf16` 설정으로 남겼다. d1 옛 llama.cpp renderer·template·native tokenizer 분기와 공동 입력/독립4 실행·평가 코드는 제거했다. **Qwen의 llama.cpp, 사용자 데이터, 과거 평가 결과, 기존 모델 파일은 삭제하지 않았다.** 과거 검증 문서는 당시 기록으로 보존했다.

  runtimes/d1_mlx/convert.py runtimes/d1_mlx/service.py

  evals/local_llm_measure.py evals/local_llm_smoke.py runtimes/d1_mlx tests/v2_local_llm

로컬 회귀 **601개**, 공통 응답 계약 **58개**, 합계 **659개 통과**. 초기 복제 전용 8개는 제외했다. mypy는 122개 src 및 별도 4개 runtime/eval 파일, Ruff와 `git diff --check`가 통과했다. 실제 count와 전송 입력 동일성·원본 snapshot 불변·불완전/초과 입력 차단·정밀도별 provenance·모델 해제를 검사했다. 독립 코드 검토에서 마지막 Docker 조회 실패가 완료된 측정 기록을 잃게 하는 문제를 발견해 CPU RED/GREEN으로 고쳤다. 로컬 그래프·검토 계약·v2/v3를 포함한 보호 대상 54개 파일의 시작 전 해시와 현재 해시는 모두 같았다. v3 실제 평가는 하지 않았다.

원시 요청·응답·정밀도별 env·변환 manifest·메모리 자료는 Git 제외 경로 `.local/runtime/v2.3-mlx8-single/`에 보관했다. 공개 문서에는 집계와 인공 사례의 실패 원인만 적는다. 모델·env·원시 산출물의 Git 제외를 확인했다. 커밋·push·PR·Folio 공개는 수행하지 않았다.
