# Docker3GiB 통과 환경과 Qwen 캐시 검사 실패 환경 비교

## 판정

동일 Docker 상한이라도 Mac 전체 메모리 상태가 같지는 않았다. **캐시를 완전히 끈 동일 인공 호출에서도 메모리 경고가 재현됐다.**
캐시 저장·복원을 실행해야 발생하는 오류가 아니라, 현재 상주 작업과 메모리 압축 상태에서 Qwen을 깨울 때 macOS 메모리 압력이 발생하는 문제다.
캐시 ON의 추가 비용을 모두 검증했다는 뜻은 아니다. 어떤 앱 하나가 과거 실패의 전부를 유발했는지는 당시 계측 부족으로 확정하지 않았다.

## 같은 조건과 달라진 관측

이전 기준은2026-11-13 19:04 KST에 생성된 실제 `synthetic/measurement.json`이다.
이는 `.local/runtime/local-web/measurement.json`과 byte 단위로 같다. 이전 검사 폴더 최상위의93표본 파일은 더 이른 검사 사본이므로 이번 비교에서 제외했다.

| 항목 | 이전3GiB 검사 | 이번 캐시 ON 검사 |
|---|---:|---:|
| Docker VM 설정 | 3072MiB | 3072MiB |
| 실행 엔진 총량 | 3,054,383,104B | 3,054,383,104B |
| Qwen 모델·엔진 | Qwen3.5-9B Q4_K_M / b12317 | 같음 |
| Qwen context·batch/ubatch | 24576 · 256/256 | 같음 |
| d1 context·batch/ubatch | 32768 · 16000/16000 | 같음 |

| 첫 인공 입력 | 244토큰 | 244토큰 |

시작 resident는779,714,560B(743.594MiB) 증가했다. 이미 사용 중인 swap도 약441.37MiB 더 많았다.
기존 swap의 양만으로 실패 원인을 단정하지 않는다. 각 검사의 추가 swap과 구분한다.
resident는 기존 active+wired+compressor 지표이고, 다른 프로세스의 RSS·footprint와 서로 더하지 않는다.

실행 자원 프로필의 차이는 새 `qwenPlanCache` 항목뿐이었다.
옛 임시 모델 경로와 현재 프로젝트 모델 경로의 device/inode/크기가 같아 실제로 같은 모델 파일을 사용했음을 확인했다.
Qwen1개·d1 1개만 상주하며 새 중복 LLM 인스턴스는 확인되지 않았다.

## 캐시 OFF로 원인 분리

현재 캐시 OFF 서버를 그대로 사용해 기존 진단용 인공 writer 호출을1회만 실행했다.
기존과 같은 인공 DB·백엔드·Vite·headless 브라우저를 만들고 원래150 Run과 실제 질문은 사용하지 않았다.
모델·배치·Docker 상한·d1 검토 설정은 변경하지 않았다. 현재 모델 실행 인자에는 `--slot-save-path`도 없다.
이 검사는 READY 증거나 문항 평가가 아니다.

| 관측 | 결과 |
|---|---:|
| Qwen 호출 | 1회, 244입력 토큰 |
| d1 호출 | 0회 — 첫 writer 기본 호출만 진단 |
| d1 계획 검토 설정 | ON 유지 |
| 응답·토큰 수 검증 | 통과 |
| 메모리 표본 | normal29·warning6 |
| 관측 resident 피크 | 20.378GiB |
| 추가 swap | 116.0MiB |
| 실행 전후 모델 인자·프로필 | 일치 |

단위 입력을 준비하는 동안 모델이 깨어났고, 실제 생성 요청 직전부터 이미 pressure2가 관측됐다.
같은 구간에 Mac wired는 약2.81→8.64GiB, compressor 점유는 약5.92→8.78GiB로 변했다.
각 값은 Mac 전체 계측이며 Qwen 전용 할당량으로 해석하지 않는다.
짧은 질문도 모델 본체와 설정된 실행 공간을 올리는 과정을 거치므로,244토큰이라는 이유만으로 적은 메모리만 쓰는 것은 아니다.

이전 인공 검사에서는 wired 최대9.074GiB에서도 정상 압력이 유지됐고 compressor 최대는7.310GiB였다.
따라서 특정 resident 총량만으로 경고 여부를 정하는 모델로 설명할 수 없다.
Apple도 메모리 압력이 free memory·swap rate·wired·file cache 등을 함께 반영한다고 설명한다.
[Apple Activity Monitor 안내](https://support.apple.com/en-mide/guide/activity-monitor/actmntr1004/mac).

## 상주 프로세스 차이

이전 전수 스냅샷과 현재 유휴 스냅샷을 같은 macOS `proc_pid_rusage` 계측기로 비교했다.
관측 시점은 서로 다르므로 이 수치를 과거 실패 순간의 사용량으로 대체하거나 모든 차이를 단일 원인으로 합산하지 않는다.

- Python 앱 프로세스는 이전5개/footprint339.5MiB, 현재15개/1233.9MiB다. 현재15개는 모두 Codex가 부모인 `code_review_graph` 도구다.
- 현재 살아 있는 것 중11개는 캐시 검사 실패 시점 전에 시작됐다. 이11개의 **현재** footprint 합계는 약907.5MiB다.
  실패 후 시작한4개를 과거 실패 원인으로 포함하지 않았다. 과거 PID 재사용 가능성이 있어 단순 PID 일치로 같은 프로세스라고 판정하지 않는다.
- Codex 앱 묶음의 footprint는8184.6→8810.9MiB, Node는1683.2→1993.2MiB, IntelliJ는1267.7→1506.1MiB로 관측됐다.
  footprint는 압축분 등을 포함하는 프로세스 회계이고 RSS와 다른 지표다.
- 공용 백엔드와 별도 인공 검사 스택은 이전에도 동시에 존재했다. 이 구성 자체를 이번에 새로 생긴 원인으로 지목하지 않는다.

증가한 개발 도구와 앱 메모리는 여유 감소의 구체적인 후보다. 특히 여러 도구 인스턴스가 실패 전부터 존재했음은 확인됐다.
그러나 캐시 실패 보고서에는 당시 앱별 카운터가 없어, 최초 증가743.594MiB 전부를 특정 도구 탓으로 확정하지 않았다.

이전5문항 성공도 계속 정상 메모리였다는 뜻은 아니었다. 당시 준비97표본은 모두 정상이었지만 웹673표본 중174개는 warning이었다.
당시와 현재가 충분한 여유를 가진 동일 환경이었다고 보기는 어렵다.

## 변경·정리와 다음 판단

제품 코드·모델 설정·Docker 제한·사용자 앱은 변경하거나 종료하지 않았다.
진단에서 만든 인공 DB·백엔드·웹·브라우저만 정리했고, 정리 후 pressure1을 확인했다.
원래 공용 서비스·실험 DB·대화는 유지했다. 캐시는 OFF 상태다.

모델 축소나 메모리 기준 완화에 앞서, 불필요한 개발 도구 인스턴스의 수명과 상주 작업부터 확인하는 것이 근거에 맞다.
원인 진단 단계에서는 도구를 종료하지 않았다. 아래 사용자 승인 정리를 마친 뒤에도 모델 부하 메모리 준비 검사 통과 여부는 미검증이다.
웹5문항·전체7행 재검사는 수행하지 않았다.

근거 원문은 Git 제외 경로 `.local/runtime/v2.2-qwen-cache/diagnosis/`에 보관한다.
실행은 기존 `process_sampler.py`·단일 인공 `probe.py`·웹 스택 진단 경로를 재사용했으며,
private `diagnosis/run.py` 종료 코드0·Qwen1회·actual input244·인자 불변을 확인했다.
새 프로세스별 기록과 비교 요약, 소스 설정 확인을 사용했고 소프트웨어 수정이 없어 단위 테스트는 재실행하지 않았다.

## 후속 — 사용자 승인으로 유휴 도구 정리

사용자의 “검토해서 중복이나 불필요한 것들 다 내려버려” 지시에 따라 실제 실행 중인 대화·서비스·도구 상태를 다시 확인했다.
현재 연결된 코드 분석 서버에 통계 요청을 보내 CPU 카운터가 증가한 인스턴스를 식별해1개 보존했다.
소유자·부모·정확한 실행 모듈·프로세스 시작 ID를 재확인한 뒤 나머지 코드 분석 서버14개와 사용하지 않는 REA 도구 서버15개를 정상 종료했다.
총29개 모두 SIGTERM으로 종료됐고 강제 종료는 없었다. 이후 통계 요청도 정상 응답했고, 재생성 없이 코드 분석 서버1개·REA서버0개를 확인했다.

종료한 프로세스의 직전 footprint 합계는2175.4MiB(약2.12GiB)다. 이를 즉시 회수한 물리 RAM 수치로 해석하지 않는다.

| Mac 전체 관측 | 정리 전 | 정리 후 안정화 표본 |
|---|---:|---:|
| 기존 resident 지표 | 15.898GiB | 중앙값15.495GiB |
| compressor 점유 | 5.950GiB | 중앙값5.266GiB |
| 사용 swap | 4616.69MiB | 3353.25MiB |
| pressure | normal1 | 5개 표본 모두 normal1 |

공용 웹5173·백엔드8080의 HTTP200, Qwen·d1의 기존 sleep 상태와 단일 슬롯을 확인했다.
공용 DB 컨테이너1개만 실행 중이며 healthy이고 검사 컨테이너는 남아 있지 않았다. Docker 엔진 총량3,054,383,104B를 유지했다.
v2/v3 워커·프런트엔드·백엔드·Qwen·d1 서비스 프로세스6개를 보존했다. 남은 Node 보조 프로세스는 중복 서버가 아닌 Codex 내부 도구 런타임으로 확인해 유지했다.
Codex 본체·Chrome·IDE 등 사용자 앱, 데이터와 모델 설정은 변경하지 않았다. 캐시는 OFF다.

기록은 같은 비공개 경로의 `cleanup-before.json`, `cleanup-selected.json`, `cleanup-result.json`,
`cleanup-after-settled.json`, `cleanup-memory-summary.json`, `cleanup-final-verification.json`에 남겼다.
모델 부하 메모리 검사와 웹 평가는 재실행하지 않았으며, 현재 정상 압력만으로 부하 준비 통과를 주장하지 않는다.
