# LocalLLM_v2.3 구현·검증 기록

기준 계획: [Qwen 분석과 d1 묶음 처리](../plans/2026-11-14-004-local-llm-v2.3-qwen-analysis-d1-joint.md).
구현과 조건부 검증을 마쳤으며, d1 묶음 후보는 **속도 통과·정확도 실패로 채택 보류**다. 기존 Q8 경로로 복귀했다.
원시 모델 응답·실험 데이터·대화·비밀값은 Git 제외 로컬 경로에 보관한다.

## 구현 범위

- Qwen의 생각/도구 인자 길이, 단계 수, 생성 속도, 진단 비용을 숫자로 기록한다. 정확한 provider 계수와 CPU tokenizer 재계수 추정을 구별한다. 생각 시간을 토큰 비율로 계산하지 않는다.
- d1 전용 Python3.12 환경에서 고정 mlx-decision1.3.0/MLX0.32.4와 LiquidAI/d1-2B BF16을 실행한다. 기존 Q8 개별 경로는 기본값과 복귀용으로 유지한다.
- 묶음은 최대16항목/실제 전체 pack16000토큰으로 분할한다. 상태 잘림·검토 누락·도구 호출 우회 없이 기존 검토 파서로 결과를 읽는다.
- 실제 모델/라이브러리/lock/서비스/검증 코드의 식별값과 메모리 증거를 연결한다. 모델 가중치 해제와 GPU allocator 해제를 확인한 뒤 Qwen을 재개한다.
- 고정 인공8사례의 A/B/C 대조와 B/C 순서 반전, 실행 중 메모리 감시와 DB OOM 확인을 구현했다.

기존 그래프·계획/최종 응답 schema·스트리밍·검토 지침/선택지/파서는 구현 전 동결한8개 파일과 일치한다.
보호 대상 그래프 소스의 HEAD 대비 변경도 없다. 기존 v2.2 미커밋 변경은 보존했다.

Docker Desktop 설정2048MiB, 실행 VM 메모리2,066,317,312바이트를 유지한다.
development는 pressure1/2를 허용하고 swap을 기록한다. pressure4/알 수 없는 상태는 다음 모델 단계를 막고 과거 실패도 유지한다.
기본 strict는 바꾸지 않았다. 호스트 active+wired+physical compressor, 프로세스 RSS, MLX 할당량은 서로 다른 지표이며 합산하지 않는다.

이16바이트는 모델을 올리기 전 작은 빈 계층을 초기화해 측정한 공용 런타임 상태다. 임의의 허용 메모리를 추가한 값이 아니다.
경고 표본 수는 검사 시간과 샘플링 간격의 영향을 받으며 실패 횟수나 전체 요청 수가 아니다.

초기 시도에서 Java21 경로와 서비스 절대 경로 불일치가 실제 모델 실행 전에 검사를 막았다.
다른 초기 시도는 Qwen 준비 중 critical로 중단됐으며 d1 BF16을 올린 결과가 아니었다.
이후 첫 BF16 실행은 빈 런타임 기준0과 남은 공용 상태8바이트 차이 때문에 해제 실패로 판정됐다.
빈 런타임을 실제 보정하고 재측정했다. 다른 앱은 종료하지 않았고, 통과한 옛 기록의 hash를 고쳐 새 증거로 만들지 않았다.

## 고정 인공 정확도·시간 대조

정상3/오류5의 기대 판정을 미리 고정했다. A는 Q8 개별, B는 BF16 개별, C는 BF16 묶음이다.
A→B는 엔진과 정밀도가 함께 바뀐 비교이고 B→C가 묶음 처리 대조다.
각8회와 B/C 반전 각1회로 최대26회이며, 준비·인공 메모리·캐시 호출은 별도로 집계한다.

**C는 정확도 관문 실패다.** 상태 정답은2/8이며 정상 비교·선택 확인 계획을 거절하고 경계·단위·비교 누락·추가 설명 오류를 승인했다.
`bad_skipped_selection`의 ISSUE도 실제 지적은 선택 누락이 아닌 trend 축 관련이므로 상태 일치와 이유의 타당성을 구별한다.
정상 계획의 잘못된 지적은 `trend_axis.compare`, `baseline.compare`의 `unexpected`였다.
이는 고정 계획을 검토한 결과이며 Qwen의 이번 계획 생성 오류로 돌릴 수 없다.
반전된 실제 항목 순서를 확인했고 해당 상태의 최종 판정은 유지됐지만, 그 자체가 올바른 판정이라는 뜻은 아니다.
C 전체 처리 중앙값4.055초, 호스트 지표 피크18.260GiB, 추가 swap0, warning/critical0/0, DB OOM 증가0이다.

B/C의 가중치·정밀도·고정 입력은 같으므로 이 두 사례에서 묶음 구성에 따른 판정 변화가 확인됐다.

development 정책에 따라 이를 기록하며 계속했으나 무경고·무swap 안정성으로 표현하지 않는다. 다른 앱의 활동과 분리한 메모리 인과 실험은 아니다.

공식 다른 backend 재현, 추가 모델 교체, 지침/선택지 변경은 이번에 실행하지 않았다.
C가 기대 판정을 모두 맞추고 신규 오류 승인이 없으며 순서 대조와 메모리를 통과해야 한다.
전체 처리 중앙값은 A보다20% 이상 짧고 B보다 짧아야 한다. 연산 시간만으로 통과시키지 않는다.
