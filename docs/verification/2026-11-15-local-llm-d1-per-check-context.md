# LocalLLM v2.4: 검사별 설명 선별 구현·비교 결과

후속 사용자 지시에 따라 [모든 검사 선별 결과](2026-11-15-local-llm-d1-all-check-context.md)가 추가됐다. 본 문서의 full 복구는 최초 비교 시점의 기록이며, 현재 실행 설정은 후속 문서의 per_check다. 아래 원래 성적·실행 기록은 보존한다.

2026-11-15. [구현 계획](../plans/2026-11-15-004-local-llm-d1-per-check-context.md)에 따라 코드 기반 선별, 준비 identity, 같은 정상 5개·오류 5개의 비교를 수행했다.

**결론:** 선별 구현·입력 보존·메모리·프로토콜 검증은 통과했다. 검사당 입력은 14.57%, 계획당 d1 검토 시간은 14.21% 감소했다. 정상 계획은 4/5→5/5로 개선됐지만, 오류 항목·정확한 사유 검출은 1/5로 그대로다. **정확도 목표는 실패했으므로 후보를 운영 권장값으로 승인하지 않는다. 공용 로컬 워커는 `full`로 복구했다.**

## 구현과 보호 범위

- `core/d1_context.py`: 검사 kind·단계·지표 ID·선행 참조로 필요한 설명을 선택한다. 새 LLM, 자연어 분류기, 임베딩, 벡터 DB는 추가하지 않았다.
- MLX `pack_requests`의 단일 검사 조립에서 `tool_contracts`만 투영한다. 한 계획의 HTTP 요청 하나, 검사별 독립 순차 처리와 한 번의 모델 load/unload를 유지한다.
- 전역 누락·출력 지표 검사와 미지원 검사는 전체 설명을 유지한다. 불확실한 참조·지표·표현도 전체 원본 문자열로 돌아간다. 알려진 지표군, 단위, 연산자, binding/scope, 선행 도구와 `definition_ref`를 함께 보존한다.
- 질문·이력·확정 문맥·원본 계획·검토 지침·선택지·검사 ID·원본 snapshot·digest는 바꾸지 않는다. 검사나 잘못된 판정을 코드로 생략·보정하지 않는다.
- `full|per_check` 설정, `d1-context-1` 규칙 버전과 selector/catalog/언어 투영/계약 의존성 hash를 실행 중 서비스, worker 설정·메모리 증거·복구 identity에서 대조한다. 기본값은 `full`이다.
- count와 추론에 같은 조립 경로를 적용하고 실제 packed hash, usage, 모델 해제, 선별/전체/fallback 메타데이터를 내부에서 대조한다. 최종 사용자 응답과 SSE에 이 메타데이터를 추가하지 않는다.
- 그래프 노드·분기·HITL·실행 도구·`submit_plan`·계획/최종 응답 schema와 v2/v3 소스는 변경하지 않았다. 재계획 최대 2회·답변 재작성 최대 1회도 유지한다.

## 고정 조건과 실행 수

두 구성 모두 d1 Q8+MLX, `group_size=1`, `independent_batch_size=1`, `en-compact-no-view`, Qwen 캐시 OFF, Docker VM **1536MiB**, development 메모리 정책을 사용했다. Qwen은 기존 GGUF Q4_K_M·llama.cpp·24K context·batch/ubatch 256 설정을 유지했다.

모델 설정과 실제 그래프 상태의 `plan_review_enabled=true`를 호출 전에 확인했다. Qwen sleep→d1 검토→d1 unload 순서를 유지했다. 메모리 경고는 기존 정책대로 허용하지만 critical·미확인 압력·모델 해제 실패는 중단하는 조건이다.

| 단계 | 실제 추론 HTTP 요청 | 결과 |
|---|---:|---|
| full 메모리 준비 | 7: Qwen 4+d1 3 | 7/7 통과 |
| full 의미 검토 | 10 | 10/10 응답·계수·입력 검증 완료 |
| per_check 메모리 준비 | 7: Qwen 4+d1 3 | 7/7 통과 |
| per_check 의미 검토 | 10 | 10/10 응답·계수·입력 검증 완료 |

| 합계 | **38** | 예산 내, 의미 검토 재시도·추가 warmup 없음 |

count 호출은 추론 요청 수와 분리했다. 의미 검토는 구성마다 62개, 합계 **124개 독립 검사**다. 준비용 인공 검사를 정확도 분모에 합치지 않았다.

full→per_check 전환 시 로컬 실행 스크립트가 종료한 자식 프로세스를 reap하지 않고 PID 종료를 기다려 멈춘 문제가 한 번 있었다. 이미 끝난 full 메모리 7회·의미 검토 10회를 보존하고, 자식은 `Popen.wait`로 정리하도록 수정한 뒤 남은 per_check 단계부터 재개했다. 제품 소스와 모델 설정은 평가 중 동결했다. 처음 중단된 실행 기록도 로컬에 보관했으며, 완료한 17회의 모델 호출을 반복하지 않았다.

검토 시간은 **d1의 고정 계획 검토**이며 전체 채팅 응답 시간이 아니다. 준비·서비스 재시작·중단/재개 대기·복구는 의미 검토 시간에 넣지 않았다. 첫 요청도 평균에 포함했고, 각 구성 첫 사례는 10.599초/9.997초, 첫 모델 load는 0.444초/0.681초였다. 모델 load와 release, 단일 검사별 backend 시간은 원시 기록에 따로 남겼다.

- 실제 선별: **22/62개**. 이 검사들의 전체 입력만 합치면 72,773→43,547토큰으로 **40.16% 감소**했다.
- 정책상 전체 유지: **34/62개**.
- 불확실성 fallback: **6/62개**. 정렬 목표를 확정할 수 없는 `unresolved_metric`으로 전체 설명을 보냈다.
- 전체 설명을 보낸 **40개 검사**는 full과 동일한 state·토큰 수·packed hash를 유지했다. 선별한 22개는 모두 실제 입력 토큰이 줄었다.
- 도구 설명 JSON만 별도로 계수한 평균은 1,924.00→1,452.61토큰, **24.50% 감소**였다. 부분 JSON을 독립적으로 토큰화한 값이므로 전체 native 입력의 가산 가능한 분해값으로 취급하지 않는다.

전체 62개 중 약 65%가 보수적으로 전체 설명을 유지하고 질문·전체 계획·지침도 남기 때문에, 선별된 검사들의 40% 감소가 전체 요청에서는 14.57% 감소로 나타났다. 입력량 15% 목표는 근소하게 미달했고 시간 10% 목표는 달성했다. **정확도 목표 5/5 오류 검출은 미달**했다. 같은 10사례·구성별 1회만으로 통계적 동등성이나 일반 성능을 주장하지 않는다.

OS 메모리, allocator, RSS는 다른 지표이며 합산하지 않는다. OS 피크에는 당시 다른 앱의 영향도 있어 순수한 모델 메모리 절감량으로 해석하지 않는다. d1의 각 추론 후 실제 unload와 allocator/cache 해제를 확인했다.

평가 전후 DB는 **150 Run /150 Run version /85 turn /224 request**, 진행 중 요청 0으로 같았고 원본·기록 보존 hash도 일치했다. 제품 소스 identity와 corpus도 동일했다. 공용 5173/8080을 그대로 사용했고 별도 웹·backend·DB를 만들거나 다른 앱을 종료하지 않았다. 메모리 준비에는 인공 입력과 기존 공용 서비스의 health 확인만 사용했다.

마지막으로 새 코드의 `full` 메모리 증거와 실행 중 full 서비스 identity를 대조해 프로토콜 준비 4회를 통과했다. 공용 로컬 워커 실행, d1 검토 ON, Q8+MLX 단일 처리, d1 released 상태, frontend/backend HTTP 200, Docker 1536MiB를 추가 모델 호출 없이 확인했다. **기본값과 현재 운영 모드는 full**이며 선별은 명시적인 실험 옵션으로 남겼다.
