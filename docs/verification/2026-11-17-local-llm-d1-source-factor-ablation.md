# LocalLLM v2.5 — R02·R03 소스 전력 오판 요인 분리

## 핵심

정상 R02·R03의 소스 전력 검사에서 **질문을 해당 조건으로 좁히면 MATCH 점수가 92.58%·93.13%로**, 원본 질문을 유지하고 다른 실행값만 복구하면 **91.39%·91.93%로** 올라갔다. 발췌 표시 제거와 요구사항 설명 복구만으로는 오판이 해소되지 않았다.

전체 질문의 세 조건과 발췌 계획의 한 조건 사이에서, d1이 현재 검사 하나의 범위를 안정적으로 유지하지 못한다는 해석을 지지한다. 단순히 인용문이 길거나 발췌 표시가 있다는 사실만으로 두 오판을 설명할 수 없다. 검사 목록만 복구해도 판정이 달라져, 실제 숫자뿐 아니라 범위·분담을 나타내는 주변 자료에도 민감함을 확인했다.

이는 두 정상 사례의 원인 분리 결과다. 내부 사고 과정을 관찰한 것은 아니며, 정상·오류 전체 정확도 개선이나 운영 적용을 검증한 결과로 확대하지 않는다.

## 실험 범위와 유지 조건

- 기존 실제 Qwen 정상 계획 R02·R03의 `filter.s_forward.source_power`만 사용했다. 예상 선택은 모두 match다.
- 지시서·선택지·선택지 순서·온도·현재 검사 경로·도구 설명·소스 전력 실행 숫자와 단위는 유지했다.
- Q8+MLX, group_size=1·independent_batch_size=1, Metal GPU, Docker VM 1536 MiB(1.5 GiB), development 메모리 정책을 유지했다.
- 실행 전 설정과 실제 그래프 상태의 `plan_review_enabled=true`를 확인했다. 기존 소스·프로필·환경 파일·그래프·최종 응답/저장 계약은 변경하지 않았다.
- 공통 지침은 기존 2번+조건부 1·4·5번이다. 범위를 좁힌 뒤 거절된 수정 2번 지침을 사용하지 않았다.
- 15개의 서로 다른 단일 변경 입력을 준비했다. 메모리 critical로 중단된 한 호출을 한 번 다시 실행해 **총 16회 시도·15개 결과 완료**였다. 완료된 결과의 재실행은 0회다.
- 새 Qwen 호출·예열·Run 도구·REPLAN·답변 재작성·웹/API 전체 질문 평가는 0회다. 후보를 제품에 반영하지 않았다.

## 한 번에 하나씩 비교한 구성

모든 비교는 같은 사례의 기준 발췌 입력에서 출발했다. 다음 그룹을 서로 섞지 않고 바꿨다.

| 구성 | 변경한 자료 |
|---|---|
| 기준 발췌 | 이전 citation 평가 입력 그대로 |
| 인용문만 축소 | R02의 현재 소스 전력 인용을 원본 질문 안의 해당 조건 구절로 축소 |
| 질문 범위 축소 | question만 해당 소스 전력 조건 구절로 축소 |
| 발췌 표시 제거 | review_view 객체만 제거 |
| 다른 실행값 복구 | 같은 단계의 pressure·bias_power 리터럴만 복구 |
| 요구사항 설명 복구 | requirements의 sources·text만 복구 |
| 검사 목록 복구 | 다른 다섯 check_specs만 추가 |
| 실행 요약 복구 | program_effects만 복구 |

R02의 기준 인용문은 전체 질문이었다. 질문만 먼저 줄이면 message_key가 가리키는 question 안에 인용문이 존재하지 않게 되므로, **인용문만 축소한 대조군을 먼저 만들고 그 입력에서 question만 줄였다.** 따라서 R02의 질문 축소 효과는 이 대조군과 비교한다. R03은 이미 부분 인용이어서 기준 입력에서 question만 바꿨다. 모든 후보에서 인용문이 question의 실제 부분 문자열임을 확인했다.

복구 시 현재 소스 전력 바인딩과 기존 필드의 상대 순서를 보존했다. 다른 실행값·요구사항 속성은 기존 필드 뒤에 추가하고, 검사 목록은 현재 검사 항목을 첫 위치에 둔 채 다른 항목을 추가했다. 검사 목록을 복구해도 실제 판정 요청은 소스 전력 한 개이며, 묶음 처리나 추가 검사 호출로 바뀌지 않았다.

각 후보와 지정된 부모 입력의 JSON 경로 차이를 assert로 검증했다. 지시서·선택지는 바이트 단위로 같고 실제 배치된 선택지 token ID·보정 온도도 같았다. 새 기준 두 건의 token ID와 모델 점수는 이전 4회 대조 실험의 발췌 결과와 정확히 일치했다.

## 판정 결과

점수는 match 선택지의 정규화된 모델 점수이며 정확도나 실제 정답 확률이 아니다.

| 구성 | R02 선택 | R02 MATCH 점수 | R03 선택 | R03 MATCH 점수 |
|---|---|---:|---|---:|
| 기준 발췌 | unexpected | 16.23% | missing | 23.41% |
| 인용문만 축소 | unexpected | 4.98% | 이미 부분 인용 | — |
| 질문 범위 축소 | **match** | **92.58%** | **match** | **93.13%** |
| 발췌 표시 제거 | unexpected | 9.73% | missing | 20.10% |
| 다른 실행값 복구 | **match** | **91.39%** | **match** | **91.93%** |
| 요구사항 설명 복구 | missing | 25.06% | missing | 30.01% |
| 검사 목록 복구 | match | 45.29% | match | 50.94% |
| 실행 요약 복구 | match | 77.62% | match | 75.07% |

R02는 인용문만 짧게 바꾼 입력에서 question만 좁히자 match가 4.98%→92.58%(+87.59%p)로 변했다. R03은 23.41%→93.13%(+69.72%p)였다. 같은 짧은 인용·실행값을 유지한 채 질문의 다른 조건들을 빼는 것만으로 두 판정이 정상화된 관측이다.

다른 실행값 복구는 원본 질문과 현재 인용을 그대로 유지했다. 압력·바이어스 실행값을 추가하는 것만으로도 두 사례의 match가 91% 이상이 됐다. 따라서 인용문을 반드시 짧게 바꿔야 정상화되는 것은 아니다.

발췌 표시를 제거해도 기존 오판은 남았고 match 점수는 오히려 낮아졌다. 요구사항 설명 복구 역시 두 사례 모두 오판했다. R02는 unexpected→missing으로 오류 종류만 바뀌었다. 자료를 단순히 늘리거나 줄이는 것만으로 같은 효과가 나지 않았다.

검사 목록 복구에서는 실제 실행 숫자를 추가하지 않아도 match가 가장 높은 선택지가 됐다. 다만 45.29%·50.94%로 질문 축소·실행값 복구보다 경쟁 선택지와 가깝다. 이 결과만으로 검사 목록 복구를 안정적인 해결책으로 채택하지 않는다.

## 원인 해석의 범위

확인된 사실은 다음과 같다.

1. 정상 소스 전력 값과 인용문이 있어도 전체 질문·한 필드 계획의 조합에서 오판한다.
2. 질문 범위를 현재 필드에 맞추거나 실행 자료의 범위를 질문에 맞추면, 같은 지시서·선택지·숫자에서 두 사례가 모두 정상화된다.
3. 범위 안내인 검사 목록이나 중복 실행 요약도 판정에 영향을 준다.
4. 발췌 표시 제거와 요구사항 문구 복구는 각각 단독 해결 조건이 아니었다.

가장 일관된 설명은 현재 입력에서 **원본 질문의 요구 범위와 검토용 실행 자료의 범위를 연결하는 일이 d1에 불안정하다**는 것이다. ‘현재 소스 전력만 검사하라’는 지시가 있어도 주변 문맥에 따라 정상 여부를 안정적으로 분리하지 못한다는 관측이다.

missing이 압력이나 바이어스를 뜻했다는 내부 사유는 기록되지 않으므로 단정하지 않는다. 어느 정보가 판정을 뒤집는지는 분리했지만 모델 내부의 유일한 원인을 증명한 것은 아니다. 복구되는 여러 경로가 있으므로 특정 필드 하나의 누락만을 유일한 원인으로 주장하지 않는다.

이번 질문 축소 문구는 원본 질문에서 직접 고른 올바른 조건 구절이다. 실행값으로 질문을 재작성하거나 정답 라벨을 모델 입력에 추가하지 않았다. 일반화할 때도 실행값에서 비교 기준을 만들면 오류값을 정답처럼 확인하는 순환 검사가 되므로, 원본 질문이나 검증된 인용에서 기준을 골라야 한다. 실제 자동 선별 방법·잘못된 인용·문맥 의존 조건·오류 계획 검출은 이번에 검증하지 않았다.

완료된 15건의 입력 합계는 25,128토큰이다. 모든 입력은 절단 없이 처리됐다. 중단된 호출은 완료된 처리 토큰·시간을 얻지 못했으므로 완료 합계에서 제외했다. 시간은 모델 채점 구간이며 가중치 로드·웹 전체 응답 시간이 아니다. 각 구성 단회 실행이고 일부는 메모리 중단 후 재개한 별도 프로세스여서 미세한 시간 차이를 정밀 속도 비교로 해석하지 않는다.

질문 축소의 R02 직접 비교는 26토큰 감소였지만 match 점수는 87.59%p 상승했다. 더 많은 토큰을 줄인 발췌 표시 제거에서는 오판이 남았으므로, 단순한 입력 길이 감소만으로 판정 변화를 설명할 수 없다.

## 메모리 중단·재개와 호출 회계

첫 실행은 12개 결과가 완료되고 13번째 호출이 진행되는 중 실제 memory pressure=4(critical)를 관측해 즉시 중단했다. OS 메모리 피크 20.345 GiB, 27표본 중 warning 10·critical 1·unknown 0, 추가 swap 1,760,810,763 bytes였다. 완료 결과와 중단된 원시 파일을 보존했다.

실험 프로세스 종료 뒤 pressure=1로 회복됐고 d1 서비스의 모델 해제 상태를 확인했다. 완료된 12개는 반복하지 않고, 중단된 검사 한 개와 미실행 두 개만 별도 실행했다. 재개 실행은 3개 모두 완료됐으며 OS 피크 16.568 GiB, 11표본, warning/critical/unknown 0, 추가 swap 0이었다. 다른 앱을 종료하거나 메모리 정책·Docker 한도를 바꾸지 않았다.

재개용 실행기를 복사하면서 Docker 한도 확인값이 잘못 치환돼 사전 검사 한 번이 실패했다. 모델 호출 전이어서 추가 추론은 0회였고 실제 Docker 설정도 변경되지 않았다. 검사값을 1536 MiB로 바로잡고 호출 한도와 설정 검사를 다시 확인한 뒤 재개했다.

총 의미 검사 시도는 13+3=16회, 완료 결과는 12+3=15개, 중단 1회·중단 호출 재시도 1회다. 모델 판정이 나쁘다는 이유로 재시도한 경우나 완료된 검사를 반복한 경우는 없다. 첫 배치 전체를 무중단 성공으로 보고하지 않는다.

## 검증·보관

각 배치 전후 운영 소스 지문·프로필·환경 파일·DB 스냅샷·등록 프로세스 ID·Docker 제한·DB OOM 횟수가 같았다. 마지막에 실제 그래프의 검토 활성화, 로컬 작업자 실행, d1 서비스의 모델 미적재·해제, 기존 메모리 검사 증거의 유효성을 확인했다.

원시 질문·실제 계획·인용·선택지별 전체 점수·패킹·실행 로그는 Git 제외 `.local/runtime/v2.5-d1-source-factor-ablation/` 및 `-rest/`에 로컬 보관했다. 입력 준비와 최종 분석에서 실제 변경 경로·출처 일관성·패킹·선택지·확률 합·기준 재현·15개 고유 완료 결과·16회 시도를 검증했다. 공개 문서에는 원본 질문·인용문·실험 수치를 포함하지 않았다.

실행한 주요 명령은 다음과 같다. 같은 경로에서 자동 반복하지 않도록 보호했다.

```text

agent/python/.venv/bin/python .local/runtime/v2.5-d1-source-factor-ablation/capture.py
agent/python/runtimes/d1_mlx/.venv/bin/python .local/runtime/v2.5-d1-source-factor-ablation/engine_probe.py --preflight
agent/python/.venv/bin/python .local/runtime/v2.5-d1-source-factor-ablation/run.py
agent/python/.venv/bin/python .local/runtime/v2.5-d1-source-factor-ablation-rest/run.py
agent/python/.venv/bin/python .local/runtime/v2.5-d1-source-factor-ablation/analyze.py
```

이번 작업은 원인 진단이다. 운영 코드 반영·전체 정상 5개/오류 5개 재평가·커밋·push·PR·배포는 하지 않았다.
