# v2_localLLM 수정·검증 기록

2026-11-12, Apple M4 Pro·통합 메모리 24GiB·macOS 15.7.9에서 실행했다.
Qwen3.5-9B MLX 4bit와 d1-2B GGUF Q8_0를 사용했다. 아래 모델 평가는 실제 로컬 추론이며
질문·Run·측정 문자열은 전부 인공 데이터다. 실험 결과, 비밀값, 대화 원문과 원시 측정 파일은 저장소에 포함하지 않는다.

사용자 변경사항을 우선한다. OS 송신 필터는 구현 범위에서 제외하고 업데이트·모델 다운로드를 허용한다.
분석 요청은 인증된 literal loopback 서버에만 전송한다. cloud fallback·환경 proxy·redirect·외부 tracing exporter는 거부한다.
v3 추가 검증과 새 상용 모델 호출은 수행하지 않았다.

## 1. d1 GPU 오류

기존 llama.cpp b11960은 이 macOS의 Metal 컴파일러에서 `constexpr bfloat4` 관련 kernel 컴파일이 실패했다.
동일 바이너리의 장치 조회에서도 재현되어 24GB 부족과 구분했다.
공식 [수정 PR](https://github.com/ggml-org/llama.cpp/pull/31360) 이후의 [b12317](https://github.com/ggml-org/llama.cpp/releases/tag/b12317)을 고정했다.
GGUF·배포 archive·실행 파일·dylib의 해시는 `runtime-manifest.json`에서 검증한다.

GPU `MTL0`, `--gpu-layers all`로 실제 native System One 요청을 처리했다. CPU fallback을 성공으로 계산하지 않았다.
짧은 인공 계획 검토 1회는 약 6.8초였다. 이전 CPU 20.8초와 질문 외 조건이 모두 고정된 벤치마크는 아니다.

## 2. 입력 한도 계산

Qwen tokenizer가 반환한 BatchEncoding의 필드 수를 세는 오류가 있었다. `input_ids` 전체를 세도록 수정했다.
d1은 일반 chat tokenizer로 대신 계산할 수 없어 고정 GGUF의 원본 choice template와 제어 토큰 escaping을 재현하고
native `/tokenize`로 질문마다 전체 입력을 센다. 서버의 실제 usage와 일치시켰다.

- Qwen 짧은 입력: 계산 38 = 실제 usage 38.
- d1 두 질문: 계산 62 + 62 = 실제 usage 124.
- d1 중간 입력: 계산 3560 + 3560 = 실제 usage 7120.
- Qwen은 출력 최대 6000을 예약한다. d1은 native 출력 token이 0이므로 같은 출력을 예약하지 않는다.
- 현재 24GB profile의 전체 입력 상한은 16000이다. d1은 context·batch·physical batch 한도도 모두 만족해야 한다.

초과·계산 불가 요청은 추론 전에 거부하며 원문·근거·이력을 자르지 않는다. JSON Schema가 prompt에 삽입되지 않는 경우에도
그 schema 크기를 보수적으로 예약한다. 계산 수가 실제 usage보다 클 수 있는 이유다.

## 3. 전체 스택 메모리와 속도

두 모델의 큰 GPU 버퍼를 동시에 상주시켰을 때 Qwen Metal 메모리 부족과 MLX process crash를 재현했다.
d1 microbatch 512로 나누는 시도는 native 서버가 긴 입력을 거부하므로 채택하지 않았다.
Qwen 호출 전 d1이 sleep으로 모델 메모리를 해제했는지 확인하고, d1 token 계산·검토 전에는 소유한 Qwen instance만 해제한다.
사용자의 다른 모델은 임의로 해제하지 않는다. 프로세스 간 잠금으로 다른 워커·상태 검사가 모델을 빼앗지 못하게 했다.

23.5K 입력 재검증은 요청 6개 모두 성공했지만 엄격한 메모리 기준은 실패했다.
시스템 active+wired+compressed 최고 합계 약 21.13GiB, warning 표본 15/95개, 추가 swap 168820736 bytes였다.
최초 측정의 추가 swap 0만으로 안정성을 주장하지 않는다. 이 결과에 따라 입력 상한·d1 batch/microbatch를 16000으로 낮췄다.

16K 재측정은 여섯 요청 모두 성공했고 메모리 압력 69개 표본이 전부 normal(1), 추가 swap 0이었다.
시스템 active+wired+compressed 최고 합계는 21876637696 bytes(약 20.37GiB)였다.
약 15.5K 입력의 Qwen 요청은 실제 입력 15454 tokens·53.732초, d1은 질문당 15489 tokens·세 질문 합계 46467 tokens·39.588초였다.
시간에는 모델 전환·준비·입력 계산이 포함된다. 디스크 모델 크기나 해당 앱만의 메모리 사용량과 구분한다.

정식 재현 명령은 인공 DB·backend·frontend·headless browser를 만들어 함께 켠 채 측정하고 소유한 서비스를 정리한다.

```sh
npm run measure:agent:local -- --env-file .env.local-llm
```

측정 JSON은 Git 밖에 보관한다. 해당 profile의 정상 메모리 압력·추가 swap 0·90초 이내의 여섯 요청을 모두 확인해야
준비 검사에 사용할 수 있다. 짧은 출력만 측정하므로 최대 6000/3000 출력과 장시간 반복 안정성은 별도 과제다.

## 4. 실제 준비 판정

항상 실패하던 임시 판정을 실제 검증으로 바꿨다. 모델·tokenizer 파일, 실제 설치된 모델/양자화,
LM Studio/MLX·d1 실행 파일과 인자, 해당 profile의 전체 스택 측정 기록, 현재 메모리 압력을 확인한다.
인공 요청으로 계획 schema·writer JSON·SSE·native d1 choice/확률·usage 계약을 확인한다.

모델 별칭만 같고 부모 모델이나 양자화가 다른 경우, 예전 profile의 측정 기록, `ready=true`만 기록한 파일은 통과하지 못한다.
최초 검사 중에는 모델을 로딩/해제하므로 launcher 대기 상한을 60초에서 600초로 맞췄다.
실제 모델 호출당 90초 제한은 그대로다. 사용 중이면 `LOCAL_MODEL_RUNTIME_BUSY`로 안전하게 반환한다.
smoke 진단도 같은 잠금과 모델 상주 전환을 사용하여 실행 중인 모델 요청과 동시에 추론하지 않는다.
16K 측정 기록을 연결한 정식 `status` 명령에서 실제 `ready:true, blockers:[]`를 확인했다.
수정된 정식 smoke 명령도 인공 plan·writer JSON·SSE·d1 검사를 약 15.319초에 통과했다.
다른 프로세스가 잠금을 가진 상태에서는 실제 CLI가 exit 2·`LOCAL_MODEL_RUNTIME_BUSY`를 반환했고 model usage가 없었다.

준비 상태는 연결·실행 환경의 판정이며 아래의 분석 품질 합격을 의미하지 않는다.

## 5. 실제 모델의 계획·판단 품질

원래 v2 그래프·검증기·질문 지침·선택지 의미·최종 응답 schema는 유지했다.
실패한 JSON/잘린 계획의 실제 생성 내용을 기존 재계획 실패 계약으로 전달하도록 local adapter를 수정했다.
실제 텍스트와 usage를 보존하고 누락된 단계나 숫자를 코드로 만들어 넣지 않는다.
브라우저 평가도 UI 단언 이전에 terminal snapshot을 보관하여 실패 원인을 잃지 않도록 했다.

첫 실제 모델 평가 24개에서 엄격한 통과는 12개였다. 16개 COMPLETE 중에도 잘못된 후보 집합이 있어 완료 상태만 합격으로 세지 않았다.
8개는 FAILED였고 합산 지연은 약 877.7초였다. 대표 오류는 요청하지 않은 제약·정렬 추가, 설명 단계 누락,
독립 검색을 AND로 합침, 중첩 계산의 측정·계산 단계 누락이다. d1이 일부 오류 계획을 PASS로 승인했다.

temperature=0, native tool protocol, 같은 도구 계약을 본문에 추가하는 진단을 수행했다.
어느 방법도 대표 실패들을 해결하지 못해 production 경로에 반영하지 않았다. 검증기나 정답 기준을 약하게 만들지 않았다.
현재 조합이 기존 상용 v2와 같은 분석 성능을 유지한다고 판단할 근거는 없다.

d1의 고정 정답/오답 계획 14쌍도 실제 native GPU 경로로 평가했다. 28개 중 17개 정답,
오답 14개 중 8개 거짓 승인, 정답 14개 중 3개 거짓 반려였다. 평균 요청 지연은 약 21.84초였다.
같은 모델과 지침이지만 이 평가는 16K 재설정 전 batch/microbatch 24000에서 수행했다.
API 연결 성공과 의미 검토 성능을 구분하며 confidence 임계값을 임의로 올리거나 확률을 만들어 합격 처리하지 않는다.

최종 16K profile의 추가 확인에서는 실제 두 Run 비교·결과 해석이 COMPLETE·d1 PASS로 끝났고,
근거에 맞는 해석과 명백한 인과 과장의 고정 1쌍도 d1이 구분했다.
반면 실제 사용자 선택 후 비교 요청은 불필요하고 잘못 연결한 설명 단계 때문에 INVALID_PLAN으로 실패했다.
모델이 유효한 확인 계획을 생성하지 못해 선택·재개에 도달하지 않았으며, 이를 HITL 검증 성공으로 세지 않았다.
코드의 고정 응답 HITL·복구·snapshot 보존 검증과 실제 모델의 계획 생성 성공 여부는 구분한다.

## 코드 검증

```sh
cd agent/python
.venv/bin/python -m pytest -c pytest-v2-local-llm.ini -q
.venv/bin/python -m mypy src/kplasma_agent/v2_local_llm/runtime.py src/kplasma_agent/v2_local_llm/config.py src/kplasma_agent/v2_local_llm/core/budget.py src/kplasma_agent/v2_local_llm/core/decisions.py src/kplasma_agent/v2_local_llm/core/model_gateway.py evals/local_llm_measure.py evals/local_llm_smoke.py
```

Python 검증은 314 passed, initial_clone 시점 전용 검사 8 deselected다. 동결한 원본 AST·지침·계약·복제본 경계 검증을 포함한다.
위 mypy 7개 파일과 `npm run typecheck`, `npm run lint`, `git diff --check`를 통과했다.
Node의 localhost 테스트는 sandbox 포트 생성 제한으로 실패한 뒤 해당 권한으로 재실행해 14개 모두 통과했다.
모델 품질 평가의 합격과 구분한다.
