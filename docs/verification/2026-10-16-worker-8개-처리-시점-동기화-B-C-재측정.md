# worker 8개 처리 시점 동기화 B/C 재측정 — 2026-10-16

## 종합 결과

**worker 8개·DB 풀 10개·100명 동시 조회** 조건에서 B/C 각 3회 전체를 집계했다. 파일 파싱을 트랜잭션 밖으로 분리한 C에서 조회 HTTP 응답은 **130.45→64.66ms(50.4% 감소)**, 업로드의 DB 연결 누적 점유는 **34.147→8.318초(75.6% 감소)**로 줄었다. 같은 시행에서 150개 업로드 완료 시간도 **10.873→9.574초(11.9% 감소)**했다.

| 지표 | B: 파싱까지 트랜잭션 | C: 파싱을 트랜잭션 밖으로 분리 | 감소율 |
| --- | ---: | ---: | ---: |
| 조회 HTTP 응답 평균 | 130.45ms | 64.66ms | **50.4%** |
| 조회 DB 연결 획득 평균 | 108.01ms | 23.90ms | **77.9%** |
| 업로드의 DB 연결 누적 점유 | 34.147초 | 8.318초 | **75.6%** |
| 150개 업로드 완료 평균 | 10.873초 | 9.574초 | **11.9%** |

각 시행의 처리 중 조회 묶음(cohort2) 100건 평균을 구한 뒤 B/C 각 3회의 평균을 비교했다. **1·2·3회차 모두 포함하며 총 조회 600건**이다. 업로드 지표는 같은 6시행의 전체 150개 처리 구간이다. 감소율은 반올림 전 평균으로 계산했다.

## 문제·분석·해결

- **문제:** 여러 업로드 worker가 파일을 파싱하면서도 DB 연결을 보유하면, 같은 풀을 사용하는 사용자 조회가 연결 반환을 기다릴 수 있다.
- **분석:** k6로 100명 동시 조회를 보내고 Java/JDBC의 연결 획득·반환 시각을 요청별 HTTP 응답과 연결했다. 고정 시간에 조회하면 아직 파일 접수 중일 수 있어, B/C 모두 실제 worker 8개의 파일 처리 신호를 확인한 뒤 조회하도록 맞췄다.
- **해결:** B의 `tx.process` 안에 있던 파일 파싱을 트랜잭션 밖으로 옮겼다. C는 `tx.prepare`에서 원본 정보를 읽고 연결을 반환한 뒤 파싱하고, `tx.publish`에서 중복을 재확인하고 결과를 원자적으로 저장한다.
- **결과:** 업로드의 연결 누적 점유가 75.6% 줄었고, 조회의 연결 획득 시간은 77.9%, HTTP 응답 시간은 50.4% 줄었다. 세 반복 모두 같은 방향의 감소를 보였다.

신호 감지 시점에는 **6시행 모두 실제 활성 작업 8개·파싱 8개**를 로그로 확인했다. 이후 100ms는 클라이언트가 같은 출발 시각을 공유하는 준비 시간이며, 제품 worker를 멈추거나 DB 연결을 인위적으로 붙잡지 않았다. 조회 부하 발생기의 로컬 신호 요청은 제품 HTTP 응답 시간에 포함하지 않았다.

이 수치는 위 로컬 부하 조건에서 측정한 3회 평균이다. 각 군의 예열·재사용 횟수는 같고, 개별 2·3회차의 서버 재사용 이력은 서로 다르다.

## 지표의 의미

| 지표 | 측정 범위 |
| --- | --- |
| 조회 HTTP 응답 시간 | 클라이언트가 제품 조회를 호출한 뒤 응답을 받을 때까지. 사용자 대기에 가까운 전체 시간 |
| 조회 DB 연결 획득 시간 | 조회가 `getConnection`을 호출해 연결을 받을 때까지. 풀 대기와 연결 검사 포함. HTTP 시간의 일부이므로 두 값을 더하지 않음 |
| 업로드의 DB 연결 누적 점유 시간 | 업로드 접수·worker가 각 연결을 빌려 보유한 시간을 모두 더한 값. 병렬 구간이 겹치므로 업로드 완료 시간보다 클 수 있음 |
| 150개 업로드 완료 시간 | 업로드 요청 시작부터 전체 등록이 완료될 때까지의 실제 경과시간 |

이번 조회는 요청마다 SQL 1회·연결 획득 1회였다. 조회 SQL 실행 평균은 **2.43→2.69ms**였고, 연결 획득 평균은 **108.01→23.90ms**였다. 조회 SQL 가속보다 업로드가 연결을 반환해 조회의 연결 획득 시간이 줄어든 점이 핵심이다.

## 집계 기준 정리

최종 보고에는 **완료한 3쌍 전체**를 사용한다. 앞서 적용한 ‘첫 서버 진입 때 정확히 8개·발송 폭 5ms 이하·쌍간 차 3ms 이하’는 과도하게 좁은 보조 기준이어서, 측정 후 검토를 통해 제외 기준에서 해제했다. 원자료와 최초 계획은 보존한다.

| 반복 | 신호 감지 시 활성 작업 B/C | 첫 조회 서버 진입 시 B/C | 100건 발송 폭 B/C | 최종 집계 |
| --- | ---: | ---: | ---: | --- |
| 1 | 8 / 8 | 7 / 8 | 2 / 3ms | 포함 |
| 2 | 8 / 8 | 8 / 8 | 4 / 2ms | 포함 |
| 3 | 8 / 8 | 8 / 8 | 2 / 9ms | 포함 |

작업 교대에 따른 8→7 변화와 2~9ms 안의 동시 발송 차이는 진단 기록으로 남긴다. 아직 worker가 시작되지 않은 이전 실험과 구분하며, 성능값에 따라 반복이나 개별 요청을 골라 제외하지 않는다. 분석 JSON의 `all_completed`가 최종 집계이고, `phase_valid`는 이전의 엄격한 보조 기준 결과다.

## 검증·도구·재현

- **정합성:** 6시행 모두 150 Run·153버전(147신규+3갱신) 확인. 전체 조회 2,400건에서 HTTP·응답 해시 오류와 예정 요청 누락 0건. 대표 비교는 그중 600건이다.
- **k6 v2.3.0:** 100 VU 동시 조회, 제품 요청별 HTTP 응답·해시 계측.
- **Python:** 병렬 업로드, DB·JVM 초기화, 기존 timing 로그의 worker 단계 감지, 공통 발송 시각 전달, 통계 집계.
- **Java/JDBC·HikariCP:** worker·파싱 구간, 연결 획득·점유 시간, 풀 상태 계측. **PostgreSQL:** Run·버전 정합성 확인. **SVG:** 결과 그래프.
- 제품 JAR은 재측정 중 변경하지 않았다. pool 10·worker 상한 8 확인. 시행 내 시계 offset 변동 최대 0.299ms.
- 측정 도구 검증: `python3 -m unittest discover -s scripts/performance -p 'test_*.py'` — 40개 통과. 100개 수신자에게 같은 미래 발송 시각이 전달되는 검증 포함.
- LLM·Phoenix 호출 없음. 종료 후 전용 DB seed 복원, Java·테스트 컨테이너 종료.

```sh

  --builds <기존-B-C-JAR-보관경로> --seed-artifacts <조회-seed> \
  --fixture <인공-업로드-fixture> --output <새-결과경로> \
  --container <전용-upload-benchmark-container> \
  --workers 8 --repeats 3 --phase-gate --load-engine k6
python3 scripts/performance/analyze_upload_phase.py <이번-원시자료-상위경로>
```
