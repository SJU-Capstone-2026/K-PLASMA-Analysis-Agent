# 공통 웹·백엔드·DB 통합 검증

사용자가 승인한 “웹·백엔드·DB 공유, LLM 경로만 분리” 구성을 적용했다.
5173 웹과8080 backend는 현재 작업 폴더의 코드로 기동했고, 기존15432 DB와 storage를 유지했다.
일반 V2와 로컬 V2는 같은 선택 UI를 사용한다. 그래프·submit_plan·응답 필드·모델 설정은 이 작업에서 바꾸지 않았다.

## 데이터 보존과 복구

- 원본 DB를 전환 전 다시 백업했다. 복구 원본·백업·SQL·비교 결과는 Git 제외 경로 `.local/runtime/unified-web/`에만 보존한다.
- 먼저 DB 사본에 복구를 실행하고 재실행의 중복 방지도 확인했다. 사본에서 V19/V20 적용을 확인한 뒤 공통 DB에 적용했다.
- 완료된 로컬 평가 대화5개의 원래 요청 ID·대화 epoch·답변 snapshot·계획·실행·모델 시도·공개 이벤트를 보존했다. epoch 충돌이 없어 번호를 바꾸지 않았다.
- 기존 Run payload·과거 답변 snapshot·요청·판단 기록의 hash가 바뀌면 전체 복구를 rollback하도록 검증했다. 실제 적용은 이 검증을 통과했다.
- 적용 후150 Run,75개 답변,40개 대화,214개 요청이며 진행 중 요청은0개였다. 기존70개 답변에 복구한5개를 추가했다. 활성 대화57은 보존했다.
- 별도5174 웹·8083 backend와 복구 DB 컨테이너만 종료했다. 복구 데이터 volume·백업과 Qwen/d1 서버는 유지했다.

## 워커와 기억 경계

상용 키는 기존 `AGENT_WORKER_TOKEN`, 로컬 키는 별도의 `AGENT_LOCAL_WORKER_TOKEN`을 사용한다.
혼합 배포에서 빈 키·동일 키를 거부하고 모든 요청별 내부 endpoint와 claim을 역할별로 제한한다.
실제 서버에서 상대 그래프의 context/checkpoint 조회4건과 혼합 claim2건이 모두403 `WORKER_GRAPH_FORBIDDEN`이었다. 정상 claim이나 새 질문은 이 검사에서 보내지 않았다.

검토 중 공통 판단 기록의 기억 조회가 로컬 메모를 상용 모델에 전달할 수 있음을 발견했다.
실패하는 인공 재현을 먼저 확인하고, V20의 서버 내부 출처와 상용 기억 필터로 수정했다.
로컬·출처 불명 기록과 이를 포함한 기존 cached pin은 상용 워커에서 거부한다. 공통 화면의 기록 조회와 공개 응답 JSON은 유지한다.

## 아직 보류된 항목

공통 서버의 로컬 워커 시작은 호스트 메모리 경고로 준비 검사를 통과하지 못했다.
관찰 값은 pressure level2, swap 사용3,783.12MiB였으며 Qwen과d1은 모두 수면 상태였다.
모델 프로필(Qwen24K·batch/ubatch256·생각모드ON, d1 검토ON)과 Docker3GiB, 기존 준비 기준은 유지했다. 다른 앱을 임의 종료하지 않았다.
비공개 시작 절차는 정상 압력이 연속으로 확인되면 기존 워커의 준비 검사를 실행한다. READY·새 질문 처리 성공은 아직 확인하지 않았다.

40문항·앞5문항 재평가·상용 모델 호출·commit/push는 실행하지 않았다.
상용 공통 워커를 유지했다. 기존 메모리 실측·응답 품질 결과를 이번 통합으로 개선됐다고 해석하지 않는다.
