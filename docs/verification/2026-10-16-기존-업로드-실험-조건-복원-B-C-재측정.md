# 기존 k6·조회 시점·서버 정책을 복원한 업로드 B/C 재측정

후속: [worker 8개 처리 시점 동기화 재측정](2026-10-16-worker-8개-처리-시점-동기화-B-C-재측정.md) — 최종3쌍과 조건 통과1쌍을 구분한다.

## 결론

**기존 설정을 복원한 6시행은 모두 정상 완료했지만, 양쪽에서 여러 업로드 worker가 동시에 처리 중인 비교 쌍은 0개였다.** 고정한 업로드 시작 약5초 후에 조회했을 때 B2만 worker가 실행 중이었고, 나머지5시행은 worker가 아직 시작되기 전이었다. 따라서 아래 HTTP 평균 **27.4% 감소를 worker8 경합 상황의 트랜잭션 분리 효과로 확정하지 않는다.** 기존 60.6%나 후속 Node 실험 1.2%와 합산하지 않는다.

업로드 전체의 DB 연결 누적 점유는 **30.438→7.409초(75.7% 감소)**였다. 누적 점유는 여러 연결의 보유 시간을 합한 자원 사용량이며 업로드 완료 경과시간과 다르다. worker 처리 연결만의 누적 점유는 **26.846→3.287초(87.8% 감소)**로, 파싱 중 연결을 반환한 효과를 별도 확인할 수 있다.

## 이번에 고정한 것

사용자는 요청 도구·업로드 후 조회 시점·서버 상태를 기존 실험과 같게 복원하고 B/C 트랜잭션 차이만 비교하도록 요청했다. [측정 전 고정 계획](../plans/2026-10-16-기존-업로드-실험-조건-복원-B-C-재측정.md)을 먼저 저장했다.

| 항목 | 복원한 조건 |
| --- | --- |
| 입력·실행 파일 | 기존과 같은150 Run·2,175파일·1,545,005,295바이트 및 동일 B.jar/C.jar. 재빌드 없음 |
| 서버·DB | 단일 JVM, worker8·관리자8, Hikari max/minIdle10, 동일 전용 PostgreSQL 컨테이너·seed |
| 부하 도구 | 기존 k6 v2.3.0 및 보존된 요청·스케줄 스크립트7개를 SHA256 동일하게 복사 |
| 요청 구성 | 100 VU, 5초마다 함께 조회, 기존 iteration 순서별 대상 배분 그대로 |
| 상대 시점 | 첫 조회 예약+5초에 업로드 시작, **cohort2=예약+10초**, 즉 업로드 시작 약5초 후 조회 |
| 시행 순서 | **B1 → C1 → C2 → B2 → B3 → C3** |
| 서버 상태 정책 | B1/C1/B2/C3는 새 JVM+동일8Run 예열, C2/B3는 직전 같은 변형 서버 재사용. 각 군 fresh2회/reuse1회 |
| 집계 | 고정 cohort2의100건을 모두 포함, 각 시행 평균을 먼저 구한 뒤 군별3회 평균. 결과가 나쁘다는 이유로 제외·추가 실행하지 않음 |

**서버 상태의 한계:** 기존 재사용 정책까지 복원했으므로 군별 fresh/reuse 개수는 같지만 개별2·3회차 B/C의 fresh/reuse 상태는 서로 다르다. 기존 실험은 이 점에서 쌍별 완전 통제가 아니었으며, 이번에도 이를 바꾸지 않고 공개한다. 호스트 CPU·OS 파일 캐시·스케줄링까지 과거 시점과 동일하다는 뜻은 아니다.

B/C JAR의 ZIP 항목 내용을 비교한 결과 차이는 `ImportWorker.class`와 그 내부 클래스뿐이었다. 보존된 소스 diff도 B의 `tx.process`를 C의 `tx.prepare → 트랜잭션 밖 파일 파싱 → tx.publish`로 나눈 내용이며, 저장 직전 중복 재확인을 포함한다. DB 풀·파서·조회 코드·인덱스·fixture는 동일하다. 전체 worker1/2/4/8 실행에서 이번 대상인 worker8 블록만 선택한 런처 외에는 보존된 실행 스크립트를 수정하지 않았다.

## 고정 시점의 전체 결과 — B/C 각3회

| 지표 | B | C | 변화 |
| --- | ---: | ---: | ---: |
| 업로드 DB 연결 누적 점유(초) | 30.438 | 7.409 | 75.7% 감소 |
| 조회 DB 연결 획득 평균(ms) | 37.195 | 28.181 | 24.2% 감소 |
| 조회 HTTP 응답 평균(ms) | 50.893 | 36.927 | 27.4% 감소 |
| 150개 업로드 완료(초) | 9.009 | 9.505 | 5.5% 증가 |

조회 대표표본은 **3쌍×양쪽100건=600건**이다. 업로드 점유·완료 시간은 같은 시행의 전체150개 업로드 구간이다. HTTP 응답은 클라이언트 호출부터 응답 완료까지이고, 연결 획득 시간은 그 안의 JDBC 연결 요청 구간이다. 둘을 더하지 않는다. 연결 획득에는 풀 내부 확인 비용도 포함되어 순수 대기만을 뜻하지 않는다.

| 반복 | HTTP 평균 B→C(ms) | 연결 획득 평균 B→C(ms) | 업로드 누적 점유 B→C(초) | 업로드 완료 B→C(초) |
| --- | ---: | ---: | ---: | ---: |
| 1 | 33.43→41.58 | 21.10→31.89 | 30.329→8.367 | 9.318→8.941 |
| 2 | 98.89→39.15 | 85.66→32.32 | 31.171→6.573 | 8.636→10.155 |
| 3 | 20.36→30.05 | 4.83→20.34 | 29.815→7.287 | 9.075→9.419 |

2회차에서는 B가 느리고 C가 빨랐지만, 1·3회차는 C가 더 느렸다. **평균27.4%는 이 고정 시간표에서 나온 관측값으로 기록하며, 반복마다 동일한 개선이 있었다고 표현하지 않는다.**

## 같은 5초에 요청했지만 실제 처리 단계는 달랐다

아래 활성 worker는 조회가 서버에 들어온 시점에 실행 중인 job 수의 평균이다. 연결 점유는 해당 worker의 claim/job이 실제 보유한 연결 수의 평균이며 둘은 다른 지표다. 마지막 열은 첫 조회가 들어온 시각을0으로 한 첫 worker 시작 시각이다. 양수는 조회 이후에 worker가 시작됐다는 뜻이다.

| 반복 | 활성 worker 평균 B/C | worker 보유 연결 평균 B/C | 첫 worker 시작 B/C(ms, 조회 기준) |
| --- | ---: | ---: | ---: |
| 1 | 0.00 / 0.00 | 0.00 / 0.00 | 749.4 / 190.5 |
| 2 | 6.61 / 0.00 | 4.92 / 0.00 | -259.6 / 1144.5 |
| 3 | 0.00 / 0.00 | 0.00 / 0.00 | 416.7 / 672.5 |

예를 들어 **C2는 조회를 보낸 뒤 약1.14초 후에 첫 worker가 시작**됐다. B2는 조회 약0.26초 전부터 worker가 처리 중이었다. B2→C2의 큰 조회 차이를 파싱 트랜잭션 분리만의 효과로 해석하면 안 된다. 파일 접수·복사·게시 작업이 먼저 진행되고, 그 소요시간이 조금만 달라져도5초 시점에 worker가 시작됐는지가 달라진다. 이번에 worker 시작이 과거보다 늦어진 세부 원인(CPU·I/O·캐시 등)을 독립적으로 분리하지는 않았다.

사전 보조 기준인 **양쪽 평균 활성 worker6개 이상**을 충족한 쌍은0개다. 따라서 조건부 경합 개선율은 **N/A**다. 이전처럼 B의 worker 연결 보유 시점에 들어온 조회만 추리면 B2의100건과 대응C2만 남지만, C2는 worker 시작 전이므로 그것만 골라 대표 성과로 만들지 않는다. 조회 시점을7초로 옮기거나 다른 묶음을 선택하는 변경은 하지 않았다.

## 발송·시계·정확성 검증

| 반복 | HTTP 호출 폭 B/C(ms) | 예약 대비 최대 지연 B/C(ms) | 업로드 시작→예약 조회 B/C(ms) | 시행 내 clock offset 변동 B/C(ms) |
| --- | ---: | ---: | ---: | ---: |
| 1 | 1 / 0 | 2 / 1 | 4983.16 / 4988.23 | 0.253 / 0.250 |
| 2 | 2 / 0 | 3 / 1 | 4990.11 / 4991.56 | 0.252 / 0.334 |
| 3 | 2 / 0 | 2 / 1 | 4993.28 / 4989.88 | 0.250 / 0.257 |

각 조회 묶음의 대상별 건수는 B/C에서 같았다. 원본 k6의 iteration 기반 배분을 유지했으므로 같은 VU의 대상까지 고정한 새 실험과는 다르다. HTTP 호출 폭은 클라이언트 `http.get` 직전 시각의 범위이고, 실제 네트워크 패킷 발송 시각은 아니다.

측정 구간의 wall/monotonic 업로드 경과시간 차이는 최대 **0.164ms**, 각 시행의 시계 offset 변동은 최대 **0.334ms**였다. k6 자체 HTTP duration 평균도 **50.813→36.920ms**로 Date.now 기반 평균과 가깝다.

다만 B3의 조회 종료 후, C3 조회 시작 전인 **시행 사이에 시스템 벽시각이 약+4,800.869ms 바뀐 기록**은 있었다. 여섯 조회 측정 구간에는 걸치지 않았고, C3은 새 k6 실행의 예약 시각에 맞춰 시작했다. 시계 변화가 전혀 없었다고 숨기거나 원인을NTP로 단정하지 않는다. 제품·예약 코드는 바꾸지 않고 외부 관측으로만 확인했다.

- **6/6시행 성공**, 시행별150 Run·153버전(147신규+3갱신), 총900 Run 등록 정합성 확인.
- 기록된 조회 **2500건**, HTTP/해시 오류0건, 예정 조회 누락0건. 대표600건과 전체 검증 건수를 구분한다.
- Hikari max/minIdle10과 worker8 상한 확인. 원본 스크립트7개 SHA256 일치, B/C JAR SHA256 일치 확인.
- 제품 코드를 수정하거나 새 측정 도구로 바꾸지 않았다. 테스트 후 전용DB seed 복원과 서버·컨테이너 종료를 완료했다.

## 도구와 기록

- **k6:** 기존100 VU·5초 주기 요청, HTTP 시간·응답 해시 기록. 이번에는 Node.js 발생기를 사용하지 않았다.
- **Python:** 기존 스크립트로 병렬업로드·DB 복원·서버 재사용 제어, 원시 로그와 고정 cohort2 집계. 외부 스레드로100ms마다 wall/monotonic 시각을 관찰했다.
- **Java/JDBC/Hikari 계측:** worker 실행·연결 획득/보유·pool 상태 확인. **PostgreSQL:** 결과 정합성 확인.
- LLM·Phoenix 호출 없음. 그래프 수치나 실제 실험 결과 payload는 공개 문서에 포함하지 않는다.
- 원시자료: Git 제외 `.local/performance/upload-original-conditions-20261016/`의 `pre-registered-plan.md`, `snapshot-sha256.json`, `launch.py`, `clock.jsonl`, `analysis.json`, `phase-diagnostics.json`, `experiment/`.
- 원본 기준: `.local/performance/upload-worker-contention-20261016/experiment/measured-harness/`와 동일 B/C JAR. `.local`은 GitHub에 올리지 않는다.

**이번 실험으로 확인한 한계:** 요청 도구·상대 시각·서버 정책을 동일하게 고정해도, 파일 접수 시간이 달라지면 실제 worker 경합 단계가 같아지지는 않는다. 다음에 경합 자체를 분리해 확인하려면 양쪽에서 정해진 수의 worker가 실제 작업을 시작한 뒤 같은100건을 발송하는 별도 실험 설계가 필요하다. 이 경우에는 기존의 업로드 후5초 조건과 다른 실험임을 명시해야 한다. 이번에는 그 조건 변경이나 추가 부하 실험을 하지 않았다.
