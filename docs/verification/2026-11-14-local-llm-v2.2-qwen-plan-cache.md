# LocalLLM_v2.2 Qwen 계획 캐시 구현·검증 기록

아래는 Docker3GiB·strict 정책에서 중단된 당시의 기록이다. 후속 사용자 지시로 적용한
Docker2GiB·경고 허용 개발 정책과 새 메모리/웹 비교는
[개발 메모리 검증 기록](2026-11-14-local-llm-development-memory.md)을 따른다.

## 결과

Qwen 계획·재계획의 디스크 KV 캐시 연결과 소프트웨어 검사를 완료했다. **운영 설정은 OFF로 유지한다.**
정식 메모리 검사가 캐시 왕복에 도달하기 전에 `LOCAL_MEMORY_PRESSURE`로 중단됐으므로,
요청한 Q01~Q05 OFF/ON 웹 비교는 실행하지 않았다(0/10). 과거 v2.1의 평가를 이번 OFF 결과로 재사용하지 않았다.

사용자의 승인 범위는 계획서 구현, Docker VM3GiB·d1 검토 유지, 메모리 통과 시에만 웹 비교다.
모델·배치·sleep·메모리 통과 기준을 완화하거나 다른 앱을 종료하지 않았다. commit/push와 운영 전환도 수행하지 않았다.

## 구현 내용

- Qwen의 기존 `submit_plan` 전후에만 저장·복원을 연결했다. 전체 입력의16K 한도를 먼저 검사하고 캐시 토큰도 한도에 포함한다.
- d1 검토는 그대로 실행한다. 답변 작성은 캐시 파일을 읽거나 갱신하지 않으며, RAM 슬롯을 사용했다는 사실만 기록한다.
- 재계획의 RAM 캐시가 유효하면 디스크 복원을 생략한다. sleep·답변 작성으로 슬롯이 바뀌면 검증한 파일에서 복원한다.
- 기본 경로는 프로젝트의 `.local/cache/v2_localLLM/qwen-plan-cache-KV/`다. `/.local/` Git 제외 규칙을 유지한다.
- 비어 있거나 이 기능의 소유 표식이 있는 전용 폴더만 사용한다. 다른 파일이 있는 폴더·심볼릭 링크·프로젝트/홈 루트는 거부한다.
  폴더0700·파일0600을 적용하고, native 쓰기 전부터0600 파일을 준비한다.
- 새 본문을 완전히 검증한 뒤 메타데이터를 원자적으로 교체한다. 저장 실패 시 이전 정상 캐시를 유지한다.
  timeout 뒤 늦게 쓰일 수 있는 비공개 임시 파일은 보존하고, 다음 native 상태 확인 뒤 미공개 파일을 정리한다.
- 손상·다른 fingerprint·캐시 I/O 실패는 전체 계산으로 돌아간다. 복원 실패 뒤 슬롯 초기화까지 실패하면 기존 모델 오류로 중단한다.
- ON 프로필은 같은 캐시 경로의 `--slot-save-path`, 새7행 메모리 증거와 인공 캐시 왕복 증거를 요구한다.
  인공 검사는 기존 캐시가 있으면 모델 호출 전에 거부해 사용자 캐시를 덮지 않는다.
- usage의 로컬 관측에 prepare/restore/save 시간과 해시 시간을 남긴다. 해시 시간은 prepare/save에 포함되므로 중복 합산하지 않는다.
  native 입력 처리·생성 시간, 실제 재사용 토큰을 별도로 보존한다. 사용자 최종 응답 schema는 바꾸지 않았다.

## 정식 메모리 검사 — 실패

`scripts/agent/measure-local-llm.mjs`의 기존 인공 DB·백엔드·Vite·실제 headless 브라우저 환경에서 실행했다.
실험 DB와 사용자 대화는 사용하지 않았다. 모델 실행 인자와 소스 fingerprint의 검사 전후 값은 일치했다.
저장소 루트에서 `PYTHONPATH=agent/python/src agent/python/.venv/bin/python .local/runtime/v2.2-qwen-cache/run_cache_measurement.py`로 실행했다.
이 비공개 실행기는 소유한 Qwen 인자만 임시 전환한 뒤 기존 Node 측정 명령에 `.local/runtime/v2.2-qwen-cache/cache-on.env`를 전달하고 원래 인자로 복원한다.

| 항목 | 결과 |
|---|---:|
| Docker 설정 `MemoryMiB` | 3072 |
| 실행 Docker 엔진 `MemTotal` | 3,054,383,104B |
| 모델 sleep·5초 안정화 후 시작 압력 | normal(1) |
| 첫 Qwen 기본 검사 | 244입력 토큰, 정상 응답, 5.273초 |
| 전체 메모리 표본 | 4개: normal2·warning2 |
| 관측 resident 피크 | 21,614,198,784B = 20.130GiB |
| 추가 swap | 0B |
| 중단 사유 | `LOCAL_MEMORY_PRESSURE` |
| 캐시 저장·복원 인공 검사 | 미도달 |
| Q01~Q05 OFF/ON 웹 평가 | 미실행(0/10) |

관측 resident는 기존 `memory_sample()`의 active+wired+compressor 계산값이며 Qwen 단독 메모리나 GPU VRAM 수치가 아니다.
Docker3GiB는 Docker VM 상한이며 Mac 전체 앱·모델의 상한이 아니다.
캐시 파일 쓰기 전의 기본 Qwen 추론에서 경고가 발생했으므로 이 결과만으로 캐시 I/O가 경고의 원인이라고 결론 내리지 않는다.
추가 swap0이어도 경고가 있으면 현재 통과 조건을 충족하지 않는다.

새 실패 보고서를 `verify_memory_report()`에 넣었을 때 `LOCAL_MEMORY_EVIDENCE_INVALID`로 거부됨을 확인했다.
기존 OFF 보고서를 ON 통과 보고서로 대신하지 않았다. 검사 소유 임시 환경은 정리했고 Qwen은 원래 캐시 옵션 없는 인자로 복원했다.
d1 실행 옵션과 Docker3072MiB 설정은 유지했다. 기본 캐시 폴더에는 소유 표식만 있고 실제 사용자 캐시는 없다.

## 도구 정리 후 정식 재검사 — 2026-11-14 16:08 KST 시작

코드 분석 서버 복제본14개와 REA서버15개를 종료한 상태에서 사용자의 지시에 따라 정식 검사를 다시 실행했다.

기존 실행기를 별도 비공개 작업 폴더에 복사해 이전 실패 증거를 보존했다.

정리 후 피크는 약0.504GiB 낮아졌지만 정상 압력 기준을 충족하지 못했다.

숫자가 낮아졌다는 이유로 경고를 통과 처리하거나 기존 준비 판정을 완화하지 않았다.

보고서의 런타임 프로필과 검사 전후 facts가 일치했고, 새 실패 증거가 `LOCAL_MEMORY_EVIDENCE_INVALID`로 거부됨을 확인했다.
시작 시 해시와 비교해 그래프·answer 계약·stream·입력 budget·최종 answer schema가 동일했다.
검사 종료 후 Qwen을 원래 캐시 옵션 없는 인자로 복원했고 Qwen·d1 sleep을 확인했다.
공용 웹5173·백엔드8080은 HTTP200이며, 공용 DB만 healthy 상태로 남고 인공 검사 컨테이너는 정리됐다.
Docker3GiB·공용 데이터·다른 앱을 유지했고 캐시는 OFF다. 종료 후 유휴 압력은1이었다.

증거 경로는 `.local/runtime/v2.2-qwen-cache/retest-after-cleanup-20261114-160823/`다.
`memory-cache-on.json`, `memory-driver-result.json`, `qwen-original.json`, `protected-before.json`과 로그를 Git에서 제외해 보관한다.
실행 명령은 비공개 실행기 `run_cache_measurement.py`에 `PYTHONPATH=agent/python/src`를 적용한 것이며, 내부적으로 기존
`node -- scripts/agent/measure-local-llm.mjs --env-file <새 cache-on.env>`를 호출했다. 본체 종료 코드는2다.
제품 코드 수정이 없어 소프트웨어 테스트477개는 반복하지 않았고 보호 파일 해시·증거 거부·서비스 상태를 검증했다.

다음에는 다른 앱을 임의로 종료하지 않는 조건에서 메모리 여유를 확보한 뒤 정식 검사를 다시 해야 한다.
검사에는 비어 있는 전용 캐시 폴더를 사용해야 한다. 기존 사용자 캐시가 있으면 별도 빈 경로와 일치하는 서버 인자를 지정한다.
전체7행과 새 캐시 왕복·실제 조건 바인딩·두 번의 d1 검토, 현재 준비 판정이 통과해야 웹 OFF/ON 비교를 실행할 수 있다.
따라서 현재는 운영 활성화, 실제 웹 정확도 유지, I/O를 포함한 전체 시간 단축을 검증했다고 표시하지 않는다.
