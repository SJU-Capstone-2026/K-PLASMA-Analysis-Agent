# 파일 업로드 대기 제거·트랜잭션 점유 개선 검증

측정일: 2026-10-15. 대상은 **150개 Run 업로드·등록**이며 LLM/Agent 응답 성능 실험이 아니다.
주 비교 A/B/C 각 10회는 완료했고, 부가 시나리오는 아래 별도 기록으로 구분한다.

## 비교와 환경

- A: 계측만 추가한 기존 동작. 작업자 1개, 작업 하나 종료 후 500ms fixed delay.
- B: 단일 작업자가 최대 32개씩 연속 처리하고 backlog가 남으면 바로 다음 bounded drain을 예약한다. 빈 큐·최초 대기는 500ms다.
- C: B에 짧은 준비 트랜잭션 → DB 연결을 놓고 파일 파싱 → 중복을 다시 확인하는 게시 트랜잭션을 적용한다.
- A/B/C는 같은 파서·파일 복사·해시·스키마·인덱스·연결 풀을 사용했다. 작업자 병렬화·Redis·Kafka는 사용하지 않았다.
- 기준 코드: A e2e803e, B ddf0e07, C 1b1bcf4. A의 claim 계측도 최종 집계 알고리즘으로 원시 로그에서 다시 연결했다.
- PostgreSQL 18.6-alpine3.24, 컨테이너 CPU 2개·메모리 3GiB, Hikari 최대 2개. Java heap 256MiB~2GiB.
- 인공 입력은 150개 고유 P/S/B, 2,175파일, 1,545,005,295바이트다. Bias-off 25개와 Bias-on 125개를 포함한다.
- 파일 크기·행/격자 분포는 로컬 원본을 참고했지만 수치와 곡선은 인공 입력이다. 생성 입력·비공개 볼륨 프로필·원시 로그·DB는 Git에서 제외한다.
- A는 전체 볼륨 워밍업 후 10회, B/C는 각 5회씩 두 블록을 교대했다. B/C 재시작 후에는 각 블록 워밍업을 별도로 제외했다.
- 매회 전용 DB·저장소를 초기화해 신규 등록이 중복 처리로 바뀌지 않게 했다. OS 캐시는 강제로 초기화하지 않았다.
- 모든 측정은 실제 HTTP multipart → 실제 scheduler → 실제 parser → 실제 PostgreSQL 등록 경로다. 입력 생성·ZIP 생성·사후 정답 검증은 시간에서 제외했다.

## 150개 신규 등록 — 각 10회 평균

| 지표 | A | B | C | A→C 관측 차이 |
| --- | ---: | ---: | ---: | ---: |
| 클라이언트 전체 | 113.254초 | 34.433초 | 34.473초 | +78.781초 |
| 서버 전체 | 112.759초 | 34.008초 | 33.838초 | +78.921초 |
| 대기 | 75.935초 | 0.344초 | 0.319초 | +75.616초 |
| 파일 복사·해시·이동 | 4.248초 | 4.200초 | 4.619초 | -0.371초 |
| 파싱·계산 | 24.752초 | 22.632초 | 21.914초 | +2.838초 |
| DB 호출·연결 획득·commit | 3.433초 | 2.580초 | 2.807초 | +0.626초 |
| 기타 | 4.391초 | 4.252초 | 4.179초 | +0.212초 |
| DB 연결 점유 — 별도 지표 | 28.684초 | 25.649초 | 3.323초 | +25.361초 |
| 트랜잭션 점유 — 별도 지표 | 28.716초 | 25.661초 | 3.341초 | +25.374초 |

클라이언트 전체는 POST 시작부터 최종 SUCCESS 관측까지이며 1초 polling 지연을 포함한다.
서버 전체는 요청 진입부터 마지막 terminal commit 관측까지다.
A→C의 서버 평균은 **112.76→33.84초, 69.99% 감소**, 클라이언트 평균은 **113.25→34.47초, 69.56% 감소**다.

파일 처리·파서는 B/C에서 변경하지 않았다.
이 구간의 차이를 복사 최적화·파서 알고리즘 개선 효과로 주장하지 않는다.
warm cache·JIT·GC·실행 시점과 처리 순서 등의 영향이 남는다.

## A→B: 작업 사이 대기 제거

- 서버 전체: **112.76→34.01초**, 78.75초 감소.
- 작업이 남은 구간을 포함한 대기: **75.94→0.34초**.
- 작업자를 늘리지 않고 기존 job 선택 순서·단일 claim·Run 게시 정책을 유지했다.
- drain 하나의 최대 작업 수를 제한해 무한 루프를 피하고, 빈 큐에는 idle backoff를 적용했다.
- 기본 코드의 149 × 500ms = 74.5초는 이론값이다. 표의 대기는 실제 scheduler 지연과 관측 비용도 포함한 실측값이다.

## B→C: 전체 시간보다 DB 점유 구간 개선

- 서버 전체: **34.01→33.84초**. 약 0.17초 차이이며 추가적인 유의미한 지연 개선으로 단정하지 않는다.
- 클라이언트 전체: **34.43→34.47초**로 약 0.04초 증가했다. C가 사용자 전체 응답을 더 빠르게 했다고 표현하지 않는다.
- DB 연결 점유 합계: **25.65→3.32초**, 약 **87.04% 감소**.
- 트랜잭션 점유 합계: **25.66→3.34초**, 약 **86.98% 감소**.
- DB 호출·연결 획득·commit 합계는 **2.58→2.81초**로 증가했다.
- 게시 시 동일 source의 버전이 이미 생겼는지 다시 확인하므로 JDBC execute 호출은 **3,156→3,456회**, commit은 **301→451회**다.
- JDBC executeBatch는 한 API 호출로 센다. PostgreSQL의 실제 statement 호출 수와 구분한다.

파일 파싱 동안 DB 연결을 점유하지 않는 구조를 만들었고, 두 처리기가 같은 source를 파싱해도 게시 트랜잭션에서 재확인해 버전 하나만 등록한다.
동시 사용자 지연·최대 처리량 향상을 측정한 결과는 아니다.
짧은 트랜잭션으로 분리했다고 SQL 실행 자체가 같은 비율로 빨라졌다는 뜻도 아니다.

## 파일·파싱·DB의 측정 범위

| 범주 | 포함 | 중복 합산하지 않는 지표 |
| --- | --- | --- |
| 대기 | 최초 작업 가능 commit 이후 대기 + 연속 job 사이 빈 시간 | 각 Run의 누적 queue wait 합계는 전체 대기가 아님 |
| 파일 처리 | 자체 임시 복사 + staging 복사·SHA + 원본 atomic move; ZIP은 컨테이너 검사 읽기도 별도 | 파서 내부 파일 읽기는 파싱에 포함 |
| 파싱 | 스칼라·그래프 읽기/검증·단위 변환·샘플/IED 폭 계산 | 파싱을 포함하는 A의 트랜잭션 전체와 합산 금지 |
| DB 처리 | JDBC execute·연결 획득·commit의 호출 시간 | DB 엔진 실행 시간, 연결/트랜잭션 점유와 구분 |
| 기타 | multipart 수신·입력 발견·직렬화·응답 구성 등 나머지 | 설명되지 않은 시간을 전부 DB에 귀속하지 않음 |

서버 전체를 설명할 때는 위의 겹치지 않는 범주만 더한다.
DB 연결·트랜잭션 점유 합계는 별도 중첩 지표다.
claim 단계에서 batch ID가 아직 연결되기 전의 SQL도 같은 job trace ID로 합쳐 집계한다.

## 부가 시나리오와 진단

계측 off/on 제어 실험, ZIP·동일 원본 재업로드·변경 원본 갱신, 실제 150개 원본의 비공개 검증은 주 비교와 분리한다.
부가 시나리오 결과는 실행 완료 후 기록한다.
실제 원본의 수치·곡선·상세 로그·golden은 공개하지 않는다.

별도 C 업로드 한 번에 JFR profile을 기록했다.
실행 표본 1,015개에서 정규식 처리 스택이 711개 관측됐다.
스택 비율을 처리 시간 비율로 환산하지 않으며, 프로파일러를 켠 실행은 주 비교 10회에 포함하지 않는다.
후속 파서 최적화의 조사 근거로만 사용한다.

## 정합성 검증

- C의 backend 전체 JUnit/Testcontainers 테스트 **160개 통과**.
- 파싱 시 실제 트랜잭션이 비활성인지 확인하는 통합 테스트 통과.
- 동일 source를 두 처리기가 동시에 파싱해도 READY 1개·DUPLICATE 1개·불변 버전 1개를 만드는 경합 테스트 통과.
- 같은 조건의 새 결과는 현재 Run을 갱신하고 과거 버전을 유지한다. 새 결과 실패 시 이전 정상 포인터를 유지하는 기존 테스트 통과.
- 시간 집계·batch 연결 전 claim·워밍업 파일 충돌·DB 초기화 방어 등 Python 테스트 **8개 통과**.
- 주 비교 30배치 모두 150개 정상 등록. 입력의 독립 scalar oracle·모든 원본 SHA-256·A의 버전/시각 제외 전체 수치와 샘플을 매회 검증했다.
- API·DB 스키마·UI 계약은 변경하지 않았다. 화면 크기별 UI 검증은 대상 변경이 없어 실행하지 않았다.

## 재현과 보관

1. 전용 PostgreSQL·별도 포트·별도 저장소를 사용한다. 서비스 DB와 원본은 초기화하지 않는다.
2. 각 비교 커밋의 backend JAR를 보존하고 실행 설정·SHA-256을 기록한다.
3. scripts/performance/generate_upload_fixture.py로 인공 입력을 생성한다. 기본 입력은 smoke용 소형이며 이번 볼륨과 구분한다.
4. 동일 볼륨 재현에는 외부로 공급하는 비공개 크기/shape 프로필이 필요하다. 실제 물리 수치를 복제한 fixture를 저장소에 넣지 않는다.
5. scripts/performance/upload_benchmark.py로 같은 입력을 업로드하고 사후 정답을 검증한다.
6. scripts/performance/analyze_upload_benchmark.py로 원시 구간을 재집계하고 평균·중앙값·편차를 계산한다.

계측은 기본 비활성이다.
JVM 시스템 속성 -Dkplasma.import-timing.enabled=true 및 -Dkplasma.import-timing.file=...로 명시적으로 켠다.
구조화 로그는 별도 로컬 파일에만 저장한다.
PostgreSQL pg_stat_statements는 계측 프로필과 같은 전용 DB 환경에서만 사용한다.

## 후속 범위

- 중복 임시 복사 통합·파서 최적화는 별도 비교로 진행한다. 이번 결과를 해당 변경의 효과로 표현하지 않는다.
- 동일 Run 처리 순서를 보장하는 제한 병렬화와 다중 사용자 부하는 후속이다.
- 미병합 순·역방향 검색 PR의 추가 인덱스·projection을 통합하면 업로드 쓰기 비용을 동일 조건으로 재확인한다.
- 로컬 개선이며 서비스 배포는 수행하지 않았다. 병합 후 신규/중복/갱신/실패 상태와 현재 버전·원본 보관을 확인한다.
