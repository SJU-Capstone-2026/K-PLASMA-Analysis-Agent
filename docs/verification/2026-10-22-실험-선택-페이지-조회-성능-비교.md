# 실험 선택 화면 DB 검색·페이지 조회 A/B/C 비교

> **이전 설계의 측정 이력이다.** 사용자 요청으로 전체 후보 사본을 제거하고 원본 DB 최신 페이지 조회로 변경했다. 현행 결과는 [사본 없는 재측정 보고서](2026-10-22-실험-선택-원본-DB-페이지-조회-재측정.md)를 따른다. 아래 수치는 이전 사본 구현의 결과로 보존한다.

**전체 목록 전송·렌더링과 반복 조회 비용은 줄었고, 전체 후보의 최초 버전을 고정하는 준비 비용은 남았다.** 10만 건의 준비된 목록 API는 A 1,870.59ms → B 157.20ms → C 3.04ms였다. 이 수치는 통계를 갱신한 뒤의 조회이며, 최초 후보 준비나 전체 Agent 응답 시간의 개선율이 아니다.

## 대상과 변경

비교할 실험을 고르는 추가 입력 화면을 대상으로 한다. 기존 A는 전체 후보를 Java에서 JSON으로 구성해 요청 문맥에 저장하고, 브라우저가 전체 목록을 받아 검색·정렬했다. B는 최초 후보·버전을 DB의 관계형 스냅샷으로 고정하고 30개씩 검색·조회한다. C는 B에 조회용 보조 인덱스를 추가한다.

| 비교군 | 구조 | 보조 인덱스 |
| --- | --- | --- |
| A | 전체 JSON 저장·전송, 브라우저 검색 | 기존 제품 그대로 |
| B | DB 후보 스냅샷, 서버 검색·선택 상태, 커서 페이지 조회 | 무결성 PK·UNIQUE만 유지 |
| C | B와 동일 | 정렬 B-tree, 선택 항목 부분 B-tree, 부분 문자열 검색 GIN(`pg_trgm`) |

선택 화면을 처음 준비했을 때의 **미선택 후보까지 같은 버전으로 유지**한다. 검색 도중 등록된 새 Run이나 새 버전으로 후보를 교체하지 않는다. 현재 페이지·검색 결과 전체·전체 실험의 세 선택 범위를 유지하며, 비교 재개 시에는 선택한 K개의 정확한 버전만 Agent에 전달한다.

## 환경과 측정 경계

- A 기준: `5c5e82f9515e390202392673a92c89b7671518de`.
- Java 21, PostgreSQL 18.6, DB CPU 2개, 메모리 한도 6GB, `shared_buffers=256MB`, `work_mem=16MB`, Hikari 기본 풀 10개.
- macOS arm64, Apple M4 Pro, RAM 24GB. Node 22.19.0, Python 3.13.7, k6 2.3.0, Playwright 1.63.0 / Chromium 153.0.8010.12.
- A/B/C 모두 `-Xms512m -Xmx8g`. 벤치마크 서버에만 적용했으며 제품 기본 힙 설정은 바꾸지 않았다.
- 150 / 1만 / 10만 / 100만 건 모두 인공 데이터. 동일 조건 중복 없이 Run당 현재 버전 하나를 생성했다. 과거 버전·갱신·삭제는 별도 통합 테스트에서 검증했다.
- 규모별 서버 재시작·동일 seed 후 워밍업 2회, 후보 준비·조회 10회. 준비된 API는 150~10만 건에서 유형별 100회 × 3블록, 100만 건에서 10회 × 3블록이다.
- 브라우저는 준비된 후보 세션에서 150·1만 건 20회, 10만·100만 건 10회 측정한다. 첫 체크박스 표시·활성화·paint까지 기다리며 제한 시간은 20초다.
- B/C JAR는 V9 마이그레이션 파일 유무만 다르다. 나머지 ZIP 항목의 바이트 일치를 `variants.py`로 검증했다.
- 측정 중 다른 빌드·부하 테스트를 병행하지 않았다. 실패·워밍업을 성공 평균에 섞지 않았다.
- B/C의 k6 반복 측정 직전에는 후보 테이블을 `ANALYZE`해 통계를 갱신한다. 앞서 측정하는 독립 세션의 첫 조회와 브라우저 시간은 이 강제 통계 갱신 전의 값이다. 두 구간을 구분하며, k6 수치를 모든 신규 선택 화면의 첫 조회 시간으로 사용하지 않는다.

| 도구 | 용도 |
| --- | --- |
| Python HTTP + `perf_counter` | 실제 요청 생성·claim·needs-input을 거친 후보 준비, 페이지 조회, 선택·재개·취소 |
| k6 | 준비된 목록·검색·다음 페이지 HTTP 반복 측정. 1 VU로 직렬 실행하여 동시 사용자 부하와 구분 |
| Playwright + Vite 개발 서버 | 실제 React 선택 컴포넌트를 실제 API에 연결한 표시·검색 시간과 반응형 검증 |
| PostgreSQL 실행 계획·`pg_stat_statements` | 인덱스 사용·스캔·정렬·버퍼·SQL 실행 통계 |
| JFR | JVM 실행·할당·GC 진단 기록 보존 |

**전체 Agent 응답 시간이나 LLM 시간의 측정이 아니다.** 후보 준비와 이미 준비된 화면의 표시를 각각 측정했다. HTTP와 브라우저 구간은 겹치므로 합산하지 않는다. 검색 표시 시간에는 B/C의 300ms 입력 대기가 포함된다. JFR 기록을 JDBC 연결 획득 시간으로 해석하지 않는다.

화면 시간은 다른 카탈로그·대화 로딩을 제외한 선택 패널의 개발 서버 측정이다. Playwright 제어 프로세스의 단조 시계로 탐색/입력 시작부터 브라우저 paint 확인까지 잰다. 배포된 전체 페이지의 성능으로 확대 해석하지 않는다. 공정 조건 표시 순서를 보정한 최종 프론트로 B의 150~10만 건 화면만 다시 측정해 `B/browser-final`에 보존하며, 기존 서버 API 수치와 후보 준비 수치는 변경하지 않는다.

## 메모리 한도 확대와 실패 기록

초기 Java 2GB 힙에서 A의 100만 건 처리가 실패해 사용자의 요청으로 힙을 8GB로 늘렸다. Java 8GB·DB 3GB에서도 거대한 JSON 저장 중 DB 메모리 부족이 발생해 전용 DB를 6GB로 늘리고 A/B/C 공통 조건을 맞췄다.

Java 8GB·DB 6GB에서도 A의 100만 건은 최초 워밍업 중 HTTP 503으로 실패했다. PostgreSQL 로그에서 `context_snapshot` JSON 갱신 중 백엔드 프로세스가 signal 9로 종료된 사실을 확인했다. 따라서 100만 건 A의 성공 평균이나 A→C 개선율은 만들지 않는다. 이전 메모리 설정의 예비 측정도 본 비교에 섞지 않는다.

B/C는 네 규모에서 **후보 준비·첫 페이지 요청을 각각 40/40회 완료**했다. 100만 건의 C 최초 준비 평균은 **75.23초**다. 메모리 증설과 전달 구조 변경으로 실행을 완료할 수 있게 됐지만, 최초 준비를 즉시 끝내는 개선은 아니다.

## 측정 결과

### 1. A→B: 전체 전송에서 페이지 조회로 전환

준비된 세션의 첫 목록 HTTP 평균이다. A는 N건 전체, B/C는 첫 30건을 반환한다. 사용자에게 첫 후보를 제공하는 방식의 비교이며 반환 행 수가 같은 SQL만의 비교는 아니다.

| 후보 수 | A 전체 목록 | B 첫 30건 | A→B 감소율 | 응답 크기 A→B |
| --- | ---: | ---: | ---: | ---: |
| 150건 | 5.61ms | 3.33ms | 40.7% | 65,845→14,170바이트 |
| 1만 건 | 168.78ms | 17.59ms | 89.6% | 4,415,634→14,172바이트 |
| 10만 건 | 1,870.59ms | 157.20ms | 91.6% | 44,275,323→14,173바이트 |
| 100만 건 | —ms | 2,147.00ms | 비교 불가 | A 실패 |

10만 건에서 요청 문맥 JSON은 **48,775,656→496바이트**, 응답은 **44,275,323→14,173바이트(99.97% 감소)**로 줄었다. 후보 N개의 버전 목록 자체는 DB 관계형 테이블에 보관한다. 전체 데이터가 사라진 것이 아니라, 거대한 JSON을 Agent 상태와 브라우저로 반복 전달하는 경로를 제거한 것이다.

### 3. 처음 후보를 준비하는 비용

요청마다 전체 후보의 당시 버전을 고정하는 `needs-input` 처리 시간과, 그 직후 첫 GET을 나눴다. 각 10회 평균이며 단위는 ms다.

| 후보 수 | 후보 준비 A / B / C | 직후 첫 GET A / B / C |
| --- | ---: | ---: |
| 150건 | 10.62 / 12.15 / 17.44 | 7.08 / 4.21 / 4.76 |
| 1만 건 | 206.36 / 371.76 / 651.71 | 179.42 / 24.50 / 7.50 |
| 10만 건 | 2,090.41 / 3,814.89 / 6,454.90 | 1,922.65 / 192.38 / 118.14 |
| 100만 건 | — / 47,477.61 / 75,232.60 | — / 11,798.10 / 8,208.26 |

**초기 준비는 개선되지 않았다.** 전체 후보·버전을 고정하는 비용이 남고, C에서는 보조 인덱스를 함께 갱신하는 비용도 추가됐다. 위 k6 반복 조회의 빠른 값으로 이 초기 준비 시간까지 줄었다고 주장하지 않는다. 신규 세션 첫 GET과 통계 갱신 후 반복 GET의 차이도 관측했으며, 통계·실행 계획이 신규 스냅샷에 미치는 영향은 후속 진단 대상이다.

### 4. 브라우저 표시와 검색

후보 준비가 끝난 상태에서 실제 선택 컴포넌트를 열었다. 첫 화면은 체크박스가 보이고 조작 가능한 시점, 검색은 입력 시작부터 결과 paint까지다. B/C 검색은 300ms debounce를 포함한다.

| 후보 수 | 첫 화면 A / B / C (ms) | 검색 A / B / C (ms) | DOM 노드 A / B / C |
| --- | ---: | ---: | ---: |
| 150건 | 75.17 / 77.21 / 75.13 | 15.36 / 363.27 / 363.21 | 932.00 / 217.00 / 217.00 |
| 1만 건 | 1,317.15 / 127.14 / 74.12 | 437.25 / 369.15 / 364.04 | 60,130.00 / 217.00 / 217.00 |
| 10만 건 | — / 335.02 / 329.90 | — / 427.26 / 429.28 | — / 217.00 / 217.00 |
| 100만 건 | — / 3,775.24 / 551.56 | — / 2,194.23 / 489.02 | — / 217.00 / 217.00 |

A의 10만 건은 첫 워밍업에서 20초 안에 체크박스를 표시하지 못했다. 성공 표본이 없어 평균을 기재하지 않았다. A의 100만 건은 서버 준비 실패로 브라우저를 실행하지 않았다. B/C는 전체 선택 시에도 선택 칩을 접힌 상태 6개로 제한하며, 목록은 페이지 단위로 렌더링한다.

150건에서는 A의 로컬 검색이 더 빠르다. DB 검색 전환은 소규모 검색 가속보다 데이터 증가에 따른 전송·렌더링 증가를 제어하는 개선이다. 10만 건의 C 첫 화면은 **329.90ms**로 B **335.02ms**와 큰 차이가 없었다. 준비된 API의 인덱스 효과를 화면 전체 개선율로 대체하지 않는다.

### 5. 선택·재개·정리

각 규모에서 2개를 선택해 재개한 단일 기능·시간 측정이다. 반복 평균이 아니므로 개선율의 핵심 근거로 사용하지 않는다. 재개는 Agent 비교 완료가 아니라 `QUEUED` 응답까지다.

| 150건 | 19.40 / 15.16 / 15.68 | 7.09 / 5.73 / 8.46 |
| 1만 건 | 315.28 / 24.83 / 20.24 | 134.95 / 8.07 / 4.62 |
| 10만 건 | 3,367.35 / 141.96 / 96.95 | 1,488.59 / 7.48 / 6.84 |
| 100만 건 | — / 3,150.29 / 8,878.27 | — / 16.89 / 10.65 |

B/C의 성공 실행에서 재개 입력은 선택한 2개의 정확한 Run·버전으로 제한하고 임시 후보 테이블 정리를 확인했다. A의 `snapshotCleaned=false`는 해당 관계형 스냅샷 기능이 없는 비교군이라는 뜻이다.

100만 건의 재개 단일 측정은 B **3,150.29ms**, C **8,878.27ms**로 C가 더 느렸다. 이 구간에는 선택 버전 검증·문맥 저장·임시 후보 삭제가 포함된다. 인덱스 적용으로 준비된 페이지 조회가 빨라진 결과를 대규모 재개·정리까지 확대하지 않는다.

## 실행 계획과 저장 비용

10만 건의 첫 페이지를 블록당 100회씩 3블록 측정한 분포도 확인했다. 아래는 **블록별 지표의 최솟값~최댓값**이며, 세 블록의 p95를 평균 내어 전체 p95로 사용하지 않았다.

| 비교군 | 블록별 중앙값 범위 | 블록별 p95 범위 |
| --- | ---: | ---: |
| A | 1,848.75~1,863.91ms | 1,936.79~2,031.96ms |
| B | 152.49~156.95ms | 167.70~171.08ms |
| C | 2.54~3.08ms | 3.68~4.64ms |

10만 건의 대표 SQL을 `EXPLAIN (ANALYZE, BUFFERS)`로 확인했다. API와 같은 검색·정렬·JOIN 조건을 사용하되 진단용 SELECT 필드는 일부 축약했다. 아래 실행 시간은 HTTP 평균이 아닌 실행 계획 한 번의 DB 시간이다.

| 조회 | B | C |
| --- | --- | --- |
| 첫 페이지 | 후보 100,000행 순차 스캔·JOIN 후 정렬, 110.772ms | `agent_run_selection_page_idx`로 31행 조회, 버전 PK 31회 확인, 0.230ms |
| 이름 부분 문자열 | 100,000행 검사 후 1행 반환, 68.506ms | `agent_run_selection_search_idx`의 Bitmap Index Scan 후 1행 반환, 50.849ms |
| 선택 목록(빈 선택) | 100,000행 검사, 49.495ms | `agent_run_selection_selected_idx` 사용, 0.030ms |

단일 SQL 안의 JOIN에서 버전 PK를 31회 조회한 것은 애플리케이션이 HTTP/SQL 요청을 31번 보내는 N+1과 다르다. 페이지 크기에 맞춰 DB 내부에서 수행된 인덱스 조회다.

같은 10만 건 반복 생성·삭제 이후 후보 테이블의 물리 할당량은 B/C 모두 **702,406,656바이트**, 인덱스 할당량은 **156,409,856→631,414,784바이트**였다. 반복 후 남은 공간을 포함하므로 하나의 활성 스냅샷 크기로 사용하지 않는다. C의 인덱스 추가에는 읽기 개선뿐 아니라 공간·쓰기 비용이 따른다.

원시 응답·JAR·JFR·로그·브라우저 스크린샷은 Git에서 제외한 `.local/performance/run-selection/`에 보존한다. 본 문서에는 인공 데이터의 집계값만 기록한다. DB 물리 할당량에는 반복 생성·삭제 후 남은 공간도 포함되므로, 이를 후보 스냅샷 하나의 논리 크기로 해석하지 않는다.

## 배포 계약

V8/V9와 새 백엔드·프론트·Python 소비자를 함께 적용한다. V8은 새 후보 테이블·숫자 자연 정렬용 ICU collation을, V9는 조회 인덱스와 `pg_trgm` 확장을 만든다. 기존 요청의 JSON 후보는 첫 접근에서 당시 목록 그대로 변환한다. 이전 전체 응답 형식을 요청하는 클라이언트에는 `CLIENT_REFRESH_REQUIRED`를 반환한다. 새 스냅샷은 이전 바이너리의 전체 JSON 계약과 다르므로, DB를 유지한 채 이전 백엔드만 단독으로 되돌리는 배포 방식은 지원하지 않는다.

## 남는 비용과 범위

계획 대비 실행 조정: 메모리는 8GB 힙·6GB DB로 통일했고, 100만 건 API 표본은 유형별 30회로 제한했다. Flyway 적용 순서 때문에 A→B→C 순차 실행했으며 교차 순서 실험은 하지 않았다. 대규모 성능 데이터는 Run당 현재 버전 1개로 통제하고 과거 버전·갱신·삭제는 기능 테스트로 확인했다. 첫/다음 페이지를 성능 측정했고 깊은 페이지는 별도 시간 측정을 하지 않았다. JDBC 연결 획득·점유, JVM/브라우저의 엄밀한 최대 힙, 대화 0건/100건 차이는 정량 비교하지 않았으며 해당 개선율을 주장하지 않는다.

전체 후보의 최초 버전을 유지하려면 DB 안에서도 N개의 후보를 고정해야 한다. 이 최초 준비 비용은 O(N)이며, C의 보조 인덱스는 읽기를 빠르게 하는 대신 생성·선택 변경·삭제 비용과 저장 공간을 추가한다. 후속 검토 대상은 공유 카탈로그 이력으로 후보 복사를 줄이는 방법이다.

대규모 최초 준비가 Agent→서버의 기존 30초 한도를 넘을 수 있어, `run_selection`의 `needs-input` 요청에만 180초 read/write 한도를 적용했다(connect/pool 대기는 10초). 벤치마크의 준비 요청 한도와 같다. 일반 조회와 LLM 제한은 바꾸지 않았다. 이 변경은 계산을 빠르게 하는 최적화가 아니라, 진행 중인 준비 요청을 너무 일찍 끊지 않도록 하는 제한 조정이다.

전체 선택은 서버 상태와 작은 제출 본문으로 처리하지만, 최종 비교 대상 K가 커지면 비교 계산·그래프·저장 비용은 여전히 커진다. 이번 결과가 100만 개 파형 비교의 완료를 의미하지 않는다. 대화 기록 수에 따른 별도 실험과 다중 사용자 부하 테스트도 이번 측정에는 포함하지 않았다.
