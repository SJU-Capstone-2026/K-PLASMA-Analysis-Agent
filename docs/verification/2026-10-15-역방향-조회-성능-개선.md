# 역방향 조회의 검색 인덱스·응답 구조 개선 검증

2026-10-15 · 인공 데이터 전용 PostgreSQL · 기준 코드 `bbe01beb` · [승인 계획](../plans/2026-10-15-001-역방향-조회-성능-개선-계획서.md)

조건에 맞는 현재 버전만 검색하고, 공통 결과와 개별 조건 탭의 합집합에 필요한 Run만 manifest와 Agent 상태에 전달하도록 변경했다. 결과가 없으면 근접 후보를 생성하지 않는다. 공정 조건·수치·순서가 같은 Q1에서 A/B/C를 비교했다. 실제 실험 데이터나 서비스 DB는 사용하지 않았다.

## 비교군과 측정 경계

| 구분 | 내용 |
| --- | --- |
| A | 변경 전 제품: 전체 현재 버전 ID 목록 고정, SQL에서 JSON 수치 정규화·조건·정렬, 0건이면 전체 후보 풀 반환 |
| B | 현재 Run에 정규화한 검색 컬럼 저장, 필요한 후보만 조회·버전 고정, 파일 수 메타데이터, 간결한 결과·체크포인트. 검색용 보조 인덱스 없음 |
| C | B의 동일 검색·응답 코드 + 부분 B-tree 4개 |

**A도 조건과 정렬을 DB에서 처리했다.** 따라서 A→B는 “Python 전체 필터링을 DB WHERE로 바꿨다”는 실험이 아니다. 매 요청의 JSON 정규화와 전체 ID 목록 조회·전달·저장을 제거한 구조 개선이다. B→C는 해당 구조에서 검색 인덱스의 효과를 비교한다. 기존 기본 키 인덱스는 모두 유지했다.

- 조회 경로 표: 테스트 전용 `/benchmark/query`가 **실제 제품 `ReverseContextQuery`**를 실행한다. A의 ID 인벤토리 조회, 검색 SQL, 스칼라 결과 매핑·JSON 응답, 로컬 HTTP 왕복을 포함한다. **manifest 저장·LangGraph는 포함하지 않는다.** SQL 2회(A) / 1회(B·C).
- Agent 표: 실제 요청 접수·claim·Java context API·manifest 저장·Python LangGraph·체크포인트·완료 저장·최종 상태 조회를 포함한다. LLM 도구 선택만 고정했다. 실제 LLM 전체 응답 개선율이 아니다.
- `EXPLAIN`은 별도 1회 실행 계획이다. `pgbench`는 제품 SQL만 반복한다. 세 측정값을 같은 지표로 섞지 않는다.

## 실행 조건

PostgreSQL 18.6 / Java 21.0.9 / Python 3.12.15 / macOS arm64. Docker DB CPU 2개, 메모리 3GiB, shared_buffers 256MiB, work_mem 16MiB, 병렬 gather 0. Java 최대 heap 4GiB, Hikari 2개, JDBC prepareThreshold 0. 자동 worker 없이 1요청씩 실행했다.

150 / 1만 / 10만 / 100만 개의 고유 P/S/B 조합을 같은 seed로 만들었다. 동일 조건 중복을 적재하지 않았으며 Run마다 현재 버전 1개이다. 에너지 150–160 eV에 해당하는 5건과 플럭스 높은 순의 정답은 규모와 관계없이 같다. 원시 공정 조건은 물리 시뮬레이션 결과가 아닌 성능 fixture이다.

쿼리는 각 군·규모별 워밍업 5회 후 200회, Agent는 각 10회다. 최종 bulk projection 갱신 뒤 두 테이블에 VACUUM/ANALYZE하고 진행 중 vacuum이 끝난 다음 측정했다. 초기 B 탐색 기록은 버리고 동일 절차의 B2만 종합했다. B/C 핵심 측정은 같은 Java 실행 파일·Python 코드에서 Flyway target 6/7로 인덱스 유무만 바꿨다.

## Q1 조회 경로: 같은 5건 반환

단위 ms, 성공 표본 평균. A의 실패는 평균·개선율로 대체하지 않는다.

| 데이터 | A | B | C | A→B 감소 | B→C 감소 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 150 | 18.357 | 1.259 | 2.020 | 93.14% | -60.47% |
| 10,000 | 551.976 | 2.402 | 1.330 | 99.56% | 44.65% |
| 100,000 | 5,940.647 | 9.406 | 1.500 | 99.84% | 84.05% |
| 1,000,000 | 타임아웃 (0/1) | 85.783 | 1.368 | 계산 안 함 | 98.41% |

150건에서는 B 1.259ms → C 2.020ms로 오히려 느렸고, 실행 계획도 순차 스캔이었다. 작은 표본에서 인덱스가 필요 없는 정상 선택이며 모든 규모에서 인덱스로 빨라졌다고 주장하지 않는다. 10만·100만 건의 좁은 조건에서는 인덱스 탐색이 효과를 보였다.

Q1의 반환량은 A/B/C 모두 **5건·4,800바이트**이다. A의 전체 ID 목록은 이 응답 body에는 없고 실제 context manifest에 포함된다. 따라서 이 Q1 표에서 HTTP payload 감소를 주장하지 않는다.

실제 제품 SQL을 생성해 100만 건에서 `pgbench -c 1 -j 1 -M simple`로 **C/B/B/C 각 100회**, 각 워밍업 5회 반복했다. 총 군별 200회 모두 성공했다.

| --- | ---: | ---: | ---: |
| B | 80.926 | 91.171 | 11.88–12.88 |

처리량은 **이 SQL만의 단일 연결 반복 처리량**이다. 서비스 사용자 처리량·LLM TPS로 해석하지 않는다. A는 HTTP와 실제 실행 계획으로 측정했고, 실패 비용·실행 예산을 고려해 추가 pgbench 반복을 수행하지 않았다.

## A의 실패 원인

- **10만 건:** 검색은 완료했으나 전체 ID 목록이 후속 상태에 반복 포함되어 checkpoint 요청이 약 20.58MB(UTF-8 bytes)가 됐다. 서버의 기존 제한인 직렬화 문자열 **16,000,000 문자**를 넘겨 저장에 실패했다. 원시 요청 크기와 서버 오류를 함께 보존했다.
- **100만 건:** 조회 harness의 60초 HTTP read timeout에 도달했다. 긴 기존 쿼리의 영향을 제외하고 A 서버를 다시 시작해 Agent만 단독 재현했다. BackendClient 30초 제한으로 Agent는 약 33.17초에 실패했고, 서버 context 요청은 61.08초 걸렸다. 전체 inventory와 JSON 검색으로 workspace 잠금·Hikari 대기도 이어졌다.
- DB container는 재시작·OOM이 없었다. 디스크 용량 부족으로 단정하지 않으며, 실패 표본을 성공 평균이나 100% 개선으로 표시하지 않는다. A 런타임·코드·원시 증거는 로컬에 보존했다.

## 0건 정책과 선택도별 정확성

Q5는 기존 A가 근접 후보 계산을 위해 전체 후보를 넘기던 기능 정책을 바꾼 경우다. Q1의 같은 출력 성능 개선율과 섞지 않는다. A 1만 건의 no-match 조회는 전체 1만 Run·9,661,674바이트를 반환했으며 평균 744.861ms였다. C는 전 규모에서 `runs: []`·11바이트, 전체 inventory 없이 정상 반환했다.

100만 건 Q2/Q3/Q4/Q5/Q6는 조회된 결과만 다시 검증하는 대신 **전체 고유 조건·수치 생성식으로 미리 만든 독립 정답**과 Run ID·버전·metrics·순서를 대조했다. Q2는 29건의 합집합, Q3/Q4는 5건, Q5는 0건, Q6은 17건의 개별 조건 합집합을 반환했다.

150건의 실제 Agent 저장 경로에서 Q5는 공통·개별 모두 0건, Q6은 공통 0건·개별 에너지 3건을 정상 완료했다. 두 경우 모두 근접 후보가 없었다. 정렬만 요청하는 Q7은 150건 전량을 반환했고 200회 평균 3.674ms였다. **넓은 조건·정렬만 요청하면 K=N일 수 있다.** 100만 건 전량 Agent 저장의 성공을 검증하거나 보장하지 않았다. 페이지네이션·결과 예산은 후속 범위다.

10만 건의 P/S/B 정확 조건은 `run_search_conditions_idx`로 1건을 찾았다(EXPLAIN 0.126ms). 소스만 1,000건, 바이어스만 500건도 정답과 일치했다. 소스 단독의 전체 계획에는 Run 결합용 순차 스캔이 남았다. 인덱스가 있으면 모든 SQL 단계가 인덱스 탐색으로 바뀐다고 주장하지 않는다. PostgreSQL은 반환량과 통계에 따라 Bitmap/Seq/Index 접근을 선택한다.

검증된 현재 버전(`searchable`)만 포함하는 부분 B-tree이다. 원본 JSON은 index INCLUDE에 넣지 않았다. 위 fixture에서 인덱스 4개 재생성과 ANALYZE의 합계는 1,147.79ms였으며 조회 시간에서 제외했다. 실제 등록 파이프라인의 파일 IO·계산·버전 저장을 포함한 쓰기 벤치마크는 수행하지 않았다.

등록 때 현재 포인터와 검색 projection을 같은 기존 트랜잭션에서 갱신한다. 기존 100행 projection 갱신·rollback의 탐색 측정은 B 65.36/64.03ms, C 145.53/79.13ms였다. Docker CLI·접속·lookup도 포함되고 표본 2회·실행 순서 영향이 있어 쓰기 증가율을 확정하지 않는다. 읽기 개선과 인덱스 유지 비용이 공짜가 아니라는 확인용이다.

## 계약·마이그레이션·검증

- V6는 검색 값과 파일 수를 기존 버전에서 한 번 backfill하고, V7은 B-tree를 생성한다. 표시된 100만 건에서 projection/file count 누락 0건을 확인했다. DDL·backfill은 유지보수 시간에 적용한다. 새 writer와 migration을 같이 배포하고 구버전 writer가 다시 쓰면 재-backfill해야 한다. 진행 중 요청을 먼저 끝낸 뒤 새 graph build를 적용한다.
- 검색 한 SQL의 시점에서 현재 버전을 선택하고 성공한 manifest를 재사용한다. 명시적으로 참조한 역사 버전은 별도 보존한다. 재등록 후 같은 요청 replay·reclaim·참조 추가에서도 기존 결과가 갱신되지 않으며, 다른 검색 조건으로 바꾸면 409를 반환한다.
- `searchResultVersion: 2`는 Run을 버전별로 1회 담고 그룹은 참조만 저장한다. 외부 answer schema 2는 유지한다. 서버와 UI의 참조·그룹 선택·archive 소비자를 함께 갱신했고, 과거 저장 결과의 legacy 읽기도 유지한다. 간결한 새 결과를 구버전 프론트로 표시할 수 없으므로 backend/agent/frontend를 함께 배포한다.
- 현재 Run 스칼라·0·NULL·변환·overflow·underflow를 Python과 SQL에서 1,870개 조합으로 대조했다. 특수 공백(NBSP 등) 불일치를 발견해 Unicode whitespace 규칙을 맞추고 최종 차이 0건을 확인했다. 상대 기준의 두 역할이 같은 버전을 가리킬 때 중복 참조 요청도 방지했다.

## 실제 LLM·Phoenix 진단

성능 반복을 끝낸 뒤 실제 `gpt-5.6-luna`, reasoning `none`으로 인공 데이터 질문 7회와 Phoenix Cloud K-PLASMA export·API 조회를 수행했다. 명시적 범위 단위의 5회는 완료(5건/0건 포함), “150 이상 160 이하” 및 반복 단위가 끼인 서술 2회는 기존 숫자 근거 검증에서 `UNGROUNDED_NUMBER` 추가 입력으로 분기했다. 이 형식의 근거 파싱 개선은 이번 조회 최적화 범위에 포함하지 않았다. 실패/추가 입력 기록을 삭제하거나 성공으로 바꾸지 않았다.

Phoenix에서 7개 해당 synthetic root와 자식 span을 실제 조회했다. 대표 완료 1건은 root 3,125.26ms, 도구 LLM 2,964.02ms, context 7.37ms, checkpoint leaf 합계 78.87ms였다. 최적화 이후 실제 응답에서는 **LLM 도구 선택 대기**가 큰 구간으로 이동했음을 확인했다. 이 1건은 진단 사례이며 성능 개선율·부하 용량 근거로 사용하지 않는다.

## 후속 제안

**k6로 HTTP 서비스 경로를 확인할 단계다.** 보존한 A 런타임과 C를 같은 조건에서 비교하고, 1 VU부터 접수→최종 완료 Trend·오류율을 측정한다. 도구 선택을 고정한 200회 정도로 먼저 시작해 실제 LLM 비용과 분리한다. 한 사용자 1 workspace의 직렬화와 여러 사용자의 병렬 요청은 별도 시나리오로 구분한다. 이번 DB 100만 건은 100만 LLM 요청이 아니다.

벤치마크 원시 출력·실행 파일·snapshot·화면·Phoenix 로그는 `.local/performance/reverse-lookup/`에만 보존하고 Git에서 제외했다. 본 문서는 인공 실험의 집계 결과만 공유한다.
