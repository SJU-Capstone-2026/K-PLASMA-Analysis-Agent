# d1 영어화 요소별 분리 실험 — 두 인공 사례, 6회

2026-11-15. [이전 v2.3 비교](2026-11-15-local-llm-v2.3-mlx8-single.md)에서 판정이 바뀐 두 사례에 한해 지침·선택지·도구 설명을 각각 단독 영어화했다. 운영 코드·설정·그래프·최종 응답 계약은 수정하지 않았다.

## 범위와 통제

- 엔진/모델: 기존 MLX d1 affine8/group64, 같은 원본 revision·변환 가중치·calibration·라이브러리. `group_size=1`, `independent_batch_size=1`로 각 검사를 독립적으로 순차 처리했다.
- 사례: 올바른 검색 결과 전체의 압력 비교(`good_compare`, 검사 9개), 질문의 `0.008 Torr`를 실행 입력 `8 Torr`로 잘못 바꾼 계획(`bad_unit`, 검사 5개). 모두 고정 인공 계획이며 새 Qwen 계획이나 실제 Run 조회를 생성하지 않았다.
- 한국어 기준에서 매번 한 묶음만 영어로 바꿨다. 변경을 누적하지 않았다.
  - **지침·정책만:** 각 검사의 `instructions`와 공통 `policy_context`.
  - **선택지 설명만:** 각 검사의 `criteria` 설명 문자열. 선택지 ID와 순서는 그대로다.
  - **도구·지표 설명만:** `tool_contracts`와 정리표·실행 효과 설명에 반복된 같은 지표 label/definition. 원본 계획, 실행 입력, 수치, 단위, 의존성은 그대로다.
- 세 묶음의 변경 경로가 겹치지 않고, 합치면 이전 `en-full` 전송 입력과 정확히 같아지는 것을 CPU로 검증했다. 질문·계획·원문 인용·검사 위치·수치/null/boolean·선택지 ID와 순서도 보존했다. 정리표 삭제나 중복 축약은 이번 실험에 적용하지 않았다.
- **실제 검토 HTTP 요청 6회, 내부 단일 검사 42개, 구성별 1회**다. 한국어/전체 영어 기준은 이전 로그를 재사용했고 재실행하지 않았다. 추가 warmup·순서 뒤집기·Qwen 호출·재계획·전체 웹 평가는 하지 않았다.

실행 전 모델 설정과 실제 LangGraph 중단 상태의 `plan_review_enabled=true`, 현재 가중치·서비스·라이브러리 provenance와 메모리 준비 증거를 확인했다. Docker 1536MiB 및 development 메모리 정책을 유지했다. 기존 유휴 로컬 워커만 모델 lease 안에서 일시 대기시켜 요청 혼입을 막고, 같은 PID로 재개했다. 모델·서버를 재시작해 추가 준비 추론을 만들지 않았다.

† 한국어의 ISSUE는 숫자 오류를 찾은 결과가 아니다. `filter.search.pressure`는 잘못된 `8 Torr`를 `match`로 통과시켰고, `request.tasks=unexpected`라는 엉뚱한 작업 종류 지적 때문에 전체가 ISSUE였다. 복구·정상 검토 성공으로 세지 않는다.

### 정상 계획: 지침 단독에서도 새 오판이 생기지만, 전체 영어와 같은 오판은 아니다

압력값 비교만 요구하고 기준 Run·경향 분석은 요구하지 않았으므로 `baseline:null`, `trend_axis:null`은 정상이다.

| 구성 | 경향축 검사 | 기준 Run 검사 |
|---|---|---|
| 한국어 기준 | match 50.45%, unclear 13.15% | match 70.46% |
| 지침·정책만 영어 | **match 58.67%**, unclear 11.08% | **unexpected 59.72%**, match 28.99% |
| 선택지 설명만 영어 | **match 51.79%**, unclear 36.46% | **match 64.85%** |
| 도구·지표 설명만 영어 | **match 54.94%**, unclear 11.16% | **match 64.43%** |
| 전체 영어 기준 | **unclear 61.31%**, match 25.65% | match 39.24% |

지침·정책 영어화만으로 정상 계획 반려가 발생했다. 다만 원인은 `baseline.compare`의 잘못된 추가 조건 판정이며, 전체 영어에서 발생한 `trend_axis.compare=unclear`를 그대로 재현한 것은 아니다.

선택지 설명만 영어화하면 `unclear` 점수가 13.15%에서 36.46%로 오르지만 최종 선택은 여전히 match다. 따라서 앞서 의심한 `unclear` 번역 뉘앙스는 영향 후보로 남아도 **그 설명 하나가 단독 원인이라는 주장은 이 실험으로 입증되지 않았다.** 선택지 설명만 변경해서는 전체 영어의 UNCLEAR를 재현하지 못했다.

전체 영어의 경향축 UNCLEAR는 이번 세 단독 구성 중 어느 것에서도 발생하지 않았다. 여러 구성 요소의 결합 효과가 후보이며, 어느 두 묶음의 조합 또는 특정 문장 때문인지는 이번 6회만으로 확정할 수 없다. 지침을 한국어로 두고 선택지·도구를 동시에 영어화한 조합도 이번에는 실행하지 않았다.

### 잘못된 숫자 계획: 전용 수치 검사 실패는 모든 구성에 존재한다

| 구성 | 작업 종류 검사 | 압력 수치 검사 | 올바른 value_changed 점수 |
|---|---|---|---:|
| 한국어 기준 | unexpected 30.90% | match 73.79% | 1.62% |
| 지침·정책만 영어 | match 56.28% | match 76.12% | 2.08% |
| 선택지 설명만 영어 | match 44.46% | match 58.09% | 7.71% |
| 도구·지표 설명만 영어 | match 44.79% | match 73.04% | 2.17% |
| 전체 영어 기준 | match 71.77% | match 67.51% | 6.89% |

어느 한 묶음만 영어로 바꿔도 작업 종류 검사의 엉뚱한 ISSUE가 사라졌고 전체가 PASS가 됐다. 숫자 전용 검사는 모든 구성에서 계속 실패했다. 따라서 이 사례의 전체 판정 변화는 특정 영어 묶음 하나에만 귀속되지 않으며, 한국어에서 잡던 숫자 오류를 영어화로 새롭게 놓쳤다고 해석하면 안 된다.

표의 퍼센트는 모델이 매긴 선택지 점수다. 실제 정답률·반복 실험의 신뢰구간으로 해석하지 않는다. 모든 행은 최초 고정 계획 검토이며 REPLAN 후 최종 성공 수치와 섞지 않았다.

## 원인 판단

1. **확인:** 검토 지침·정책 영어화만으로 정상 사례의 오반려가 발생한다. 선택지 설명만 또는 도구·지표 설명만 영어화한 두 단독 구성은 이번 정상 사례에서 PASS를 유지했다.
2. **확인:** 수치 검증 실패는 한국어부터 존재한다. 한국어 전체의 ISSUE는 다른 검사항목의 오판에 기대고 있어 안정적인 숫자 검증의 증거가 아니다.
3. **미확정:** 전체 영어에서 발생한 경향축 UNCLEAR의 특정 문장 또는 두 요소 간 상호작용. 이번에는 한 묶음씩 바꿨으므로 원래 전체 영어의 오판과 같은 오류를 단독 재현하지 못했다.

따라서 `unclear` 표현 한 줄만 바꾸면 해결된다고 결론 내릴 수 없다. 운영 지침을 자동 교체하거나 검토 기준·그래프·응답 형식을 변경하지 않았다.

## 실행 증거와 보관

Git 제외 경로 `.local/runtime/v2.3-d1-english-ablation/`의 `probe.py --self-check`로 입력 분리를 확인한 후 `probe.py`를 1회 실행했다. 기존 `make_input_guard`, native `/v1/count`, 실제 `review_plan` 요청·응답 검증 및 원본 기반 `parse_plan_review`를 사용했다. 모든 요청에서 계수 입력과 실제 POST가 같고, 사용 토큰·검사 ID·singleton 그룹·원본 digest·모델 해제가 일치했다.

- 추론 요청 **6/6 완료**, 오류·자동 재시도·추가 모델 호출 0.
- 메모리 감시 통과, pressure warning/critical·swap 증가·DB OOM kill 모두 0. 관찰한 OS 활성/wired/압축 합 피크는 약 **17.16GiB**다.
- 모델·그래프·계약을 포함한 로컬 운영 소스/설정 51개 파일은 전후 SHA-256이 같았다. 기존 실제 DB의 Run/version/turn 집계 해시와 요청 수는 전후 같았고 활성 요청은 0이었다.
- 일시 대기한 워커 PID 31881은 정상 재개 상태를 확인했다. 운영 env·모델 서비스·웹·백엔드는 교체하지 않았다.
- 원시 요청·응답·선택지별 점수·메모리 표본은 `result.json`에 비공개 보관했다. 이 문서에는 인공 사례의 집계와 실패 원인만 기록했다.

전체 회귀 테스트·40문항 웹 평가·코드 수정·commit/push는 수행하지 않았다. 두 사례와 구성별 1회 진단이므로 다른 질문의 품질이나 번역의 일반적인 효과는 보장하지 않는다.
