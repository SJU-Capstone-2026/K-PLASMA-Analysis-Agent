# d1 영어화 분리 비교 — 정상 5개·오류 5개, 5구성 50회

2026-11-15. [두 사례 분리 진단](2026-11-15-local-llm-d1-english-ablation.md)을 같은 질문의 정상·오류 계획 5쌍으로 확장한다. 운영 코드·설정·그래프·최종 응답 양식은 유지한다.

## 사전 고정한 평가 조건

- 기존 M4 Pro 24GB의 Q8+MLX d1, 각 검사를 하나씩 순차 처리. Docker VM 1536MiB 및 development 메모리 정책 유지.
- 정상 계획 5개와 오류 계획 5개를 모든 구성에 동일하게 넣는다. 각 오류 계획은 정상 계획에서 실행 입력 한 곳만 바꾼다.
- 한국어 전체 / 지침·정책만 영어 / 선택지 설명만 영어 / 도구·지표 설명만 영어 / 전체 영어의 5구성, 구성별 10개를 1회씩 실행한다.
- **총 50개 검토 HTTP 요청, 내부 독립 검사 310개**다. 한국어와 전체 영어 기준도 새로 실행하며 이전 결과를 새 평가 건수로 합치지 않는다. 별도 반복·warmup·Qwen 호출·추가 모델 준비 추론은 없다.
- 원문 질문·원본 계획·원문 인용·확정 문맥·수치·단위·검사 ID·선택지 ID/순서는 유지한다. 중복 축약과 정리표 삭제는 적용하지 않는다.
- 지침 묶음은 검사 `instructions`와 공통 `policy_context`, 선택지 묶음은 `criteria` 설명, 도구 묶음은 `tool_contracts`와 정리표/실행 효과에 반복된 지표 설명이다. 세 묶음을 합치면 같은 사례의 `en-full` 입력과 정확히 같아지는 것을 CPU로 검증한다.
- 실행 전 설정 및 실제 LangGraph 중단 상태의 `plan_review_enabled=true`, 현재 모델/서비스/라이브러리 provenance와 메모리 준비 증거를 확인한다. 유휴 로컬 워커만 일시 대기시켜 요청 혼입을 막고 종료 후 재개한다. 실제 DB·Run을 바꾸거나 모델 입력으로 조회하지 않는다.

## 정답표 — 모델 호출 전 고정

각 행을 정상/오류 계획으로 만들어 총 10개로 사용한다. 정상 계획은 모든 검사항목의 기대 선택이 `match`다. 오류 계획은 아래 항목·사유 하나만 기대하고 나머지는 `match`다.

| 쌍 | 정상 실행 입력 | 오류 실행 입력 | 기대 검사 항목 | 기대 사유 |
|---|---|---|---|---|
| P05 경계 | 플럭스 50 이상: gte | 같은 값의 gt로 변경 | filter.search.ionFlux | boundary_changed |
| P06 숫자 | 0.008 Torr | 같은 Torr 단위의 8로 변경 | filter.search.pressure | value_changed |
| P08 비교 대상 | 검색 결과 전체 | 기존 선택 Run으로 변경 | targets.compare | target_changed |
| P10 정렬 | 높은 플럭스 순: maximize | minimize로 변경 | ordering.search | direction_changed |
| B01 기준 Run | 질문에 지정한 R1 | R2로 변경 | baseline.compare | target_changed |

P05/P06/P08/P10은 기존 인공 의미 검토 fixture를 사용한다. B01은 같은 인공 Run 참조로 만든 단일 기준 변경 쌍이다. 모든 계획은 실제 `PlanDraft`와 `validate_plan`의 구조 검증을 통과한다. P08 정상과 P06 오류의 한국어 입력은 이전 두 사례의 기록된 전송 입력과도 정확히 같다.

P06은 단위 문자열은 유지하고 숫자만 바꾸었으므로 엄격한 정답은 `value_changed`다. 다른 오류 사유로 같은 항목을 지적하면 항목 검출에는 포함하고 정확한 사유 적중에는 포함하지 않는다. 결과를 본 뒤 정답표를 바꾸지 않는다.

## 집계 기준

- **판정 일치 /10:** 정상 PASS 또는 오류 ISSUE인 경우. 엉뚱한 검사항목의 ISSUE도 이 수치에는 들어갈 수 있으므로 이것만 정확도로 제시하지 않는다.
- **정상 통과 /5:** 정상 계획을 PASS로 판정한 수. ISSUE·UNCLEAR는 오반려로 구분한다.
- **오류 차단 /5:** 오류 계획을 ISSUE로 판정한 수. PASS·UNCLEAR는 별도로 기록한다.
- **오류 항목 검출 /5:** 정답표의 검사 항목에서 오류 선택지를 고른 수. match·unclear는 검출 성공이 아니다.
- **항목·사유 적중 /5:** 정답표의 정확한 검사 항목과 사유를 함께 맞힌 수.
- **전체 검사 엄격 일치 /10:** 모든 검사 선택이 정답표와 같고 전체 판정도 맞은 수. 오류 항목을 맞혔더라도 다른 항목에 엉뚱한 지적이나 unclear가 있으면 제외한다.

모든 결과는 최초 고정 계획에 대한 d1 검토다. 실제 Agent 전체 웹 평가나 REPLAN 복구 평가가 아니며, 기존 최대 2회 재계획·필요한 답변 검토/최대 1회 재작성 코드는 변경하지 않는다.

### 오류 항목·사유의 실제 비교

| 오류 계획 | 기대 검사 항목 | 기대 사유 | 그 항목에서 실제 고른 선택 |
|---|---|---|---|
| P05: gte를 gt로 변경 | filter.search.ionFlux | boundary_changed | 5구성 모두 match |
| P06: 0.008을 8로 변경 | filter.search.pressure | value_changed | 5구성 모두 match |
| P08: 전체 검색 결과를 기존 선택으로 변경 | targets.compare | target_changed | 5구성 모두 match |
| P10: maximize를 minimize로 변경 | ordering.search | direction_changed | 5구성 모두 match |
| B01: 기준 R1을 R2로 변경 | baseline.compare | target_changed | 5구성 모두 match |

오류 항목 자체를 모두 정상으로 판정했으므로, 정확한 사유만 엄격하게 채점해서 0/5가 된 결과가 아니다. 오류 계획 5종류를 5구성으로 검토한 25개 실행에서 기대 항목·사유를 맞힌 경우는 0개였다. 이는 25개의 서로 다른 오류 질문을 평가한 수치가 아니다.

정답표와 다른 선택은 다음 네 패턴으로만 나타났다.

- 한국어 P06.good/P06.bad: `request.tasks=unexpected`. 숫자가 올바른 계획과 잘못된 계획 모두에 같은 엉뚱한 작업 종류 지적을 했다.
- 지침·정책 영어 P08.good: `baseline.compare=unexpected`. `baseline:null`인 정상 계획에 요청하지 않은 기준을 추가했다고 잘못 판정했다. 실제 오류를 넣은 P08.bad는 모두 match로 통과했다.
- 전체 영어 P08.good/P08.bad: `trend_axis.compare=unclear`. 정상/오류 두 계획을 같은 경향축 판단 불가로 처리하면서, 오류가 있는 `targets.compare`는 둘 다 match였다.
- 선택지 설명만 또는 도구·지표 설명만 영어인 구성은 10개 계획의 모든 검사를 match로 선택했다. 정상 통과 5/5만으로 검토 품질 개선이라고 볼 수 없다.

한국어·선택지 영어·도구 영어·전체 영어의 네 구성은 각각 5쌍 모두 정상/오류 계획의 전체 검사 선택 벡터가 같았다. 지침 영어 구성도 4쌍은 같았고, 남은 P08 쌍에서는 정상 계획만 반려하는 반대 방향의 차이가 났다. 계획 입력을 한 곳 바꿨을 때 실제 수치 확률은 달라졌지만 올바른 오류 선택으로 이어지지 않았다.

## 해석과 한계

1. **공통 문제:** 이번 다섯 종류의 실행 입력 오류는 한국어에서도 검출되지 않았다. 현재 d1 검토 경로를 신뢰할 만한 오류 감지기로 검증한 결과가 아니다.
2. **지침·정책의 영향:** 영어화 단독으로 P08 정상 계획의 새 오반려가 재현됐다. 다만 이는 기준 Run 항목의 unexpected이며, 전체 영어에서의 경향축 unclear와는 다른 오류다.
3. **선택지 번역의 단독 영향:** 선택지 설명만 영어화했을 때 새 오반려는 없었다. 앞서 의심한 unclear 설명 한 줄이 전체 문제의 단독 원인이라고 확정할 근거는 얻지 못했다.
4. **결합 효과:** 전체 영어의 P08 경향축 unclear는 이번 세 단독 영어 구성에서 재현되지 않았다. 두 묶음 조합이나 특정 문장의 효과는 이 5구성만으로 분리하지 않았다.
5. **재현:** 이전 기록과 전송 입력이 같은 두 사례를 각 구성에서 대조한 10건은 전체 선택 벡터뿐 아니라 원시 선택지 확률도 같았다(최대 차이 0). 기존 기록은 비교 참고로만 사용하며 새 50회에 중복 합산하지 않았다.
6. **책임 구분:** 입력 언어 구성의 효과와 기록된 선택의 전달은 확인했지만, d1 자체의 한계·프롬프트 설계·MLX 수치 구현의 책임까지 분리한 실험은 아니다. 공식 다른 엔진이나 다른 모델과의 추가 대조는 실행하지 않았다.

운영 프롬프트·선택지·도구 계약을 자동 수정하거나 영어 구성을 새 권장값으로 채택하지 않았다. 실제 Agent 전체 웹 평가와 일반적인 다른 질문의 정확도를 보증하지 않는다.

## 메모리·환경·계약 검증

- 지정한 **50개 요청/310개 독립 검사 완료**, 예외·입력 잘림·자동 재시도·추가 준비 추론 0.
- 요청별 native `/v1/count` 입력과 실제 `/v1/systemone` 입력, 실제 usage 합, 검사 ID와 singleton 그룹이 모두 같았다. 310개 검사에서 원시 확률 argmax·원시 선택·파싱된 선택도 모두 같았다. 모델의 선택을 파서가 바꾼 결과가 아니다.
- 현재 가중치·서비스·라이브러리·준비 증거 및 전후 runtime fingerprint가 일치했다. 모델은 매 요청 후 해제됐고 Qwen 생성 요청은 없었다.
- Docker VM **1536MiB 유지**, DB OOM kill 0. OS 활성/wired/압축 메모리 합 피크 **19.900GiB**, pressure normal 1,714표본·warning 18표본·critical/unknown 0표본, swap 최대 증가 **830.69MiB**였다.
- warning 18표본은 `tools_only:P08.good` 12개, `tools_only:P08.bad` 6개였다. 기존 development 정책은 warning과 기록된 swap 증가를 허용하고 critical·알 수 없는 압력은 중단하므로 기존 판정 기준으로 감시는 통과했다. warning 표본 수를 독립 경고 사건 수로 해석하지 않는다.
- 로컬 운영 소스/설정 51개 파일의 전후 SHA-256, 고정 corpus SHA-256, 실제 DB의 Run/version/turn 집계 해시와 요청 수는 같았다. 기존 Run/version 150개씩을 유지했고 활성 요청은 전후 0이었다.
- 기존 워커 PID 31881을 같은 PID로 재개했다. 종료 후 MLX Q8 single·모델 해제·메모리 준비 증거 유효성·웹/백엔드 HTTP 200·현재 memory pressure normal을 추가 추론 없이 확인했다.

## 재현·원시 증거

Git 제외 경로 `.local/runtime/v2.3-d1-english-ablation-50/`에 `run.py`, 호출 전에 고정한 `corpus.json`, 회차별 요청·응답과 메모리 표본을 담는 `result.json`을 보관한다.

```sh
PYTHONPATH=agent/python/src:agent/python agent/python/.venv/bin/python \
  .local/runtime/v2.3-d1-english-ablation-50/run.py --self-check
```

위 명령은 모델 호출 없는 CPU 입력·집계 검사다. 실제 실행은 같은 스크립트를 `--self-check` 없이 1회 호출한다. 기존 결과가 있으면 덮어쓰거나 자동 재평가하지 않는다. 원시 모델 입력·실제 env·비밀값은 Git에 넣지 않는다.
