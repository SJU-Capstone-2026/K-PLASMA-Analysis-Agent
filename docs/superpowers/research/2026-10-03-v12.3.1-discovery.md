# v12.3.1 현황 조사와 확정 사항

조사일: 2026-10-02~03. 목적은 기준 프로토타입의 기능·데이터·구현 차이를 설계에 반영하는 것이다.

## 사용자와 확정한 사항

- 구현 위치: `K-PLASMA-Analysis-Agent`.
- 주요 코드 영역: `backend/`, `frontend/`, `agent/`.
- 기술: Spring Boot + Gradle, React + TypeScript + Vite, PostgreSQL.
- 1차 실행 환경: 팀원 각자의 로컬 개발 환경.
- 데이터도 우선 각자 보관·사용하고 팀 공용 환경은 후속 구성.
- 실제 결과 원본과 파생 결과·그래프 JSON, DB 데이터·사용자 기록은 GitHub에 올리지 않음. 기준 150개 Run의 실제 payload도 저장소 밖에서 공급.
- v12.3.1의 UI·UX·기능을 빠짐없이 실제 애플리케이션으로 이관.
- 실제 Agent가 없는 초기에는 기존 결정론적 fallback을 사용.
- 파일 업로드·파싱·재처리는 실제 기능으로 구현.
- 업로드는 상대 폴더 구조를 유지하는 폴더 선택과 ZIP을 모두 지원.
- 원본이 동일하면 중복으로 처리하고, 조건은 같아도 결과가 다르면 새 버전으로 보관. 최신 성공 버전을 검색에 사용하고 과거 기록은 당시 버전을 참조.
- 배치 업로드는 정상 Run을 등록하고 실패 Run은 사유와 함께 별도로 표시. 실패 Run은 검색에서 제외하고 재처리 지원.
- UI·UX는 원본을 재현하되 Run 관리의 목업 문구·시연 버튼만 실제 폴더/ZIP 업로드·재처리로 전환. 해당 영역의 기존 레이아웃과 스타일 유지.
- 초기화는 대화·판단 기록·참조만 삭제하고 등록한 Run과 원본 파일은 유지. 초기화 후 후보 참조가 남는 오류 수정.
- 폴더 역할: frontend는 화면, backend는 업로드·파싱·원본 보관·DB, agent는 프론트엔드에서 재사용하는 기존 JavaScript fallback 라이브러리. 실제 Agent 연결은 나중에 교체할 수 있게 분리.
- 협업은 작업 브랜치와 PR로 진행하고 `main` 직접 push를 금지.

## 조사 기준과 사본

기준 원본은 별도 로컬 폴더의 `deliverables/kplasma-conversational-agent-prototype-v12.3.1/`이다.

- 조사 당시 로컬 원본 루트: 구현 저장소 옆의 `../kplasma agent/` 폴더.
- `deliverables/채팅형/...v12.3.1 2`는 기준 폴더와 모든 파일 내용 해시가 동일했다.
- `deliverables/채팅형/...v12.3.1`은 검증 TXT 두 파일명의 Unicode 정규화 형태만 달랐다. 파일명을 NFC로 비교하면 내용은 동일했다.
- HTML 1개, JavaScript 12개, CSS 1개와 안내·검증 TXT로 구성된다. React, npm 프로젝트, 외부 CDN, 외부 API 또는 실제 Agent 연결은 없다.

## fallback

- 질문 분류 → 저장 Run 검색·비교 → 답변 모델 → 대화 스냅샷 저장의 순수 JavaScript 동기 처리다.
- 정방향 검색 상태: `EXACT`, `NEAREST_ONLY`, `NO_DATA`.
- 역검색 상태: `INVALID`, `MATCH`, `NO_MATCH`.
- 변화 설명 상태: `READY`, `NO_PAIR`, `NOT_CONTROLLED`.
- 조건이 부족하면 `CLARIFICATION`으로 안내한다.
- 기준 Run의 Energy를 조금 높이라는 이어질문은 기준값보다 +5~20 eV인 필수 범위로 검색한다. 근거: `assets/app.js:337`.
- 설명의 고정 문구와 개념 콘텐츠는 `view-models.js`에도 있다. `explanation-engine.js`만 보존해서는 답변이 같아지지 않는다.
- 외부 Agent 실패를 감지해 fallback으로 전환하는 기능은 없다. 현재 fallback 자체가 초기 동작이다.
- 숫자 없는 변화 질문은 준비된 demo pair를 선택한다. 일부 변화 설명의 결론은 변경 변수가 Pressure/Bias여도 Source Power 문구를 사용한다. 보존 또는 수정의 경계를 설계에 명시해야 한다. 근거: `assets/agent-engine.js:204`, `assets/view-models.js:788`.

### 기존 수치의 산출 규약

Flux의 원본 단위는 `#/cm²sec`, UI 표기는 `10¹⁸ m⁻²s⁻¹`이다.

IED Width는 일반 FWHM으로 계산하면 기존 125개 값과 모두 달랐다. 원본 intensity 누적합에서 실제 격자점 P10과 P90을 고르고, 보간 없이 `P90−P10`을 유효숫자 8자리로 저장하면 125개 값이 모두 정확히 일치했다. **문서에서 확인한 정의가 아니라 기존 수치와의 차등 검증으로 추론한 규약**이다. 파서 구현 시 전체 fixture로 다시 검증해야 한다.

엄밀 수렴은 마지막 residual 행에서 iteration을 제외한 종별 잔차의 `max(abs(value)) ≤ INI [Option].conv`로 계산하면 150개가 전부 일치하고 true는 6개다. `finalResidualMax`도 불일치가 없었다.

1D 샘플링은 원본 길이 N과 표시 길이 M에서 `roundHalfEven(i × (N−1)/(M−1))`의 인덱스를 고르면 IED/IAD/current/potential 각각 125개, residual 150개의 좌표·값·순서가 모두 일치한다. 일반 half-up `Math.round`를 사용하면 IED 100개에서 인덱스가 달라진다. 표시 길이는 IED 161, IAD 101, current/potential 각 121, residual 81이며 residual 값은 해당 행 종별 절댓값 최대다. 원본 current/potential 길이는 Run마다 달라 1201로 고정할 수 없다.

대표 Run의 2D는 IEAD 31×61점(angle→energy 순서), density 41×31점(phase 선택·distance 유지)이 원본과 정확히 일치했다. 2D 전체 125개는 아직 전수 비교하지 않았으므로 구현 후 필수 검증으로 남긴다. 해당 산출·샘플링 규약도 문서 정의가 아닌 차등 검증으로 복원한 규약이다.

## 저장·초기화·접근성

원본 저장 키는 다음 세 가지다.

- `kplasma.prototype.agentConversation.v1`: 대화·기준 Run·답변 스냅샷. 전체 그래프 payload는 제외.
- `kplasma.prototype.decisionMemory.v1`: legacy REV와 version 2 EXP 기록, 당시 조건·수치·목표 평가 스냅샷.
- `kplasma.reference.v11`: 단일 Run 또는 후보 집합 참조.

후보 답변의 EXP 실험 기록은 채택 Run 정확히 1개와 추가 후보 최대 2개를 선택한다. 추가 후보는 보류/반려만 가능하고 단계 이동과 카드/표 전환에서 선택·메모가 유지된다. 별도의 legacy REV 기록은 한 Run을 채택·보류·제외로 판단하며, 실험 데이터 탐색에도 이 흐름의 진입점이 남아 있다. 두 기록 형식의 저장 규칙을 합치지 않는다. 근거: `assets/decision-memory.js:19`, `assets/decision-memory.js:29`, `assets/app.js:1157`, `assets/app.js:1160`.

`새 대화`는 대화·기준 Run·후보 참조를 지우고 판단 기록은 유지한다. 반면 기존 전체 초기화 코드에는 후보 참조와 세 번째 저장 키를 지우는 처리가 빠져 있다. DB 전환 시 초기화 계약을 명시하고 이 차이를 숨기지 않아야 한다. 근거: `assets/app.js:1991`, `assets/app.js:2067`.

카드 Enter/Space, 모달 Escape·focus trap·focus 복귀, live region, reduced-motion을 보존해야 한다. 원본 시각 확인 폭은 390 / 800 / 1008 / 1440px이다. 원본 CSS는 버전별 override가 많아 이관과 정리를 동시에 하면 화면 차이가 발생할 수 있다.

## 기준 테스트 검증

원본 `tests/`에는 Node `node:test` 기반 파일 12개, 실제 등록 테스트 102개가 있다. 문자열에서 `test(`를 세면 107개이지만 추가 5개는 RegExp의 `.test()` 호출 및 코드 검색용 문자열이며 테스트가 아니다.

테스트가 참조하는 `../prototype/` 폴더는 현재 존재하지 않는다. 원본을 변경하지 않고 Node 프로세스의 모듈 탐색과 파일 읽기만 기준 v12.3.1 경로로 매핑해 실행했다.

- 검증 환경: Node v22.19.0.
- 결과: tests 102 / pass 102 / fail 0.
- 이 결과는 기준 엔진·모델·구조 테스트의 결과다. 실제 브라우저 E2E·스크린샷 비교·새 파서 테스트는 포함하지 않는다.
- 구현 저장소에서는 팀이 재현 가능한 기준 fixture와 정상적인 테스트 경로를 마련해야 한다.

## 설계에 반영한 경계

- 초기 앱에서 저장한 기록의 DB 복원은 필수이며 다른 origin의 기존 브라우저 기록 자동 이관은 초기 범위에서 제외한다.
- 다른 fallback의 알려진 문구·기본 비교 동작은 이관 범위에서 유지하며 별도 개선으로 다룬다.
- 실제 기준 패키지는 버전·checksum과 함께 저장소 밖에서 공급하고 환경변수로 위치를 지정한다. 실제 결과는 GitHub와 CI에 포함하지 않는다.
