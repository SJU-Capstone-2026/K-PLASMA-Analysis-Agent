# Agent Graph v2 계획·실행·저장 계약 초안

[주 설계서](2026-10-31-agent-v2-design.md)의 확정 사항을 구현 가능한 계약으로 구체화하는 작성자 제안이다. 이 문서의 필드명·상태 이름·정확한 직렬화는 아직 사용자 개별 확정 사항이 아니다. 제품 코드와 기존 API를 변경한 문서도 아니다.

## 1. 계획과 실행 기록의 소유권

일반 LLM은 `submit_plan` 한 번으로 전체 계획을 제출한다. 재계획도 수정된 전체 계획을 제출한다. 전체 계획 재제출과 전체 도구 재실행은 구분한다.

| 계획 제출 필드의 제안 | 의미 |
|---|---|
| `schema_version` | 계획 제출 스키마의 버전. 그래프 버전·최종 답변 스키마 버전과 별개다. |
| `request_mode` | `general_only` 또는 `data_request`. 혼합 질문은 후자다. 코드가 원문 참조·실행 기록·답변 근거와 함께 검사한다. |
| `base_revision` | 코드가 제공한 이전 계획 수정본을 가리킨다. 오래된 계획 위에 변경을 적용하지 않는다. |
| `requirements` | 원문·확인 응답의 요구 ID, 출처 메시지 키·원문 구절, 처리 단계 연결. |
| `steps` | 고유 ID, 작업 종류, 요구 ID, 선행 단계, 입력 출처, 필요한 출력과 실행 전제. |

요구 목록 자체의 누락·잘못된 해석은 스키마만으로 증명할 수 없다. 2026-11-06 추가 계약으로 코드 검사 다음에 계획용 Decisions가 원문과 실제 실행 조건을 대조한다. 세 항목 모두 일치할 때 실행하며, 불일치·판정 불가는 기존 재계획 최대 2회를 공유한다. API 장애는 신규 실행을 중단한다. 전체 계획·입력 digest와 revision을 고정하고 확률은 기록만 한다. [계획 검토 운영 계약](../../development/agent-v2.md#실행-전-계획-의미-검토)을 따른다. 최종 Decisions는 별도로 답변에 포함된 정성적 해석의 근거를 심사한다.

코드가 요청·계획 수정본·단계 실행·근거 ID와 실제 Run 버전을 발급하고 관리한다. 모델은 완료·검증 성공·실제 Run 버전·남은 수정 횟수를 확정하지 않는다. 제출 함수는 새 계획 데이터를 받는 기술 인터페이스이며 복합 업무를 감춘 새 실행 도구가 아니다.

## 2. 단계 종류와 입력 참조

| 단계 종류 | 허용 범위 |
|---|---|
| `tool` | `forward_lookup`, `reverse_search`, `compare_runs` 중 하나. 등록부의 해당 도구 인자만 사용한다. |
| `derive` | 등록한 최솟값·최댓값·차이·배수·비율·평균 중 하나. 코드가 계산한다. |
| `await_input` | 입력 부족·모호함을 확인하는 제어 단계. 하위 유형은 Run 선택·조건값/단위·비교 기준/축·계산 방향 확인이다. Run 선택에는 기존 확인 정책을 적용하고 검색마다 일괄 추가하지 않는다. |

각 도구의 계획 입력은 필드별로 원문 리터럴·확인된 문맥·결과 참조를 허용하는 별도 스키마로 만든다. 아무 JSON이나 넣는 인자 사전이나 임의 실행 코드를 허용하지 않는다. 실행 직전 참조를 실제 값으로 해석한 뒤 기존 도구 입력 스키마를 다시 적용한다.

| 출처 종류 | 계약 |
|---|---|
| 원문 리터럴 | 값·원문 단위·출처 메시지 키와 구절을 보존한다. 모델의 임의 수치 변경·단위 배율 변환을 금지한다. 생략된 단위는 기존 정책으로 처리한다. |
| 확인된 문맥 | 서버가 제공한 선택·기준·축의 참조만 사용한다. 선택 Run의 조건 이어쓰기는 사용자가 명시한 경우에만 적용한다. |
| 결과 참조 | 생산 단계·등록된 필드·대상 범위를 명시한다. 실제 JSON 경로를 모델이 작성하지 않는다. |

다음은 실제 도구 인자가 아닌 결과 참조의 표현 예시다. `ionFlux`는 등록된 지표 이름이며 결과 JSON 경로가 아니다.

```json
{
  "kind": "result_ref",
  "step_id": "compare_1",
  "field": "ionFlux",
  "scope": {"kind": "confirmed_selection", "step_id": "choose_1"}
}
```

참조를 해석하면 값만 반환하지 않고 값·단위·Run 참조와 고정 버전·출처 실행·누락 상태를 함께 유지한다. 배열에서는 값과 Run의 대응을 보존한다. 계획 모델은 질문의 의미로 비교 대상이 검색 결과 전체인지, 이미 선택한 Run인지, 추가 선택이 필요한지 판단한다. 코드 검사는 비교 대상 참조의 출처와 형식을 검증한다. 검색 결과 전체인 경우, `compare_runs.inputs.runs`는 `reverse_search`의 `candidates`를 `candidate_group` 범위로 참조한다. 서버는 비교에 넘긴 Run과 버전이 저장된 전체 후보 목록과 정확히 일치하는지 확인한다. 결과가 두 개 미만이면 검색 결과와 비교하지 못한 이유를 보여준다. 이미 선택한 Run은 `selected_runs` 문맥으로 참조한다. 일부 후보를 지정해야 하거나 비교 범위가 모호하면 검색을 먼저 실행하고 그 결과를 사용자에게 선택지로 보여준다. 선택지에는 저장된 검색 결과에서 해당 Run 버전의 필터·정렬에 사용한 출력 지표 값과 단위를 포함한다. 비교 단계는 확인 단계의 `selection` 출력을 `scalar` 범위로 참조한다. 첫 두 후보를 자동 선택하지 않는다.

입력 확인은 계획에서 미리 선언할 수 있고, 실행 직전 검사에서 발견하면 코드가 같은 단계의 확인 대기를 생성할 수도 있다. 확인 질문에는 대상 단계·필드·허용 입력·대기 식별자·요청 수정본을 연결한다. 사용자의 구조화된 응답은 그 필드의 확정 입력으로 바인딩하고 코드 검사를 다시 실행한다. 같은 작업에 필요한 값·선택만 채우는 데는 LLM 재계획을 추가하지 않는다. 의미나 전략을 바꾸어야 한다면 남은 재계획 한도를 적용한다.

정확한 비교 대상 개수를 지정하면 모델은 `await_input.inputs.selection_count`에 그 개수를 넣는다. 검색은 전체 일치 결과를 유지하고, 선택 화면과 재개 API는 같은 `minSelections`·`maxSelections`를 적용한다. 정확한 개수가 없는 계획은 `selection_count`를 생략하거나 `null`로 두며 기존 최소 두 개 선택 정책을 따른다. 검색 결과가 필요한 개수보다 적으면 비교 대신 검색 결과와 완료하지 못한 이유를 제공한다. 선택 목록의 기본 순서는 저장된 검색 결과 순서다.

단위 생략은 기존 코드 정책으로 해석할 수 있으면 확인을 추가하지 않는다. 기준 없이 가능한 값·절대 차이·범위 비교도 그대로 수행한다. 방향·분자·분모·축이 필요한 계산만 모호한 입력을 확인한다. 실제 Run의 누락된 측정값을 사용자가 채팅에 쓴 숫자로 대체하는 경로는 두지 않는다.

## 3. 검사와 순차 실행

명시된 숫자 범위는 “가깝게”라는 표현이 있어도 역방향 검색의 양끝 포함 조건으로 처리한다. 예를 들어 평균 이온 에너지 150–160 eV와 높은 이온 플럭스를 요청하면 범위 안에서 플럭스 내림차순으로 검색한다. 검토 근거에는 필수 조건과 정렬 목표의 후보별 측정값과 단위를 포함한다.

초기 검사에서는 등록 도구·연산, 단계 ID 중복, 존재하지 않는 참조, 순환 의존, 자료형·단위 계약과 요청 항목을 검사한다. 필요한 출력이 생산 단계의 요청 항목에 빠진 것을 정적으로 알 수 있으면 실행 전에 잡는다.

실행기는 선행 결과와 입력이 준비된 단계 중 계획의 안정적인 순서로 하나씩 실행한다. 각 단계의 검증을 끝낸 뒤 다음 단계로 간다. 독립 도구의 병렬 실행은 초기 범위에 넣지 않는다.

실행 전제는 등록된 결과 상태·개수·필드 가용성 검사로 구체화한다. 조건부 작업은 원문에 명시된 분기만 표현하고 자유 형식 코드나 식을 실행하지 않는다. 정확한 전제 표현 스키마는 주 설계서 D04의 최종 계약 검토에서 확정한다.

| 단계 기록의 상태 축 | 제안 값과 의미 |
|---|---|
| 실행 | 대기 / 실행 중 / 성공 / 실패 / 사용자 확인 대기 / 조건상 생략 / 무효화 |
| 데이터 | 정상 / 검색 0건 / 일부 값 누락 / 데이터 비가용 / 해당 없음 |
| 코드 검증 | 미검사 / 통과 / 실패 |

예를 들어 비교 호출은 성공했고 ‘폭 없음’이라는 상태를 정확하게 반환해 코드 검증을 통과할 수 있다. 그렇더라도 다음 계산이 폭 값을 요구하면 해당 출력 전제는 충족되지 않는다. 검증 통과와 모든 필요한 값의 존재를 같은 뜻으로 취급하지 않는다.

## 4. 내부 계산 계약

| 연산 | 입력·출력과 검사 |
|---|---|
| 최솟값·최댓값 | 동일 물리량의 비어 있지 않은 값 집합. 코드의 허용된 단위 변환 후 같은 단위의 스칼라를 반환한다. |
| 평균 | 같은 물리량·호환 단위의 값 집합에 대한 산술평균. 가중평균을 요청받으면 산술평균으로 대체하지 않는다. |
| 차이 | 같은 물리량 두 값. 부호 있는 차이는 원문에 지정된 방향이 필요하고, 기준 없이 가능한 절대 차이는 기존 비교 정책을 따른다. |
| 배수 | 실제 값과 요청에 근거한 무차원 배수. 원래 물리량의 단위를 유지한다. |
| 비율 | 같은 물리량의 명시된 분자·분모. 단위를 맞춘 뒤 무차원 비율을 반환하며 분모가 0이면 중단한다. |

누락·비유한 수·빈 집합·지원하지 않는 단위 조합은 계산 불가 상태로 남긴다. 필요한 집합 중 누락값을 제외하고 최소·최대·평균을 계산해 원래의 ‘모두’ 조건을 바꾸지 않는다. 모델이 계산한 임계값과 반올림된 표시값을 원본 대신 사용하지 않는다. 백분율 표시·단위 변환·표시 반올림은 코드의 별도 정책을 따른다.

## 5. 중첩 작업의 연결 예시

다음은 사용자가 ‘30~40 eV 후보를 flux 높은 순으로 보여주고, 두 개를 선택하면 비교한 뒤 같은 에너지 범위에서 두 Run 모두보다 flux가 높고 IED 폭이 좁은 후보를 찾아줘’라고 요청한 가상 계획이다. 실제 실험 결과·Run ID는 포함하지 않는다.

| 단계 | 작업과 입력 | 필요한 출력 |
|---|---|---|
| `search_1` | `reverse_search`: `meanIonEnergy`, `operator=between`, `min=30`, `max=40`, `unit=eV`. 목표는 `ionFlux`, `direction=maximize`. | 실제 후보 참조·검색 상태 |
| `choose_1` | `await_input`의 Run 선택 유형으로 요청된 두 Run을 확인받는다. 이 시점은 명시적인 확인 대기다. | 서버가 확인한 두 Run의 고정 버전 참조 |
| `compare_1` | `compare_runs`: 확인된 참조에 `comparison_fields=[ionFlux, iedWidth]`. 요청하지 않은 기준·축은 지정하지 않는다. | 각 Run의 두 지표와 단위·누락 상태 |
| `flux_bound` | 비교한 두 Run의 `ionFlux`에 최댓값 연산. | 검증된 스칼라와 단위 |
| `width_bound` | 같은 두 Run의 `iedWidth`에 최솟값 연산. | 검증된 스칼라와 단위 |
| `search_2` | 원래 에너지 범위 유지 + `ionFlux`의 `operator=gt` 기준으로 `flux_bound` 참조 + `iedWidth`의 `operator=lt` 기준으로 `width_bound` 참조. | 실제 후보·검색 상태 |

확인 응답 뒤 자동 실행 중에는 대상·조건을 유지한다. 비교 출력에 폭이 없으면 `search_2`를 실행하지 않는다. 실제 값을 얻을 수 있는 등록 도구·인자가 있다면 그 부분을 재계획하고, 실제 데이터가 없다면 가능한 결과와 누락 이유를 표시해 다시 확인을 기다린다. 자동 실행 중 사용자가 대상을 바꾼다고 가정하지 않는다.

## 6. 재계획·답변 수정과 재사용

재계획 요청에는 원문·확인 문맥·고정 참조·현재 전체 계획·검증된 실행 결과·실패 단계·필요한 출력·구체적인 검사 오류를 보낸다. 원인과 관련된 단계 및 그 출력에 의존하는 작업을 수정한다. 필요하면 앞 단계로 돌아갈 수 있다.

코드는 새 전체 계획을 이전 계획과 비교한다. 입력·대상 버전·출력 의미와 검증 근거가 그대로 유효한 결과만 재사용하고, 변경된 단계의 의존 결과를 무효화한다. 과거 실행과 계획 스냅샷은 덮어쓰지 않는다. 진행 가능성이 생기지 않은 동일 실패를 남은 횟수만큼 반복하지 않는다.

| 반복 종류 | 확정된 한도 |
|---|---|
| 같은 도구 호출 자동 재시도 | 없음 |
| LLM 재계획 | 최초 계획 외 요청 전체에서 최대 2회. 도구별 한도가 아니다. |
| 근거가 충분한 답변 오류의 재작성 | 요청 전체에서 별도 최대 1회. 수정본도 다시 검증한다. |

카운터는 추가 호출 전에 누적·보존하는 방향으로 구현하며, 대기·재개만으로 초기화하지 않는다. 무효한 수정 계획도 숨겨진 추가 생성 호출로 고치지 않고 이 한도 안에서 처리한다. 코드가 변경된 입력으로 도구를 새로 실행하는 것은 실패한 동일 호출의 재시도와 구분한다.

## 7. 최종 답변과 Decisions 계약

답변 작성 단계는 관측·계산 근거의 선택과 정성적 해석, 내용별 근거 연결을 한 응답으로 만든다. 표는 검증된 코드 결과로 렌더링한다. 해석·가정·한계에 실험값이 필요한 경우 LLM이 해당 항목의 근거 ID를 `{{value:ID}}` 또는 `{{value:ID|항목}}`으로 참조한다. 코드는 연결된 근거에 값이 있는지 확인하고 수치와 단위를 채운 문장을 검토와 표시 양쪽에 사용한다. v2는 문장에 수치 표현이 있다는 이유만으로 답변을 반려하지 않는다. 일반 개념 질문의 설명용 숫자는 실제 Run 결과와 구분한다.

순·역방향 조회와 Run 비교의 결과는 고정된 Run과 입력으로 다시 계산해 값·단위·순서까지 코드로 대조한다. 화면은 이 검사를 통과해 저장된 도구 결과로 표를 표시한다. 작성·코드 검사 실패로 유효한 초안이 없으면 확인 가능한 결과와 실행 오류를 안내한다.

실험 답변에서 표시할 `interpretations`가 있을 때 한 번의 Decisions 요청으로 `interpretation_scope`를 판정한다. 입력은 화면에 표시할 해석 문장과 가정, 각 `evidence_ids`가 가리키는 근거다. 검색 결과가 인용됐으면 연결된 검색의 조건·후보·측정값도 함께 제공한다. 수치 표와 질문 전체의 재채점은 여기서 처리하지 않는다. 새 답변은 해석 판정만 저장하며, 이전의 세 항목 검토가 담긴 답변도 읽을 수 있다.

| 선택값 | 동작 |
|---|---|
| `within_evidence` | 해석 검토 통과를 기록한다. |
| `overclaim` | 기존 실행 근거로 답변을 한 번 수정하고, 남은 해석을 다시 검토한다. |
| `unassessable` | 의미 판정 불가를 기록하고 마지막 유효 답변을 표시한다. |

수치·목록 답변과 순수 일반 지식은 최종 해석 Decisions를 생략하고 `SKIPPED`로 저장한다. 데이터 요청의 실행 전 계획 검토와 별개다. 재계획은 계획 의미 불일치·실행·입력 검증 실패에서 판단하며, 해석 판정은 답변 수정에만 사용한다. 확률과 confidence는 기록에 남긴다. 통신 실패, 판정 불가, 수정 한도 소진 시에는 마지막으로 코드 검사를 통과한 답변과 실제 검토 상태를 유지한다.

### 호출 실패·형식 오류의 상세 제안

| 상황 | 처리와 한도 |
|---|---|
| 도구의 시간 초과·통신 실패 | 같은 호출을 자동 재시도하지 않는다. 실제 근거를 얻을 다른 지원 경로가 있을 때만 재계획을 검토한다. 없으면 성공한 결과와 실행 실패 이유로 부분 종료하며 검색 0건으로 바꾸지 않는다. |
| 계획 API의 통신 실패·거절 | 숨겨진 전송 재시도를 두지 않는다. 계획이 없으면 실행 실패 안내로 종료한다. 이미 검증된 결과가 있으면 그 상태를 유지하고 부분 종료한다. |
| 계획 제출의 형식·참조 오류 | 코드 오류를 피드백해 같은 `submit_plan`으로 수정받고 요청 전체 재계획 2회에서 차감한다. v1의 별도 형식 repair·재시도 루프를 한도 밖에서 상속하지 않는다. |
| 답변 작성의 형식·코드 검사 실패 | 근거가 충분하면 답변 수정 1회를 사용한다. 수정도 실패하면 마지막 코드 검사 통과 초안을 사용하고, 그런 초안이 없으면 확인 가능한 결과·오류를 안내한다. |
| 답변 작성 API의 통신 실패·거절 | 동일 호출을 자동 반복하지 않는다. 유효한 이전 초안이 있으면 사용하고, 없으면 결과·오류 안내로 종료한다. |
| Decisions의 통신 실패·거절·응답 형식 오류 | 별도 자동 재호출 없이 검증 미완료를 기록하고 마지막 코드 검사 통과 답변을 표시한다. 내용이 없는 판정으로 재작성·재계획을 반복하지 않는다. |

v2의 SDK 전송 재시도도 현재 클라이언트처럼 0으로 제안한다. 형식 오류를 고치기 위한 추가 모델 호출은 정해진 재계획·답변 수정 카운터에 포함한다. 이는 동일 실행 호출의 무조건 재전송과 구분하며, 원인·추가 호출·사용량을 기록한다.

## 8. 저장·API 경계의 필수 항목

v1 기본값과 과거 대화를 보존한다. D10-S에 따라 새 대화 화면에서 v1·v2를 선택한다. 첫 요청 전의 빈 화면에서도 선택 가능해야 하며, 요청이 시작된 대화에는 실행 버전을 고정하는 방향으로 상세 계약을 제안한다. 처리 도중에는 바꾸지 않고 다른 버전을 쓰려면 새 대화를 만든다. 기존 v1 체크포인트를 v2 상태로 읽거나 자동 이관하지 않는다.

저장할 항목은 요청·입력 문맥 스냅샷, 그래프·계획·답변 스키마 버전, 계획 수정본, 단계 ID, 확정 실행 입력, Run 고정 참조, 원본 결과·상태·검증 기록, 근거 연결, 수정 카운터, 최종 판정과 표시한 답변이다. 실행 완료 여부·의미 검증 결과·답변 표시 여부는 서로 구분한다. 표시했다는 이유로 검증 통과로 기록하지 않는다.

HTTP·스냅샷 확장은 아래 §9, 초기 실행 예산과 완료 기준은 §10의 작성자 제안으로 구체화한다. 구현 계획에서는 생산자·소비자·스키마·마이그레이션·계약 검증을 함께 변경한다. 현재 v1 API가 이 계약을 이미 지원한다고 간주하지 않는다.

D10-O에 따라 최종 답변을 먼저 표시하고 주요 중간 검색·비교 결과는 접어서 제공한다. 각 결과를 펼쳐 보고 해당 결과의 Run을 판단 기록 대상으로 선택할 수 있게 한다. 내부 실행·검증 기록도 유지한다. 다른 검색 단계의 후보를 하나의 출처 없는 목록으로 합치지 않도록 단계·후보 그룹의 출처를 보존한다.

기록·참조 입력에는 요청 또는 대화 턴, 불변의 출처 실행 ID, 출처 단계 ID, 후보 그룹 ID, 실제 Run 참조·고정 버전을 연결하는 방향으로 계약을 확장한다. 서버는 해당 Run이 그 실행·그룹의 실제 결과에 속하는지 확인한다. 같은 단계 ID가 재계획에서 재사용되어도 출처 실행 ID로 과거와 현재 결과를 구분한다. 기존 v1 참조와 판단 기록은 기존 계약을 유지한다.

v2의 접기·펼치기 상태는 실행·결과 그룹별 UI 상태로 분리하고 원본 결과를 덮어쓰지 않는다. 무효화된 예전 실행을 현재 계획의 유효한 후보로 자동 사용하지 않는다. 기록 시에는 선택한 Run과 출처 실행의 스냅샷을 고정해, 이후 입력·계획 변경이 과거 판단 기록을 바꾸지 않게 한다. D10-V에 따라 실제 의미 검증 상태와 항목별 결과는 상세정보에서만 보여주고 일반 답변 옆에는 별도 판정 표시를 붙이지 않는다.

실제 실험 결과·대화·판정 로그와 비밀값은 저장소에 넣지 않는다. 계약 예시와 자동 검증 fixture에는 소량의 인공 데이터만 사용하고 실데이터 비교는 저장소 밖에서 수행한다.

## 9. 제출·버전 선택·단계 실행·저장의 구체 계약 제안

이 절은 구현 계획을 세울 수 있도록 작성자가 정한 초안이다. 사용자 개별 확정 사항은 주 설계서의 결정 기록을 따른다. 정확한 OpenAPI·JSON Schema와 클래스는 구현 계획의 산출물로 만들되 다음 필드·책임·호환성 규칙을 기준으로 한다.

### 9.1 계획과 답변의 고정 형태

계획의 최상위 필드는 §1의 다섯 필드로 제한한다. `requirements`에는 `id`, `sources`, `text`, `handled_by`를 두고, `sources`는 코드가 제공한 메시지 키와 원문 구절의 목록이다. 단계에는 `id`, `kind`, `requirement_ids`, `depends_on`, `inputs`, `requires`, `run_if`를 둔다. 종류별 도구명·연산·확인 유형은 판별 가능한 하위 스키마로 구분한다.

리터럴 입력은 `kind=literal`, `value`, `unit`, `source`로, 문맥 입력은 `kind=context_ref`, `key`로, 결과 입력은 §2의 `result_ref`로 구분한다. 등록된 문맥 키·결과 필드만 사용하고 전체 스키마에서 알 수 없는 필드를 거부한다. `requires`는 선행 결과의 필드·개수·자료형·단위·검증 상태 요구다. 이 요구가 충족되지 않으면 실행을 막는다.

모델에 보내는 `submit_plan` 스키마의 `unit`은 지원 단위의 표준 표기, `unsupported`, `null`로 제한한다. 원문 표기와 수치는 출처 인용에 유지하며, 다른 배율의 단위를 서로 바꾸지 않는다. `null`은 원문에 단위가 없는 경우에 사용한다. 명시한 단위를 `unsupported`로 제출하면 검증에서 실행을 막는다. 검색 제약은 연산자에 따라 스키마에서 필수 경계를 구분한다. 단일값 제약은 `value`를, `between`은 `min`과 `max`를 요구한다. 저장 계획은 이전 리터럴 단위 표기와 호환된다.

`run_if`는 원문에 명시된 조건부 작업을 위해 결과 상태 또는 후보 개수를 비교하는 등록 조건의 목록으로 제안한다. 상태 동일 여부와 개수의 `eq`, `lt`, `lte`, `gt`, `gte`만 사용하고 목록은 AND로 처리한다. 충족하지 않은 조건부 단계는 실행하지 않은 이유를 기록한다. 필요한 필드가 없다는 이유로 원문이 요구한 작업을 조용히 생략하는 데 사용하지 않는다. 생략될 수 있는 생산 단계의 결과를 쓰는 후속 작업은 같은 실행 조건을 가져야 하며, 맞지 않는 분기 참조는 계획 검사에서 거부한다. 이 범위를 넘는 분기는 확인 또는 재계획으로 처리하고 임의 코드·표현식을 실행하지 않는다.

계획은 native 함수 목록에 `submit_plan`만 노출하고 응답당 단일 제출을 요구한다. 실제 세 도구는 제출 계획의 등록된 작업으로 표현하며 모델이 직접 실행하지 않는다. 스키마 준수는 원문 이해의 정확성을 보장하지 않는다.

실험 답변 작성 응답은 `fact_ids`, `interpretations`, `limitations`로 제안한다. 해석 항목은 내용 ID·텍스트·근거 ID·가정을, 한계 항목은 내용 ID·텍스트·관련 근거 ID를 갖는다. 코드가 선택한 사실의 수치·조건·상태를 렌더링하고 자유 해석과 결합한다. 설명 요청의 해석·가정·한계는 결과 표 아래에 표시한다. 수치만 요청한 경우 답변 작성 단계에서 해석을 비워 둔다. 일반 개념 응답은 일반 지식의 문단과 지식 출처만 가지며 실제 Run 참조는 비어 있어야 한다.

일반 지식 경로 선택에는 최초 계획의 의미 분류가 포함된다. 원문에서 명시적으로 요청한 Run·비교·실험값, 실행 도구·결과 사용 여부와 실제 수치 주장을 함께 검사하며, 문맥에 Run이 첨부되어 있다는 이유만으로 모든 개념 질문을 실험 요청으로 보지는 않는다. 모호한 경우는 데이터 요청·입력 확인 쪽으로 처리한다. 이 분류도 모든 간접 표현을 코드로 증명할 수는 없으므로 오분류 평가가 필요하다.

### 9.2 외부 API와 대화 버전

현재 제출 경로 `/api/agent/requests`와 요청·재개·취소의 생명주기를 유지하면서 다음과 같이 확장한다.

| 위치 | 새 필드·처리 제안 |
|---|---|
| 제출 `Submission.graphVersion` | 선택적 `v1` 또는 `v2`. 첫 요청에서 생략하면 v1, 고정된 대화에서는 생략 시 그 버전을 사용한다. |
| 대화 `agentGraphVersion` | 첫 요청 수락 전에는 미고정 상태, 수락 후에는 서버가 고정한 버전. 기존 `conversation.version`은 데이터 형식 버전으로 유지한다. |
| 요청 조회 `graphVersion` | 서버가 고정한 실행 버전. 제출·문맥·요청 레코드·worker가 같은 값을 사용한다. |
| 기존 재개 본문 | `expectedRequestRevision`, `pendingInputId`, `input`을 유지한다. 서버가 현재 대기 단계·허용 필드·계획 수정본을 검사하며 재개 때 다른 그래프를 선택하지 않는다. |

첫 제출을 수락하는 기존 workspace 잠금·트랜잭션 안에서 대화 버전과 요청 버전을 함께 고정한다. 이미 고정된 버전과 다른 명시 값은 `GRAPH_VERSION_MISMATCH` 충돌로 거부한다. 지원하지 않는 버전도 오류로 반환하며 조용히 v1으로 바꾸지 않는다.

첫 요청 전 UI의 선택은 제출 본문에 반영하고 선택 조작 자체로 대화를 초기화하거나 Run 참조를 지우지 않는다. 전송 중·수락 여부 미확정·실행 중·확인 대기에는 버전 선택을 잠근다. 새 대화 생성은 기존 초기화 범위를 따르고 기본 선택을 v1으로 되돌린다. 같은 idempotency key로 복구할 때는 처음 제출한 버전과 본문을 유지한다.

기존 요청·대화와 이미 수락된 과거 요청은 v1으로 취급한다. 데이터가 전혀 없는 새 대화만 첫 제출 전 선택이 가능하다. 기존 답변 JSON은 재작성하지 않는다.

### 9.3 worker와 요청 안의 단계 실행

현재 worker의 v1 직접 import를 버전별 graph factory로 교체하는 계획이다. v1은 기존 그래프·상태·검증을 유지하고 v2는 별도 모듈·체크포인트 이름공간을 사용한다.

claim에는 선택적 `supportedGraphVersions`를 추가한다. 기존 worker가 생략하면 v1만 claim할 수 있게 하고, 새 worker는 구현한 버전을 명시한다. 서버가 요청 버전에 맞춰 배분해 v1 worker가 v2 요청을 가져가지 않도록 한다. 기존 claim generation·lease·request revision fencing은 유지한다.

v2에는 `agent_step_execution`에 해당하는 별도 단계 실행 기록을 제안한다. 키는 요청·계획 수정본·단계 ID와 불변 execution ID이며, 도구·확정 입력·출처·상태·결과·검증을 연결한다. 부모 요청의 단일 operation/result 슬롯을 도구마다 덮어쓰지 않는다.

| 내부 경로의 제안 | 책임 |
|---|---|
| `POST /internal/agent/requests/{id}/steps` | 실행을 예약하고 도구 호출 예산을 차감한다. 승인된 계획·단계·입력과 현재 fencing을 검사한다. |
| `POST /internal/agent/requests/{id}/steps/{executionId}/context` | 기존 context·query 동작을 단계별로 분리한다. 서버가 확인한 Run 버전과 해당 단계의 조회 근거를 반환한다. |
| 단계별 comparison outputs | 기존 출력·그래프 근거 조회에 execution ID를 연결해 다른 단계의 비교 근거와 섞이지 않게 한다. |
| `POST /internal/agent/requests/{id}/steps/{executionId}/result` | 기존 계산·검증 책임 분리를 유지해 결과와 근거를 확인하고 그 실행에 저장한다. 내부 연산도 입력 근거·연산·결과를 확인한다. |
| 단계 실행 조회 | 재시작·응답 유실 시 저장 상태를 확인한다. 성공한 실행을 다시 호출하거나 원본 결과를 덮어쓰지 않는다. |

API 분리는 현재의 데이터 조회·Python 계산·서버 검증 책임을 임의로 한쪽으로 옮기려는 것이 아니다. 기존 등록 도구의 계산·검색 정책을 재사용하면서 요청 내 여러 실행을 구분하기 위한 계약이다. 실제 엔드포인트 구현 형태를 조정하더라도 실행 단위와 fencing·출처 분리 규칙은 유지한다.

진행 중 장애로 완료 여부를 알 수 없으면 저장 상태를 대조한다. 결과가 저장되지 않았다고 같은 도구를 자동 재실행하지 않는다. 불확실한 실행 실패로 남기고 부분 종료·오류 정책을 적용한다. 모델 호출의 카운터도 호출 전에 서버/체크포인트에 예약·보존해 재시작이 한도를 초기화하지 않게 한다.

### 9.4 최종 스냅샷과 판단 기록

새 답변 계열은 `(implementationId=v2, graphVersion=v2, schemaVersion=1)`로 제안한다. 기존 v1의 답변 schemaVersion 2·3과 다른 계열이다. Python 타입 이름도 기존 `AnswerSnapshotV2`와 혼동되지 않게 `GraphV2AnswerSnapshotV1` 등으로 분리한다. 프런트엔드는 구현·그래프 계열을 먼저 구분하고 그 안에서 스키마 버전을 판별한다.

v2 스냅샷에는 원문·확인 문맥·계획 수정본, 순서가 고정된 `stepResults`, 근거 목록, 선택한 사실과 해석, 렌더링된 답변, 실제 수행 상태, 검토 상태·항목별 판정, 수정 카운터를 포함한다. 서버는 v2 완료를 v1 단일 도구 답변으로 검증하지 않고 별도 검증기를 사용한다. 최종 intent는 실험 복합 답변에 `COMPOSITE_ANSWER`, 순수 개념 답변에 `GENERAL_ANSWER`를 사용하는 안이다.

`hasIncompleteWork`는 실행 실패, 필요한 후속 단계 미완료 또는 부분 도구 결과를 표시한다. 정상적으로 완료된 도구 실행의 설명문 작성 실패는 이 값에 반영하지 않는다. 화면은 실제 작업이 미완료일 때 안내를 표시한다. 검토 판정은 저장된 스냅샷에 남긴다.

부모 요청의 처리 완료와 질문의 전체 수행 여부, 의미 검증 통과 여부는 독립 필드로 관리한다. 의미 검증 미통과 답변도 표시했으면 그 사실을 저장하고, 모두 수행하지 못한 작업은 부분 상태와 이유를 남긴다. UI 상세정보에 검토 통과·미통과·미완료·생략과 항목별 판정을 표시한다. 일반 답변 옆에는 별도 검토 표시를 붙이지 않는다.

주요 도구 결과는 기존 후보·비교 카드의 모델을 활용해 단계별로 접어서 표시한다. Run 기록·후속 참조에는 `turnId`, `executionId`, `stepId`, `groupId`, Run 고정 참조를 연결한다. 서버는 그 execution의 실제 후보·비교 결과에 속하는 Run인지 검증한다. 과거 단계의 같은 이름이나 같은 Run ID만으로 새 결과의 출처를 대신하지 않는다.

새 단계 실행·대화/요청 버전·카운터 저장은 새 DB 마이그레이션으로 도입한다. 과거 스냅샷은 그대로 두고 필요한 레코드 메타데이터만 v1으로 호환 처리한다. 공유 TS 계약, backend DTO/검증, Python 계약, frontend renderer·기록·resume과 OpenAPI/스키마 및 계약 테스트를 함께 갱신한다. 새 코드·마이그레이션은 이 문서 작성 단계에서는 실행하지 않는다.

## 10. 초기 실행 예산과 평가 완료 기준 제안

다음 숫자는 작성자의 초기 설정안이다. 사용자 확정인 재계획 2회·답변 수정 1회와 구분하며, 최적값이라고 주장하지 않는다. 환경 설정과 평가 결과로 조정할 수 있게 한다.

| 예산 | 초기값의 제안 |
|---|---|
| 계획·재계획 모델 | 기본 `gpt-6-luna`, `reasoning.effort=low`. `AGENT_V2_PLAN_MODEL`과 `AGENT_V2_PLAN_REASONING_EFFORT`로 재정의한다. 답변 작성은 v1 설정을 상속하고 Decisions 모델은 별도 설정을 따른다. |
| 계획 수정본의 최대 단계 | 16. 도구·내부 연산·입력 확인을 포함한다. |
| 요청 전체의 실제 도구 실행 | 최대 12회. 이미 검증한 결과 재사용은 새 호출로 세지 않는다. 실패한 실행 시도도 포함한다. |
| 계획·답변 출력 | 호출당 최대 6,000 토큰. v1 클라이언트 기본 상한을 초기 기준으로 사용한다. Decisions에는 일반 생성의 출력 토큰 필드를 가정해 전달하지 않는다. |
| 모델 입력 | 역할별 기본 24,000 토큰을 제안하며 실제 선택 모델의 가용 문맥·출력 여유보다 작게 적용한다. |
| 호출 시간 | 모델과 백엔드 호출에 각각 최대 30초를 초기값으로 제안한다. 남은 요청 시간보다 길게 잡지 않는다. |
| 요청의 자동 처리 시간 | 사용자 확인 대기 제외 600초. 대기 전 사용 시간을 보존하고 재개·재시작만으로 초기화하지 않는다. |
| worker lease | 초기 60초. 호출 전 남은 lease가 호출 deadline + 10초보다 작으면 갱신한다. 긴 작업도 기존 heartbeat/fencing 계약으로 갱신하고 lease를 잃은 worker의 결과 저장은 거부한다. |
| 추가 모델 호출 | 숨겨진 SDK 재시도 0. 재계획 2회·답변 수정 1회·부분 종료 작성 1회를 각 카운터로 제한한다. 최악 경로의 전체 모델 요청은 13회 이내를 불변량으로 제안한다. |

13회는 최초 계획·작성·검토 3회, 두 번의 재계획 각각 최대 계획·작성·검토 3회, 답변 수정·재검토 2회, 부분 종료 작성·검토 2회로 계산한다. 현재 정상 경로는 단순 데이터 2회·데이터 해석 4회·순수 일반 지식 2회다. 최초 계획과 두 수정본의 PLAN_REVIEW 예약은 최대 3회이며 전체 13회 상한에 포함한다. 단계·도구 예산과 각 역할의 실제 호출 수는 별도로 기록한다.

코드가 원문 조건이나 결과 개수를 몰래 줄여 한도에 맞추지 않는다. 입력이 너무 크면 등록된 코드 근거의 필요한 필드만 구성할 수 있지만 원문·사용자가 요청한 근거를 조용히 잘라내지 않는다. 보존할 정보가 상한에 들어가지 않으면 처리 범위 확인·명시적인 부분 종료·입력 오류 중 해당 정책으로 종료한다. 실행 결과와 UI의 전체 후보를 모델 입력 편의를 위해 임의 top-N으로 바꾸지 않는다.

모델 입력 상한은 제공자와 실제 모델의 가용 문맥보다 작도록 설정 검증한다. 주어진 문맥에서 필요한 근거를 담을 수 없으면 자동으로 다른 모델을 호출하거나 의미를 바꾼 요약으로 대신하지 않는다. 호출 시간·lease를 바꾸면 두 값의 여유 조건도 함께 검사한다. 실행 취소·lease 만료 뒤 늦게 도착한 응답은 현재 결과를 덮어쓰지 않는다.

도구·시간 예산 소진은 영구 데이터 누락과 다른 사유로 기록한다. 더 이상 자동 실행·재계획을 하지 않고 가능한 결과와 한계로 부분 종료한다. 종료 처리에 모델 호출 예산·시간이 남아 있지 않으면 새 생성을 하지 않고 마지막 코드 검사 통과 답변 또는 코드가 확인한 결과·이유를 표시한다. 부분 종료가 다시 일반 실행으로 돌아가지 않게 한다.

### 검증과 평가의 산출물

| 구분 | 완료 기준 |
|---|---|
| 계약·코드 검증 | 인공 fixture에서 계획 검사, 입력 확인/재개, 단계 결과와 단위·버전, 0건/누락/오류 구분, 한도, 오래된 실행 차단, 출처별 기록의 필수 시나리오 통과. v1 관련 필수 회귀 검증도 통과해야 한다. |
| UI 검증 | 새 대화 버전 선택, 최종 답변·접힌 중간 결과·기록·상세정보와 대기/실패/일반 지식 경로를 390 / 800 / 1008 / 1440px에서 확인한다. |
| 실제 모델 평가 | 같은 질문·데이터·가능한 모델 설정을 고정해 v1과 v2 결과를 보고한다. 복합 질문은 예상 정답·허용 도구 흐름·실패 시 기대 상태를 사람이 라벨링하고 특정 계획 문자열의 일치만으로 채점하지 않는다. |

초기 모델 평가 묶음은 단순 조회·비교, 중첩/독립 복합 질문, 0건·누락·미지원·오류, 일반 개념/혼합 질문을 포함한다. 최소 24개 사례를 제안하며 그룹별 충분성은 평가 결과를 보고 확장한다. 원래 질문의 요구 충족, 실제 사실 정확도, 출처·대상·단위 준수, 과장 해석, 불필요한 수정과 복구 성공률, 최종 제공 답변 오류와 API 비용·지연을 함께 보고한다. Decisions 통과율만으로 정확도를 대신하지 않는다.

모델 효과를 비교할 때는 v2 그래프·질문·인공 Run·프롬프트·도구·답변 및 Decisions 설정을 고정한다. 계획·재계획 설정만 `gpt-5.6-luna/none`(기준), `gpt-5.6-luna/low`, `gpt-6-luna/none`, `gpt-6-luna/low`로 바꾼다. 그래프 효과는 공통 모델 설정으로 v1과 v2를 별도 비교한다. 최초 계획의 의미 정확도와 최종 제공 답변의 정확도를 나눠 기록하고, 대표 실패 사례는 설정별 최소 3회 반복해 성공이 일관적인지 확인한다. 후보 검색의 정답은 실행된 계획 문자열 대신 기대 후보·엄격한 경계·누락 시 실행 금지를 기준으로 판단한다.

기본 버전은 계속 v1이며 v2는 명시적으로 선택하는 평가용이다. 초기 opt-in 구현의 검수에는 필수 코드·계약·UI 검증 통과와 모델 평가 보고서를 요구한다. 현재는 근거 없는 모델 정확도 합격률을 고정하지 않는다. 모델 평가 미실행이면 미실행으로 남기고 품질 검증 완료라고 보고하지 않는다. 기본 버전을 v2로 전환하는 것은 이 설계에 포함하지 않으며 실제 평가 후 별도 결정한다.

이 설계 문서 작성 중에는 제품 테스트·실제 모델 평가·유료 API 호출을 실행하지 않았다. 실제 평가 데이터·응답·그래프·스크린샷은 저장소 밖에서 보관하고 저장소에는 스키마와 소량의 인공 fixture만 둔다.

## 11. 검토 상태

2026-11-01 두 문서를 함께 읽는 builder-check를 수행했다. 첫 검토에서 복합 결과·수치 서술·필수 입력·실패 처리·검토 상태 UI·예산과 완료 기준을 확인했고, 사용자 선택과 기존 코드 정책을 반영해 보완했다. 보완본의 재검토 결과는 ‘nothing important left’였다. 이는 설계에서 중요한 추측이 남는지에 대한 검토이며 실제 구현·모델 품질의 검증 결과가 아니다. 이 문서의 기술 제안 전체는 사용자 최종 검토 대상이다.

2026-11-01 사용자가 주 설계서와 이 문서를 기준으로 구현 계획 작성을 요청했다. [구현 계획](../plans/2026-11-01-agent-v2-implementation-plan.md)의 기준으로 사용하며, 아직 제품 구현이나 실제 모델 평가를 수행한 상태는 아니다.
