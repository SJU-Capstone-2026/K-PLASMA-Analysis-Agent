# K-PLASMA v12.3.1 실제 구현 설계

작성일: 2026-10-03

상태: 2026-10-03 사용자 승인 완료. 기존 설계 유지, 상세 구현 계획 작성 완료.

현황 근거: [v12.3.1 조사 기록](../research/2026-10-03-v12.3.1-discovery.md)

사용자는 데이터 범위가 기존 3변수의 150 Run에서 늘어나지 않는다고 확인했다. 문서 검토에서 제안한 다섯 추가 보완은 후속으로 미루고 이 설계 방향을 유지한다. 구현 작업과 유예 항목은 [상세 구현 계획](../plans/2026-10-03-v12.3.1-implementation-plan.md)에 기록한다.

## 1. 목표와 완료 기준

v12.3.1의 분석 Agent, 실험 데이터 탐색, 의사결정 기록, Run 데이터 관리, 사용 방법 화면을 실제 애플리케이션으로 이관한다. 기준 데이터와 초기 상태가 같을 때 화면, 문구, 조작, 검색 결과, 수치, 그래프, 기록 저장 및 복원 동작이 일치해야 한다.

합의한 변경은 두 가지다.

1. Run 관리의 목업 문구와 네 시연 버튼을 실제 폴더/ZIP 업로드·파싱·재처리로 전환한다. 기존 레이아웃과 스타일을 유지한다.
2. 전체 초기화 후 후보 참조가 남는 오류를 수정한다. 초기화는 대화·판단 기록·참조만 삭제하고 등록한 Run과 원본 파일은 유지한다.

그 외의 임의 디자인 변경, 기능 축소, 질문 규칙 변경, 수치 변경을 이관 작업에 섞지 않는다. 동등성을 확인하지 못한 항목은 완료로 표시하지 않는다.

1차는 팀원 각자의 PC에서 개발·실행하고 각자 데이터를 사용한다. 코드 협업은 GitHub의 작업 브랜치와 PR로 진행한다. 실제 결과 원본, 파생 결과 JSON, DB 데이터, 사용자 기록은 GitHub에 올리지 않는다.

## 2. 기술과 실행 단위

| 영역 | 선택 | 역할 |
| --- | --- | --- |
| backend | Java 21, Spring Boot, Gradle, Spring Data JPA, Flyway | 업로드·파싱·재처리, 원본 보관, PostgreSQL 저장·조회 |
| frontend | React, TypeScript, Vite | 원본 화면·조작·차트, fallback 연결, 서버 데이터 조회 |
| agent | 기존 결정론적 JavaScript를 재사용하는 라이브러리 | 질문 해석, 검색·정렬, 변화·개념 설명, 기록 재사용 |
| DB | PostgreSQL 18 계열 | Run 버전, 파싱한 결과·그래프, 작업 상태, 대화·판단 스냅샷 |
| 로컬 DB 실행 | Docker Compose | 팀원이 같은 DB 설정으로 실행하도록 지원 |

초기 실행 프로세스는 React 개발 서버, Spring 서버, PostgreSQL이다. `agent`를 별도 서버로 실행하지 않는다. `agent` 라이브러리를 frontend 빌드에서 사용한다.

JavaScript 계산을 Java로 다시 작성하는 안은 수치·정렬·문구의 차이를 늘리고, Node Agent 서버를 추가하는 안은 서비스 연결과 운영 작업을 늘린다. 원본 보존과 현재 Agent 부재에 맞춰 라이브러리 재사용을 선택한다.

런타임의 구체적인 패치 버전, Gradle Wrapper, npm 잠금 파일, DB 이미지 버전은 초기 환경 구성 단계에서 함께 고정한다. 최소 호환 조건은 [Spring Boot 시스템 요구사항](https://docs.spring.io/spring-boot/system-requirements.html), [Vite 실행 요구사항](https://vite.dev/guide/), [PostgreSQL 지원 버전 정책](https://www.postgresql.org/support/versioning/)을 따른다. Node는 22 LTS의 지원 패치를 사용하고 Vite의 최소 조건인 22.12 이상을 충족한다.

## 3. 폴더와 책임

아래는 구현할 구조다. 현재 생성된 제품 코드가 있다는 뜻은 아니다.

```text
K-PLASMA-Analysis-Agent/
├─ backend/
│  ├─ src/main/                    # Run·파싱·기록 API와 도메인
│  ├─ src/test/                    # 인공 입력 기반 테스트
│  ├─ storage/                     # 원본·임시 업로드, Git 제외
│  └─ build.gradle, Gradle Wrapper
├─ frontend/
│  ├─ src/features/                # 기존 5개 상위 화면
│  ├─ src/api/                     # 서버 API와 데이터 변환
│  ├─ src/prototype/               # 원본 스타일·표시 함수의 이관
│  └─ src/components/              # 모달·차트·참조 칩 등 공통 UI
├─ agent/
│  ├─ src/fallback/                # 원본 질문·검색·설명·기록 로직
│  ├─ src/contracts/               # Agent 입력·출력 계약
│  └─ tests/                       # 인공 데이터·외부 기준 비교
├─ docs/superpowers/
│  ├─ research/
│  ├─ specs/
│  └─ plans/
└─ .github/                        # PR 템플릿과 구현 단계의 CI
```

JavaScript 영역은 npm workspace로 frontend와 agent를 함께 관리한다. backend는 Gradle 프로젝트로 관리한다. 팀원은 화면·서버·fallback 계약을 기준으로 병렬 작업하며, API 계약 변경은 관련 영역을 함께 갱신한다.

backend의 도메인은 Run·버전, 데이터 적재·파싱 작업, 대화, 판단 기록, workspace 상태로 나눈다. frontend는 서버 데이터와 모달·선택·입력 같은 UI 상태를 분리한다. 원본 CSS를 먼저 보존하고 이관 완료 전에는 대규모 CSS 정리를 하지 않는다.

## 4. 데이터 흐름과 Agent 경계

### 업로드와 분석

1. 사용자가 기존 Run 관리 영역에서 폴더 또는 ZIP을 선택한다.
2. frontend가 파일과 상대경로를 backend에 전송한다.
3. backend가 원본 파일을 보관하고 Run 단위 파싱 작업을 만든다.
4. 파싱한 조건·수치·그래프·품질 정보를 PostgreSQL에 저장한다.
5. frontend가 검색 가능한 최신 Run 목록을 갱신한다.
6. `agent`의 기존 fallback이 이 목록으로 질문을 처리한다.
7. frontend가 기존 답변 형식으로 표시하고 당시 대화·참조·수치 스냅샷을 backend에 저장한다.

원본은 Spring이 관리하는 보관 폴더에 파일로 저장한다. 사용자는 수동으로 복사하지 않는다. 파싱된 수치와 표시용 그래프는 DB에 저장하므로 조회할 때 매번 원본을 읽지 않는다. 재처리는 보관한 원본을 다시 읽고 새 처리 버전을 만든다. 같은 원본은 재처리할 때 다시 복사하지 않는다.

### fallback 계약

입력에는 질문, 기준 Run의 ID와 버전, 후보 참조 집합, 추가 조건 응답을 전달한다. 데이터 문맥에는 조회 가능한 Run, 필요한 비교 데이터, 과거 판단 기록을 전달한다. 출력에는 원본의 intent, 상태, 조건·평가, 후보, 설명 근거와 표시용 답변 모델을 보존한다.

adapter는 검색 후보인 `candidateRunsLatest`와 과거 참조인 `referenceRunsByVersion`을 분리한다. 검색·정렬은 최신 성공 버전 집합에서만 수행하고, 기준 Run·이전 후보·설명 비교쌍은 명시한 버전으로 해석한다. 원본의 Run ID 조회 지점도 이 계약에 맞게 변경한다. 과거 버전을 최신 후보 목록에 섞거나 같은 ID의 최신 버전으로 기준값을 대체하지 않는다. Run당 버전이 하나인 기준 데이터에서는 원본과 결과가 같아야 한다.

목록 응답은 검색에 필요한 조건·scalar·상태를 제공한다. 상세·변화 설명을 만들기 전에는 선택한 버전을 `hydrateFullRun`으로 조회한다. 이 계약은 `iedDistribution`, `analysis.current.points`, `analysis.potential.points`, `analysis.density.rows`, `analysis.residualTrace`, 엄밀 수렴·최종 잔차, 설명에 필요한 중간 지표와 `sourceFiles`를 원본 구조로 제공한다. 아직 조회하지 않은 그래프를 출력 부재로 판정하지 않는다. 비교쌍의 상세 조회가 실패하면 설명을 완료한 것처럼 표시하지 않는다.

- 정방향: `EXACT`, `NEAREST_ONLY`, `NO_DATA`.
- 역검색: `INVALID`, `MATCH`, `NO_MATCH`.
- 변화 설명: `READY`, `NO_PAIR`, `NOT_CONTROLLED`.
- 입력 보충: `CLARIFICATION`.

호출부는 비동기 adapter로 감싸되 현재 fallback은 결정론적 계산을 수행한다. 나중에 실제 Agent가 생기면 adapter의 구현을 서버 연결로 바꿀 수 있다. 초기에는 실제 LLM, Agent 장애 감지·자동 전환, Python 서비스, RAG를 구현하지 않는다.

설명 문구가 있는 `view-models.js`까지 이관 기준에 포함한다. 현재의 기본 demo 비교와 일부 Source Power 중심 설명 문구는 그대로 보존하고 알려진 제한으로 기록한다. 없는 수치·곡선·실행하지 않은 조건이나 확정되지 않은 인과관계를 생성하지 않는다.

## 5. 데이터 모델과 버전

| 개념 | 보관할 내용 |
| --- | --- |
| Run | 기존 표시 ID, 조건, 지원 형식·species·모드, 현재 검색 버전 |
| Run 버전 | 원본 집합, 파서 버전, 처리 상태, 조건·scalar, 완료·품질·엄밀 수렴 |
| 원본 집합·파일 | 상대경로, 크기, 내용 해시, 내부 보관 위치, 파일 종류 |
| 그래프 | Run 버전·종류, 좌표·값·순서, 원본/표시 shape, 단위, 비가용 사유 |
| 적재 배치·작업 | Run별 상태·오류·진행률·시각·재처리 이력 |
| 대화 | 질문·intent·당시 기준/후보 버전·답변 스냅샷·순서·UI 복원 상태 |
| 판단 기록 | REV/EXP 형식, 작성자·공통/개별 메모·판단·당시 수치/평가/Run 버전 |
| workspace | 현재 대화·단일 Run/후보 집합 참조, 초기화 및 대화 세대·상태 revision |

조건·검색 지표는 타입이 있는 컬럼으로, 표시용 그래프·답변/판단 스냅샷은 JSONB로 관리한다. 큰 그래프를 매 대화 스냅샷에 반복 저장하지 않는다. 실제 파일 위치는 서버 내부에서만 해석하고 UI에는 기존 파일 정보 형식으로 표시한다.

원본 집합의 중복은 Run 내부 상대경로와 파일 내용의 해시로 판정한다. 숨김 운영체제 파일과 ZIP 포장 순서는 비교에서 제외한다. 폴더와 ZIP으로 같은 파일을 올려도 같은 원본 집합으로 판정한다.

- 완전히 같은 원본 집합: `DUPLICATE`, 불필요한 복사·등록을 하지 않는다.
- 같은 조건의 다른 원본: 기존 결과를 유지하고 새 버전을 만든다.
- 검색은 해당 조건의 최신 성공·검색 가능 버전을 사용한다.
- 새 버전이 실패하면 이전 정상 버전은 계속 검색 가능하다.
- 과거 답변·판단·참조 상세는 저장 당시 버전을 사용한다. 현재 버전으로 바꾸지 않는다.
- 기존 조건만으로 지원 형식을 구분할 수 없는 입력은 임의로 합치지 않는다. 초기 파서는 현재 원본의 Ar, TCP/CW, release 8.8.1 형식을 대상으로 한다.

등록한 새 Run은 검색·격자·상세·참조 복원에 같은 데이터 계약으로 반영한다. 기존 정적 150개 목록만 frontend에 고정하지 않는다. 같은 조건의 여러 버전은 격자 셀을 늘리지 않고 최신 검색 버전을 사용한다.

## 6. 실제 업로드와 파서

### 입력과 작업 처리

전체 결과 폴더와 단일 Run 폴더를 지원한다. ZIP과 폴더 입력은 상대경로를 가진 동일 파일 목록으로 변환한 뒤 하나의 파서를 사용한다. 이름만 같은 `Ar+.txt`를 IED/IAD/IEAD/DEN으로 혼동하지 않는다.

기준 원본은 150 Run, 2,180파일, 약 1.5GB다. 초기 제한은 폴더 배치의 총 파일 크기 2GiB, ZIP 컨테이너 크기 2GiB, ZIP 해제 후 총 크기 2GiB, 파일 5,000개다. 개별 일반 파일과 ZIP 내부 파일은 64MiB로 제한하며 ZIP 컨테이너에는 이 개별 파일 제한을 적용하지 않는다. 실제 기준 데이터를 두 업로드 방식 모두로 통과시키는 검증을 포함한다. 업로드·ZIP 처리는 디스크 임시 보관과 스트림을 사용한다. 전체 배치를 메모리에 올리지 않는다. ZIP 경로 이탈, 동일 경로 충돌 및 한도 초과는 명시적인 오류로 처리한다.

파싱은 Spring 내부의 제한된 작업 실행기로 수행한다. 대규모 큐 서비스나 별도 Python 파서를 추가하지 않는다. 상태와 시도 이력은 DB에 저장하며 frontend는 실제 상태를 조회한다. 진행률을 기존 목업의 고정 8/54/100% 타이머로 표시하지 않는다.

Run마다 원자적으로 결과를 등록한다. 정상 Run은 등록하고 실패 Run은 사유를 표시한다. 컨테이너 자체가 손상돼 Run을 식별할 수 없으면 배치 수준 오류로 표시한다. 실패·불완전 Run은 검색에서 제외하고 Run 관리에서 확인·재처리할 수 있다. 성공 버전 활성화와 결과 저장은 같은 트랜잭션으로 처리한다.

재시작으로 중단된 작업은 중단 사유와 재처리 가능 상태를 남긴다. 같은 요청이나 재처리의 중복 클릭으로 중복 등록하지 않는다. 새 UI에 취소·원본 다운로드 등 요청하지 않은 기능을 추가하지 않는다.

### 파일과 판정

- INI의 Pressure/Source/Bias와 단위가 있는 solver 로그에서 조건을 읽는다. 폴더에 조건 값이 있으면 교차 검증하고 충돌을 숨기지 않는다.
- 현재 INI의 `rfCycle`에는 실제 제어문자 값이 포함된다. 이 확인된 필드의 문법을 처리하고 원본을 보존한다. 모든 제어문자를 일괄 삭제하거나 정상 파일을 일괄 거부하지 않는다.
- 기본 등록 판정에는 조건·scalar를 읽을 INI와 solver 로그가 필요하다. 완료·수렴·화면 동등성에는 output/residual 로그 및 해당 조건에서 기대되는 출력이 필요하다.
- 필수 결과가 부족하면 `INCOMPLETE`, 문법이나 수치가 손상되면 `PARSE_FAILED`로 표시한다. 사유와 누락 경로를 보관한다.
- Bias=0이면 분포·파형 파일이 없는 것이 정상이다. IED Width는 `null`과 기존 비가용 이유를 유지한다.
- 완료, 파싱 성공, 품질 상태와 엄밀 수렴은 별도 필드다. 엄밀 수렴이 false라는 이유만으로 기존 정상 144개 Run을 검색에서 제외하지 않는다.
- 기타 XML/KRP/dump 등의 파일은 원본 집합과 파일 정보로 보관한다. 초기 파서에서 필요하지 않은 파일 내용을 임의 실행하거나 새 물리 모델로 해석하지 않는다.

fallback의 사용 가능 판정은 원본과 같이 `qualityStatus=VERIFIED`, `convergenceStatus=CONVERGED`, `catalogStatus=READY`를 모두 요구한다. 새 파서는 다음 대응 규칙으로 호환 필드를 만든다.

| 호환 필드 | 설정 조건과 의미 |
| --- | --- |
| `catalogStatus=READY` | 지원 형식의 조건·필수 scalar·예상 출력이 파싱되고 필수 수치가 유한함 |
| `qualityStatus=VERIFIED` | 조건·단위·출력 구성의 일관성 검증 통과. 물리 모델 자체를 검증했다는 의미로 확대하지 않음 |
| `convergenceStatus=CONVERGED` | `output.log`의 `INFO: Finished!`와 유효한 마지막 residual 행 확인. 원본의 완료 상태 호환 값이며 엄밀 수렴과 별도 |

필수 출력·완료 근거가 부족하면 `INCOMPLETE`, 손상된 문법·수치면 `PARSE_FAILED`이며 위 세 성공 값을 모두 갖지 않도록 한다. `strictConvergence`는 별도 계산한다. 기준 150개는 모두 검색 가능하고 그중 엄밀 수렴 6개만 true인 기존 동작을 보존한다.

원본 보관용 manifest와 기존 화면의 `sourceFiles`는 별도로 관리한다. manifest는 업로드한 전체 파일을 추적하고 중복 판정·재처리에 사용한다. 기존 상세·설명·기록의 `sourceFiles`는 Bias-off에서 `0d_setting.ini`, `solver.log`, `residual.log` 순서의 3개이며, Bias-on에서는 이어서 IED, IAD, IEAD의 `Ar+.txt`, `J0h_h.txt`, `pot.txt`, DEN의 `Ar+.txt`를 붙인 9개다. 상대경로·종류·크기 표시·순서를 유지한다. 완료 판정에 사용하는 `output.log` 등 전체 manifest 파일을 이 목록에 임의로 추가하지 않는다. 실제 Run 관리의 업로드 파일 목록에서는 전체 manifest를 조회할 수 있다.

### 기준 수치와 샘플링

아래 규약은 원본 수치와의 차등 검증으로 복원한 규약이다. 일반적인 과학 정의로 주장하지 않는다.

| 항목 | 기준 규약 | 조사 검증 범위 |
| --- | --- | --- |
| Flux | 원본 `#/cm²sec` → 기존 UI `10¹⁸ m⁻²s⁻¹`; 기존 값·표시 정밀도 유지 | 구현 시 150개 scalar 전수 비교 |
| IED Width | intensity 누적합의 실제 격자 P90−P10, 보간 없음, 유효숫자 8자리 | 125개 일치 |
| strictConvergence | 마지막 residual 행의 종별 잔차 절댓값 최대 ≤ INI conv | 150개 일치, true 6개 |
| 1D 샘플 | 양 끝점 포함, `roundHalfEven(i × (N−1)/(M−1))` 원본 인덱스 선택 | IED/IAD/current/potential 125개씩, residual 150개 일치 |
| residual 표시값 | 해당 원본 행의 종별 잔차 절댓값 최대 | 150개 일치 |
| IEAD | angle→energy 순서, 축별 원본 격자 선택 | 대표 Run 1개 확인, 구현 후 125개 전수 비교 필수 |
| density | phase 축 선택, 원본 distance 축 유지 | 대표 Run 1개 확인, 구현 후 125개 전수 비교 필수 |

표시 샘플 수는 IED 161, IAD 101, current/potential 각 121, residual 81, IEAD 31×61, density 41×31이다. 원본 current/potential 길이는 Run마다 다르므로 1201로 고정하지 않는다. 일반 `Math.round`로 half-even을 대체하지 않는다.

현재 기준 데이터보다 짧은 유효 1D 입력은 표시 길이를 원본 길이 이하로 제한해 원본 점만 선택한다. N=1이면 해당 점 하나를 사용하며 M−1로 나누지 않는다. 빈 출력, 모순되는 shape와 지원하지 않는 문법은 오류 또는 비가용 상태로 표시한다. 보간·임의 값·가짜 곡선으로 채우지 않는다. 2D 전체 동등성 검증이 끝나기 전에는 그래프 이관 완료를 선언하지 않는다.

## 7. 화면과 기록 동등성

### 공통 UI

원본 색상·타이포그래피·간격·모달·그래프·스크롤·toast·단위·배지·반응형 배치를 재현한다. 390/800/1008/1440px에서 비교한다. Enter/Space 카드 선택, 모달 Escape·focus trap·focus 복귀, live region과 reduced-motion을 보존한다.

상위 탭 변경, 후보 선택, 결과 탭, 참조 해제·더보기, 예시 입력은 기존 부작용과 실행 순서를 유지한다. 참조 칩은 6개 먼저 보여주고 나머지는 더보기로 표시한다. 선택한 후보 탭 전체가 후속 참조이며 새 숫자 조건은 전체 검색 가능 Run에서 검색한다.

### 검색과 설명

필수 수치·범위를 먼저 적용하고 방향 표현으로 정렬한다. 조건 없는 높게/낮게 질문은 입력 보충을 요구한다. 일치하는 실제 Run을 빠짐없이 반환하고 상위 몇 개로 자르지 않는다. 정확 일치/실제 최근접/검색 실패, 단위 변환, 근접도·차이의 의미를 그대로 유지한다.

Energy 이어질문의 +5~20 eV 범위를 필수 제약으로 적용한다. 개념·변화 설명에 실제 후보 조작 버튼을 추가하지 않는다. 비교 근거의 관찰/문서/가능한 해석/확인 불가 상태와 원본 파일의 비가용 이유를 유지한다.

### 두 기록 형식

- EXP 실험 기록: 채택 정확히 1개, 추가 후보 최대 2개, 추가 후보는 보류/반려만 가능. 채택은 2단계에서 고정하고 공통 코멘트·개별 메모·수치/평가 스냅샷을 저장한다.
- REV 기록: 데이터 탐색에서 한 Run을 채택·보류·제외로 판단하는 기존 흐름을 유지한다. EXP의 채택 1개 규칙을 적용하지 않는다.
- 카드/표 전환과 이전 단계 이동에서 선택·판단·작성 중 메모가 유지된다.
- 과거 판단 재사용은 기존의 명확한 비용 반려 규칙과 횟수 확인을 유지한다. 공통 코멘트를 개별 Run 사유로 추측하지 않는다.
- 사용자 메모는 안전한 텍스트로 표시한다. 당시 질문·시각·작성자·Run 버전·판단과 메모를 보존한다.

### 복원과 삭제

DB가 대화·판단 기록·현재 참조의 영속 저장소다. reload 시 Run 버전 조회와 기록 복원을 완료한 뒤 참조를 검증한다. 과거에 참조한 버전이 현재 검색 버전과 달라도 보존된 버전으로 상세를 연다.

| 조작 | 삭제 | 유지 |
| --- | --- | --- |
| 새 대화 | 현재 대화·기준 Run·후보 참조 | 판단 기록, Run 버전·그래프·원본 |
| 데모 데이터 초기화 | 대화·판단 기록·모든 참조 | Run 버전·그래프·원본·등록 데이터 |

삭제는 원자적으로 처리하며 후보 참조가 reload 후 부활하지 않게 한다. 판단 스냅샷이 대화 삭제에 따라 함께 사라지지 않게 한다.

비동기 저장과 초기화의 경합도 계약에 포함한다. 모든 상태 저장은 `workspaceEpoch`를 보내고 현재 대화·참조 저장은 `conversationEpoch`와 상태 revision도 보낸다. 새 대화는 대화 세대를, 전체 초기화는 workspace와 대화 세대를 삭제와 같은 트랜잭션에서 증가시킨다. backend는 workspace 행 잠금 안에서 세대를 검증한 뒤 저장하며 오래된 요청을 `409 STALE_CONTEXT`로 거부한다. frontend는 이전 세대의 저장·조회·Agent 응답을 중단하거나 폐기한다. 초기화 전에 시작한 요청이 나중에 도착해 삭제한 기록·참조를 재생성하지 않아야 한다. 현재 참조 수정은 revision 충돌도 확인한다.

원본의 대화 저장 키 v1, 판단 저장 키 v1, 참조 저장 키 v11과 기록 객체의 형식을 구분한다. EXP 객체는 `version=2`이며 legacy REV 객체에는 `version` 필드가 없다. 이를 같은 v2 형식으로 간주하지 않는다. 서로 다른 브라우저 origin에 저장된 과거 localStorage를 자동 읽는 기능은 초기 범위에 포함하지 않는다. 초기 앱에서 새로 저장한 기록의 reload 복원은 필수다.

## 8. API 계약과 오류

아래 리소스 경계를 기준으로 backend와 frontend 계약을 먼저 고정한다. 상세 DTO와 스키마는 구현 계획에서 작업 단위로 작성한다.

| API 영역 | 계약 |
| --- | --- |
| Run 목록·검색 데이터 | 최신 검색 버전의 scalar·상태·조건과 관리 화면용 실패/불완전 목록을 구분 제공 |
| Run 버전 상세·그래프 | 명시한 버전의 수치·품질·파일 정보·그래프 또는 비가용 사유 제공 |
| 적재 배치 | 폴더/ZIP 접수, Run별 작업·전체 진행·성공/실패 조회 |
| 재처리 | 보관한 원본으로 새 처리 시도를 생성, 과거 성공 버전을 유지 |
| 대화·참조 | 현재 상태 조회, 턴 스냅샷 저장, 참조 변경, 새 대화 |
| 판단 기록 | REV/EXP 저장 검증, 목록 필터, 당시 스냅샷 상세 |
| 기록 초기화 | 대화·판단·참조만 삭제하는 독립 계약 |

클라이언트 생성 요청에는 중복 등록 방지 식별자를 사용한다. 상태 저장의 세대·revision 검증은 중복 방지와 별도로 적용한다. 오류는 입력 부족, 파일 누락, 손상, 지원 형식 밖, 중복, 저장 실패, 중단, 오래된 상태 요청을 구분한다. 화면은 기존 안내·toast·상태 영역을 사용하며 실패를 성공처럼 표시하지 않는다.

저장 실패 시 작성 중 입력을 유지하고 미저장 상태를 알린다. 등록 작업 실패는 다른 성공 Run의 결과를 되돌리지 않는다. DB·원본 보관소가 준비되지 않으면 가짜 데이터로 대체하지 않고 원인을 안내한다.

## 9. 실제 데이터 공급과 GitHub

실제 기준 데이터는 저장소 밖의 패키지로 전달한다. 프로젝트 담당자가 원본 결과, 실제 `analysis-data.js`, 수정하지 않은 reference UI, 실제 기대값을 포함하는 기존 테스트 묶음을 버전·checksum과 함께 제공한다. 팀원은 이 패키지를 별도 경로에 두고 환경변수로 위치를 지정한다. 파일 전달 채널은 제품 실행 코드와 분리한다.

- 앱의 로컬 보관 경로는 `backend/storage/`를 기본으로 하고 설정으로 바꿀 수 있다.
- `KPLASMA_REFERENCE_ROOT`로 로컬 기준 패키지 위치를 지정한다. 특정 개발자의 절대 경로를 코드에 넣지 않는다.
- DB schema 마이그레이션과 실제 데이터 적재를 분리한다. 실제 값이 들어간 SQL seed를 커밋하지 않는다.
- clone만으로 실제 150개 Run이 생기지 않는다. 데이터가 없는 최초 실행은 빈 상태와 업로드 안내로 처리하고 가짜 Run을 생성하지 않는다.
- 원본 보관·적재 명령과 기준 데이터 비교 방법을 팀 실행 문서에 포함한다.
- 원본, 실제 결과 JSON, DB/사용자 기록·백업, 실제 데이터가 보이는 화면·검증 출력은 GitHub에 게시하지 않는다.
- 저장소와 CI에는 코드·schema·마이그레이션·설정 예시와 소량의 인공 테스트 fixture를 둔다. 인공 데이터를 실제 연구 결과로 제품에 표시하지 않는다.

현재 [`.gitignore`](../../../.gitignore), [AGENTS.md](../../../AGENTS.md), [CONTRIBUTING.md](../../../CONTRIBUTING.md)에 이 정책을 반영했다. `.gitignore`에 기대어 검토 없이 파일을 추가하지 않는다.

## 10. 검증과 완료 판정

### GitHub CI

빌드·TypeScript 검사·정적 검사, Java 파서/도메인 테스트, fallback 인공 데이터 테스트, API/저장 계약 테스트, 인공 데이터 기반 UI 테스트를 실행한다. 인공 fixture는 파일 문법·단위·half-even·비가용·검색 경계·기록 규칙을 검증하도록 직접 만든다. 실제 결과를 인공 fixture에 복사하지 않는다.

### 로컬 실데이터 필수 검증

1. 기존 102개 검증의 대응표를 만들고 각 assertion의 의미를 유지한다. 원본 JS의 구조 검사는 React의 실제 DOM·조작 검사로 대응시키며 검사 목적을 잃지 않는다.
2. 실제 기대값이 들어 있는 원본 테스트와 baseline payload는 외부 패키지에서 읽는다. 기존 검증을 원본에만 실행하고 새 구현 통과라고 보고하지 않는다.
3. 원본 150 Run을 실제 파서로 등록해 모든 조건·scalar·가용성·완료·품질·엄밀 수렴·파일 정보를 비교한다.
4. 125개의 2D를 포함한 모든 그래프의 좌표·값·shape·순서·샘플링을 전수 비교한다. 기존 8자리 수치 등 정확 일치 가능한 필드는 임의 오차로 완화하지 않는다.
5. 같은 브라우저·폰트·시간대·locale·고정 시각·초기 기록·데이터에서 reference와 React를 390/800/1008/1440px로 비교한다. 타임스탬프를 같은 값으로 고정하며 실제 내용 차이를 mask하지 않는다. 합의한 Run 관리 전환과 초기화 오류 수정만 차이 목록에 허용한다.
6. 검색·참조·결과 탭·Run 상세·격자·두 기록 형식·reload·삭제·부분 실패·중복·새 버전·재처리의 사용자 흐름을 실제 브라우저로 확인한다. 과거 버전을 기준으로 한 이어질문, 상세 조회 전후 가용성, 초기화 후 늦게 도착한 저장·조회 응답도 검증한다.

시각 기준은 레이아웃·문구·상태·간격·그래프가 같은 것이다. 고정 환경에서 설명되지 않는 시각 차이는 수정하며 광범위한 pixel tolerance로 숨기지 않는다. 검증 결과는 데이터가 없는 요약으로 기록하고 실제 화면·diff·원본 로그는 로컬에 보관한다.

데이터가 없으면 인공 테스트와 실제 동등성 결과를 구분한다. 전체 검증 명령은 기준 패키지가 없을 때 실패/미검증 상태를 명시하며 실제 동등성 통과로 처리하지 않는다. 초기 CI가 통과해도 로컬 실데이터 검증을 하지 않은 변경은 100% 이관 완료로 표시하지 않는다.

## 11. 협업과 범위

작업 브랜치 → PR → 필수 검증 → 작성자 외 팀원 1명 이상 승인 → Squash merge를 기본 절차로 한다. `main` 직접 push와 공유 브랜치 force push를 금지한다. schema와 계약 변경은 관련 소비자·마이그레이션·검증을 같은 목적의 PR에 포함한다.

현재 폴더는 GitHub의 `SJU-Capstone-2026/K-PLASMA-Analysis-Agent` 저장소와 연결되어 있다. 2026-10-03의 초기 설계·협업 문서 등록에 한해 사용자의 명시적 요청으로 `main` 직접 push를 허용한다. 이후 구현은 별도 작업 브랜치와 PR로 진행한다. 브랜치 보호·CI 설치·제품 scaffold·배포는 이번 문서 등록에 포함하지 않는다.

후속 범위는 실제 Agent 연결, 팀 공용 서버·DB·파일 보관소, 공용 환경의 사용자·접근 권한, 추가 simulator 형식이다. 현재 이관에서는 새 물리 시뮬레이션 실행, 자유 과학 질의, 예측·보간·최적 레시피 생성을 추가하지 않는다.
