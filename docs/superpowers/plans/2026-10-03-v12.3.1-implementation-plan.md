# K-PLASMA v12.3.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 고정된 3변수·150 Run을 대상으로 v12.3.1의 화면과 fallback을 실제 업로드·파싱·PostgreSQL 저장 기능에 연결한다.

**Architecture:** React가 기존 JavaScript fallback 라이브러리를 호출하고 Spring이 원본 파일·파싱·Run 버전·사용자 기록을 관리한다. frontend와 agent는 npm workspace, backend는 Gradle 프로젝트다. 서로 같은 데이터 계약을 사용하는 하나의 제품이며 별도 Agent 서버는 두지 않는다.

**Tech Stack:** Java 21, Spring Boot 4.1.1, Gradle, JPA, Flyway, PostgreSQL 18, React, TypeScript, Vite, npm workspaces, JUnit, Testcontainers, Vitest, Playwright.

**Spec:** [승인된 구현 설계](../specs/2026-10-03-v12.3.1-implementation-design.md), [원본 조사 기록](../research/2026-10-03-v12.3.1-discovery.md).

작성일: 2026-10-03. 설계 승인 완료. 사용자가 계획과 권장 작업별 구현·검토 방식을 승인했으며 구현을 시작한다. 아래 작업은 승인된 구현 기준이며 각 체크박스와 말미 검증 기록은 실제 구현·리뷰·실행 상태를 나타낸다.

## Global Constraints

- 제품 코드는 `backend/`, `frontend/`, `agent/`에 둔다. 문서·실행 설정·검증 스크립트는 루트의 보조 파일로 둔다.
- 사용자 확정: Pressure `[2,4,6,8,10]` × Source `[100,200,300,400,500]` × Bias `[0,200,400,600,800,1000]`, 총 150 Run을 사용하며 데이터 범위 확장은 이번 목표가 아니다.
- 기존 Run을 backend에서 업로드·조회한다. 고정 데이터라는 이유로 실제 수치 payload를 frontend 소스에 다시 넣지 않는다.
- Java 21, PostgreSQL 18 계열, Node 22의 지원 패치이면서 최소 22.12 이상. Gradle Wrapper는 Spring Boot 호환 범위인 8.14 이상 또는 9.x에서 하나를 고정한다.
- 원본 CSS·문구·질문 해석·정렬·수치·그래프·키보드 동작을 보존한다. 시각 비교 폭은 390/800/1008/1440px이다.
- Run 관리의 목업을 실제 폴더/ZIP 업로드·재처리로 전환하고, 초기화는 대화·판단·참조만 삭제한다. 등록한 Run·그래프·원본은 유지한다.
- 원본 업로드는 폴더 총 2GiB, ZIP 컨테이너 2GiB, ZIP 해제 후 총 2GiB, 5,000파일. 개별 일반 파일·ZIP 내부 파일은 64MiB이며 ZIP 컨테이너 자체에는 적용하지 않는다.
- 실제 원본·분석 JSON·기록·DB·실데이터 검증 화면은 GitHub에 올리지 않는다. 공개 테스트에는 소량의 인공 데이터를 사용한다.
- 실제 Agent·LLM·Python 서비스·RAG·공용 서버·로그인은 후속 범위다. 없는 수치·곡선·가상 Run을 생성하지 않는다.
- 원본은 수정하지 않는다. 구현은 작업 브랜치에서 진행하고 PR로 반영한다. 초기 문서 등록에 대한 main 직접 push 예외는 종료됐다.

### 데이터 경계

- `RunRef = { runId: string; runVersionId: string }`. 표시 ID와 내부 버전 UUID를 구분한다.
- `RunSummary`는 RunRef, pressure/sourcePower/biasPower, 원본 metrics·units, 검색/격자에 쓰는 analysis scalar, 품질·완료·등록 메타데이터를 포함한다. 그래프 배열은 포함하지 않는다.
- `FullRun`은 RunSummary와 원본 전체 `analysis`, `iedDistribution`, 표시용 `sourceFiles`를 포함한다. 원본 payload의 필드·배열 구조는 Task 2에서 고정한다.
- `AgentRequest = { text, baseline?: RunRef, candidateReferences: RunRef[], clarification?: object }`.
- `AgentContext = { latestCandidateReferences?: RunRef[], candidateRunsLatest: RunSummary[], referenceRunsByVersion: ReadonlyMap<string, FullRun>, decisionRecords: DecisionRecord[], hydrateFullRun(ref: RunRef): Promise<FullRun> }`.
- `executeFallback(request: AgentRequest, context: AgentContext): Promise<AgentResponse>`. AgentResponse는 원본 intent·status·후보·설명·답변 스냅샷을 보존하고 사용한 RunRef를 담는다.
- Task 10/R12: `latestCandidateReferences`는 최신 후보 그룹 턴의 현재 UI와 저장된 RunRef에서 만든 런타임 전용 문맥이다. 기록 재사용의 참조 순서는 명시 재시도 참조 → 언급한 최신 후보 그룹 → 현재 참조 → active Run이며, 수치 검색은 전체 최신 Run을 유지한다. threshold/undo는 `clarification.useSuppliedMemoryReference=true`로 저장 당시 참조를 명시한다. HTTP/OpenAPI/Java DTO는 변경하지 않는다. R15: 압축 snapshot의 `candidateRunRefs`는 후보 조작·EXP·그래프의 버전을, `excludedRunRefs`는 제외된 검색 결과의 버전을, `memoryRequest.referenceRunRefs`는 재시도의 저장 당시 참조 버전을 구분한다. 제외 결과와 재시도 참조의 표시 ID가 같아도 각 역할의 불변 버전을 유지한다. `usedRunRefs`는 전체 hydrate 목록이며 역할 조회에 표시 ID만으로 사용하지 않는다. 외부 원본 비교는 이 세 ID 메타데이터만 분리 검증하고 물리 수치·질문·상태는 그대로 비교한다.
- `StateToken = { workspaceEpoch: number; conversationEpoch: number; revision: number }`. 기록 저장은 workspaceEpoch, 현재 대화·참조 저장은 전체 StateToken을 검증한다.
- `TurnUiSnapshot`은 원본의 collapsed/openRunIds/runDetailTabs/activeCandidateGroup/continuedRunId/lookupExpanded/selectedCandidateRunId를 보존한다. `TurnSnapshot`은 id/askedAt/question/intent/context(선택 RunRef)/answerRunRefs/answerSnapshot/ui를 포함한다. answerSnapshot에는 전체 Run·그래프를 중복 저장하지 않는다.
- `ReferenceState = { kind: "단일 Run" | "후보 집합"; runs: RunRef[] } | null`. `WorkspaceView`는 StateToken과 conversation(version=1, activeRun, turns), candidateReference를 포함한다. 상위 화면·탐색 필터·작성 중 입력은 원본처럼 일시 UI 상태로 유지한다.
- `DecisionRecord`는 원본 REV와 EXP의 구별된 합집합이다. REV에는 version이 없고 EXP에는 `version: 2`가 있다. 일반 EXP 입력은 채택 1개와 추가 후보 최대 2개를 검증한다.
- Java DTO의 JSON 필드명은 위 이름과 동일하게 한다. 숫자는 JSON number, 비가용 값은 null, 시각은 ISO 8601, ID는 string이다. 내부 파일 경로는 응답하지 않는다.
- 오류 형식은 `{ code, message, field?, details?, requestId }`. 설계의 오류 구분에 더해 오래된 기록 요청은 HTTP 409와 `STALE_CONTEXT`를 사용한다.

Java의 `RunRef`, `Summary`, `Full`은 `RunDto.java`의 nested record다. `StateToken`, `TurnUiSnapshot`, `TurnSnapshot`, `ReferenceState`, `WorkspaceView`, `DecisionWrite`, `DecisionRecord`는 `WorkspaceDto.java`, `UploadManifest`, `BatchView`, `CatalogView`는 `ImportDto.java`에 정의한다. 작업의 짧은 타입명은 이 nested record를 import한 표기다. Task 2에서 원본 형식에 맞춰 각각의 세부 필드까지 명시한다. 질문의 숫자는 등록된 격자 밖 값도 받아 최근접 조회를 유지한다.

`CatalogView`는 `runs`, `jobs`, 버전 UUID별 실제 3/9개 표시 파일 메타데이터 `sourceFilesByVersion`을 포함하며 그래프 배열은 싣지 않는다. 작업 파일 조회는 정확한 source_root 디렉터리 경계 안의 OS·보조·output.log 파일까지 보존하고 형제 Run·배치 밖 보조 파일을 섞지 않는다. 빈/dot root는 전체 선택 Run 업로드를 뜻하며, 배치 수준 파일은 보관소에 유지한다. 재처리는 같은 sourceId와 이 작업 범위 전체 원본 lineage를 새 작업에 보존한다.

BatchView는 `batchId`, `status`, `receivedBytes`, `totalBytes`, `processedRuns`, `totalRuns`, `jobs[]`를 포함한다. 작업 상태는 QUEUED/PROCESSING/READY/DUPLICATE/INCOMPLETE/PARSE_FAILED/INTERRUPTED, 배치 종료 상태는 SUCCESS/PARTIAL_SUCCESS/FAILED이다. 상태와 scalar·그래프 저장의 원자성은 Task 7이 책임진다.
