# Agent v3 규칙 기반·RAG 비교 실험 방법 — 초안

작성일: 2026-11-11. [팀 개발 규칙](agent-v3-team-development-draft.md)의 독립 복제 원칙을 따른다.
목표는 **같은 질문을 규칙 기반만으로 처리했을 때와 규칙 기반에 RAG를 더했을 때의 차이**를 평가하는 것이다.
이번 문서 작성은 유료 실행 승인이 아니며, v3 실행기·모드 옵션·신규 평가 문항은 아직 구현·확정하지 않았다.

## 1. 비교 조건

| 조건 | 구현 | 규칙 기반 | RAG | 역할 |
| --- | --- | --- | --- | --- |
| 보존 v2 | 고정된 기존 코드 | 새 기능 없음 | 없음 | 기존 성능 기준. 과거 결과와 동시 재실행 결과를 구분한다 |
| v3 도구 추가 전 | 독립 복제한 v3 | OFF | OFF | 우선 인공 응답으로 복제·연결의 동작 대응 검사 |
| A | 동일 v3 커밋 | ON | OFF | 주 비교군 |
| B | 동일 v3 커밋 | ON | ON | RAG 추가군 |

A/B는 코드·공통 지시문·모델·추론 수준·Run/메모 스냅샷·정답·HITL 행동·예산을 같게 한다.
RAG ON에 필요한 기능 노출과 검색·근거 추가만 의도된 차이로 허용하고 실제 차이를 manifest에 기록한다.
별도 도구 추가가 계획 선택까지 바꾸면 이 결과는 RAG를 포함한 전체 Agent 효과이며 검색기 단독 효과로 부르지 않는다.

## 2. 평가셋은 세 종류를 구분한다

| 평가셋 | 확인할 내용 | 정답 |
| --- | --- | --- |
| 기존 Agent 고정 40문항 | 경계·단위·정렬·조회·비교·개념·HITL의 회귀 | 기존 독립 정답 유지 |
| 신규 기록 검색·RAG 문항 | 같은 질문에서 규칙 기반과 RAG 추가의 차이 | 검색 대상 기록·관련성·최종 후보와 근거의 독립 정답 |
| Decisions 단독 80회 | 고정 계획의 의미 일치 판별 | 정상 40·오류 40의 사전 정의 라벨 |

기존 40문항만으로 새 기록 검색의 정확도를 검증했다고 하지 않는다.
신규 문항은 직접 표현·동의어·부정/불확실 표현·복수 기록 충돌·0건·근거 부족·
수치 검색 후 기록 제외 후 비교·HITL 선택·설명까지 포함한다.
예시 요구는 “비용 때문에 반려된 후보를 제외하고 선택한 두 Run을 비교해줘”처럼
검색과 후속 작업을 연결하는 것이다. 예시를 동결 문항이나 실제 정답으로 간주하지 않는다.

개발용 질문과 최종 비교 질문을 구분하고, 정답은 실행 결과·Decisions PASS·RAG 반환값에서 만들지 않는다.
모델에 주는 검색 코퍼스에는 정답 라벨·평가 해설을 섞지 않는다.
질문·정답·Run/메모·코퍼스·인덱스에는 버전과 해시를 붙이고 실험 도중 수정하지 않는다.

## 3. 실행 전 고정·검사

- v2 보존 SHA, v3 SHA, 설정·프롬프트·스키마 digest와 의존성 잠금 버전을 기록한다.
- 1차 비교의 제안 모델은 계획·답변·Decisions 모두 `gpt-6-luna`, 계획·재계획·답변 추론은 `low`다.
  Decisions API가 effort 설정을 노출하지 않는 사실도 기록한다.
- 계획 의미 Decisions ON을 설정과 실제 그래프 상태의 `plan_review_enabled=true`로 확인한다.
  비활성·검토 생략 경로로 실제 평가를 시작하지 않는다.
- 모델 timeout 90초, 요청 전체 재계획 최대 2회·답변 재작성 최대 1회와 동일 모델 호출 상한을 유지한다.
- RAG의 검색 방식·embedding/reranker 모델·top-k·근거 채택 규칙·인덱스 스냅샷을 고정한다.
  구체적인 값은 구현 설계와 사전 검사에서 확정하며 여기서 존재하지 않는 설정을 가정하지 않는다.
- 평가 전용 DB·storage·대화·캐시를 사용한다. A/B가 서로의 실행 결과나 새 판단 기록을 읽지 않게 한다.
- 고정 사용자 선택을 정하고 실제 pending ID·revision·선택지에 맞춰 재개한다. 선택 불가나 예정에 없는 추가 질문은 그대로 기록한다.
- Phoenix 연결은 모델을 호출하지 않는 trace로 먼저 확인한다. 요청·조건·문항·반복·버전으로 추적을 연결한다.

## 4. 실행 순서와 횟수 제안

먼저 무료 검사로 v2 보존, v3 독립성, 도구 OFF의 호출 0회, 모드 고정·재시작, 인공 정답과 UI를 검사한다.
그다음 사전에 승인한 유료 실행 목록만 수행한다. 실패를 통과로 바꾸려고 문항을 자동 재실행하지 않는다.

같은 문항을 A/B 각각 새 대화에서 실행한다. 문항별 A→B와 B→A를 균형 있게 배치하고 순서를 미리 고정한다.
이 순서의 seed는 실행 순서 재현용이며 LLM 응답의 동일성을 보장하는 seed가 아니다.
웹은 실제 입력·버튼·선택창·화면을, API는 실제 backend의 접수·대기·재개·저장을 사용한다.

| 범위 | 1회 비교의 질문 실행량 |
| --- | ---: |
| 기존 40문항 × 웹/API × A/B | 160회: A 80 / B 80 |
| 신규 N문항 × 웹/API × A/B | 4N회 |
| 보존 v2의 기존 40문항을 같은 시점에 재평가하는 경우 | 별도 80회 |
| Decisions 단독을 재평가하는 경우 | 별도 80호출 |

이 수는 제안 산식이지 이번 실행 지시가 아니다. 신규 N, 반복 수, 웹/API 범위와 비용을 확정한 뒤 실행한다.
과거 v2 결과를 참고하면 새 유료 80회를 추가하지 않는다. 3반복을 원하면 해당 비교 범위의 실행량도 3배다.
질문 실행량과 계획·검토·재계획·작성의 실제 유료 모델 호출 수는 따로 집계한다.
기존 단일 회차 이름을 덮어쓰지 않고 v3 실험 ID 아래 A/B·웹/API·문항·반복을 구분한다.

## 5. 판정 지표

### 검색·규칙 기능

관련 기록과 최종 제외/유지 후보를 사전 정답과 대조한다. 잘못 제외한 비율과 놓친 비율을 구분한다.
순위 검색을 사용하면 고정 k의 precision/recall과 근거 적합성을 보고한다.
정답 관련 기록이 0건인 문항은 recall 평균에 억지로 넣지 않고 불필요한 검색·근거 생성 여부로 따로 판정한다.
검색 결과가 실제 기록 ID·원문 위치·Run 버전에 연결되는지, 근거 없음·불확실·오류를 구분하는지 확인한다.

### Agent 전체 흐름

요청 이행, 도구 선택·순서·입력, 후보 집합·정렬·수치·단위, HITL 재개,
답변의 근거와 한계, 최종 저장 상태를 검사한다. 계획이나 검색만 맞아도 최종 통과로 올리지 않는다.
자동 정답 검사와 독립 답변 검토 성적을 분리한다. 검토 주체가 사람·주 에이전트·별도 심사 모델 중 누구인지 밝힌다.
가능하면 검토자에게 A/B 조건을 가리고, 별도 유료 심사 모델은 횟수·비용을 추가 승인받는다.

### 화면·복구·비용

웹은 390/800/1008/1440px에서 표·그래프·선택창·인용·수식·오버플로·새로고침 복원을 확인한다.
화면 자동 통과와 답변 내용 통과를 별도 보고하고 API 결과만으로 화면을 검증했다고 하지 않는다.
최초 계획 통과, Decisions 지적, 재계획 후 최종 통과·실패, 답변 재작성을 구분한다.
정해진 요청 내부 복구는 새 평가 질문으로 세지 않는다. RAG 호출이 최초 실패를 복구했는지와
계획 Decisions가 오류를 잡아 복구했는지도 서로 다른 지표로 남긴다.

지연 시간, 모델·검색 호출 수, 제공자의 입력·출력·추론 토큰, timeout·HTTP·연결·출력 한도 종료를 집계한다.
로컬 기록과 Phoenix의 요청별 usage를 대조한다. 미반환 usage는 0으로 만들지 않으며 추론 토큰을 출력에 다시 더하지 않는다.

## 6. A/B 비교 보고

| 같은 문항의 최종 결과 | 해석 |
| --- | --- |
| A 통과 / B 통과 | 유지 |
| A 실패 / B 통과 | RAG 추가 조건에서 개선 관측 |
| A 통과 / B 실패 | RAG 추가 조건에서 회귀 관측 |
| A 실패 / B 실패 | 미해결 |

웹/API·기존/신규 문항·조건별 통과율과 위 대응표를 함께 보고한다.
전체 통과율만으로 기존 기능의 회귀를 감추지 않는다. 한 번의 확률적 실행 결과를 보편적 정확도나 단일 구성요소의 인과 효과로 확정하지 않는다.
허용 회귀 기준은 실행 전에 팀이 정한다. v2 코드 보존과 v3 성능 유지는 서로 다른 검증 항목이다.

## 7. 현재 실행 가능한 명령과 공개 범위

현재 명령은 [v2 평가 실행 안내](https://github.com/SJU-Capstone-2026/K-PLASMA-Analysis-Agent/blob/e6ea1b8a05fc83fe75acc8ce6189c456ff28c59e/docs/development/agent-v2-evaluations.md)의 Decisions 단독·v2 웹/API 평가다.
v3를 선택하거나 모드를 전달하는 옵션은 아직 없으므로, 다음 명령을 v3 A/B 실행기로 표시하지 않는다.

```sh
# 현재 구현된 v2 Decisions 단독 80회
npm run eval:decisions:local -- --env-file /path/to/eval.env --output /tmp/decisions-run-001

# 현재 구현된 v2 Agent 웹 40 / API 40
npm run eval:agent:local -- --live --bundle /path/to/private-bundle --connection /path/to/connection.json --env-file /path/to/eval.env --output /tmp/agent-run-001
```

v3용 실행기·모드 사전 검사·문항·정답을 구현한 뒤 실제 명령과 새 실행 ID를 이 문서에 추가한다.
집계 성적·방법·설정·실패 요약은 문서·PR에 공개할 수 있다. 물리 실험 파일, 실제 Run payload,
사용자 원문을 담은 응답·trace·스크린샷·DB와 비밀값은 로컬에 둔다. 유료 평가를 CI에 연결하지 않는다.
