# K-PLASMA Agent v2 운영과 평가

새 대화에서 Agent 버전 v2를 선택한다. 첫 요청이 수락되면 대화의 버전이 저장된다. 운영 기본 버전은 v1이다.

- 계획과 재계획은 기본적으로 `gpt-6-luna`의 `low`를 쓴다. `AGENT_V2_PLAN_MODEL`과 `AGENT_V2_PLAN_REASONING_EFFORT`로 조정한다.
- 답변 작성도 기본적으로 `gpt-6-luna`의 `low`를 쓴다. v2의 계획·재계획·답변 작성·Decisions 모델 기본값은 모두 `gpt-6-luna`다. `AGENT_V2_ANSWER_MODEL`과 `AGENT_V2_ANSWER_REASONING_EFFORT`로 답변 모델과 추론 수준을 조정한다.
- 계획 의미 검토와 최종 해석 검토는 Decisions의 `gpt-6-luna`를 기본으로 사용한다. `AGENT_V2_DECISIONS_MODEL`과 `AGENT_V2_DECISIONS_BASE_URL`은 별도 설정이다.
- 계획 스키마 2는 `request_mode`를 유지하고 `interpretation_requested`를 제거한다. `explain_answer`가 없는 조회·수치 비교·그래프 요청은 검증된 도구 결과로 바로 완료한다. 표와 그래프는 웹이 표시한다.
- 확인된 두 Run의 비교가 이미 제공하는 절대 차이와 요청한 파형 폭은 계획 검증에서 재사용한다. 후속 단계가 값을 참조하는 계산은 실행 계획에 남긴다.
- 기준 Run을 사용자가 직접 고르겠다고 하면 계획은 기준 확인 단계와 후속 비교를 지정한다. 코드는 그 비교의 Run 목록을 선택창에 표시하고, 선택값을 비교 기준으로 연결한 뒤 같은 요청을 재개한다.
- 경향·의미·이유를 요청하면 답변 모델로 해석을 작성하며, 작성된 해석이 있을 때 Decisions로 근거를 검토한다. 일반 개념 답변은 답변 모델을 거친다.
- 해석에 필요한 실험 수치는 모델이 인용한 근거에서 코드가 수치와 단위를 채운다. 수치 표현 자체는 재작성 조건이 아니다.
- 입력 예산은 로컬 `o200k_base` 추정으로 검사한다. 네트워크 제한 환경은 실행 전에 인코딩 캐시를 준비한다. 실제 사용량은 제공자 응답을 기준으로 기록한다.

## explain_answer와 계획 스키마 2

v2 계획의 도구는 `forward_lookup`, `reverse_search`, `compare_runs`, `explain_answer`다. `derive` 계산과 `await_input` 제어 단계는 유지한다. PLAN 지시문은 역할·요청 모드·요구사항·검색·비교/HITL·지표/계산·재계획 절로 구분하며 모든 지침을 한 계획 호출에 제공한다.

- `general_only`: 요구사항을 비우지 않고 `explain_answer(mode=concept)` 한 단계에 연결한다.
- `data_request`: 실제 데이터 작업을 수행한다. 설명이 없으면 코드 결과만 표시한다.
- 설명이 필요하면 마지막에 `explain_answer` 하나를 둔다. 다른 모든 실행 단계가 선행해야 하고 `run_if`·`requires`는 빈 배열이다. 다른 단계가 이 설명을 참조하지 못한다.
- `concept`는 개념 설명이며 실제 Run 결과를 설명 근거로 모델에 제공하지 않는다. 혼합 요청은 데이터 결과와 일반 개념 설명을 함께 저장·표시한다.
- `results`는 선행 조회·검색·비교의 검증된 근거를 설명한다. 개념 설명과 결과 해석을 함께 요청하면 같은 단계가 처리한다.
- 설명 실행·검토·최대 1회 재작성은 기존 답변 모델 시도 기록을 재사용한다. 수치 실행 예약·결과에는 가짜 설명 Run을 만들지 않으며, 계획 ID와 담당 요구사항은 작성 모델 입력에 보존한다.

새 worker는 계획 스키마 2를 제출하고 과거 완료 답변 스냅샷 스키마 1은 계속 읽는다. 서버는 저장된 계획 1과 새 계획 2를 구분해 수락하며 DB 마이그레이션은 없다. 실행 중인 스키마 1 요청은 기존 worker로 마친 뒤 worker를 갱신한다. 계획 계약 변경 후 예전 의미 검토를 승인으로 재사용하지 않는다.

## 실행 전 계획 의미 검토

계획 검토를 켠 v2 데이터 요청은 코드가 계획 구조·참조·단위를 검사한 다음, Decisions가 원문과 실제 실행 입력을 대조한다. 한 HTTP 요청 안에서 필터 지표별 수치·단위·경계, 정렬, 비교 대상·출력·기준·경향 축, derive 연산, 선택 개수·출처와 조건부 실행을 독립적으로 판정한다. 요청 작업·필터/독립 그룹·선택 단계의 누락도 검사하므로 조건을 통째로 빼도 검사 자체가 사라지지 않는다. 모든 항목이 `match`일 때만 신규 도구를 실행한다. 원문을 코드로 파싱하지 않고 실제 계획에서 검사 위치를 만든다. 확률·confidence는 기록하며 분기에 쓰지 않는다.

불일치나 판정 불가는 기존 재계획 경로와 요청 전체 최대 2회 한도를 공유한다. 검토 API 장애·잘못된 응답·입력 예산 초과는 성공이나 0건으로 바꾸지 않고 실행을 중단한다. 통신 자동 재시도는 없다. 스키마 2에서는 순수 개념도 실제 설명 단계가 있으므로 실행 전 계획 의미 검토를 받는다. 최종 개념 설명의 해석 Decisions는 생략한다. 단순 데이터 요청은 계획+계획 검토 2회, 개념 설명은 계획+계획 검토+작성 3회, 결과 해석은 계획+계획 검토+작성+해석 검토 4회가 정상 경로다. 전체 모델 요청 13회 상한은 유지하며 `PLAN_REVIEW`는 최대 3회다.

`AGENT_V2_PLAN_REVIEW_ENABLED`의 기본은 `true`다. `false`는 새 요청의 계획 검토를 끄고 `SKIPPED`로 기록하는 명시적 운영 롤백 설정이며, 실제 Agent 평가에는 사용할 수 없다. 실제 평가는 이 설정이 꺼져 있으면 시작하지 않는다. 시작한 요청은 설정을 고정한다. 계획 revision·원문/입력·계획 digest·프롬프트 버전과 조건별 결과를 내부 모델 시도 및 체크포인트에 저장한다. schema 2 결과는 현재 검사 집합 전체와 대조한다. schema 1 과거 기록은 읽되 새 실행 승인으로 재사용하지 않는다. 정해진 HITL 선택은 통과한 계획을 재사용하고, 계획 밖 조건·대상 변경은 새 계획과 검토가 필요하다.

검토 입력에는 원문, 전체 계획, 확인된 Run 별칭·버전, 도구 계약을 보낸다. `execution_view`와 `program_effects`는 **실제 계획 입력에서 코드로 만든 보조 표시**이며 원문을 다시 해석하거나 조건을 보정하지 않는다. 미사용 null, 범위의 min/max, 검색 조건의 AND, 비교 도구 내부 특징값 계산, 결과 참조의 단위 상속을 명시한다. 미래 측정값이나 전체 파형을 요구하지 않는다. 숫자 입력에 수치 목록을 연결한 타입 오류는 코드가 실행 전에 반려하고 기존 재계획으로 보내며, 실제 데이터 누락과 구분한다. 이 검토 역시 모델 판단이므로 정확도는 독립 정답으로 평가해야 한다.

반려 choice는 `value_changed`, `unit_changed`, `boundary_changed`, `direction_changed`, `target_changed`, `missing`, `unexpected` 등 해당 항목에 허용된 유형이다. `unclear`도 실행 승인으로 보지 않는다. 코드가 저장된 입력에서 `condition_id`, 원문 `sources`, 실제 `plan_values`의 JSON pointer와 값을 연결해 `checks[].issue` 및 `plan_review_feedback.issues`에 남기고 기존 재계획 모델로 보낸다. 이 증거를 Decisions가 새로 생성하게 하지 않는다. 자유로운 이유 문장이나 과거 내부 추론을 제공하는 기능은 아니며, 원문과 값의 의미가 다른지는 여전히 모델 판정이다. 이 내부 기록은 공개 진행 이벤트나 채팅 본문에 자동 노출하지 않는다.

## 진행 기록과 답변 스트리밍

v1과 v2 모두 실제 실행 이벤트로 회색 진행 기록을 표시한다. 사용자 질문과 AI 기본 본문은 공통 본문 크기인 15px를 사용한다. 진행 기록·작성 상태·완료 시간은 14px로 표시한다. 질문 확인, 계획 검증, 검색, 비교, 내부 계산, 사용자 입력 대기, 작성, Decisions 검토, 수정과 저장을 구분한다. 화면 문구를 만들기 위한 모델 호출은 없다. 내부 추론이나 전체 계획 JSON은 공개 이벤트에 포함하지 않는다.

- 진행 중에는 최근 완료 작업 3개와 현재 작업을 표시한다. 이전 기록은 펼쳐 볼 수 있다.
- 실행·큐 대기 중에는 입력창 오른쪽 전송 버튼이 사각형 정지 아이콘으로 바뀐다. 기존 취소 API로 요청을 중지하며, 취소 요청 중 중복 클릭을 막는다. 완료·실패·취소 후에는 전송 버튼으로 돌아간다. 사용자 선택 대기의 취소 동작은 기존 입력 확인 화면에 유지한다.
- 저장이 끝나면 기록을 접고 `38초 동안 작업함`과 구분선을 답변 위에 표시한다. 시간은 서버의 RUNNING 구간 누적값이다. 큐 대기와 사용자 선택 대기는 제외하며, 과거 요청에 기록이 없으면 추정해서 추가하지 않는다.
- v1 일반 답변과 v2 일반 답변·실험 해석은 제공자가 생성하는 텍스트를 즉시 전송한다. 완성 답변을 타자 효과로 재생하는 방식이 아니다. 해석은 작성 중·검토 중임을 구분한다.
- v2 구조화 응답의 JSON과 근거 ID는 본문으로 노출하지 않는다. 수치 자리표시자는 인용 근거가 확정된 뒤 기존 코드와 같은 함수로 실제 값·단위로 채운다. 불완전한 수식은 끝 구분자를 받을 때까지 보류한다.
- 검토에 따라 재작성하면 해석 영역만 비우고 같은 자리에서 수정문을 스트리밍한다. 이미 검증된 표·그래프는 유지한다. 재계획 2회·답변 수정 1회 한도와 기존 최종 표시 정책은 유지한다.
- 단순 조회·수치 비교·그래프는 계획 의미 검토 후 작성 모델과 최종 해석 Decisions를 호출하지 않는다. 검증된 도구 결과는 최종 저장 전에도 읽기 전용으로 표시한다.
- 최신 메시지를 따라 읽을 때만 높이 증가에 맞춰 내려간다. 이전 대화를 읽고 있으면 위치를 유지하고 작은 아래 화살표로 최신 답변에 이동한다.

입력창의 하단 여백은 `frontend/src/prototype/styles.css`의 `:root` 안에 있는 `--agent-composer-bottom-gap` 하나로 조절한다. 기본값은 28px이다. 값을 키우면 입력창이 위로, 줄이면 아래로 이동한다. 페이지 하단 여백과 sticky 위치에 같은 값을 사용하며 모바일 안전 영역은 보존한다.

백엔드의 `V17__agent_public_events.sql`이 공개 이벤트와 실행 시간 필드를 추가한다. 이벤트는 요청별 순번과 중복 방지 키로 저장한다. worker의 claim generation·요청 revision·lease를 검사해 취소되거나 만료된 worker의 전송을 거절한다. 완료 저장과 종료 이벤트는 같은 트랜잭션으로 처리한다.

웹은 `GET /api/agent/requests/{id}/events?after={seq}`의 SSE를 구독한다. 연결 실패 시 같은 순번으로 `format=json` 이벤트 조회를 사용하며, 기존 요청 상태 조회도 최종 저장 상태 확인에 유지한다. `results.ready`는 해당 순번의 읽기 전용 결과 조회로 연결한다. 정확한 필드는 OpenAPI와 `agent/src/contracts/progress.ts`를 따른다.

새로고침이나 채팅방 복귀 시 저장된 초안·이벤트 순번을 복원한다. 복원을 위해 모델이나 도구를 다시 실행하지 않는다. 입력 대기·종료 시 연결을 닫고, 방 이동 시 이전 방의 늦은 응답을 반영하지 않는다. 진행 전송 장애가 최종 답변 생성을 다시 호출하게 하지는 않는다.

로컬 브라우저 회귀 검사는 실행 중인 실제 DB 대신 인공 API 응답을 사용한다.

```sh
npx playwright test --config frontend/streaming.playwright.config.ts
```

변경 후 실측과 남아 있는 해석 한계는 [스트리밍 검증 기록](../verification/agent-streaming.md)에 정리한다. 배포를 되돌릴 때는 코드를 이전 버전으로 되돌리되 대화 보존을 위해 이 마이그레이션이나 이벤트 테이블을 삭제하지 않는다. 추가 응답 필드는 선택 항목이며 기존 최종 답변 계약은 유지한다.

로컬 검증은 JDK 21, Docker, 잠금 파일의 Python 환경, Playwright 브라우저를 준비한 후 실행한다.

```sh
uv sync --project agent/python --frozen --extra tracing
uv run --project agent/python --frozen python -c 'import tiktoken; tiktoken.get_encoding("o200k_base")'
npm run test:e2e:v2
npm run test:e2e:v2 -- --live
```

첫 브라우저 명령은 인공 Run과 스크립트 모델을 사용한다. `--live`는 인공 Run이 등록된 격리 앱에서 v2를 실제 API로 실행한다. 일반 개념, 엄격한 검색 경계, 사용자 선택 후 비교→max→검색을 검사하며, 실제 모델 실행에서도 실패 상태나 틀린 후보는 비정상 종료한다. 질문별 판정, 화면에 표시된 답변과 스크린샷은 명령이 출력한 임시 폴더에 저장한다. `KPLASMA_VERIFY_ENV_FILE`로 평가용 모델 환경을 지정할 수 있다. `test:e2e`와 `test:e2e:live`도 각각 같은 v2 명령이다.

## 기본 CI의 검사 범위

`Synthetic verification / verify`는 PR과 main push에서 아래 순서로 실행한다. LLM API를 호출하지 않는다.

1. `npm run test:agent`: `pytest-v2.ini`가 지정한 v2 계약·계획·도구 실행·추가 입력·스트리밍·계획/답변 검토·평가기 검사와 공통 수치·단위·진행·관찰 회귀 검사. 평가기는 고정 모델 응답으로 검사한다.
2. 성능 측정기의 작은 정확성 검사, Python lint/type, 공개 파일 검증, frontend/공통 계약 단위 검사, TypeScript/lint/build와 backend 전체 검사.
3. `npm run test:ui:v2`: v2 비교 그래프·상세 모달·태그와 대화방 보존, 진행/답변 스트리밍·재연결·취소·이전 기록 읽기. 390/800/1008/1440px, ko-KR, Asia/Seoul, 배율 1을 사용한다.
4. `npm run test:e2e`: 인공 Run 3개를 실제로 업로드한 독립 DB·서버·v2 worker·브라우저에서 개념, 검색, 선택 후 복합 실행과 네 화면 폭을 검사한다. 모델 응답만 고정한다.
5. `npm run test:agent:restart`: v2 접수 요청, 선택 대기와 고정 선택지, worker/서버 종료 후 비교→max→검색 재개, 완료 결과의 멱등 재개를 네 시나리오로 검사한다.

v1 전용 Python 그래프/평가기, TypeScript fallback 평가, v1 브라우저·종단 실행은 기본 대상에서 제외한다. v1 제품 코드와 기존 실행기는 보존하며, 공통 API·저장·보안·모델 통신과 과거 답변 스냅샷을 안전하게 읽는 회귀 검사는 유지한다. frontend의 `v1-*.test.tsx`도 저장된 과거 답변의 정확한 버전·안전한 텍스트 표시를 검사하므로 유지한다. 이 전환은 새 대화의 제품 기본 버전을 변경하지 않는다.

## 실제 LLM의 판단 평가

Decisions 단독 80회와 실제 웹 40회·API 40회의 준비물, 비용 없는 사전 검사,
유료 실행 명령과 점수 해석은 [v2 평가 실행 가이드](agent-v2-evaluations.md)를 따른다.
웹/API 실행은 `npm run eval:agent:local`이며 아래 메모리 그래프 비교와 구분한다.

앞으로 모든 실제 Agent 평가(웹·API·메모리 그래프)는 계획 의미 Decisions를 켠다. 실행 전에 모델 설정과 그래프 상태가 모두 `plan_review_enabled=true`인지 확인하며, 꺼져 있으면 평가를 중단한다. `run_v2 --live`는 `--plan-review off`와 비활성 환경 설정을 거부하고, 허용된 실행은 두 곳 모두 `true`로 고정한다. 기존 요청 전체 최대 2회 재계획, 필요한 답변 검토와 최대 1회 재작성은 유지한다. 실제 모델을 호출하지 않는 스크립트 유닛 테스트는 비활성 경로도 검증할 수 있다.

평가 결과는 최초 계획 통과, Decisions 지적, `REPLAN`을 거친 최종 통과·실패를 별도로 보고한다. 복구 후 통과를 최초 통과에 합치지 않는다. 아래 고정 계획 검토 실험은 Agent 종단 평가와 별개이며, 사용자가 지정한 평가 횟수에 자동 추가하지 않는다.

Decisions의 계획 검토 80회 평가는 **CI와 별개로 로컬에서 수동 실행**한다.
기존 78회에 정상·오류 계획을 각 1개 추가한 정상 40 / 오류 40 구성이다.
기존 반복을 포함하며 서로 다른 계획은 28개다. 저장소 루트에서 다음 명령을
직접 실행할 때만 유료 API를 호출한다.

```sh
npm run eval:decisions:local -- --env-file /path/to/local.env --output /tmp/kplasma-decisions80-live
```

`OPENAI_API_KEY`와 필요한 Decisions 모델 설정은 로컬 env 파일에 둔다.
실험마다 새로운 출력 경로를 사용하며 결과의 `results.jsonl`과 `summary.json`은
로컬에 보관한다. backend·DB·브라우저를 시작할 필요는 없다. GitHub Actions나
PR 필수 검사에 이 명령을 연결하지 않는다. CI의 평가기 유닛 검사는 API를 호출하지 않는다.

모델 비교는 `agent/python`에서 실행한다. 기본 실행은 평가 목록만 작성하며 `--live`가 실제 API를 사용한다.

```sh
uv run --frozen python -m evals.run_v2 --output /tmp/kplasma-v2-matrix
uv run --frozen python -m evals.run_v2 --live --output /tmp/kplasma-v2-model-eval
```

질문 24개를 계획 모델 설정 네 가지에서 각각 실행한다. 복합·경계·누락 사례 8개는 각각 3회씩 실행해 전체 160회다. 코드의 도구 실행과 인공 데이터는 동일하며 계획 모델·추론 수준만 바뀐다. 전체 모델 평가와 웹 비교는 별도 표본이다. 정답은 계획·실행·최종 답변 단계별로 확인한다.

이 실행기는 실제 모델이 계획을 만들고 v2 그래프가 도구를 실행하며 필요한 답변 작성·검토까지 수행한다. HTTP/DB 대신 인공 Run을 제공하는 메모리 저장소를 사용한다. `results.jsonl`의 `pass`와 오류를 확인해야 하며, 이 모델 비교 실행기의 종료 코드 자체는 품질 통과 기준이 아니다. HTTP/DB/worker/화면까지 실제 연결하는 검사는 위의 `test:e2e:live`다. 어느 쪽도 기본 PR CI에 포함하지 않으며, 키와 유료 호출은 로컬에서 명시적으로 준비한다. 일반 지식의 과학적 정확성 전체를 이 사례만으로 보장하지 않는다.

2026-11-06 main의 실험 선택 V8–V11을 보존하고, 아직 main에 없던 v2 마이그레이션을 V12–V17로 옮겼다.
